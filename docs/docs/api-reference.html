概述：三个必须先知道的要点

  1. API 门面只有两个类：TaskPool（即时任务）与 TaskScheduler（定时任务），另有一个未导出的异步门面 TaskEngine（见第八节）。工作流编排 API 不存在——没有 WorkflowEngine / WorkflowDefinition / TaskNode / WorkflowConfig。

  2. 同步方法 ≠ 同步实现：所有"同步版"方法都通过 asyncio.run_coroutine_threadsafe 把协程投递到后台事件循环线程执行并阻塞等待结果（🔧 task_pool.py:300 _run_coroutine）。因此绝大多数公开方法内部先调用 _ensure_running()——不先 start() 直接调 submit() 也会自动启动；但 wait_for_result 等不触发自动启动，需保证池已运行。

  3. TaskScheduler 是一个"组装器 + 委托器"：它内部持有一个 TaskPool，39 个公开方法中 24 个是原样委托（🔧 task_scheduler.py:699 起"委托给 TaskPool 的方法"注释段），真正自研的只有：延时/定点提交（委托时附加 delay）、周期任务管理族、get_stats 附加段、cancel 双查逻辑。

1.1 生命周期：start 一次，自动启动的池

def start(self) -> None                      # 启动后台事件循环线程并拉起全部组件
def shutdown(self, graceful: bool = True, timeout: float = 30) -> None

🔧 task_pool.py:310。start() 会创建一个 daemon 线程，在该线程内 new_event_loop 并依次启动：事件总线 → 队列调度器 → Worker 池 → 监督器，然后按存储类型附加节点管理/心跳/回收器/上报器等分布式组件（详见《节点监控》），最后 loop.run_forever()。

shutdown()（🔧 369）的关闭顺序与启动相反：停收新任务 →（graceful 时）等队列清空 → 停分布式组件 → 停核心组件 → 关存储连接。两个细节值得注意：

  • graceful 语义是"等队列清空"，不是等 Worker 优雅退出后再停——随后 worker_pool.stop(graceful, timeout) 才处理执行中任务，两段分别受 timeout 约束。

  • 关闭仓库时捕获 "different loop" 异常并忽略（🔧 411-414）：SQLite/Redis 连接若在别的线程创建，跨循环关闭会炸，源码选择吞掉。

为什么这么设计：把整个 async 世界隔离在一个专属后台线程里，业务线程就能以"同步 API 调协程"的方式使用——代价是 _run_coroutine 是阻塞桥，在事件循环线程内调用任意同步方法会死锁（这是常见事故，见第十节故障 1）。异步版本 API（submit_async 等）就是为此提供的逃生门。

📝 生命周期标准姿势：

from neotask import TaskPool

pool = TaskPool(executor=my_task)   # executor 可为同步/异步函数，见下
# with TaskPool(...) as pool:       # 写法等价，退出自动 shutdown
pool.start()
try:
    task_id = pool.submit({"data": 1})
    result = pool.wait_for_result(task_id, timeout=60)
finally:
    pool.shutdown(graceful=True)

1.2 任务提交：submit 的 delay 就是"延时任务"

def submit(self, data, task_id=None, priority=TaskPriority.NORMAL, delay: float = 0, ttl: int = 3600) -> str
async def submit_async(self, ...) -> str                                # 同参
def submit_batch(self, tasks: List[dict], priority=TaskPriority.NORMAL) -> List[str]
async def submit_batch_async(self, tasks, priority=...) -> List[str]

🔧 task_pool.py:473。submit 把任务交给 TaskDispatcher.dispatch（入队 + 持久化 + 发 task.created 事件），返回任务 ID。参数语义：

参数 默认 说明
data 必填 任意可 JSON 序列化对象，原样传给执行函数
task_id None 自定义 ID；重复提交统一抛 TaskAlreadyExistsError——入队前 create_task 先做存在性检查（🔧 lifecycle.py:64-66），与存储后端无关
priority NORMAL(2) 接受 TaskPriority 枚举或整数，0=CRITICAL 1=HIGH 2=NORMAL 3=LOW，小者先出队
delay 0 延迟秒数，>0 时进延时队列（ZSET 方案见《延时任务》），这不是 TaskScheduler 的专利
ttl 3600 任务生命周期秒数，写入 Task.ttl；目前仅作元数据，没有内置 reaper 依据它删除任务

submit_batch 不是批量原语：源码是 for 循环逐个调 submit（🔧 501-512），无事务、无原子性，中途失败前面已提交的任务不回滚。

📝 四种提交形态等价关系：scheduler.submit_delayed(d, s) ≈ pool.submit(d, delay=s)；scheduler.submit_at(d, t) ≈ pool.submit(d, delay=max(0, (t - now).total_seconds()))——TaskScheduler 的实现正是这样逐字委托（见第二节）。

1.3 任务等待：最容易被低估语义的一组

def wait_for_result(self, task_id: str, timeout: float = 300) -> Any
async def wait_for_result_async(self, task_id: str, timeout: float = 300) -> Any
def wait_all(self, task_ids: List[str], timeout: float = 300) -> Dict[str, Any]
async def wait_all_async(self, ...) -> Dict[str, Any]

🔧 task_pool.py:529。底层是 TaskLifecycleManager.wait_for_task（🔧 core/lifecycle.py:265），完整语义链：

  1. 任务不存在 → 抛 TaskNotFoundError(task_id)；

  2. 已终态：SUCCESS → 直接返回 task.result；FAILED → raise Exception(task.error)；CANCELLED → raise Exception("Task was cancelled")（注意都是裸 Exception，不是 TaskError）；

  3. 未终态：取 Future 等待，future.wait(timeout) 超时抛 neotask.common.exceptions.TimeoutError（自定义类，见第七节）；等待异常后再查一次任务状态兜底（🔧 lifecycle.py:291-306 的防漏通知逻辑）。

为什么这么设计：失败/取消的任务以"抛异常"而非"返回错误字典"呈现，是为了让调用方无法忽略失败——代价是与 wait_all 的行为不对称（见下）。

wait_all（🔧 537）是串行循环：逐个 wait_for_result(task_id, timeout)，任何异常（含超时）都被捕获并塞成 {"task_id": {"error": "..."}} 返回，永不向上抛。两个推论：

  • 总耗时最坏 = N × timeout（不是共享一个超时预算）；

  • 单任务失败被静默吞进结果字典，{"error": ...} 与正常任务返回的真字典混在一起难以区分。

📝 严谨的等待姿势（区分三类失败）：

from neotask import TaskPool, TaskNotFoundError
from neotask.common.exceptions import TimeoutError as NeoTimeoutError

task_id = pool.submit({"order_id": 1})
try:
    result = pool.wait_for_result(task_id, timeout=30)
except TaskNotFoundError:
    ...  # ① ID 不存在
except NeoTimeoutError:
    ...  # ② 30s 未完成（自定义异常！见第七节）
except Exception as e:
    ...  # ③ 任务 FAILED / CANCELLED（裸 Exception 携带 error 信息）

1.4 任务查询：get_task 与 get_result 的序列化差异

def get_task(self, task_id) -> Optional[dict]      # 完整任务字典
def get_status(self, task_id) -> Optional[str]     # "pending"/"running"/"success"/...
def get_result(self, task_id) -> Optional[dict]    # {task_id, status, result, error, created_at, completed_at}
def task_exists(self, task_id) -> bool
# 每组均有 _async 版（get_task_async / get_status_async / get_result_async / task_exists_async）

🔧 task_pool.py:569-623。三个方法都调 lifecycle.get_task，差异在返回形态：

  • get_task → Task.to_dict()（🔧 models/task.py:64）：14 个字段，但 data 与 result 是 JSON 字符串（存储格式），时间字段是 ISO 字符串，空值被归一化为 ""；

  • get_result → 手工拆包的小字典：result 字段已被 json.loads 还原为对象（来自 from_dict），并附 status/error/created_at/completed_at；

  • get_status → 只取 task.status.value。

最容易踩的坑：pool.get_task(id)["result"] 与 pool.get_result(id)["result"] 类型不同（前者字符串、后者对象），下游代码混用会拿到 '{"data": 1}' 而不是 {"data": 1}。Task.to_dict 的序列化行为在 Memory/SQLite/Redis 三存储间是同一个函数，无后端差异。

1.5 任务管理：cancel 只管状态机，retry 走重派发

def cancel(self, task_id: str) -> bool
def delete(self, task_id: str) -> bool
def retry(self, task_id: str, delay: float = 0) -> bool
# 每组均有 _async 版

🔧 task_pool.py:627-653。cancel 先 queue_scheduler.remove(task_id) 尝试从队列移除，再调 TaskLifecycleManager.cancel_task（🔧 core/lifecycle.py:227）：

  • 任务不存在或状态不在 PENDING/RUNNING → 返回 False；

  • 成功 → 状态置 CANCELLED、存库、通知 Future（等待方会收到裸 Exception("Task was cancelled")）、发 task.cancelled 事件。

一个真实的语义盲区：Worker 执行前校验任务必须是 PENDING（🔧 worker/pool.py:255），但执行成功后无二次状态检查就直接 complete_task 落库。因此对 RUNNING 任务 cancel：只把状态标记成 CANCELLED，不中断执行中的函数；函数若随后正常返回，状态会被覆写回 SUCCESS 并照常发 task.completed。生产上把 cancel 当作"只对排队中（PENDING）任务可靠"更稳妥。

retry = TaskDispatcher.redispatch(task_id, delay)（🔧 dispatcher.py:99）：只做存在性检查（查无此任务返回 False），然后按任务原优先级重新入队——不校验状态是否 FAILED、不递增 retry_count、不发事件。所以它是"把任意任务硬塞回队列"的手动重试；retry_count < 3 的阈值只在 Worker 自动失败链路里生效（模型侧 is_retriable()，🔧 models/task.py:151），手动 retry 不受次数约束。

delete 直接走 lifecycle.delete_task（🔧 core/lifecycle.py:251）：存储删除 + 清缓存 + 移除 Future + 发 task.deleted，不区分状态，且恒返回 True（存储层删除失败的返回值被忽略）。运行中的任务被删后，Worker 完成时 complete_task 会再次 repo.save——三后端 save 均为覆盖/upsert 写（SQLite INSERT OR REPLACE），记录会以执行前的旧快照重建，等于"删了还会回来"。

1.6 队列控制：pause 的是"调度器取任务"这个动作

def pause(self) / def resume(self) -> None     # 暂停/恢复处理新任务
def clear_queue(self) -> None                  # 清空待处理队列
def get_queue_size(self) -> int                # 当前队列深度
# 均有 _async 版

🔧 task_pool.py:736-766。四者全部委托给 QueueScheduler：pause 停的是调度器从队列取任务交给 Worker 的循环，已入队任务保留、执行中任务不打断；clear_queue 清空的是待处理队列（各后端实现不同，Redis 是删除 ZSET 键）。pause 期间 submit 仍可入队，队列长度会涨。

1.7 统计监控：get_stats 真实结构

def get_stats(self) -> dict
def get_stats_async(self) -> dict
def get_worker_stats(self) -> Dict[int, Any]
def get_health_status(self) -> dict

🔧 task_pool.py:736-800。get_stats() 的返回结构：

{
    "queue_size": 10,        # 队列当前深度
    "total": 100,            # 全部任务数（pending+running+终态）
    "pending": 5, "running": 3, "completed": 85, "failed": 5, "cancelled": 2,
    "success_rate": 0.944,   # = completed / (completed + failed)；总数为 0 时恒为 1.0
    "node_id": "DESKTOP-xxx",
    "metrics": {...},        # 仅 enable_metrics 时出现；get_full_summary() 摘要，含 system（cpu/memory 等，psutil 缺失时为 None）
    "reclaimer": {...},      # 仅 redis 模式时出现（回收器统计）
    "prefetcher": {...},     # 仅 enable_prefetch 时出现；含 empty_streak 等预取统计
}

success_rate 初始为 1.0 而非 0.0（stats.total > 0 else 1.0，🔧 670）——新池"零失败率"，语义是"没有失败过"而非"全成功"。

get_health_status()（🔧 800）返回 {"status", "node_id", "last_check", "checks", ...}。启用 enable_health_check（默认 True）时，同步/异步版本都会先经 _refresh_health_if_stale() 惰性执行检查：仅当上次结果超过 HEALTH_CHECK_TTL = 5.0 秒才重新探测，否则复用缓存。检查项为 storage / queue / system，逐项串行执行，单项超时 DEFAULT_CHECK_TIMEOUT = 5.0 秒并记为 UNHEALTHY（message 为 timed out after Xs）；未安装 psutil 时 system 项记 healthy 且 details = {"available": False}（psutil 属可选 [monitor] extra）。enable_health_check=False 时不带 checks 键，只返回 {status, node_id} 与分布式字段。get_worker_stats() 直通 WorkerPool 的统计（每 Worker 一个条目）。

五、事件回调与内部订阅关系

注册 on_created 等回调只是向总线 subscribe，总线本身是异步队列 + 独立 worker 派发（🔧 event/bus.py）。源码把"指标记录"也实现为总线订阅（_setup_event_handlers，🔧 task_pool.py:271）：

  • 指标订阅（subscribe_global）覆盖 created/started/completed/failed/cancelled/retry 六类事件；

  • task.created 的 payload 是 Task.to_dict()、带 priority，因此 priority_counts 记录真实优先级分布；task.retry 带 retry_count，记入 total_retried。

对用户而言：事件回调是"尽力而为"的通知，不是任务结果的一致来源——结果一致性请用 wait_for_result / get_result，回调只适合日志、旁路统计等可丢场景。

九、为什么这么设计：门面与桥的取舍

  1. 同步门面 + 异步内核：任务调度器的用户大多是同步业务代码（Web 请求线程、脚本），强制 async 会劝退大部分使用者。NeoTask 选择"专属事件循环线程 + run_coroutine_threadsafe 阻塞桥"，让 pool.submit() 像普通库一样调用——代价是同步方法与事件循环线程有死锁红线（见故障 1），于是又补了全套 *_async 逃生门。

  2. _ensure_running() 隐式启动：submit 系列都带自动启动（🔧 295-298），wait/cancel 不带——设计意图是"提交是主路径，不能让用户忘了 start"，但副作用是"忘 start 直接 wait"会抛 RuntimeError("TaskPool not started. Call start() first.")。两者行为不对称是刻意的：等待一个没启动的池是程序错误，应尽快暴露。

  3. 委托而不是继承：TaskScheduler 组合 TaskPool 而非继承它，因此能对 cancel、get_stats 做差异化覆盖（周期任务优先），又不必背上锁/节点那组与定时调度无关的方法。代价就是上面那张"25 个方法不存在"的委托矩阵——查文档前先想清楚你手里的是哪个门面。

  4. 异常即状态：等待 API 用"抛异常"表达失败/取消（而不是返回 error 结构），保证 result = await wait() 成功路径拿到的必是可用结果。

十、故障场景实战

故障 1：在事件循环线程里调同步 API → 死锁

症状：自定义 executor 是异步函数，内部调用了 pool.wait_for_result(...) 或 pool.submit(...) 等同步方法，程序卡死无日志。

根因：executor 跑在池的专属事件循环线程里；同步方法走 _run_coroutine 向同一个循环投递协程并 future.result() 阻塞等待——循环正忙于执行你的 executor，永远没机会跑新投递的协程，经典"自己等自己"死锁（🔧 task_pool.py:300-306）。

修复：执行器内部一律用 await pool.submit_async(...) / await pool.wait_for_result_async(...)；拿不准时统一 *_async 族。

故障 2：except 接不住超时，异常被桥吞掉

症状：wait_for_result 超时后 try/except 没打印任何东西，进程却挂着卡死；或 except TimeoutError 从未命中。

根因：两层叠加——① 自定义 TimeoutError 遮蔽内建名（见第六节）；② _run_coroutine 对协程异常是 future.result() 直接上抛，若外层只 except (TaskNotFoundError, TimeoutError) 而任务实际 FAILED（裸 Exception），异常一路逃逸。

修复：

from neotask.common.exceptions import TimeoutError as NeoTimeout, TaskNotFoundError

try:
    result = pool.wait_for_result(task_id, timeout=10)
except TaskNotFoundError:
    ...
except NeoTimeout:
    ...   # 超时：查 get_task 决定重试还是放弃
except Exception as e:   # FAILED / CANCELLED 都在这
    status = pool.get_status(task_id)
    ...

故障 3：wait_all 一批 50 个任务，偶发"整个调用耗时几分钟"

症状：单任务平均 1s，wait_all(ids, timeout=60) 本应 ~60s 封顶，实测偶发跑到几分钟。

根因：wait_all 是串行 for 循环，每个任务独立计时 60s（🔧 537-550）。若最后一个任务恰好失败且靠后，前面 49 个各等满 60s 累计 ≈ 50 × 60s。timeout 是"每任务"预算，不是整批预算。

修复：大批次分批等（如每批 10 个）；或改并发等待——自己 asyncio.gather（异步环境）：

async def wait_all_parallel(pool, ids, per_task_timeout=30):
    async def one(tid):
        try:
            return tid, await pool.wait_for_result_async(tid, per_task_timeout)
        except Exception as e:
            return tid, {"error": str(e)}
    return dict(await asyncio.gather(*(one(t) for t in ids)))

故障 4：get_task 里"读不到结果"

症状：任务显示 success，但 pool.get_task(tid)["result"] 拿到的值 json.dumps 后是字符串、if not result 判断还经常误判。

根因：to_dict() 把 result 序列化成 JSON 字符串（🔧 models/task.py:79），空结果存成 ""；而 get_result(tid)["result"] 才是解析后的对象（None 保持 None）。两个 API 的 result 通道类型不同且"空"的表现不同（"" vs None）。

修复：读结果一律用 get_result()；确实要完整任务字典时，对 data/result 字段自行 json.loads 并兼容空串。
