架构设计

三种部署形态、装配拓扑、两阶段生命周期与关键架构决策。

更新于 2026-04-21 约 18 分钟 读完 GitHub

文档定位：这是一篇架构文档。重点是解释组件之间的职责、数据流和关键设计取舍，并区分当前实现与设计层面的推演。
事实边界：实现文档：功能、接口和代码行为以文中标注版本对应的源码为准；仓库后续版本可能发生变化。
权威来源：NeoTask 源码仓库；涉及版本历史时，以仓库 Release / CHANGELOG 为准。
代码标记：如果正文出现“源码/实现”字样，表示对应代码路径可在仓库中核对；示例代码仅用于演示调用方式，不应理解为项目源码原样。
版本基线：本文对照 NeoTask v1.0.2（PyPI 发布版）。
代码标注约定：🔧 表示真实源码（仓库原样摘录，附文件路径，可自行对照）；📝 表示示例代码（用法演示、改进建议或教学代码，不代表仓库实现）。
本文是系列"整体架构"篇。三个核心认知：形态由存储后端决定（能力阶梯）→ TaskPool 是装配枢纽（两阶段生命周期）→ 组件存在≠组件可用（接线状态清单）。

太长不看：

  1. NeoTask 是一套代码、三种形态：storage_type 一个配置决定你得到的是"进程内队列"（memory）、“单机持久队列”（sqlite）还是"真正分布式调度"（redis）。分布式组件（节点注册、心跳、回收器、协调器、死信）只在 Redis 形态下装配（task_pool.py:134），其余形态连代码路径都不存在——能力不是"全有全无"，而是阶梯式供给。

  2. 架构的灵魂是 TaskPool 的装配拓扑，而不是分层。真实结构是一个门面对象在构造期组合 10 类组件、启动期在后台线程的事件循环里按依赖序拉起 9 个异步部件（含指标收集器；详见表 2-1/2-2）。

  3. 组件存在 ≠ 组件可用：完整接线（如生命周期→存储→事件）、条件接线（Redis 才有分布式组件）、以及仍需注意的未接线项——task.progress 事件无发布方、Coordinator 的选节点/再平衡为占位实现、NodeManager._health_check_loop 的故障处理是 TODO。另一方面，死信队列与时间轮都已接线（前者由 Worker/回收器自动投递，后者承接 submit_delayed 的延时任务）。评估 NeoTask 能力时，应以"谁调用谁"为准，而不是以"存在哪个类"为准。

一、三种部署形态：由存储后端决定的能力阶梯

1.1 形态总览

⚠️ 三个易错点（架构级）：

  1. sqlite 形态下队列仍在内存：重启后 PENDING 任务在任务表里"复活"，但队列水位归零——任务不会自动重新入队；此外多个进程共用一个 sqlite 文件时，各自维护独立的内存队列，会出现"任务记录可见、队列无人消费"的脑裂（详见故障场景 2）。

  2. "分布式"三个字只属于 Redis 形态："高可用、去中心化"能力全部由 Redis 形态提供；SQLite 形态连回收器都不会启动，节点宕机后的任务没有自动接管机制。

  3. 切换形态只需改 config，这正是架构最大的卖点——同一套业务代码可以在开发（memory）、单机（sqlite）、集群（redis）之间无痛迁移。

1.2 为什么按存储后端而非功能开关来分形态

问题 答案
为什么不做"always on"的全量组件？ 分布式组件的每条心跳、每次回收都是对共享存储的写操作；memory/sqlite 形态没有"其他节点"概念，装配它们只会空转耗资源。孤儿回收本身也要求有节点管理器才能判定活跃节点——未装配时回收器会直接跳过该路径（见 5.2 节），不会误判单机任务
为什么锁不跟着存储走？ 锁语义取决于"谁会竞争"：内存形态单进程内无竞争（状态守门已够）；Redis 形态才需要跨进程互斥。TaskPool 因此把锁类型做成独立配置项 lock_type，但执行路径写死 TTL=30（worker/pool.py:268），lock_timeout 配置仅影响 LockFactory 构造默认值
为什么队列实现要跟存储绑定？ 队列是"消费竞争"发生的场所：单进程内用 heapq 足够，多进程必须把队列放到共享存储并原子弹出。TaskRepository 与 QueueRepository 由 StorageFactory 成对返回（factory.py），天然保证形态内聚

要点（与旧图的关键差异）：

  • TaskScheduler 是 TaskPool 的客户而非兄弟：它内部持有一个 TaskPool 并全量委托（submit_delayed 直接调 pool.submit），还复用了 TaskPool 的事件循环（task_scheduler.py:103-126）。TaskEngine（core/engine.py）同理但未导出，用户不可直接使用。

  • Supervisor、Reclaimer 在真实代码里不是 WorkerPool 的兄弟节点：Supervisor 由 TaskPool 持有并观察 WorkerPool（supervisor.py:32-42）；Reclaimer 直接依赖 lifecycle/queue/lock 三个组件（reclaimer.py:90-104），与 WorkerPool 平行。

  • DelayedQueue 自带 0.1s 调度循环，从队列系统内部到期转正（queue_scheduler.py:59-70）；TimeWheel 在 TaskScheduler 侧，enable_time_wheel=True 时承接 submit_delayed / submit_at 的延时任务（见 3.4 节）。

2.2 两阶段生命周期的完整清单

阶段一：__init__（构造期，调用方进程内纯组装，10 类组件） 🔧

步 组件 关键事实
1 Executor 默认执行器 {"result":"executed","data":data}；同步函数被包装（task_pool.py:212-232）
2 存储 StorageFactory.create 一次返回 Task/Queue 双仓库
3 Lock memory/redis 由 lock_type 决定（task_pool.py:247-256）
4 EventBus 全局唯一实例，后续组件共享
5 FutureManager 等待通道
6 QueueScheduler 接收 queue_repo 与 queue_max_size
7 TaskLifecycleManager 含缓存字典（cache_enabled=True）
8 TaskDispatcher node_id 来自 config
9 WorkerPool + Supervisor set_retry_config 注入 max_retries/retry_delay
10 分布式五件套 仅 Redis 形态：NodeManager/HeartbeatManager/Reclaimer/Coordinator/DeadLetter（task_pool.py:148-210）

阶段二：start()（启动期，后台线程事件循环中按序拉起 9 个异步部件） 🔧

事件总线 → 队列调度器 → Worker 池 → 监督者 → （Redis 形态）节点管理 → 心跳 → 回收器 → 指标收集器 → （可选）Reporter。启动失败（如心跳连不上 Redis）只会打 error 日志，不中断整体启动——这是"看起来起了，实际组件瘫了"类故障的温床。

阶段三：shutdown()（逆向优雅关闭） 🔧

disable() 停收新任务 → graceful 时 wait_until_empty(timeout) → 停 回收器/心跳/节点 → Supervisor → WorkerPool（带超时强杀）→ 队列 → Reporter → 事件总线 → 存储连接（捕获 “different loop” 冲突异常）。

2.3 为什么门面 + 独立事件循环是正确取舍

问题 答案
为什么不是"在用户协程里跑"？ 嵌入式调度器的目标用户是任意 Python 进程（含同步 Web 框架、脚本、线程池代码）。让每个调用方管理 loop 会毁掉易用性；自带守护线程 + run_coroutine_threadsafe 桥接让同步 API 处处可用
为什么 start 前允许构造？ 门面先组装后启动，使 submit() 内的 _ensure_running() 自动起步成为可能，也便于测试时只构造不启动
代价是什么？ 组件状态横跨两个线程（构造在调用线程、运行在后台循环），直接读内部字段可能读到过期值；所有状态查询 API 都经线程桥回到事件循环执行，慢但一致。web 监控线程同理另起 uvicorn（web/server.py:16-27），形成第三条线程

三、关键架构决策解码

3.1 D1：状态守门 + 执行前锁 = 两道防重，缺一不可

提交→执行的正确性依赖三层机制，职责完全不同：

层 机制 位置 防什么
1 原子弹出（Redis Lua ZRANGE+ZREM） storage/redis.py:238-252 多节点不会取到同一任务
2 执行前分布式锁（task:{id} TTL=30 + 看门狗续期） worker/pool.py:260-281 同一任务被两个 Worker 同时执行（含重试/回收路径的重复入队）
3 PENDING 状态守门 worker/pool.py:255-258 + lifecycle.py:136-141 跳过已被取消/已完成的任务

为什么锁在弹出之后、执行之前拿而不是在弹出脚本里拿？因为队列只保证分发不重复，执行前再拿锁是为了覆盖"任务在队列里被重复放入"的场景（重试、回收、redispatch 都可能再次入队，见去中心化篇）。内存形态没有锁管理器，防重完全依赖第 3 层守门。

3.2 D2：双通知通道——Future 快通道 + 事件慢通道

wait_for_result 与外部订阅走完全不同的通道：

  • FutureManager（core/future.py）：内存 asyncio.Event，complete() 由 lifecycle 直接调用（lifecycle.py:181/220/245），O(1) 唤醒等待方；wait_for_task 异常后二次查状态兜底（lifecycle.py:291-306）。

  • EventBus（event/bus.py）：发布/订阅，供 MetricsCollector、用户扩展等多接收方使用，TaskPool 内部也靠它把 completed/failed/cancelled 转给 FutureManager（task_pool.py:276-288）——注意这里事件又转回了 Future 通道，说明事件总线是扩展面而非等待链路的必要环节。

代价：双通道可能失同步。当前仍存在的唯一断链是 task.progress（有订阅接口、无发布方，_update_task_progress 无调用点）；task.retry 已由指标采集器订阅，task.reclaimed 仅用于 debug 日志。详见核心功能篇 7.1 节。

3.3 D3：抢占消费 + 内存缓冲（预取器）解耦"竞争"与"吞吐"

Redis 形态下如果每个 Worker 每次都直接 pop 共享 ZSET，Redis 会成为瓶颈。架构给出的答案是 WorkerPool 内嵌 TaskPrefetcher（pool.py:80-91）：预取器按水位（min/max 阈值由 prefetch_size 派生）批量搬运任务到进程内缓冲，Worker 只消费本地队列，缺货才触发下次搬运。单机形态没有预取器（enable_prefetch 虽默认 True，但内存队列 pop 几乎零成本，预取不改变语义）。吞吐调优的唯一入口是 TaskPoolConfig.prefetch_size（详见预取机制篇）。

3.4 D4：能力要"存在"，也要"接线"

架构评估最重要的清单：各组件的接线状态。

组件 接线状态 证据
Lifecycle → Repository → EventBus ✅ 完整接线 create_task 落库+事件（lifecycle.py:76-82）
FutureManager（等待） ✅ 完整接线 lifecycle 三处 complete 直接调用
NodeManager/HeartbeatManager/Reclaimer ✅ 条件接线 仅 Redis 形态（task_pool.py:134）
Prefetcher/Dispatcher/Supervisor ✅ 完整接线 pool/start 中创建并运行
DeadLetterQueue ✅ 完整接线 装配后注入 WorkerPool（set_dead_letter_queue）与 Reclaimer，重试超限/回收失败时自动 send（task_pool.py:180-207）
TimeWheel ✅ 完整接线 TaskScheduler 启动它（task_scheduler.py:147-153）；enable_time_wheel=True 时 submit_delayed/submit_at 经 add_task 入轮，shutdown 时 drain 回延时队列
task.progress 事件 / _update_task_progress ⛔ 未接线 方法存在（pool.py:381-403）但无调用方
task.retry 事件 ✅ 完整接线 发布方 pool.py（失败重试路径），订阅方为指标采集器（task_pool.py:292）
ConsistentHashSharder ⛔ 未接线 完整实现（150 虚拟节点/三种哈希）但 TaskPool/Coordinator 未使用
Coordinator（_select_node/rebalance/handle_node_failure） ⛔ 未接线 实例被创建，但真实提交走 TaskDispatcher，上述方法为占位实现
PeriodicTaskManager ✅ 完整接线 TaskScheduler 默认启用（enable_periodic_manager=True，storage=None 内存态）

教训：文档能力清单 ≠ 可用能力清单。判断某个功能能不能用，应 grep 它的调用方，而不是看类是否存在。

4.2 工厂：一次调用、成对返回 🔧

StorageFactory.create(config)（storage/factory.py）按 StorageConfig 返回 (TaskRepository, QueueRepository) 元组，TaskPool 一行完成存储装配（task_pool.py:64）。三个后端的实现差异（键格式、索引、写策略）详见持久化篇与核心功能篇 8.1 节；此处只强调架构级结论：

  • Memory/SQLite 的任务仓库与队列仓库都活在进程内——SQLite 的持久化只覆盖任务记录，不覆盖队列与周期任务注册表；

  • Redis 是全异步实现（redis.asyncio + ConnectionPool，decode_responses=True），存储调用全部经事件循环执行——同步 API 的每次 submit/get 都包含一次线程桥 + Redis 往返，批量场景应使用 submit_batch 或异步 API 减少桥接次数。

五、高可用架构的真实形态

5.1 节点生命周期：不是"注册→可疑→死亡"，是三个字面状态

真实的节点管理很简单——只有三个字面状态，没有"可疑"中间态，也没有分级超时：

  • 节点注册：NodeManager 与 HeartbeatManager 共用同一份注册表，写 HSET neotask:node:{node_id}（node_id/status/started_at/last_heartbeat），键 TTL = timeout × 2；同时 SADD neotask:nodes（node.py:64-65、heartbeat.py:46-52）。

  • 节点状态只有三种值：active（心跳中）、stopped（优雅关闭时写入，TTL 60s）、reclaimed（被其他节点判死后标记）——没有"可疑"中间态。

  • 判死逻辑一刀切：每个节点在自己的 _monitor_loop 里（每 cleanup_interval=30s）扫描其他节点，status != "stopped" 且 now - last_heartbeat > timeout(20s) 即判死（heartbeat.py:162-165）。心跳周期 5s、超时 20s（4 个周期），没有宽限期、没有分级。

stateDiagram-v2
    [*] --> active: 注册（HSET neotask:node:{id} + SADD neotask:nodes）
    active --> active: 每 5s 刷新 last_heartbeat
    active --> stopped: 优雅关闭（TTL 60s 后消失）
    active --> reclaimed: 他节点判死（20s 无心跳）
    reclaimed --> [*]: 任务回收后节点键过期

5.2 任务回收：两条已闭环的路径

Redis 形态装配了两套回收机制，任务状态一律经 TaskRepository 读写：

机制 周期 触发条件 真实状态
HeartbeatManager 死节点回收 30s 检查 他节点 20s 无心跳 ✅ 经 list_by_status(RUNNING) 取任务，只回收 task.node_id == 死亡节点 的任务；置 PENDING、清 node_id/started_at、写 error、repo.save、重新入队；入队失败则置 FAILED
TaskReclaimer 超时回收 30s RUNNING 且执行时长 > task.ttl（默认 3600s） ✅ 生效（"超时"口径是任务 ttl 而非执行超时）；重试入队被拒或超限时置 FAILED + 投递死信
TaskReclaimer 孤儿回收 30s RUNNING 且非本节点、node_id 不在活跃节点 ✅ 活跃节点来自 NodeManager.get_active_nodes()；未装配节点管理器时返回 None 并跳过整轮，本节点任务显式跳过——不会误伤正常执行的任务

架构结论：Redis 形态的"高可用自动恢复"链条（判死 → 回收 → 重入队 → 重执行）已闭环，失败任务有明确归宿（FAILED + 死信队列）。唯一仍需注意的未实现项是 NodeManager._health_check_loop 内部的 # TODO: 处理故障节点（节点管理器自身的健康巡检）。详见故障恢复篇与核心功能篇 6.2 节。

5.3 Supervisor：执行侧的"健康守护"，粒度是整池

TaskPool 启动顺序里第 4 位是 WorkerSupervisor（默认 30s 检查一次）：对每个 Worker 做挂起检查（busy 且 300s 无活动）与失败率检查（样本 >10 且失败率 >50%）。但"重启 Worker"的实现是停掉并重启整个 WorkerPool（supervisor.py:113-115）——挂起判定与并发任务时长强相关（长任务超过 300s 会被误判），且整池重启会中断所有在途任务。这是执行侧 HA 的已知粗糙点。

六、可观测性：事件采集 + 注册式检查 + 上报器

可观测性由四个相互独立的组件构成（都在 monitor/ 包）：

6.1 MetricsCollector：事件驱动计数 + 周期系统采样 🔧

  • 任务指标：TaskPool 内部以一个全局事件订阅把 task.created/started/completed/failed/cancelled/retry 转发给采集器（task_pool.py:274-295），task.created 带 priority、task.retry 带 retry_count；内部维护 per-task 的时间账本，产出 TaskMetrics：成功率/失败率、平均与 p50/p90/p95/p99 执行耗时、平均排队时间、吞吐量（metrics.py 计算属性）。

  • 系统指标：metrics.start() 在启动期拉起后台循环周期采集 CPU/内存等（_collect_system_metrics_loop），metrics.stop() 在关闭期停止；get_stats() 返回完整摘要，因此经 pool.get_stats()["metrics"] 能看到 system 段（psutil 为可选依赖，缺失时为 None）。

  • Prometheus 出口：to_prometheus_format() 直接输出文本格式（另有 contrib/prometheus.py 生态桥接）。注意：没有 HTTP /metrics 拉取端点，该出口需要调用方自行暴露。

6.2 SystemHealthChecker：注册式，三项内置检查 🔧

monitor/health.py 的 SystemHealthChecker 基于通用 HealthChecker（register/check_all/get_status，healthy/degraded/unhealthy 三态聚合）注册了恰好三个检查：

检查项 做法 降级条件
storage repo.exists("health_check") 探活 抛异常 → UNHEALTHY
queue queue.size() >10000 → DEGRADED
system psutil CPU/内存/磁盘 任一 >90% → DEGRADED

健壮性要点：get_health_status()/_async 会先调 _refresh_health_if_stale()——结果在 HEALTH_CHECK_TTL = 5.0s 内直接复用，过期才重新检查；每个检查都包在 asyncio.wait_for(..., timeout=DEFAULT_CHECK_TIMEOUT=5.0) 里，超时则该项判为 UNHEALTHY 并给出 timed out after Xs 消息，因此某个依赖不可达不会再无限期挂住调用方。psutil 缺失时 system 检查返回 HEALTHY 且 details 为 {"available": False}（可选依赖，不代表系统不健康）。get_health_status() 会把 WorkerPool 统计 + 上述结果拼成一个 dict。启用条件为 enable_health_check=True（默认开）。

6.3 ReporterManager：周期推送（默认关闭） 🔧

enable_reporter=True 时才装配（默认 False）：ReporterManager 每 60s 取一次 get_stats() 回调结果，推给已注册的 reporter。内置三种 reporter：ConsoleReporter（默认注册）、FileReporter、PrometheusReporter（pushgateway 模式）。

6.4 Web UI 与 CLI：不参与装配的独立面

  • WebUIServer（web/server.py）：FastAPI + uvicorn 后台线程，默认 127.0.0.1:8080。TaskPool 不持有、也不会实例化它——全库没有 WebUIServer(...) 的调用方，只能由调用方自行传入 scheduler 手动启动；当前仅暴露 / 与 /api/stats 两个路由（不是完整的任务/节点 REST + WebSocket 面板）。

  • CLI（cli/）：start / webui 两个命令，薄封装。

  • 结论：监控面板是"可选外挂"，不是架构内件；进程内可观测性的正式出口是 metrics + health 两个组件。

七、架构事实速查表

# 易混淆点 当前真实情况
1 是否有 WorkflowEngine 入口 不存在；入口只有 TaskPool/TaskScheduler（+未导出 TaskEngine）
2 是否有 Elector 选举器 无此模块；去中心化架构无主节点，无需选举
3 架构分层 不是线性分层；TaskPool 星型装配 + 两阶段生命周期
4 TimeWheel 归属与状态 属 scheduler/，由 TaskScheduler 装配；enable_time_wheel=True 时 submit_delayed/submit_at 经 add_task 入轮（已接线）
5 心跳与判死 心跳 5s、判死 timeout=20s 一刀切，状态仅 active/stopped/reclaimed
6 抢占与加锁 Lua 只做 ZRANGE+ZREM 原子弹出；锁在 Worker 执行前单独 acquire（TTL=30）
7 超过重试次数的去向 FAILED + 自动投递死信队列（Worker/回收器均已接线），dlq.replay() 支持运维重放
8 失败重试退避 线性：delay = retry_delay × 新次数
9 监控结构 MetricsCollector 事件驱动 + SystemHealthChecker 三项注册式检查（5s TTL / 5s 单项超时）+ ReporterManager；web 为独立组件
10 状态机 创建即 PENDING；FAILED 为终态；重试是 RUNNING→PENDING 的复位入队（worker 内部）
11 分片/一致性哈希 ConsistentHashSharder 完整实现但无装配（Coordinator 未使用）
12 分布式"高可用/回收" 回收链路已闭环（HeartbeatManager 按 node_id 回收、Reclaimer 超时/孤儿回收），见 5.2 节；NodeManager._health_check_loop 的 # TODO: 处理故障节点 仍未实现
13 Coordinator 已实例化但未接线，_select_node/rebalance/handle_node_failure 为占位实现；真实提交走 TaskDispatcher

八、为什么这么设计（架构层汇总）

问题 答案
为什么 TaskScheduler 复用 TaskPool 的事件循环，而不是自建？ 单进程只跑一个事件循环，避免两套 loop 间任务互投的死锁；TaskScheduler 本质是 TaskPool 的"定时投递器"
为什么状态推进集中在 lifecycle，而不是让 Worker 直接改状态？ 状态变更伴随缓存更新、Future 通知、事件发布三件套；集中式门面保证任一执行路径都不会漏掉通知（除 task.progress 外均已收敛到单点）
为什么 Redis 队列延迟到期用 ZSET score=5 转正而非原优先级？ 源码未注释动机；行为上"延迟任务不插队即时任务"。多延迟场景下需实测，勿按直觉假设
为什么周期任务默认由 PeriodicTaskManager 管理却持久化缺位？ enable_periodic_manager=True 但 storage=None：架构预留了存储参数（periodic.py 有 _load/_save_tasks），尚未接通——属于"接口先行、接线后补"
为什么仍有组件"存在但没接线"？ 仓库代码呈现"能力先行"的演进痕迹：分片器、Coordinator 的选节点/再平衡、periodic.py 的加载保存均为先落地接口、再等调用方接入的形态。阅读时应以本文"接线状态"清单为准；死信队列与时间轮则已有明确调用方（Worker/回收器投递死信、enable_time_wheel=True 时延时任务走时间轮）

九、故障场景实战（架构级）

场景 1：以为在用"分布式"，实际是三个独立的内存队列 📝

现象：python main.py --worker 起了 3 个进程，都用默认配置（TaskPoolConfig() → memory）。提交 100 个任务，3 个进程各自执行了一部分，get_stats() 各自只看到自己的任务。

根因：memory 形态的任务仓库与队列都是进程内对象——进程间既看不到任务也抢不到队列。这不是"分布式失败"，而是形态选择错误：多进程消费必须 TaskPoolConfig.redis(url=...)。

对策：按 1.1 节能力阶梯表核对部署拓扑：单进程内多线程/多协程可 memory；单机多进程或跨机必须 redis 形态（或每进程独立 memory 池做隔离用途）。

场景 2：SQLite 双进程：任务表共享、队列脑裂 📝

现象：两个进程以 sqlite 形态共用一个 db 文件。A 进程提交任务后崩溃，B 进程 get_task 能看到 PENDING 记录，但永远等不到执行；重启 A 后任务才被消费。

根因：SQLite 只持久化任务记录；队列与 Worker 状态都在各自进程内。A 崩溃时任务在 A 的内存队列里消失，落库状态停留在 PENDING，B 无从知晓（B 的队列里没有该 task_id）。sqlite 形态无心跳/回收组件，无人接管。

对策：SQLite 形态严格限定单进程（官方默认单写约束）；需要多进程接管能力的场景直接上 Redis 形态；实在要双进程，用 Redis 队列 + SQLite 存储的混合方案（NeoTask 不支持，需自行扩展 QueueRepository）。

场景 3：把"存在的类"当成"可用的能力" 📝

现象：项目引入 NeoTask 后，以为分片/协调等能力开箱即用，结果任务分发并没有按一致性哈希路由，Coordinator 也没有做负载再平衡。

根因：这些组件属于"已实现但未接线"（3.4 节）：ConsistentHashSharder 无装配点，Coordinator 被实例化但真实提交走 TaskDispatcher，其 _select_node/rebalance/handle_node_failure 是占位实现。对照之下，死信队列与时间轮已经接线——失败任务会自动进死信（enable_dead_letter 默认开）、enable_time_wheel=True 时延时任务会走时间轮。

对策：① 以本文 3.4 节"接线状态"清单作为能力底账，逐项对照要用的功能；② 需要分片/再平衡时，需自行扩展（框架未提供装配点）；③ 评估新能力前先 grep 它的调用方，避免被"开关存在"误导。

场景 4：Supervisor 把整个池重启了 📝

现象：一个任务运行超过 300 秒（如视频处理），随后日志显示 WorkerPool 被 stop/start，所有在途任务被中断。

根因：WorkerSupervisor 默认 worker_timeout=300s，busy 且 300s 无活动即判挂起（supervisor.py:80-83）——长任务天然满足触发条件；_restart_worker 以整池 stop(graceful=False) + start() 收尾（113-115 行）。

对策：长任务场景调大 SupervisorConfig.worker_timeout（TaskPool 未暴露该配置，需在构造后替换 pool._supervisor._config 或自行实例化 WorkerSupervisor）；或把长任务拆分为进度上报型短任务，保证 last_active 持续刷新（但注意 task.progress 更新链路未接线，进度需由业务自行回写）。
