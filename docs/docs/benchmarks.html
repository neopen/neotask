一、为什么一个调度框架要自带基准测试

为什么这么设计：性能数字是框架的"体检报告"，不带基准的调度框架等于不提供血压计的医疗设备。

NeoTask 在 tests/benchmark/ 下放了四个脚本（run_benchmark.py / run_fast.py / run_complete.py / test_performance.py），并把实测结果沉淀为 docs/性能基准测试.md。这套设施回答三类问题：

使用者 要回答的问题 基准的作用
框架开发者 这次重构有没有让调度变慢？ 回归守护：断言阈值挡在 CI 里
选型者 它够不够快？适合什么负载？ 提供可信基线，而非营销数字
使用者 我的配置/硬件下应该期待多少？ 给出对照基准与复现方法

对使用者来说，基准最重要的价值反而是校准预期：

  • 调度框架的吞吐由"提交 → 持久化 → 排队 → worker 执行 → 状态回写"整条链路决定，任何一个环节都可能是瓶颈；

  • 官方报告明确写"该数据在什么机器、什么存储、什么版本下测得"——这就是给"跨环境对比"立的规矩；

  • 脚本即文档：noop / light / cpu / io 四种执行器把"调度开销"与"业务执行时间"解耦测量，使用者可以照着构造自己的负载画像。

二、如何读懂一份基准报告：五个先决问题

拿到任何一行吞吐数字，先问五个问题，再决定它能不能用：

flowchart TB
    Q1{1. 测的是哪一段链路?} -->|纯队列操作| A1[数据结构级<br/>30万 ops/s 很正常]
    Q1 -->|端到端任务调度| A2[全链路<br/>1千~1万 ops/s 量级]
    Q2{2. 任务负载是什么?} --> B1[noop: 纯调度开销]
    Q2 --> B2[light: 微计算]
    Q2 --> B3[io: 网络/睡眠为主]
    Q3{3. 什么环境测得?} --> C1[OS/Python/CPU/存储后端]
    Q4{4. 统计口径是什么?} --> D1[吞吐 or P50/P95/P99? 含不含排队?]
    Q5{5. 测试意图是什么?} --> E1[压极限 or 模拟稳态流量?]

对照官方报告的每个表格，逐一作答：

数据 链路 负载 意图
优先级队列 31 万 ops/s 纯内存堆操作 无 数据结构压测
TaskPool 1697 ops/s 提交+调度+执行全链路 noop 端到端压测
持续负载 64.6 ops/s 全链路 light 模拟低频稳态提交（见 4.5 的陷阱解读）

同一个框架，不同测法可以得出相差四个数量级的"吞吐"——不是框架骗人，是口径不同。 对外宣传时必须说明测的是哪一段；对内调优时必须盯住与业务同构的那一段。

三、官方基准脚本结构解析

3.1 四层执行器：把"框架开销"与"业务开销"分离

🔧 tests/benchmark/test_performance.py 定义了四个执行器，这是整个基准体系的分母设计：

# 🔧 tests/benchmark/test_performance.py —— 真实脚本摘录

async def noop_executor(data: Dict) -> Dict:
    return {"result": "done"}

async def light_executor(data: Dict) -> Dict:
    _ = sum(range(100))
    return {"result": "done"}

async def cpu_executor(data: Dict) -> Dict:
    count = data.get("count", 10000)
    result = 0
    for i in range(count):
        result += i
    return {"result": result}

async def io_executor(data: Dict) -> Dict:
    await asyncio.sleep(data.get("sleep", 0.001))
    return {"result": "done"}

设计意图：

  • noop：任务体约等于零，测的是纯调度链路（提交、入队、状态写、worker 分配）的上限；

  • light：模拟真实微任务（几微秒计算），最接近"大量小任务"的生产画像；

  • cpu：可控计算量，用于测量 CPU 密集型任务下 worker 的并行收益；

  • io：任务内睡眠，模拟网络/存储等待，用于测量 IO 并发度——sleep 越长的任务，单位时间能并发执行的数量越大。

为什么这么设计：用"可控负载"而不是"业务代码"做基准，结果才能跨机器复现、跨版本对比。 若拿真实业务（Redis 往返、第三方 API）测，测出来的其实是业务下游的延迟分布，框架优劣被噪声淹没。

3.2 BenchmarkResult：延迟分布的统计骨架

🔧 同一个文件里的 BenchmarkResult 类，负责把原始耗时收敛成可读指标：

# 🔧 tests/benchmark/test_performance.py —— 真实脚本摘录（关键属性）

@property
def p95_latency_ms(self) -> float:
    if not self.latencies:
        return 0
    sorted_times = sorted(self.latencies)
    idx = int(len(sorted_times) * 0.95)
    return sorted_times[idx] * 1000

@property
def p99_latency_ms(self) -> float:
    if not self.latencies:
        return 0
    sorted_times = sorted(self.latencies)
    idx = int(len(sorted_times) * 0.99)
    return sorted_times[idx] * 1000

@property
def throughput_ops(self) -> float:
    if self.duration <= 0:
        return 0
    return self.total_requests / self.duration

注意它同时报告 avg / p50 / p95 / p99 四档延迟，而不是只给平均值——平均延迟对长尾无感，P99 才是线上体感的代理指标。

3.3 测试覆盖的五类场景

🔧 tests/benchmark/run_benchmark.py 中 run_all_benchmarks() 的编排顺序，本身就是一份"该测什么"的清单：

1. 基础吞吐量测试      → TaskPool 端到端吞吐 + 延迟分布
2. 队列性能测试        → 优先级队列吞吐 / 预取器对比 / 批量弹出对比
3. 并发性能测试        → Worker 1/2/4/8 扩展性 + 50 并发提交
4. 任务类型性能测试    → light 任务 / IO 任务
5. 压力测试            → 5 秒持续负载 + 500 突发负载

五类场景分别回答：上限多高、队列多快、加人不加量、任务画像差异、扛不扛得住。

3.4 断言阈值：基准如何变成回归守护

🔧 test_performance.py 中，基准不只是打印，还带断言：

# 🔧 tests/benchmark/test_performance.py —— 真实脚本摘录
assert stats['success_rate'] > 0.95          # 吞吐测试：成功率不低于 95%

# 优先级队列测试中（同类断言）：
# assert total / duration_push > 1000        # 入队吞吐下限 1000 ops/s

这个断言阈值刻意定得远低于实测值（实测 30 万+ vs 阈值 1000）。为什么这么设计：CI 里的阈值不是为了卡性能天花板，而是为了抓"灾难性回归"——性能测试跑在共享 CI 机器上，波动两个数量级都正常，阈值设在"从 30 万掉到不足 1000 才算失败"的位置，只拦截结构性破坏（如死循环、锁死、O(N²) 引入），不误伤环境抖动。若把阈值贴近实测值，基准测试就会变成天天误报的"狼来了"，最终被开发者跳过——那才是真正的回归失守。

4.2 端到端与数据结构两级吞吐

🔧 官方实测：

测试项 结果 说明
TaskPool 基础吞吐（1000 noop 任务） 1697.31 ops/s 成功率 100%
轻量任务吞吐（500 × sum(range(100))） 1395.82 ops/s 平均延迟 0.72ms
IO 任务吞吐（200 × 5ms 睡眠，20 worker） 4671.37 ops/s 平均延迟 0.21ms
优先级队列入队 / 出队（5000 任务） 208,371 / 312,443 ops/s 纯内存堆操作
单条弹出 vs 批量弹出（10条） 250,033 vs 499,976 ops/s 提升 2.00x

4.3 深读一：为什么端到端 1697 与队列 31 万差了两个数量级？

队列测试只调用 PriorityQueue.push/pop——一次 heapq 操作，微秒级；而 TaskPool 测试中每个任务经历完整生命周期：

flowchart LR
    subgraph chain["一个任务的完整生命周期"]
        A[submit_async<br/>入队] --> B[存储写<br/>task 记录]
        B --> C[worker 取任务] --> D[状态置 RUNNING]
        D --> E[执行 executor] --> F[状态置 SUCCESS]
        F --> G[事件发布/统计]
    end

每一步都有协程切换与字典/状态操作，noop 任务本身虽快，但每个任务在多个协程间移交，事件循环的调度开销被放大。1697 ops/s 意味着单任务全链路约 0.59ms——其中 executor 只占几十微秒，其余全是框架的调度与状态机开销。

结论：30 万 ops/s 是"队列组件"的性能，1697 ops/s 是"整个框架"的性能。宣传与对比时若混用两者，误差超过两个数量级。 做架构对比（NeoTask vs Celery vs 自研）必须用端到端口径。

4.4 深读二：Worker 扩展性 1.00x——是不是说明并发没用？

🔧 官方实测：

Worker 数量 吞吐量
1 801.58 ops/s
2 853.25 ops/s
4 805.08 ops/s
8 858.27 ops/s
扩展效率 1.00x（4 workers vs 1 worker）

为什么加 worker 不加速？ 测试用的是 light 任务（几微秒计算），瓶颈根本不在"执行"，而在提交端：测试主协程串行 submit_async，提交速度就是吞吐上限。worker 从 1 加到 8，队列里始终没有积压，自然测不出并行收益。

这个"不理想"的结果恰恰暴露了基准设计的诚实：报告如实记录"扩展效率 1.00x"，而不是挑一个好看的任务类型掩盖它。 正确读法是：

  • 对微任务，吞吐上限在提交链路（事件循环单线程串行提交），加 worker 无效；

  • 对 IO 任务（4.2 中 4671 ops/s），20 worker 才有意义——sleep 让出事件循环，worker 并发数直接决定在飞任务数；

  • 想让 worker 扩展性变好，测试必须让执行时间显著大于调度开销（IO 任务或 cpu_executor 加量）。

4.5 深读三：持续负载 64.6 ops/s——报告里最"难看"也最有信息量的数字

🔧 官方实测：持续 5 秒提交，总计 323 个任务，错误 0，64.60 ops/s。

表面看这数字低得离谱（比端到端 1697 还低 26 倍），先别急着下结论，看脚本怎么写的：

🔧 tests/benchmark/run_fast.py 中持续负载测试的核心循环：

# 🔧 run_fast.py —— 真实脚本摘录（节选）
duration = 5
start = time.time()
while time.time() - start < duration:
    await pool.submit_async({"index": total_submitted}, task_id=unique_id)
    total_submitted += 1
    await asyncio.sleep(0.001)   # ← 关键行：每提交一个任务，睡 1ms

数学验算：5 秒提交 323 个 → 每轮循环耗时 ≈ 5000ms / 323 ≈ 15.5ms。而脚本只让协程睡 0.001s（1ms）——实际却花了 15.5ms，差异从哪来？

根因：Windows 的系统定时器粒度。 官方测试跑在 Windows 10 上，Windows 默认定时器分辨率约为 15.6ms（除非进程调用 timeBeginPeriod 主动提频）。asyncio.sleep(0.001) 在 Windows 上实际唤醒周期受此限制，1ms 的睡眠被放大成 ~15.6ms。于是这个测试的提交速率不是被框架限制的，而是被操作系统定时器限制的——脚本本意是"模拟每 1ms 来一个任务的稳态流"，在 Windows 上实际变成"每 15.6ms 来一个任务"，吞吐自然只有 ~64 ops/s。

这个数字的三个启示：

  1. 读基准必须先读脚本——64.6 ops/s 不是框架能力下限，是脚本节流 + 平台定时器共同作用的结果；

  2. 跨平台对比基准前，先确认定时器/时钟行为：同一脚本在 Linux（定时器高精度）上会得到完全不同的数字；

  3. 官方报告"失败/异常"栏目同样有价值（见下），它划清了"哪些数字可信"的边界——比一份全绿但口径可疑的报告诚实得多。

4.6 官方报告承认的两个未完成测试

🔧 docs/性能基准测试.md 中的"未完成测试"：

测试项 状态 官方记录的原因
高并发提交测试（50 并发 × 20 批） 失败 asyncio 事件循环绑定问题
预取器性能测试 异常 测试结果不符合预期（可能实现问题）

怎么读这张表？

  • 高并发提交：pytest 的 event_loop fixture 与 TaskPool 内部事件循环在特定环境下的绑定冲突，属测试基建问题而非框架缺陷——run_fast.py 单独运行时已覆盖同类场景（200 突发/50 并发等均成功）；

  • 预取器对比：报告怀疑"可能实现问题"。这一条最有价值——它把疑问写进了文档，后来者（v0.5 的预取优化）才有据可查。可结合系列《预取机制》一文对照阅读：预取是否生效，取决于消费端是否真能消化批量任务；若 worker 取走一批后处理不过来，预取只把积压从 Redis 搬到本地。

为什么这么设计：测试报告要记录失败，而不是只记录成功。 只报绿的数字会诱导使用者做出错误的容量规划；注明"哪项没测成、为什么"，报告的信任边界才清晰。

4.7 突发负载：500 任务 0.08s（6565 ops/s）说明什么

500 个任务全部通过 asyncio.gather 并发提交，总耗时 0.08s——其中包含并发提交与全部执行完。对比基础测试 1000 任务串行提交 0.59s：

  • 提交从串行（每次 await 完整往返）改为并发（gather 批量发起），提交侧不再是瓶颈；

  • 0.08s 是"50 worker 并发消费 500 个微任务"的真实水平，这才是并发能力的体现——与 4.4 的 1.00x 扩展性并不矛盾：只要提交端能并发灌入，worker 并行度立刻转化为吞吐。

五、为什么这么设计：三个被低估的细节

细节一：批量弹出（pop 10）比单条弹出快 2 倍

🔧 官方实测：250,033 → 499,976 ops/s（2.00x）。脚本中两种模式的差异在循环次数：

单条：1000 次 pop(1)      → 每次调用完成 取锁→heapq→解锁 完整往返
批量：100 次 pop(10)      → 每次调用一次取锁，一次处理 10 个元素

本质是摊薄固定开销：每次方法调用都有锁获取（内存模式为 asyncio.Lock，Redis 模式为一次网络 RTT）与堆操作。pop(10) 一次调用完成 10 个元素，固定开销只付一次。这正是《预取机制》文章中"worker 按批拉取"设计的性能依据——能用批量接口，就不要逐条调用。

细节二：延迟统计四档齐全，而不是只有一个平均值

BenchmarkResult 同时输出 avg / p50 / p95 / p99。平均延迟对异常值（比如 GC 停顿、调度抖动）不设防，P99 才贴近用户最差体验。调度框架的延迟画像天然右偏（少数任务撞上重负载窗口），只报平均值会系统性低估长尾。

细节三：成功率断言与吞吐断言分离

assert success_rate > 0.95 放在吞吐测试里——高吞吐而低成功率毫无意义。真实系统里"快但丢任务"比"慢而全对"更危险：任务悄悄失败，业务侧无从感知。基准同时守护吞吐与可靠性两个维度，与框架把"任务状态机 + 回收器"作为一等公民的设计互为印证。

6.2 构造你自己的负载画像

📝 示例：模仿官方的执行器分级，先跑一组"业务画像基线"，再决定配置：

# 📝 示例代码：自定义负载画像（参照官方四层执行器的方法）
import asyncio
from neotask.api.task_pool import TaskPool, TaskPoolConfig

async def business_executor(data):
    # 1. 你的真实业务第一步（比如一次带缓存的 DB 查询）
    await asyncio.sleep(0.002)          # 模拟 IO 等待
    # 2. 你的真实业务计算段
    _ = sum(range(500))
    return {"ok": True}

async def main():
    # 先测 4 worker，再测 8/16，观察吞吐拐点
    for workers in (4, 8, 16):
        pool = TaskPool(executor=business_executor,
                        config=TaskPoolConfig(worker_concurrency=workers))
        pool.start()
        # 并发灌入 2000 个任务（gather 并发提交，参照官方突发负载法）
        tasks = [pool.submit_async({"i": i}) for i in range(2000)]
        task_ids = await asyncio.gather(*tasks)
        # 等待全部完成……统计耗时 → 得到该 worker 数下的端到端吞吐
        pool.shutdown()

asyncio.run(main())

复现纪律：换机器跑基准，必须连"环境信息"一起记录（OS / Python 版本 / CPU 型号 / 存储后端 / 版本号 / 日期），否则数字无法二次使用。

七、从数据到配置：性能调优决策路径

官方报告末尾的性能建议，本质是把实测规律翻译成配置决策：

flowchart TB
    LOAD[我的任务画像?] -->|绝大多数是 IO 等待| IO[worker = CPU核 × 2~4<br/>例: 12线程 × 3 ≈ 36]
    LOAD -->|CPU 密集| CPU[worker ≈ CPU 核数<br/>例: 12]
    LOAD -->|微任务海量| LIGHT[worker 少量即可<br/>瓶颈在提交端, 优先优化提交方式]
    IO --> BATCH[能用批量接口用批量<br/>pop 批量 / 预取]
    CPU --> BATCH
    LIGHT --> BATCH
    BATCH --> STORE{需要持久化/分布式吗?}
    STORE -->|单机开发/最高吞吐| MEM[内存存储]
    STORE -->|轻量持久化| SQL[SQLite]
    STORE -->|多节点高可用| REDIS[Redis]
决策点 依据（本文数据） 建议
worker 数量 IO 任务 20 worker 达 4671 ops/s；微任务加 worker 无效 按任务画像选择，见上图
提交方式 串行 1697 vs 并发突发 6565 ops/s 高吞吐场景用 asyncio.gather 批量并发提交
消费接口 批量弹出快 2.00x 队列层优先 pop(count>1) / 开启预取
存储后端 内存最快，Redis 含网络 RTT 吞吐敏感选内存/SQLite；分布式才上 Redis
延迟目标 P99 与 avg 分开设 SLO 用 BenchmarkResult 同款口径监控生产

八、与版本演进目标量级的对照说明

系列《版本演进》一文还列有一组"性能基准"数字（单机 1 worker 50k QPS、10 worker 100k QPS、Redis 3 节点 25k QPS、预取 30k QPS……）。这组数字是设计目标/规划量级，不是实测数据，与本文引用的官方实测（1697 ops/s）用途不同，请勿混读：

出处 性质 用途

规则一句话：说"实测"必须带环境与版本；说"目标"必须标注是设计值。 两者错位正是性能文章最常见的失实来源。

九、故障场景实战：基准测试的四个误用陷阱

场景一：把"队列吞吐 31 万"当框架能力对外汇报

现象：汇报材料写"NeoTask 吞吐 30 万 ops/s"，架构评审按这个量级做了容量规划，上线后实际只有不到 2000，被质疑数据造假。

根因：混淆了"组件基准"与"端到端基准"——队列测试不含提交、存储、状态机、执行，只测了 heapq 的裸速度。

处置：汇报口径统一为"端到端调度吞吐（noop 负载，内存存储，某环境）≈ 1.7k ops/s；其中队列组件单测可达 30 万级"。组件数据用于内部优化定位，端到端数据用于对外承诺。

场景二：Windows 上跑延时类基准，数字莫名低一个数量级

现象：本地 Windows 复现基准，持续负载只有 ~60 ops/s，同事 Linux 机器上同样代码却有几万，怀疑代码有平台 bug。

根因：Windows 定时器默认粒度 ~15.6ms，asyncio.sleep(0.001) 实际唤醒 ~15.6ms/次（本文 4.5 节的 323 次/5s 即此现象）；代码无 bug，是平台定时器差异。

处置：① 涉及 sleep 节流的基准，先在代码注释里写明"受平台定时器分辨率影响"；② 跨平台对比时，把节流 sleep 提到 50ms 以上（远大于两种平台的粒度）或用 time.perf_counter 驱动的无 sleep 压测循环；③ 生产环境若需要高精度延时调度，请勿依赖 Python 层 sleep——参考框架的延时任务实现（DelayedQueue 堆 / Redis ZSET 到期扫描，或开启可选时间轮），把精度问题交给存储层的到期时间判断。

场景三：冷启动污染首轮数据

现象：第一次跑基准吞吐只有几百，第二次同脚本跑到几千；开发者把低值写进报告，或把高值当成稳定水位。

根因：首轮包含惰性初始化——连接池建立、Lua 脚本注册、worker 线程创建、JIT/解释器预热等一次性开销被计入统计窗口。

处置：基准脚本先跑 1~2 轮"预热负载"（如先提交 200 个任务并等待完成），再开始计时统计；报告注明"已预热"。官方脚本在计时前 await asyncio.sleep(0.5) 等待 worker 就绪，同理。

场景四：拿别人的数字做自己的容量规划

现象：参考"官方 1697 ops/s"给 10 万日任务量的系统选型，结论是"性能不够要换框架"；或反过来，参考"30 万 ops/s"拍板不用队列优化，上线即积压。

根因：把"特定环境、特定负载、特定版本"的实测，当成普适常量。官方数据基于 Windows 笔记本 + 内存存储 + v0.3.0 noop/light 任务；真实业务是 Redis 存储 + 分布式 + 混合负载，数字会整体下移；而"日任务量 10 万"平均每秒不足 2 个，离 1697 差着三个数量级，容量规划的核心从来不是峰值基准，而是你自己的业务吞吐 + 峰值倍率 + 恢复目标。

处置：选型前用 6.2 的方法跑自己的负载画像；把基准当作"量级参考"而不是"精确承诺"。归档公式：需要容量 = 日均任务数 / 86400 × 峰值倍数 × 重试放大系数，再与自测端到端吞吐对照，留 2~3 倍余量。

十、总结

主题 结论
为什么自带基准 回归守护 + 选型基线 + 预期校准，脚本即文档
五种负载形态 noop/light/cpu/io 四执行器 + 突发/持续两类压力，把框架与业务开销解耦
最大量纲陷阱 组件基准（30 万级）与端到端基准（千级）相差两个数量级，不可混用
Worker 扩展性 微任务瓶颈在提交端（1.00x）；IO 任务才有并发红利；提交要 gather 并发
64.6 ops/s 之谜 Windows 定时器 15.6ms 粒度放大 sleep(0.001)，是平台效应而非框架缺陷
报告诚实性 官方文档记录失败与异常测试，划定数据可信边界，比全绿报告更有价值
断言阈值设计 CI 阈值只拦灾难性回归（量级下滑），不设贴近实测的"理想值"
调优路径 画像 → worker/提交/批量/存储四步决策，见第七节决策树

一句结语：性能数字是测量方法的函数。NeoTask 的基准体系最值得借鉴的不是某个数字，而是它的方法论——可控负载分级、全链路与组件分离、四档延迟统计、失败照实记录。用这套方法论去测任何调度系统，你都能得到可信的结论；跳过方法论直接抄数字，再快的框架也会在容量规划里翻车。
