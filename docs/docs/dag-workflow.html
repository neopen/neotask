一、为什么任务调度最终需要编排层

单看 v0.1~v1.0 的能力，NeoTask 已经能回答三个问题：任务何时执行（延时/周期/Cron）、按什么顺序执行（优先级队列）、会不会重复执行（分布式锁 + 看门狗 + 回收器）。但真实业务很少只有一个任务：

flowchart TB
    subgraph biz["一个典型业务：订单履约"]
        direction TB
        A[接收订单] --> B[库存预占]
        B --> C{风控审核}
        C -->|通过| D[生成出库单]
        C -->|拒绝| E[自动退款]
        D --> F[通知物流]
        E --> F2[通知用户]
        F --> G[订单完成]
        F2 --> G
    end

把这段流程写成"若干独立任务"直接提交，调度器只会得到一堆互不相干的任务 ID——执行的先后、分支的选择、结果的汇聚，全部散落在业务代码里，每次都要重复实现一遍，且无法被框架观测。

这就是编排层存在的理由：把任务之间的"关系"从业务代码中抽出来，变成框架可理解、可持久化、可恢复的一等公民。

单体代码 vs 拆碎的任务 vs 编排层

方案 可观测性 故障边界 重试粒度 水平扩展 代码形态
单体流程函数 好（一个请求栈） 差：一处异常整段回滚 整段重放 难 嵌套调用、局部变量传递
拆碎后手工串 差：任务间关系不可见 中：单任务可重试 单任务 好 到处是"查上个任务结果"的胶水代码
编排层（DAG） 好：整张图可见 好：节点级隔离 单任务 + 工作流两级 好 声明式定义，引擎驱动

为什么这么设计（一）：把流程控制权交给框架，是编排层的第一动机。

单独一个任务的可靠性（重试、超时、锁）v1.0 已经解决得很扎实；编排层不是要另起炉灶，而是把"多任务的时序与选择"也纳入框架的可靠性边界。这样业务里不再出现手写的 while True: 轮询上个任务结果——那既不可观测，也无法从宕机中恢复（轮询状态在进程内存里，进程一死就归零）。

二、编排层要解决的四个问题

四个问题对应四种能力，缺一个都不能叫"编排"：

flowchart LR
    subgraph core["编排四要素"]
        direction TB
        SEQ[顺序依赖<br/>A 完成后 B 才能开始]
        PAR[并行执行<br/>同一层多个节点同时跑]
        BR[条件分支<br/>上游结果决定走哪条边]
        AGG[聚合等待<br/>多个上游全部完成才继续]
    end

1. 顺序依赖（Sequential）

严格的前驱-后继关系。例如"先扣库存、再生成出库单"。调度上等价于上游终态触发下游就绪。

2. 并行执行（Parallel）

无依赖关系的节点可以同时执行。注意区分两个"并行"：

  • 队列层并行：框架早就支持——多个 worker 同时从优先级队列取任务。这与 DAG 无关，是执行资源层面的并行；

  • 依赖层并行：DAG 中"同一时刻有多个可执行节点"。这才是编排层引入的并行度，受 worker 并发上限约束。

3. 条件分支（Conditional）

边的守卫（guard）：上游完成后，评估下游每条入边的条件，只有条件为真的边才会让下游节点"就绪"。常见的两种实现风格：

风格 语义 优点 缺点
节点内 if 任务自己判断并返回"跳过" 实现简单 分支逻辑不可见；"跳过"还要定义状态
边上守卫 分支是图结构的一部分 整张图可绘制、可审计 需要结果求值表达式能力

为什么推荐守卫在边上（见第五节第三个决策）。

4. 聚合等待（Join）

“等 B 和 C 都完成才执行 D”。引擎需要为每个节点维护未满足的前驱计数，每个上游完成时递减，归零才放行。

聚合等待的反面是扇出（Fan-out）：一个上游触发多个下游。扇出 + 聚合组合成"钻石依赖"，是最考验引擎实现的图结构。

三、DAG：依赖图的建模选择

3.1 为什么必须是 DAG

  • Directed：依赖有方向（A→B 表示 B 依赖 A），不可反向；

  • Acyclic：无环。环意味着"死锁的依赖"——任何节点都无法率先满足条件，工作流永远无法推进；

  • Graph：节点 + 边，天然支持分支与汇聚。

flowchart TB
    subgraph bad["有环依赖：永远无法启动"]
        X --> Y
        Y --> Z
        Z --> X
    end

为什么这么设计（二）：用无环性换取"可推进性"的确定性。

有环图并非不能调度（有环需要运行时破环策略，语义复杂），但任务编排的核心诉求是确定性：给定同样的输入与同样的执行结果，工作流必然推进到同一终态。DAG 保证每个节点存在拓扑序，引擎可以无条件按拓扑序推进，不会出现"所有节点都在等别人先完成"的活锁。环需求的正确解法是拆出"循环任务"（用周期调度表达），而不是允许图中有环。

3.2 建模：节点是模板，边是依赖，一次提交是一个实例

沿用 NeoTask 一以贯之的"定义与执行分离"思想（Cron 定义 vs 一次触发），工作流的建模分三层：

层 概念 生命周期 示例
定义 WorkflowDefinition（节点 + 边） 长期存在，可重复提交 "订单履约流程"定义一次
实例 WorkflowExecution（一次提交） 单次执行，有终态 订单 #12345 跑一遍该流程
节点执行 实例内某个任务的一次运行 最短，受状态机约束 库存预占（订单 #12345）

这里的关键是模板与实例分离：同一张图可以并发跑 1000 个实例（1000 个订单），各自状态互不串扰。若把图本身当状态存，并发提交立刻互相污染。

3.3 定义示例：本文设计的提交方式

📝 仓库尚未公开工作流 API，下面两个接口形态是本文为讲清设计而提出的提案（规划项，v1.0.2 中不存在）：

engine.submit_workflow(definition)   # 提交工作流（设计提案，v1.5 规划）
engine.wait_workflow(execution_id)   # 等待工作流（设计提案，v1.5 规划）

📝 依据上述形态与 ADR-005 决策，一个"订单履约"定义的合理形态如下（设计示例）：

from neotask.workflow import WorkflowDefinition, WorkflowNode, WorkflowEdge

# 📝 设计示例：定义一张 DAG —— 订单履约流程
definition = WorkflowDefinition(
    workflow_id="order_fulfillment",
    nodes=[
        WorkflowNode(id="receive",     task="order.receive",     params={"source": "ctx.order_id"}),
        WorkflowNode(id="inventory",   task="order.prestock",    params={"order_id": "ctx.order_id"}),
        WorkflowNode(id="risk",        task="order.risk_check",  params={"order_id": "ctx.order_id"}),
        WorkflowNode(id="ship",        task="order.create_ship", params={"order_id": "ctx.order_id"}),
        WorkflowNode(id="refund",      task="order.auto_refund", params={"order_id": "ctx.order_id"}),
        WorkflowNode(id="notify_ship", task="order.notify_ship", params={"order_id": "ctx.order_id"}),
        WorkflowNode(id="notify_refund", task="order.notify_refund", params={"order_id": "ctx.order_id"}),
        WorkflowNode(id="done",        task="order.mark_done",   params={"order_id": "ctx.order_id"}),
    ],
    edges=[
        WorkflowEdge(from_="receive", to="inventory"),
        WorkflowEdge(from_="inventory", to="risk"),
        # 条件分支：风险通过走发货链路，拒绝走退款链路
        WorkflowEdge(from_="risk", to="ship",   guard="result.passed == true"),
        WorkflowEdge(from_="risk", to="refund", guard="result.passed == false"),
        # 并行扇出
        WorkflowEdge(from_="ship",   to="notify_ship"),
        WorkflowEdge(from_="refund", to="notify_refund"),
        # 聚合等待：两类通知都完成才收尾
        WorkflowEdge(from_="notify_ship",   to="done"),
        WorkflowEdge(from_="notify_refund", to="done"),
    ],
)

execution_id = await engine.submit_workflow(definition, context={"order_id": 12345})

几个建模细节：

  1. task 指向已注册的任务模板，节点不携带实现，只携带参数绑定——与 TaskPool 的"executor + data"心智一致；

  2. guard 是表达式字符串，求值对象是上游节点的 result。表达式必须在引擎内做白名单求值（只允许取结果字段和上下文，不允许任意代码执行）——这是安全底线；

  3. context 是整个实例共享的输入，下游参数用 ctx.xxx 引用（见第七节）。

四、引擎核心循环：就绪队列驱动拓扑推进

4.1 一次推进的完整时序

sequenceDiagram
    participant Client
    participant Engine
    participant Store as 执行记录存储
    participant Pool as TaskPool(worker)
    participant Lock as 分布式锁

    Client->>Engine: submit_workflow(definition, context)
    Engine->>Store: 创建 Execution(RUNNING)，写入全部节点状态
    Engine->>Engine: 计算入度，就绪集 = 无入边节点
    loop 每处理完一个节点
        Engine->>Pool: 提交就绪节点任务(携带 node_id)
        Pool-->>Engine: 任务完成/失败事件
        Engine->>Store: 更新节点终态 + 结果
        Engine->>Engine: 更新下游入度计数
        alt 入度归零 且 所有守卫通过
            Engine->>Engine: 加入就绪集
        else 存在失败节点(策略=终止)
            Engine->>Store: Execution → FAILED
        end
    end
    Engine-->>Client: execution 终态（wait_workflow 返回）

4.2 就绪队列 + 入度计数的最小骨架

📝 设计示例：演示"为什么入度计数比每次扫全图高效"——推进一个节点只需 O(出边数) 的更新，而不是 O(全图) 的重算：

import asyncio
from collections import deque

# 📝 设计示例：DAG 调度骨架（演示就绪队列推进算法，非仓库实现）

async def run_dag(nodes: dict, edges: list):
    """nodes: {node_id: coro}，edges: [(from, to, guard)]"""
    indegree = {nid: 0 for nid in nodes}
    dependents = {nid: [] for nid in nodes}
    for frm, to, guard in edges:
        indegree[to] += 1
        dependents[frm].append((to, guard))

    results = {}
    ready = deque(nid for nid, d in indegree.items() if d == 0)
    completed = 0

    while ready:
        node_id = ready.popleft()
        results[node_id] = await nodes[node_id]()

        for child, guard in dependents[node_id]:
            if guard and not evaluate(guard, results.get(node_id)):   # 守卫不过
                indegree[child] -= 1                                    # 仍然放行计数，
                continue                                                # 但不触发 child（见 5.3）
            indegree[child] -= 1
            if indegree[child] == 0:
                ready.append(child)
        completed += 1

    assert completed == len(nodes), "存在不可达节点（环或守卫全部不满足）"
    return results

4.3 三个必须注意的实现细节

  1. 依赖"结果"而非"完成"：聚合节点等待的是所有入边的结果都可用（失败也是一种结果），因此入度递减发生在"节点进入终态"时，而不仅是"成功"时；

  2. 分布式下入度计数必须持久化：计数若只活在内存里，引擎节点一宕机整张图的推进状态就丢了——这是第六节讨论存储的关键；

  3. 推进事件与任务完成事件必须串行化：同一节点的下游只允许被推进一次，防止"完成事件被重放导致节点重复入队"。落地手段就是系列文章反复出现的分布式锁 + 幂等状态更新（lock:workflow:{execution_id}:{node_id}）。

五、为什么这么设计：五个关键决策

决策一：为什么是"依赖就绪 + 事件推进"，而不是"任务回调任务"？

直觉方案是：上游任务成功后，在代码里直接 submit(下游任务)——任务回调任务，无需新引擎。

这个方案的三个致命伤：

问题 说明
回调链不可恢复 "任务 A 提交 B"这一动作发生在 A 的进程里。A 成功、提交 B 之前进程崩溃 → B 永远丢失，而 A 已标记成功，无人知道该补 B
调用图不可观测 谁依赖谁只存在于运行时的函数调用里，无法预检环、无法计算 ETA、无法可视化
无法整图控制 想"整个工作流失败时把已并行跑的任务都取消"？没有图的全局视角就做不到

事件推进的反向设计：节点只负责产生"终态事件"，由引擎（而非节点）决定下一步。节点永远不需要知道自己的下游是谁——图的拓扑是引擎的数据，不是任务的代码。这样"推进决策"集中在一处，可持久化、可恢复、可观测。

一句话：任务不知道图，图才拥有任务。 这与 v1.0 的回收器设计一脉相承——执行者不负责自己的善后，善后由框架的独立组件负责。

决策二：为什么需要独立的执行实例状态，而不是复用任务状态？

每个节点任务确实会走 TaskPool 的状态机（PENDING→RUNNING→终态）。但工作流还需要一层节点级状态：PENDING(未就绪) / READY(可执行) / RUNNING(已提交) / SUCCESS / FAILED / SKIPPED(守卫未过) / CANCELLED。

复用任务状态为什么不够？

  • 任务的 PENDING 语义是"在队列里等 worker"，节点的 PENDING 语义是"在图上等依赖"，同一个词、两种含义，混用必然误判；

  • 节点可能被多次执行（重试），需要区分"节点状态"与"单次任务状态"；

  • SKIPPED 是图专属状态——被守卫挡下的节点从未进入队列，任务状态机里根本没有对应物。

所以：任务状态描述"一次执行的命运"，节点状态描述"该节点在这张图实例里的命运"，两层状态机各司其职，用 execution_id + node_id + attempt 关联。

决策三：为什么条件分支放在"边上"，而不是"节点内"？

把分支写成节点内 if，表面上省了表达式引擎，代价是：

  1. 审计性：运营人员想确认"什么条件下会退款"，图上直接可见一条带守卫的边；写在代码里则需要读任务实现；

  2. 跳过语义混乱：节点内 if 的"不满足分支"该返回什么？返回成功会让下游误以为真执行过；返回特殊错误会被重试策略重试。SKIPPED 只有作为图级状态才干净；

  3. 可视化 = 真相：边上的守卫可以直接渲染成流程图上的菱形与标注，图本身就是文档。

守卫放边上的代价是引擎需要一个受限表达式求值器。约束：只允许访问 result（上游输出）与 ctx（实例上下文），只允许比较/逻辑运算，严禁执行任意 Python。表达式一律在提交时做静态校验（可参考仓库中 Cron 解析器"提交即校验"的既有风格），非法表达式直接拒绝提交，而不是运行到一半才炸。

决策四：扇出并行会不会打爆 worker？限流放在哪一层？

一条"通知 10 万用户"的扇出，若引擎一次性把 10 万节点全部提交到队列，会瞬间排空 worker 的可用并发，挤占其他工作流的任务。

所以引擎提交就绪节点时必须节流：

  • 扇出上限：单次事件最多放行 N 个节点（如 100），其余留在就绪集，worker 空闲事件继续驱动；

  • 优先级映射：节点以定义时的 priority 写入优先级队列（复用 ZSET 语义，CRITICAL=0 ~ LOW=3），不同工作流的节点天然混排、按优先级抢占——编排层不应自建独立队列系统，而是复用调度器的混排语义；

  • 并发预算：一个 execution 同时 RUNNING 的节点数有上限（如 50），防止单个大扇出工作流饿死其他工作流。

这三条合起来回答了一个常见疑问："DAG 引擎要不要自建 worker？"不需要。引擎只做拓扑推进与节流，真正的执行仍交给 TaskPool——见第六节。

决策五：失败传播的两种默认策略

策略 语义 适用
fail-fast 任一节点失败 → 取消所有未执行节点，工作流 FAILED 数据管道：一个环节错，后续没有意义
fail-continue 失败节点标记 FAILED，与它无依赖关系的分支继续 监控告警类：一个分支失败不影响其他分支

对 fail-fast 还要补一个设计问题：要不要自动重跑整个 DAG？ 建议只提供"手动重跑 + 按失败节点及其下游重跑"两种，不提供无条件整图自动重试——自动重试一张大图，很可能重复执行了大量只读边界之外的有副作用的节点（如已发出的退款通知）。副作用操作的重试决策必须由人参与，这比"看起来自动化"更重要。

六、从既有原语到 DAG：v0.4-v1.0 如何被复用

6.1 映射关系

编排层诉求 复用的既有原语 出处
节点按优先级混排 优先级队列（Redis ZSET） v0.4
节点间"等一会儿再跑"（重试退避） 延时队列（queue:delayed） v0.3
节点只执行一次（防重入） 分布式锁 lock:task:{task_id} + 看门狗 v1.0
引擎崩溃后的节点恢复 回收器：超时回收 + 锁清理 v1.0
执行过程可观测 事件总线 / Metrics / 状态索引 status:{value} v0.2/v1.0
节点执行的持久化 task 表 JSON + 状态索引 v0.1~v1.0 演进

6.2 引擎崩溃恢复：复用 v1.0 的回收语义

这是整套设计里最值得展开的一环。工作流执行中引擎进程宕机，正在 RUNNING 的节点任务不会死——它们跑在别的 worker 上，有看门狗续期、有锁保护。真正丢的是引擎内存里的推进状态（哪些节点已完成、入度还剩多少）。

因此执行记录存储必须记录：

execution:{id}        → Execution 主记录（状态、上下文引用、创建时间）
execution:{id}:node:{nid} → 节点状态（PENDING/READY/RUNNING/SUCCESS/FAILED/SKIPPED）
execution:{id}:ready  → 就绪集合（待提交的节点，Redis SET）

恢复流程（与 v1.0 回收器"扫描-判定-重整"三段式同构）：

sequenceDiagram
    participant Recover as 新的引擎节点
    participant Store as 执行记录存储
    participant Lock as 分布式锁
    participant Pool as TaskPool

    Recover->>Store: 扫描 RUNNING 的执行实例
    Recover->>Lock: 获取 execution 级恢复锁（防双引擎同时恢复）
    Recover->>Store: 对每个节点重算状态
    Note over Recover: 节点任务实际仍在跑(RUNNING, 有看门狗)? → 保持 RUNNING，等事件
    Note over Recover: 节点任务已超时(回收器已重新入队)? → 保持 RUNNING，等事件
    Note over Recover: 节点成功但事件未处理? → 从 task 终态补推下游
    Recover->>Store: 重建 ready 集合与入度
    Recover->>Pool: 恢复推进（幂等：重复提交被锁挡住）

恢复的关键词是幂等重建：恢复动作不信任"宕机前内存里最后的推进到哪"，只信任存储里的节点终态，从终态反推下一步。这正是分布式系统里最常见的恢复哲学——状态决定动作，而不是动作的记忆决定状态。

6.3 为什么不自研"分布式事务"来保证 DAG 原子性？

有人会问：整张图要么全成功要么全失败，不该用分布式事务吗？

任务编排与数据库事务的目标不同：事务追求"瞬间的原子性"，工作流追求"过程中的最终一致性"。 一个跑了 40 分钟、期间发出退款通知的工作流，不可能也不应该"回滚"——通知发出去了就是发出去了。工作流的正确语义是：

  • 可恢复：任何一步崩溃都能从持久化状态继续推进；

  • 可补偿：对已产生的副作用，用专门的补偿节点（如退款撤销、库存回补）处理，而不是回滚；

  • 可观测：失败发生在哪个节点、为什么，随时可查。

用分布式事务强撑编排，等于把"长流程"硬塞进"短事务"的模型里，结果必然是锁粒度失控 + 事务超时泛滥。调度系统的原子单位是"单个节点任务的提交"，不是"整张图"——图的一致性靠状态机收敛，不靠两阶段提交。

七、工作流状态机与上下文传递

7.1 工作流实例状态机

与系列其他组件一样，状态机用 stateDiagram 表达（与版本演进文章 ADR-005 的公开状态设计保持一致）：

stateDiagram-v2
    [*] --> PENDING: 创建执行实例
    PENDING --> RUNNING: 校验通过，开始推进
    PENDING --> CANCELLED: 提交后、执行前取消

    RUNNING --> WAITING: 有节点执行中
    WAITING --> RUNNING: 有节点就绪/完成
    RUNNING --> SUCCESS: 全部节点终态且无失败
    RUNNING --> FAILED: 失败策略触发
    RUNNING --> CANCELLED: 用户取消

    SUCCESS --> [*]
    FAILED --> [*]
    CANCELLED --> [*]

注意 PENDING 阶段包含整图静态校验：环检测（拓扑排序失败即拒绝）、守卫表达式合法性、参数绑定完整性、节点 task 是否已注册。校验失败在提交时就报错，而不是执行到一半报错——这是廉价而高价值的防御。

7.2 上下文：结果如何传递给下游

每个节点执行时拿到：

ctx:           工作流输入（订单 ID、用户 ID……全实例共享，只读）
upstream_result: 各上游节点的输出（按上游 node_id 索引）

两个必须想清楚的设计点：

  1. 上下文存储引用而非值：下游任务真正消费的是"订单 ID"这种小值；若上游输出是 10MB 的中间数据，塞进每个下游任务的 payload 会让任务体膨胀、Redis 内存告急。合理做法是：小值入上下文，大结果写对象存储/数据库，上下文只存 ref://storage/xxx；

  2. 上下文不可变：执行期间上下文只读。若允许运行中修改 ctx，两个并行节点同时写同一 key 会产生不可预期的竞态——把"共享可变状态"放进 DAG，等于把并发 bug 重新请进门。需要中间产物传递，请用节点结果 + 显式依赖。

八、超时、重试与失败策略

8.1 两级超时

超时 对象 默认建议 触发动作
节点执行超时 单次节点任务 复用任务级超时/回收阈值（300s 级） 任务回收重试/节点 FAILED
工作流整体超时 整个 execution 定义时显式指定 execution → FAILED（TIMEOUT），尽量取消未执行节点

工作流整体超时尤其重要：它防止"一个节点被无限重试导致整张图悬空"。整体超时到期时，引擎把未执行节点标记 CANCELLED，RUNNING 节点不强行中断（与 v1.0 看门狗的哲学一致：不杀正在跑的合法任务，只停止推进新节点），等它们自然终态后收尾。

8.2 重试语义：子任务独立重试

重试是"节点级"的，不是"图级"的：

  • 每个节点任务沿用 max_retries / 退避策略（v1.0 既有配置）；

  • 重试仅重新入队该节点任务，入度计数与下游不受影响；

  • 幂等是重试的前提：节点任务必须能安全执行多次（写操作幂等键、资源预占带请求 ID）。编排层不负责替业务保证幂等，但文档与框架约定必须把这个要求摆在明面上。

8.3 失败后的两种恢复入口

flowchart LR
    FAILED[Execution FAILED] --> OPT1[仅重跑失败节点及其下游]
    FAILED --> OPT2[按新上下文重新提交新实例]
    OPT1 --> REC[推进直至终态]
    OPT2 --> REC

  • 局部重跑：修改失败节点参数（或修复其 task 实现）后，从失败节点开始续跑——适合"代码 bug 修复后恢复生产流程"；

  • 整实例重跑：业务上需要全新执行的场景（如重新发起履约），新实例携带新 execution_id，与旧实例完全隔离——不要复用旧 execution_id 续跑，历史审计会乱。

九、故障场景实战：编排层设计的推演式验证

说明：v1.0.2 尚未实现 workflow，本节故障场景按本文设计推演预期行为，用于检验设计缺口。每个场景给出"若不这样设计会怎样"的反面推演。

场景一：引擎宕机，工作流执行到一半

现象：execution 停在 RUNNING；若干节点任务仍在其他节点上正常执行（有看门狗续期）；推进停滞。

根因推演：推进状态（就绪集、入度）只存在于宕机引擎的内存。

处置路径（按第六节恢复流程）：

  1. 新引擎节点接管：获得 execution 恢复锁；

  2. 扫描节点终态：SUCCESS 的补推下游；RUNNING 的等待事件；PENDING 的按入度重建就绪；

  3. 重新提交就绪节点——幂等靠任务级分布式锁挡住重复（同一 execution_id:node_id:attempt 只会成功 acquire 一次）。

反面推演：如果推进状态不持久化，恢复后唯一选择是整图重跑——所有已成功节点的副作用全部重放一遍，这在"发通知/扣款"类工作流里是事故。

场景二：守卫误判 + 人工重试，导致钻石依赖节点跑两遍

现象：“notify_ship” 已成功，但引擎因事件重放把聚合节点重复推进，或人工局部重跑时把"成功且不可重入"的节点又跑了一遍。

根因推演：节点缺少执行幂等键；局部重跑的范围判定只看"失败节点"，没有把"该节点在别的分支是否已有成功副作用"纳入判断。

处置路径：

  1. 节点任务必须携带幂等键：execution_id + node_id + attempt，业务侧落库去重；

  2. 局部重跑前，引擎给出该节点的上下游影响面清单（谁会被连带重跑），人工确认；

  3. 对明显不可重入的节点（通知、转账），重跑范围收紧到"仅失败节点"，并拒绝连带已成功节点的路径。

反面推演：若把"重试"做成黑盒自动操作，钻石依赖结构会让同一条副作用链路被并发跑两次，且两个实例彼此不可见。

场景三：10 万级扇出把队列与 Redis 连接池打满

现象：一个大扇出工作流提交后，队列积压、其他工作流的任务延迟飙升、Redis 连接池告警。

根因推演：引擎一次性把全部扇出节点写入队列 + 一次写完 10 万个节点状态（每个节点一次 SET），吞吐瞬间打爆连接池。

处置路径：

  1. 状态写入必须分批 pipeline（参考 v1.0 update_status_batch 的既有做法），严禁逐条 RTT；

  2. 就绪集分批放行（扇出上限）；

  3. 扇出目标节点共用一个 task 模板 + 不同参数，模板实现内部自行循环分批处理（如分页处理 10 万用户），而不是图里真放 10 万个节点——图的粒度应该对齐"业务步骤"而不是"数据行"。

反面推演：允许用户把"数据行级"扇出画进 DAG，任何引擎都会在节点元数据层面先垮掉，任务还没执行 Redis 先爆。

场景四：客户端超时重试导致同一工作流提交两次

现象：submit_workflow 调用因网络抖动超时，客户端自动重试——同一订单创建了两个 execution，业务被重复履约。

根因推演：提交接口没有幂等保障，服务端"执行了但响应丢失"与"没执行"无法区分。

处置路径：

  1. submit_workflow 接受调用方幂等键：client_request_id 或由 definition.workflow_id + context 指纹 推导；

  2. 服务端以幂等键为唯一约束：重复提交返回同一个 execution_id，而不是新建；

  3. 对订单类场景，业务侧再落一个"订单已履约"标记兜底——框架幂等和业务幂等是两层保险。

反面推演：不做提交幂等，“at-least-once 提交”（客户端重试）和"exactly-once 履约"（业务期望）之间的鸿沟，最终会以重复扣款的形式爆发在生产环境。

十、总结

主题 结论
编排的本质 把任务间的时序、分支、汇聚从业务代码抽到框架层，纳入可靠性边界
为什么是 DAG 无环保证拓扑序存在，推进确定、可预检、可可视化
推进模型 依赖终态事件驱动 + 入度计数，节点不知下游，引擎独占拓扑
分层状态 任务状态（单次执行）与节点状态（图内命运）必须分离
条件分支 守卫在边上而非节点内，求值器白名单化，提交时静态校验
执行复用 节点任务仍走优先级队列 + 分布式锁 + 回收器，编排层不重造执行引擎
恢复哲学 状态决定动作：从持久化的节点终态反推下一步，而非相信内存记忆
事务边界 原子性是"单节点提交"而非"整图"，长流程靠可恢复 + 可补偿 + 可观测收敛

一句结语：任务调度解决"单个任务可靠地执行"，任务编排解决"一组任务可靠地按图执行"——前者是 v0.1~v1.0 已交的答卷，后者是 v1.5 正在推演的设计题。本文的价值不在于给出"标准答案"（v1.5 尚未发布，最终实现以官方为准），而在于把这道设计题的约束、取舍与陷阱摊开：将来 v1.5 落地时，你可以带着这些判断去阅读真实源码，而不是被任何一篇"源码解析"牵着走。
