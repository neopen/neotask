概述

延时/定时能力是任务调度系统的"全场景覆盖"关键。NeoTask 从 v0.3 起提供了完整的定时调度 API：延时执行（delay）、指定时间点（at）、固定间隔（interval）、Cron 表达式。底层是"单节点内存定时器（最小堆）为主、时间轮为 opt-in 旁路 + 全链路任务实体持久化"：

能力 实现
延时主链路 DelayedQueue：最小堆（(到期时间, 优先级, task_id) + heapq），到期弹出并提升到优先级队列
时间轮 opt-in：enable_time_wheel=True 时 submit_delayed 走轮，量程外自动回退延时队列
任务实体存储 String JSON（task:{id}，全系列一致）
多节点并发 无共享延时队列扫描器；触发计划只活在提交节点的内存堆里，靠 worker 执行锁保证不重执行
重启行为 任务实体落库不丢；到期触发计划易失——重启后已提交的延时任务不会再被触发（见持久化一节）

一句话版本：v1.0.2 的延时任务是"单节点内存定时器（最小堆）+ 全链路任务实体持久化"的架构，分布式安全由 worker 执行锁兜底，而不是由"分布式延时队列"兜底。理解这个边界，比记住 API 更重要。

flowchart LR
    API[TaskScheduler.submit_delayed<br/>或 TaskPool.submit delay>0] --> DISP[TaskDispatcher<br/>create_task 实体落库 PENDING]
    DISP --> QS[QueueScheduler.push delay>0]
    QS -->|enable_time_wheel=True 且量程内| TW[TimeWheel 时间轮]
    QS -->|默认| DQ[DelayedQueue<br/>最小堆 (time,priority,id)]
    TW -->|到期回调| PQ[PriorityQueue 入队]
    DQ -->|到期回调| PQ
    PQ -->|pop| WP[WorkerPool 执行]
    WP --> LK[执行锁 lock:task:{id}]

延时任务的核心挑战

  1. 时间精度：误差要可接受。NeoTask 的延时精度 = 0.1s（DelayedQueue.check_interval），周期任务精度 = 1s（扫描间隔）；

  2. 持久化：要区分两层——任务实体（落库 ✅）与触发计划（仅内存 ⚠️）；

  3. 高并发性能：大量延时任务等待时不能每任务一个定时器——用堆把"下一个到期者"收敛到 O(log n)；

  4. 分布式不重复：触发本身在提交节点单点发生；执行时靠 lock:task:{id} + PENDING 状态检查防止多节点重复执行。

主链路解剖：DelayedQueue 最小堆

数据结构与入队（🔧 src/neotask/queue/delayed_queue.py）

class DelayedQueue:
    def __init__(self, check_interval: float = 0.1):
        self._heap: List[Tuple[float, int, str]] = []  # (execute_time, priority, task_id)
        self._tasks: Dict[str, DelayedTask] = {}       # task_id -> DelayedTask（含 data）
        self._scheduler_task: Optional[asyncio.Task] = None
        self._check_interval = check_interval           # 0.1s

    async def schedule(self, task_id, priority, delay, data=None) -> bool:
        if delay <= 0:
            return False
        execute_time = time.time() + delay
        async with self._lock:
            heapq.heappush(self._heap, (execute_time, priority, task_id))
            self._tasks[task_id] = DelayedTask(...)     # 携带 data
        return True

三个值得玩味的实现细节：

① 堆元组是 (execute_time, priority, task_id)——priority 为什么在中间？ 堆排序按元组从左到右比较。当两个任务同一瞬间到期（execute_time 相同）时，priority 小的先出堆——同一毫秒到期的任务自动按优先级触发。这是零成本的顺带设计：不用写任何"到期后重排序"逻辑，优先级语义天然嵌在定时器里。task_id 放最后兜底字典序（元组比较不能只有前两项）。

② 到期不是"等 0.1s 轮询"，而是"最紧要者驱动"。调度循环（🔧）：

async def _scheduler_loop(self) -> None:
    while self._running:
        try:
            now = time.time()
            tasks_to_execute = []
            async with self._lock:
                # 弹出一批所有已到期的任务
                while self._heap and self._heap[0][0] <= now:
                    execute_time, priority, task_id = heapq.heappop(self._heap)
                    task = self._tasks.pop(task_id, None)
                    if task:
                        tasks_to_execute.append((task_id, priority, task.data))

            for task_id, priority, data in tasks_to_execute:
                if self._callback:
                    try:
                        await self._callback(task_id, priority, data)
                    except TypeError:          # 兼容两参回调
                        await self._callback(task_id, priority)
                    except Exception:
                        pass                   # ← 回调异常被静默吞掉（见故障场景 2）

            next_time = self._heap[0][0] if self._heap else now + 1
            wait_time = min(self._check_interval, max(0.0, next_time - now))
            await asyncio.sleep(wait_time)
        except asyncio.CancelledError:
            break
        ...

每轮把所有已到期任务一次性弹出（一批），然后：

  • 若最近到期任务在 0.1s 以内 → 精确睡到那一刻（误差 <1ms）；

  • 否则睡 0.1s 再巡检。

为什么不是纯"睡到下一个到期时刻"？ 那样空闲期确实零唤醒，但每睡醒一次只能精确处理一个"波次"；而 0.1s 轮询保证新调度进来的短延时任务最多 0.1s 内被纳入——比如 delay=0.05s 的任务若纯按"下一个到期时刻"睡觉，可能排在 10s 后的任务后面永远不被发现。固定间隔巡检 + 到期时刻微调的组合，同时拿到了"新任务响应快"和"到期触发准"。

③ 精度为什么是 0.1s？ Python asyncio.sleep 在 Windows 上的实际粒度受系统定时器限制（默认 ~15.6ms），Linux 上通常 1ms 级；0.1s 是"平台无关的安全精度"——在性能基准一文已经看到 Windows 15.6ms 定时器粒度如何拖垮持续负载基准，延时调度同样受此约束。业务上"30 分钟后取消订单"的 0.1s 抖动完全可接受；要毫秒级定时，请交给专门的定时框架，别用通用任务调度器。

谁在用 DelayedQueue？（🔧 queue/queue_scheduler.py）

class QueueScheduler:
    def __init__(self, queue_repo=None, max_size: int = 10000):
        self._priority_queue = PriorityQueue(queue_repo, max_size)
        self._delayed_queue = DelayedQueue()          # ← 内存堆
        ...

    async def push(self, task_id, priority, delay=0) -> bool:
        ...
        if delay > 0:
            return await self._delayed_queue.schedule(task_id, priority, delay)
        else:
            return await self._priority_queue.push(task_id, priority)

    async def _on_delayed_task_ready(self, task_id, priority, data=None):
        if not self._disabled:
            await self._priority_queue.push(task_id, priority)   # ← 返回值未检查

主链路全貌（与优先级文章的 dispatcher 链路衔接）：

TaskPool.submit(data, delay=N)
  → TaskDispatcher.dispatch
    → lifecycle.create_task      # 任务实体落库，状态 PENDING
    → queue.push(task_id, priority, delay=N)   # delay>0 走堆
      → DelayedQueue.schedule
        → (N 秒后) _scheduler_loop 弹出
          → _on_delayed_task_ready
            → PriorityQueue.push（内存堆 或 Redis ZSET）
              → WorkerPool.pop → 执行锁 → 执行 → 状态流转

为什么延时任务复用 TaskPool.submit(delay=) 而不是独立的调度组件？ 这是刻意的架构决策：延时只是"入队时机不同"，任务的生命周期（创建/状态机/重试/超时回收/结果查询）与即时任务完全共用一套——submit_delayed 返回的 task_id 可以像即时任务一样 wait_for_result、重试、取消，业务心智负担为零。如果延时任务走独立的"定时器组件直接调 executor"，就得重复实现生命周期、持久化、失败恢复一整套逻辑。把"何时触发"与"如何执行"彻底分离，是任务调度框架的基本功。

持久化：实体不丢，触发计划易失

三层数据，两层持久

数据 存放 是否持久 重启后
任务实体 task:{id}（data/priority/status/ttl） Redis String JSON / SQLite / 内存 ✅（Redis/SQLite 模式） 存在，但状态停在 PENDING
触发计划（谁、何时、到期回调） DelayedQueue 内存堆 / TimeWheel 内存槽 ❌ 丢失——没有任何代码从存储恢复触发计划
执行结果/状态流转 同上实体 ✅ 已完成的保留

结论：Redis 模式下重启节点，已提交未到期的延时任务会"卡死"在 PENDING——不会再被触发，也不会自动失败或告警（与优先级文章发现的"入队静默失败→永久 PENDING"是同一类可观测性缺口）。这是 v0.3 设计定位的代价：Redis 持久化解决的是"任务记录不丢"，"触发计划恢复"属于故障恢复的进阶能力，当前版本尚未实现。

Redis queue:delayed 通道：存在但主链路不写

RedisQueueRepository 里确实有完整的 queue:delayed ZSET 实现（push 时 delay>0 → zadd queue:delayed score=到期时间戳；pop 时惰性迁移到期任务回 queue:priority）。但标准主链路中没有任何代码调用 repository.push(delay>0)——QueueScheduler.push 把 delay>0 的任务交给了内存 DelayedQueue，PriorityQueue.push 对 delay>0 直接返回 False。也就是说：

  • 标准 API 全链路（TaskPool/TaskScheduler + Redis 存储）：queue:delayed 永远是空的；

  • 只有绕过 QueueScheduler、直接操作 repository 的集成代码，才会让 queue:delayed 有数据；

  • 这条旁路通道的惰性迁移不保留优先级：ZSET 只存 (task_id → 到期时间)，没有优先级字段，迁移回 queue:priority 时统一按 TaskPriority.NORMAL（2）入队。

queue:delayed 是未接入主链路的预留通道。接入方若假设"Redis 里有我的延时任务、可跨节点恢复"，会踩空——多节点下的真实语义见下一节。

多节点部署的正确姿势

既然触发计划只在提交节点内存里，多节点部署的语义就是：

节点 A 提交 submit(delay=300)      → 计划活在 A 的内存堆
节点 A 崩溃                        → 计划丢失（实体仍在 Redis，PENDING 卡死）
节点 A 存活到到期                   → 回调入 Redis 共享队列 → 任一节点 worker 抢锁执行

幂等/不重复靠的是 worker 侧（执行前 PENDING 检查 + lock:task:{id} 互斥，见分布式锁），不是"分布式延时队列"。这里刻意没有做"多节点同时 ZRANGEBYSCORE 扫描 + SET NX 防重"的多级架构——单点触发在工程上是合理简化：触发本身是廉价的入队动作（不做业务），真正的执行安全和负载均衡全部下沉到共享队列层，架构上不存在"分布式定时器"这一层。代价是需要跨节点容错的延时（提交节点挂了任务必须换节点触发）当前版本做不到，请在外层加补偿（见故障场景 1）。

TimeWheel：可选的高性能延时通道

真实实现解剖（🔧 src/neotask/scheduler/time_wheel.py）

@dataclass
class TimeWheelTask:
    task_id: str
    priority: int
    data: Optional[Dict] = None
    round: int = 0
    execute_at: float = 0.0

class TimeWheel:
    def __init__(self, slot_count: int = 60, tick_interval: float = 0.1, max_rounds: int = 100):
        self._slots: List[deque] = [deque() for _ in range(slot_count)]
        self._current_slot = 0
        self._task_index: Dict[str, TimeWheelTask] = {}

    async def add_task(self, task_id, priority, delay, data=None) -> int:
        if delay <= 0:
            if self._callback:
                await self._callback(task_id, priority, data)  # 零延迟直接回调
            return 0
        slots_needed = int(delay / self._tick_interval)
        if slots_needed >= self._slot_count * self._max_rounds:
            return -1                                    # ← 超过轮数上限拒绝（返回 -1）
        target_slot = (self._current_slot + slots_needed) % self._slot_count
        rounds = slots_needed // self._slot_count
        ...
        self._slots[target_slot].append(task)            # O(1) 入槽
        self._task_index[task_id] = task
        return target_slot

实现细节对照（部分与常见"时间轮"教学实现不同）：

维度 常见教学实现 TimeWheel 真实实现
未到期任务 移入下一圈对应槽位 留在原槽、round 减 1，转满一圈再回来看
任务存储 槽位挂链表 每个槽一个 deque
上限 无 max_rounds=100：delay > 槽数×轮数×tick 拒绝（返回 -1）
零延迟 入槽等待 直接回调
删除 常称 O(1) 遍历所有槽线性查找（🔧 cancel_task）——O(槽数×槽长)

几个必须知道的边界：

  1. "时间轮 O(1) 删除"不成立：cancel_task 遍历所有槽逐个找成员再 del slot[i]（deque 删除本身 O(n)）。O(1) 的只有添加（append）；

  2. 容量上限是硬边界：slot_count × max_rounds × tick。TimeWheel 类默认 60 槽 × 100 轮 × 0.1s = 600 秒；但 TaskScheduler 接线时用 SchedulerConfig.time_wheel_tick（默认 1.0s），即 60 × 100 × 1.0 = 6000 秒（100 分钟）。越界的 add_task 返回 -1；

  3. add 一个任务 = 一次持锁操作（锁内 append），海量短延时（秒杀倒计时、限流令牌）场景下 add 竞争集中在同一把 asyncio.Lock——高吞吐时锁是热点（不过单事件循环内 asyncio.Lock 无跨线程竞争，代价主要是协程切换）。

    self._time_wheel = TimeWheel(
        slot_count=self._config.time_wheel_slots,  # 默认 60
        tick_interval=self._config.time_wheel_tick # 默认 1.0
    )
    await self._time_wheel.start(self._on_delayed_task_ready)

# submit_delayed 中：有轮且 delay>0 就走轮，否则走 DelayedQueue
if self._time_wheel and delay_seconds > 0:
    return self._run_async(
        self._submit_delayed_via_time_wheel(data, delay_seconds, task_id, priority, ttl)
    )
return self._pool.submit(data, task_id, priority, delay_seconds, ttl)

核心是"先建任务、再进轮"的顺序——_submit_delayed_via_time_wheel 先经生命周期管理器创建 PENDING 任务（此时任务已可见、可取消，但不入队），再 add_task 进轮。到期时轮的回调把同一个任务入队：

async def _submit_delayed_via_time_wheel(self, data, delay_seconds, task_id, priority, ttl):
    created_id = await self._pool.create_pending_task_async(data, task_id, priority, ttl)
    slot = await self._time_wheel.add_task(created_id, priority_value, delay_seconds, data)
    if slot < 0:
        # 超出量程：退回延时队列，避免任务卡在"已落库却永不入队"的中间态
        await self._pool.retry_async(created_id, delay_seconds)
    return created_id

async def _on_delayed_task_ready(self, task_id, priority, data=None):
    enqueued = await self._pool.enqueue_task_async(task_id)
    if not enqueued:
        debug(f"Delayed task {task_id} not enqueued (missing or not PENDING)")

由此得到四条明确语义：

  • 量程内：任务进轮、按 tick 粒度触发，到期后由 enqueue_task_async 放入共享队列，worker 正常消费；

  • 量程外（add_task 返回 -1）：自动回退到 DelayedQueue 堆，任务不会丢——调用方无需自己检查返回值；

  • 等待期取消：任务早已 PENDING 可查，cancel() 直接生效；到期回调再查一次状态，非 PENDING 就静默跳过（enqueue_task_async 的状态守卫），不依赖从轮里摘除；

  • 停机不丢：shutdown() 先 drain() 出轮内未到期任务，按 execute_at 重算剩余延时后回投延时队列，再停轮。

为什么默认不开？ 对照 DelayedQueue 的堆实现看：延时任务规模在万级以下时，堆的 O(log n) 完全够用（1 万个任务插入也才 ~14 次比较），而堆实现的精度自适应（任务越近睡越准）和取消能力（dict 直删 O(1)+堆重建）反而更简单。时间轮的 O(1) 优势要到"百万级短延时 + 每秒海量 add/cancel"才体现——那是网关限流、连接超时管理的量级，不是业务任务调度的量级。因此它保持 opt-in，默认仍走堆。

独立使用（不经过 TaskScheduler）时注意自行处理 -1：

# 📝 独立使用 TimeWheel（框架组件）
from neotask.scheduler.time_wheel import TimeWheel

async def on_ready(task_id, priority, data):
    await pool.submit_async(data, task_id, priority)

wheel = TimeWheel(slot_count=360, tick_interval=0.1, max_rounds=1000)  # 上限 10 小时
await wheel.start(on_ready)
slot = await wheel.add_task("t1", 2, delay=300)   # 300s 后触发
if slot == -1:
    ...  # 超过容量上限，需要业务补偿

周期任务与 Cron：PeriodicTaskManager 全链路

双模型结构

周期任务不是"重复提交的延时任务"，它有独立的定义/实例/执行记录三层（🔧 scheduler/periodic.py）：

PeriodicTaskDefinition  （周期任务定义：interval/cron、data、max_runs、start_at/end_at、missed_policy、ttl）
      │ 1:1
PeriodicTaskInstance    （运行实例：next_run、run_count、success/failed_count、last_run、status）
      │ 1:N
PeriodicExecutionRecord （每次执行的记录：task_instance_id、scheduled_time、result/error）

调用链（🔧 api/task_scheduler.py）：

submit_interval / submit_cron
  → PeriodicTaskManager.create_interval / create_cron
      → definition = PeriodicTaskDefinition(...)
      → next_run = _calculate_next_run(definition)   # interval: now+interval；cron: 下一次匹配时刻
      → instance = PeriodicTaskInstance(...)

每秒扫描的调度循环（🔧）

async def _scheduler_loop(self) -> None:
    while self._running:
        now = datetime.now()
        tasks_to_execute = []
        async with self._lock:
            for task_id, instance in self._tasks.items():
                if instance.status != ACTIVE: continue
                if max_runs 已达标: → COMPLETED; continue
                if now < start_at: continue
                if now > end_at:   → COMPLETED; continue
                if instance.next_run and instance.next_run <= now:
                    tasks_to_execute.append(...)
        for task_id, instance in tasks_to_execute:
            await self._execute_periodic_task(task_id, instance)   # ← 顺序 await！
        await asyncio.sleep(self._scan_interval)                   # 1.0s

每次执行（🔧 _execute_periodic_task）：

# 1. 若 miss 多轮，先按策略补课
if instance.next_run:
    missed_count = self._calculate_missed_count(instance)
    if missed_count > 1:
        await self._handle_missed_executions(instance, missed_count)

# 2. 提交一次新任务（每次都是独立 task_id）
task_instance_id = await self._task_pool.submit_async(
    data=definition.task_data, priority=definition.priority, ttl=definition.ttl)

# 3. 若定义了 timeout → 同步等待结果并记账；否则异步 fire-and-forget
if definition.timeout:
    result = await self._task_pool.wait_for_result_async(task_instance_id, timeout=...)
else:
    record.status = "running"

# 4. 推进下次执行时间
instance.next_run = self._calculate_next_run(definition, after=datetime.now())

周期语义的三个要点

① 首次执行由 run_immediately 控制：submit_interval(run_immediately=True)（默认）会让首个 next_run = now，即下一轮扫描立刻提交——前提是 start_at 不在未来；若 start_at 在未来，则以 start_at 为准（_calculate_next_run 里 immediately and not (start_at and start_at > now) 的判定）。run_immediately=False 时 next_run = now + interval，即等满一个周期再首次执行。两条路径（有/无 PeriodicTaskManager）都读这个参数。

② 周期精度 = 1s：扫描循环固定睡 1s，next_run 的秒级抖动平均 ~0.5s、最大 ~1s。interval 任务从"到期时刻"到"实际提交"最多差 1 秒，叠加任务队列排队时间——周期任务不是精确时钟，设计心跳/报表任务时接受秒级误差。

③ 四种错过策略各有明确语义：MissedExecutionPolicy 定义了 IGNORE / RUN_ONCE / CATCH_UP / SKIP，实现集中在 _execute_periodic_task（🔧 scheduler/periodic.py）：

策略 行为
IGNORE / SKIP 语义相同：丢弃错过的槽位，只把 next_run 推进到未来，本轮不提交
RUN_ONCE 本轮提交一次，不补跑错过的槽位
CATCH_UP 补跑错过的槽位，单轮最多 MAX_CATCH_UP（5）次防雪崩

默认策略 default_missed_policy="skip" 即"错过就错过，等下一轮"。实际提交次数在 CATCH_UP 下是 min(missed_count + 1, 5)，其余策略为 1。

timeout 参数的隐藏代价

create_interval(timeout=60) 会让每次执行同步等待结果（最长 60s），而 _scheduler_loop 是顺序 await 的——一个慢周期任务会阻塞整条周期调度循环，其他周期任务全部延误。默认 timeout=None 走异步分支没问题；显式设置 timeout 时，请评估该任务最长执行时间对调度循环的影响。

submit_at 与 Cron：时间换算与表达式

  • submit_at：delay = max(0, execute_at - now) 后走 submit_delayed（🔧 纯时间换算，无独立队列）；

  • submit_cron：走 CronParser（🔧 scheduler/cron_parser.py）解析五段表达式（分 时 日 月 周），每次执行后 cron_obj.next(after=now) 求下一次匹配。Cron 属于 PeriodicTaskManager 体系，同一套 1s 扫描与 missed 逻辑；

  • 默认时区：全程使用 datetime.now()（本地时区）——没有时区参数，跨时区部署时各节点以自己的本地时间解释 Cron，需在部署层统一 TZ 环境变量。

配置速查（🔧 SchedulerConfig 真实默认值）

字段 默认 含义 备注
scan_interval 1.0 调度循环扫描间隔（秒） 周期任务粒度
enable_periodic_manager True 启用周期任务管理器 关闭则退回本地 dict 存储路径
enable_time_wheel False 启用时间轮 开启后 submit_delayed 走轮，量程外自动回退延时队列
time_wheel_slots 60 时间轮槽位数 与 tick 共同决定量程
time_wheel_tick 1.0 时间轮滴答间隔 组件参数（TimeWheel 类默认 0.1）
default_max_runs None 周期任务默认最大次数 None=无限
default_missed_policy “skip” 错过执行策略 IGNORE/SKIP 同义、RUN_ONCE、CATCH_UP

注意 time_wheel_tick 在 config 默认 1.0，而 TimeWheel 类默认 0.1——TaskScheduler 接线时用 config 值（1.0s 滴答），即 60 槽 × 100 轮 × 1s = 100 分钟延迟上限、1 秒触发粒度。相比之下堆实现的精度自适应（任务越近睡越准）在秒级以下的延时上更细，这也正是时间轮保持 opt-in 的原因。

使用示例（真实 API 📝）

from neotask import TaskScheduler, SchedulerConfig

async def remind(data):
    print(f"提醒: {data['user_id']} {data['message']}")

scheduler = TaskScheduler(executor=remind)          # 默认 memory 存储
scheduler.start()

# 30 秒后执行（🔧 submit_delayed(data, delay_seconds, task_id?, priority?, ttl?)）
tid = scheduler.submit_delayed(
    data={"user_id": 12345, "message": "订单即将过期"},
    delay_seconds=30,
)

# 指定时间点（内部换算 delay）
from datetime import datetime, timedelta
scheduler.submit_at(data={"action": "daily_report"},
                    execute_at=datetime.now() + timedelta(hours=1))

# 每 5 分钟一次（默认 run_immediately=True：先立即跑一次，之后每 5 分钟）
scheduler.submit_interval(data={"action": "heartbeat"},
                          interval_seconds=300,
                          max_runs=24, name="hb")

# Cron：每天 9 点（本地时区）
scheduler.submit_cron(data={"action": "summary"},
                      cron_expr="0 9 * * *", name="daily")

# 延时任务同样支持结果等待
result = scheduler.wait_for_result(tid, timeout=60)

故障场景实战

场景 1：进程重启，延时任务集体"蒸发"

现象：提交了一批 submit(delay=3600)（1 小时后执行）的任务；凌晨发布重启进程；1 小时后任务没跑，task:{id} 状态永远停在 PENDING，无任何日志。

根因：触发计划在 DelayedQueue 内存堆里，重启即失；实体虽在 Redis 但没有任何恢复逻辑把它重新入队。重启前已到期未执行的会丢，重启后到期的更不会执行。

排查：对比提交日志与执行日志；ZSCAN task:* 找 PENDING 且 created_at 早于重启时刻的任务。

解决：v1.0.2 无内建恢复。生产方案（📝）：① 应用层补偿——启动时扫描"应执行未执行"的 PENDING 任务重新 submit；② 对必须不丢的延时业务，用独立组件（Redis 过期键监听 / 消息队列延时消息）驱动 NeoTask 提交，让 NeoTask 只做"到期后如何执行"；③ 接受"延时计划易失"，把不丢诉求放在业务侧（订单状态机自愈扫描）。发布窗口避开批量延时提交高峰是最低成本的止损。

场景 2：到期触发了，但任务没执行

现象：偶发任务"该到没到"；DelayedQueue 统计 executed 在涨，但对应任务从未 RUNNING。

根因链（两处失败点）：

  1. _scheduler_loop 回调段：任务一旦从堆中弹出，回调抛任何异常（Redis 连接抖动、事件循环阻塞超时）就永久失去触发机会——现在这个异常会以 Delayed task {id} callback failed: ... 记入 error 日志，不再是静默 pass；

  2. QueueScheduler._on_delayed_task_ready 调 priority_queue.push(...) 返回 False（队列满，max_size=10000）时，会记 could not be promoted: priority queue is full 的 error 日志。

两条路径的共同后果：任务实体 PENDING、无锁、无 node_id——回收器不回收（非 RUNNING 超时、非孤儿），永久滞留。日志是定位它们的唯一线索。

排查：对账 delayed_queue.get_stats() 的 executed 计数与实际执行数；按 error 日志里的 task_id 反查任务状态。

解决（📝）：日志只给出线索，补偿要自己做——对日志中出现的 task_id 主动 redispatch(task_id)；根因若是队列满，先扩 max_size 或提升消费能力再重投。

场景 3：开启时间轮后延时精度变粗

现象：设了 enable_time_wheel=True，1~2 秒的短延时任务明显比预期晚触发，最多晚接近 1 秒。

根因：TaskScheduler 用 SchedulerConfig.time_wheel_tick（默认 1.0s）建轮，触发粒度就是 1 秒——一个落在刻度中间的任务要等到下一格。相比之下 DelayedQueue 堆是"任务越近睡越准"的自适应精度，短延时上更细。

排查：get_stats() 看轮配置；对比 time_wheel_tick 与你的延时量级。

解决：需要更细粒度就调小 time_wheel_tick（如 0.1），但记住量程 = time_wheel_slots × max_rounds × tick 会同步缩小——0.1s 粒度下默认 60 槽只剩 600 秒上限，超出部分会自动回退延时队列（见上文接线方式的量程回退）。若延时普遍在秒级且精度要求高，直接保持默认的堆实现更省心。

场景 4：周期任务 timeout 引发调度雪崩

现象：给周期任务配了 timeout=60 后，其他周期任务开始不定期延迟，任务堆积。

根因：_execute_periodic_task 在 timeout 非空时 await wait_for_result(...)（最长 60s），而它是被 _scheduler_loop 顺序 await 的——一个慢任务把每秒扫描的调度循环堵死；若该任务失败重试链较长，阻塞更久，后面的周期任务集体错过 next_run，触发 missed 追赶（CATCH_UP 最多补 5 次）→ 追赶又排队 → 恶性循环。

解决：周期任务不设 timeout（默认异步 fire-and-forget，由 TaskPool 的 task_timeout 兜底执行超时）；确实需要同步确认结果的场景，把结果确认逻辑放进业务函数内部，别用调度器等结果。

总结

主题 实现
延时主链路 DelayedQueue 最小堆，0.1s 精度，单节点内存
任务详情存储 String JSON task:{id}
Redis 延时队列 queue:delayed 主链路空置；旁路迁移不保留优先级，统一按 NORMAL 入队
TimeWheel O(1) add / 量程上限 / cancel 非 O(1)；opt-in：开启后接 submit_delayed，量程外回退延时队列
周期/Cron PeriodicTaskManager 1s 扫描 + definition/instance/record 三层
持久化 实体落库；触发计划易失
分布式防重 worker 执行锁兜底；触发计划单点
run_immediately / missed 策略 均生效：run_immediately 决定首跑时刻（受 start_at 约束）；IGNORE/SKIP 同义、RUN_ONCE 单次、CATCH_UP 补跑≤5

延时任务在 v1.0.2 是"够用但别过度信任"的模块：API 层语义完整（delay/at/interval/cron + 统一生命周期），调度层是朴素的单节点最小堆，可靠性层存在触发计划易失与多处静默失败。生产使用请记住三件事：发布窗口别压延时提交、到期回调要自己加补偿、周期任务别设 timeout。
