概述

任务调度系统里，“持久化"一词往往被简化成"数据别丢”，但在 NeoTask 里它实际管理着两类性质完全不同的数据：

  1. 任务实体（Task）：任务的完整档案——数据载荷、状态、优先级、时间戳、结果、错误。它是"事实"，按 task_id 查、按状态扫。

  2. 排队索引（Queue）：一张极瘦的"待办清单"——只存 task_id 和排序键。它是"意图"，按优先级顺序取。

实体与索引分离，是理解 NeoTask 持久化层的总钥匙。围绕它有三个要点：

  • 存储格式由模型驱动，且没有自动清理：Redis 任务存储用 String 存整份 to_dict() JSON（不是 Hash）、出队用 Lua ZRANGE+ZREM（脚本内不加锁），SQLite tasks 表含 progress/progress_message 两列；而"每小时清理 / 保留 7 天"这类自动清理策略在源码中并不存在。

  • 三种存储的可靠性不是一个梯度，而是三个维度：内存靠拷贝与锁防身、SQLite 的出队操作非原子（多进程共享有重复领取窗口）、Redis 靠数据结构与 Lua 获得真正的跨进程原子性——这也是只有 Redis 模式才能启用全套分布式组件的根本原因。

  • 清理函数存在，但没有调度者：cleanup_expired() 实现完整（终端状态、TTL 判定、缓存联动），但框架内没有任何地方调用它。任务数据在默认配置下只增不减。

存储接口细节已在 架构设计 中铺垫，本文聚焦三层：实体模型怎么序列化 → 三种存储怎么落盘 → 数据怎么（不）被清理。

一、数据模型：14 个字段的实体与它的序列化边界

1.1 实体字段全景

Task 是持久化的最小单元（🔧 neotask/models/task.py），一个 dataclass 承载 14 个字段：

字段 类型/默认值 语义 谁在写
task_id str 主键（TSK+时间戳+随机数） dispatcher 生成
data dict 用户业务载荷 submit 时
status TaskStatus 状态机当前值 worker/生命周期
priority TaskPriority 0~3 四级 submit 时
progress float=0.0 进度 0~1（update_progress 截断到 [0,1]） 业务方 update_progress
progress_message str=“” 进度文案 业务方 update_progress
node_id str 执行/最后执行节点 worker start 时
retry_count int 已重试次数 worker 失败处理
ttl int=3600 双语义，见 1.2 submit 时
created_at datetime（UTC） 创建时刻 实体创建时
started_at / completed_at datetime? 生命周期节点 worker
result / error dict? / str? 终态产物 worker

注意两点。第一，progress/progress_message 是长任务进度上报的载体，SQLite tasks 表里有对应的两列（真实 DDL 见 3.2 节）。第二，所有时间戳统一 datetime.now(timezone.utc)（字段默认工厂也是 UTC），而队列表里的 created_at 用 datetime.now().isoformat()（本地时间）——实体表 UTC、队列表本地时间，两套时间体系并存，好在队列表时间只用于同优先级排序，不与 UTC 比较，才没有埋出 bug。

1.2 ttl 的双语义：一个数字两种用途

ttl: int = 3600 字面意思是"生存时间（秒）"，但它在代码里被两个完全不同的机制读取：

机制 读法 含义
任务执行超时（worker/reclaimer 侧） RUNNING 任务从 started_at 起超 ttl “这个任务最多跑 1 小时”
终端数据保留（cleanup_expired 侧） 终态任务的 completed_at 距今超 ttl “成功/失败记录最多留 1 小时”

提交时传 ttl=3600 同时约束了"最长执行时间"和"结果保留时长"。前者在 故障恢复 一文详述（reclaimer 回收），后者在本文章节五。设计上这是刻意的简化——大多数任务两者量级一致，但长耗时任务 + 短审计需求的场景下，调 ttl 会同时拉扯两个指标，只能二选一迁就。

1.3 双层序列化：JSON 字符串里的 JSON 字符串

实体落盘的唯一通道是 to_dict()/from_dict()（🔧 neotask/models/task.py:64）：

def to_dict(self) -> Dict[str, Any]:
    return {
        "task_id": self.task_id,
        "data": json.dumps(self.data) if self.data is not None else "{}",
        # ...
        "result": json.dumps(self.result) if self.result is not None else "",
        "created_at": self.created_at.isoformat() if self.created_at else ...,
    }

data 和 result 这两个字段的值，在 to_dict 阶段就已经被 json.dumps 序列化成字符串了。于是无论落到 SQLite 的 TEXT 列、Redis 的 String、还是内存字典，task.data 存的都是"JSON 的字符串形式"，读取侧再由 from_dict 的 parse_json 解回 dict。也就是说：

  • 写一次任务 = 至少两次序列化：先 json.dumps(task.data) 内层，再 json.dumps(task.to_dict()) 外层（Redis 路径，default=str 兜底 datetime）。

  • 存储里看到的是转义地狱：Redis GET task:xxx 的结果中，data 字段是 "{\"url\": \"...\"}" 这样的转义字符串，外部系统若直接读键，需要解两层才能拿到业务字段（见故障场景三）。

  • 空值语义有损：result=None 落盘成 ""，读回 parse_json("") 得 None，碰巧一致；但 data 的空 dict 落盘成 "{}" 读回 {}，而"用户真的没传 data"与"用户传了空 dict"在存储层无法区分。

为什么这么设计：模型驱动的全量序列化

不做"字段级映射"，而是让 Task 自己负责扁平化，换来三点：

  1. 字段演化的零成本：实体加字段（比如 v1.0.2 加的 progress）不需要同步改任何存储层代码——SQLite 靠 INSERT OR REPLACE 全列重写、Redis 靠整串覆盖，字段表只在一个文件里维护。

  2. 存储层零 JSON 知识：三个 Repository 只认 Task 对象和 to_dict 产物，不关心业务字段语义，仓库实现因此极其薄。

  3. 整体覆盖保证一致性：一次 SET/INSERT 就是一份完整快照，不存在"状态更新了、结果没写进去"的字段撕裂。

代价是"读单字段也必须全量反序列化"，以及存储里不可直接按业务字段查询（SQLite 的 data 列是整块 TEXT，无法 WHERE data->>‘url’ 之外的花活）。对任务表"按 ID 查、按状态扫"的访问模式而言，这是划算的交易。

二、架构总览：实体库与队列索引的双写模型

2.1 两个仓库接口的分工

🔧 neotask/storage/base.py 定义了两个抽象，所有后端成对实现：

TaskRepository（实体库）                    QueueRepository（队列索引）
├─ save(task) / get(id)                    ├─ push(task_id, priority, delay=0)
├─ update_status(id, status, **kwargs)     ├─ pop(count) → List[str]
├─ list_by_status(status, limit, offset)   ├─ remove(id) / peek(count)
├─ delete(id) / delete_batch(ids)          ├─ size() / clear()
└─ exists(id) / list()                     └─ （pause/disable 语义见后）

接口设计暴露了清晰的分工意图：实体库操作按 id 或 status 寻址，队列索引只按 顺序 取 task_id——队列的出队结果只是一个字符串列表，worker 拿到后再回实体库 get(task_id) 取载荷。

2.2 为什么实体与索引必须分离

这是 NeoTask 存储层最重要的一个设计决定，理由按重要性排列：

  1. 访问模式完全不同：实体是"点查 + 状态扫描"（OLTP 式），队列是"最小序取头 N 个"（无 WHERE 的扫描）。把两者塞进同一结构，要么队列操作被实体的体积拖累，要么实体查询被队列的排序约束绑架。

  2. 出队操作保持极轻：队列里只有 (task_id, 排序键)，pop 不必搬运任务载荷。Redis 的 ZSET 若直接塞载荷，ZRANGE 的大对象传输会直接打穿网络预算；SQLite 若 SELECT * 连 data 一起取，纯属浪费。延迟到 worker 需要时才取实体，还能让"出队了但没执行"的窗口期内存代价最小。

  3. 索引可重建：实体是唯一事实源。极端情况下清空队列（clear()），所有任务实体仍在存储中（PENDING 态）——虽然默认没有自动对账逻辑把它们找回队列（见故障场景四），但数据没有丢。

  4. 存储选型可分离：三套后端成对出现并非必然，理论上可以 SQLite 实体 + Redis 队列，只是 NeoTask 默认按场景绑定成三档套餐。

2.3 双写模型留下的两个一致性窗口

任何"实体 + 索引"的分库设计都要直面两个一致性窗口，NeoTask 对它们的处理方式决定了可靠性边界：

窗口 位置 NeoTask 的处理 风险后果
写窗口 create_task 落实体 → push 入队之间 先实体后索引；入队失败会标记 FAILED 并抛 QueueFullError（队列满/禁用可覆盖），但两步之间崩溃无补偿 进程在两步之间崩溃时，实体成为无索引孤儿（见故障场景四）
读窗口 pop 出队 → 执行锁 acquire 之间 出队无"领取中"中间态，靠执行锁兜底 节点崩溃后任务既不在队列也不算 RUNNING，滞留到超时回收（故障恢复 已详述）；出队本身重复时靠锁去重

后文三节逐一拆解三种存储如何实现这两个仓库，各自的原子性边界在哪。

三、三种存储的真实实现与数据格式

3.1 内存存储：deepcopy 的双向防御

内存实现（🔧 neotask/storage/memory.py）是"最安全"也最诚实的一种——它明确自己只活在一个进程里。

任务仓库的底层是一个 dict + asyncio.Lock，但真正的精髓是 copy.deepcopy 的双向使用：

async def save(self, task: Task) -> None:
    async with self._lock:
        self._tasks[task.task_id] = copy.deepcopy(task)   # 存入拷贝

async def get(self, task_id: str) -> Optional[Task]:
    async with self._lock:
        task = self._tasks.get(task_id)
        if task:
            return copy.deepcopy(task)                    # 返回拷贝
        return None

为什么保存要拷贝、取出也要拷贝？因为没有序列化这堵墙：如果 save 存引用，调用方随后修改自己的 task.data dict 会污染已入库实体（Task 的 data/result 是可变 dict，dataclass 的浅拷贝挡不住）；如果 get 返回内部引用，读取方对 data 的原地修改会击穿存储。深拷贝把内存仓库伪装成"值语义"的数据库——代价是每次读写都是 O(载荷大小) 的复制，大 data 场景下 save+get 一次任务要拷四遍（入两份、出两份）。

队列仓库用 heapq 堆 + 自增 _sequence 维护严格 FIFO（元组 (priority, sequence, task_id)），每次读写同样持锁（🔧 memory.py:177，与优先级文一致，详见 优先级任务）。

内存模式的质量结论：单进程内并发绝对安全（锁 + 拷贝），但锁与拷贝都无法跨进程——这也是它只配开发测试的原因。数据本身随进程消亡，无持久性可言。

3.2 SQLite 存储：表结构与非原子出队

SQLite 是"单机生产"档位。两个仓库落在同一个 db 文件里（工厂统一传参，见 3.4），但语义完全不同。

tasks 表：14 列 + 2 索引（🔧 neotask/storage/sqlite.py:32）：

CREATE TABLE IF NOT EXISTS tasks (
    task_id TEXT PRIMARY KEY,
    data TEXT NOT NULL,
    status TEXT NOT NULL,
    priority INTEGER NOT NULL,
    node_id TEXT NOT NULL,
    retry_count INTEGER NOT NULL,
    ttl INTEGER DEFAULT 3600,
    created_at TEXT NOT NULL,
    started_at TEXT,
    completed_at TEXT,
    result TEXT,
    error TEXT,
    progress REAL DEFAULT 0.0,
    progress_message TEXT DEFAULT ''
);
CREATE INDEX IF NOT EXISTS idx_tasks_status ON tasks(status);
CREATE INDEX IF NOT EXISTS idx_tasks_priority ON tasks(priority);

写路径是 INSERT OR REPLACE 整行覆盖——Task 任何字段变化（包括进度上报）都重写整行；update_status 支持按 kwargs 拼 UPDATE 白名单（node_id/retry_count/error/completed_at/started_at/progress/progress_message），是三种存储里唯一真正做"字段级更新"的后端。

queue 表：只有 3 列：

CREATE TABLE IF NOT EXISTS queue (
    task_id TEXT PRIMARY KEY,
    priority INTEGER NOT NULL,
    created_at TEXT NOT NULL
);

为什么队列表这么瘦？因为载荷在 tasks 表，queue 只是"谁排在第几个"的指针。出队排序键是 priority ASC, created_at ASC——created_at 存 datetime.now().isoformat()，ISO 8601 文本的字典序恰好等于时间序，一个 TEXT 列同时承担了存储与排序，省掉时间戳换算。

pop 的非原子性（🔧 sqlite.py:298）：

async def pop(self, count: int = 1) -> List[str]:
    await self._ensure_init()
    cursor = await self._conn.execute(
        "SELECT task_id FROM queue ORDER BY priority ASC, created_at ASC LIMIT ?",
        (count,))
    rows = await cursor.fetchall()
    task_ids = [row[0] for row in rows]
    if task_ids:
        placeholders = ",".join("?" * len(task_ids))
        await self._conn.execute(
            f"DELETE FROM queue WHERE task_id IN ({placeholders})", task_ids)
        await self._conn.commit()
    return task_ids

"查询头部 → 删除"之间没有事务包裹（无 BEGIN/COMMIT）、没有行锁，而且全程散布 4 个 await 切换点。在 asyncio 单线程模型里，worker A 执行完 SELECT、await fetchall 的间隙，worker B 的 SELECT 完全可以插入并读到同一批 task_id——两个 worker 同时"领取"了同一批任务。这不是理论推演：WorkerPool 直接模式下调 pop 时并无外层锁（🔧 worker/pool.py:209：task_ids = await self._queue.pop(self._prefetch_size)）。

那为什么默认配置下"看起来没出事"？因为重复领取还有第二道防线——执行锁：两个 worker 都去 acquire("task:{task_id}")，先到者执行，后到者 acquire 失败直接放弃（分布式锁 一文详述）。但这道防线有前提：锁管理器必须对两个 worker 可见。默认 lock_type="memory" 时锁只在进程内共享，因此：

部署形态 出队重复风险 执行锁兜底 结论
SQLite + 单进程（默认） 存在（await 窗口） ✅ 同进程 memory 锁可见 极端时序下任务可能执行两次（首个执行者已释放锁后，迟到的第二份才 acquire 成功）
SQLite + 多进程共享 db 存在且放大 ❌ 各进程 memory 锁互不可见 重复执行成为常态风险
SQLite + lock_type=redis 存在 ✅ 跨进程 出队仍可能重复，但执行被锁拦下

正确姿势：SQLite 定位就是单进程单机。若确需多进程共享 SQLite 文件，至少要同时配 lock_type="redis"，并把 pop 包进 BEGIN IMMEDIATE 事务（📝 见故障场景一补丁）。

另有一个隐藏坑：直接实例化仓库时，SQLiteTaskRepository 默认路径是 data/tasks.db，而 SQLiteQueueRepository 默认是 tasks.db——实体和队列会分库！TaskPool 走工厂统一传参所以永远同库，只有绕过工厂直用仓库层才会踩中。

3.3 Redis 存储：String JSON + SET 状态索引 + ZSET 队列

Redis 模式（🔧 neotask/storage/redis.py）是唯一为跨进程设计的后端，键空间分四类：

键 类型 内容 用途
task:{task_id} String 整个 to_dict() 的 JSON 字符串 实体快照（整份 JSON）
status:{status_value} SET task_id 成员 按状态倒排索引
queue:priority ZSET member=task_id, score=priority.value(0~3) 优先级队列
queue:delayed ZSET member=task_id, score=到期时间戳 延迟队列

任务实体的写入（🔧 redis.py:53，RedisTaskRepository.save）：

async def save(self, task: Task) -> None:
    """保存任务 - 使用 JSON 序列化存储"""
    client = await self._get_client()
    key = f"task:{task.task_id}"

    # 同步状态索引：先移除旧状态的成员关系，否则任务会同时残留在多个 status:* 集合中
    old_data = await client.get(key)
    if old_data:
        try:
            old_status = json.loads(old_data).get("status")
        except (ValueError, TypeError):
            old_status = None
        if old_status and old_status != task.status.value:
            await client.srem(f"status:{old_status}", task.task_id)

    # 使用 JSON 字符串存储整个任务
    task_dict = task.to_dict()
    await client.set(key, json.dumps(task_dict, default=str))

    # 添加到状态索引
    await client.sadd(f"status:{task.status.value}", task.task_id)

注释直白地写着"使用 JSON 字符串存储整个任务"——任务实体是整串 String，不是 Hash。save() 会先读出旧 JSON、比对 status，旧状态与新状态不同时先 SREM 掉旧集合，再 SET 新快照、SADD 新集合，因此同一个 task_id 不会同时残留在多个 status:* 索引里。状态查询靠 status:{值} 这个 SET 倒排索引：list_by_status 先 SMEMBERS 取出集合、内存切片 offset/limit、再逐个 GET 实体（N+1 次往返，状态扫描类操作在 Redis 模式下天然偏贵）。

状态索引的维护出现在 update_status（🔧 redis.py:149）：先 GET 旧 JSON → 改 status 字段 → 整体 SET 回去 → 再 SREM 旧状态集合 + SADD 新状态集合。注意实体更新与索引搬迁是两个独立命令，二者之间没有 Lua 包裹，理论上存在"实体已到新状态、索引还在旧集合"的瞬时窗口——对状态查询而言是轻微的一致性问题，但因为状态集合只用于列表/统计，不参与出队判定，实际危害有限。

出队用注册好的 Lua 脚本（🔧 redis.py:264）：

local queue_key = KEYS[1]
local count = tonumber(ARGV[1])
local task_ids = redis.call('ZRANGE', queue_key, 0, count-1)
if #task_ids > 0 then
    redis.call('ZREM', queue_key, unpack(task_ids))
end
return task_ids

ZRANGE 取头 N 个、ZREM 删除、整体由 Redis 单线程执行 → 一次 Lua 调用完成原子批量出队，脚本里没有任何 SETNX lock: 环节——领取即删除，执行互斥完全交给后置的执行锁。另外 pop() 主路径开头还会先处理延迟队列的到期迁移（queue:delayed 中 score≤now 的任务迁回优先级队列，score=5 的魔法数问题见 优先级任务 一文）。

3.4 String JSON 而不是 Hash：四个设计理由

这是 Redis 任务存储最值得探讨的设计点。任务实体有 14 个字段、状态频繁整体重写，为什么用整串 String 而不是 Hash？

  1. 整体覆盖天然原子：状态机每步转换（RUNNING → SUCCESS/FAILED）都要同时改 status + 时间戳 + 结果，String 一次 SET 原子替换整份快照；Hash 若要同样原子，必须把 14 个字段打包进一次 Lua 或事务，否则存在"状态变了、completed_at 没写"的撕裂窗口。update_status 的实现也印证了这一点——先读出、改完、整串 SET 回写（🔧 redis.py:169），读写路径都假设"一份 JSON = 一个一致快照"。

  2. 模型驱动，零字段映射成本：to_dict()/from_dict() 直通 String；Hash 则需要为 14 个字段维护 HSET 白名单与 HGETALL 后的手工装配，且每次加字段要同步改仓库层——恰好破坏 1.3 节说的"字段演化零成本"。

  3. 字段级更新的收益微薄：任务读多写少、每次状态转换几乎都要重写大半字段（时间戳、node_id、retry_count、result 联动）。Hash 的 HSET 单字段优势在这种"整状态重写"模式下发挥不出来。

  4. 调试与缓存友好：String 一条 GET 即可看到完整任务，生命周期缓存层整存整取也简单。

Hash 什么时候反而更优？高频独立更新单个字段、单字段承载大 blob、需要字段级独立 TTL 的场景——任务调度都不符合（唯一接近的"进度上报"也是低频小写）。代价也要坦白：双层 JSON 转义让 redis-cli 直接读键时人眼不可读、Redis 侧无法按业务字段查询、体积比 Hash 略大。取舍的本质是"以反序列化成本换取一致性简单性"。

3.5 三存储对照总表

维度 memory sqlite redis

状态查询 dict 遍历 WHERE status=? + 索引 status:{v} SET 倒排索引

四、工厂与装配：为什么分布式组件只认 Redis

4.1 双配置、双工厂的真实装配链

从用户配置到仓库实例的完整链路（🔧 api/task_pool.py:234）：

def _init_storage(self):
    if self._config.storage_type == "memory":
        storage_config = StorageConfig.memory()
    elif self._config.storage_type == "sqlite":
        storage_config = StorageConfig.sqlite(self._config.sqlite_path)
    elif self._config.storage_type == "redis":
        storage_config = StorageConfig.redis(self._config.redis_url)
    else:
        raise ValueError(f"Unknown storage type: {self._config.storage_type}")
    return StorageFactory.create(storage_config)

这里出现两层配置：用户碰的是 TaskPoolConfig（memory()/sqlite(path)/redis(url) 三个类方法，🔧 models/config.py），内部翻译成存储层专用的 StorageConfig，再由 StorageFactory.create 分发（🔧 storage/factory.py:58）。为什么套两层？因为 TaskPoolConfig 是面向 TaskPool 的门面（还携带锁、心跳、死信等与存储无关的字段），而 StorageConfig 是仓库层的最小契约——工厂只认后者，避免仓库依赖整个调度配置。

有趣的是 RepositoryFactory（注册模式，标着 “Alternative factory”）已把三套后端注册进 _repositories 字典，但它的 create() 与 StorageFactory 一样是硬编码 if/elif，注册表从未被消费——扩展点的半成品。对当前三个后端，分支直写反而更直观；真要加第四种后端（如 PostgreSQL），需要先补全这个注册模式的消费逻辑。

4.2 分布式组件只认 Redis：装配源码

🔧 api/task_pool.py:117：

# ========== 分布式组件（去中心化）==========
self._node_manager: Optional[NodeManager] = None
...
# 仅在 Redis 模式下启用分布式组件
if self._config.storage_type == "redis" and self._config.redis_url:
    self._init_distributed_components()

无论哪种存储，WorkerPool、预取器、QueueScheduler 都会装配；而 NodeManager / HeartbeatManager / TaskReclaimer / Coordinator / 死信队列只在 Redis 模式初始化。这从代码层面回答了"为什么单机后端跑不了去中心化集群"：

  • 集群的全部协调原语——节点注册、心跳键、任务认领、执行锁、重试/死信集合——都以 Redis 键为共享内存，靠的是"任何进程都能原子地读写同一份状态"（ZSET 原子操作、Lua、SETNX）。

  • SQLite 文件理论上也可多进程共享，但缺两个东西：原子领取原语（出队非原子，3.2 已证）和跨进程互斥原语（memory 锁不可见）；Redis 的 ZSET + Lua + 分布式锁恰好把这两块补齐。

  • memory 则连"共享"都不存在。

因此存储选型本质上是可靠性档位的选择：memory = 单进程玩具、sqlite = 单进程生产、redis = 跨进程集群。组合 storage_type 与 lock_type 有讲究：

storage_type lock_type 效果 评价
memory memory（默认） 全内存开发环境 ✅ 开发测试
sqlite memory（默认） 单进程生产；出队窗口靠进程内锁兜底 ⚠️ 可接受，但勿开多进程
sqlite redis 出队重复但执行互斥跨进程 ✅ 多进程共享 SQLite 的最低安全配置
redis redis 完整分布式能力 ✅ 生产首选

五、TTL 语义与数据清理

5.1 cleanup_expired：实现

🔧 core/lifecycle.py:363 提供了过期清理的完整实现：

async def cleanup_expired(self) -> int:
    cleaned_count = 0
    now = datetime.now(timezone.utc)
    terminal_statuses = [TaskStatus.SUCCESS, TaskStatus.FAILED, TaskStatus.CANCELLED]
    for status in terminal_statuses:
        tasks = await self._task_repo.list_by_status(status, limit=1000)
        for task in tasks:
            is_expired = False
            if task.completed_at:
                age_seconds = (now - task.completed_at).total_seconds()
                if age_seconds > task.ttl:          # 终态保留 = ttl（默认 3600s）
                    is_expired = True
            elif task.created_at:
                age_seconds = (now - task.created_at).total_seconds()
                if age_seconds > task.ttl * 2:      # 异常终态（无完成时间）双倍宽限
                    is_expired = True
            if is_expired:
                await self._task_repo.delete(task.task_id)
                # 缓存、future 联动清理...
                cleaned_count += 1
    return cleaned_count

配套还有 cleanup_expired_by_time(max_age_seconds=86400)（按固定时长一刀切）。逻辑本身写得周到：只处理三种终端状态、completed_at 超 ttl 即删、没有 completed_at 的终端任务（异常残留）按 created_at 双倍宽限、删除时同步清理生命周期缓存与 Future。

5.2 触发时机由使用方负责

cleanup_expired 只在 lifecycle.py 内定义，TaskPool、调度器、监督者均无引用。也就是说：

  • 不存在任何周期调度器：框架不会按"每小时一次、每次最多一千条"自动清理，cleanup_expired 只能由使用方手动或外部定时器触发；

  • "保留 7 天"说的是死信队列：TaskPoolConfig.dead_letter_ttl = 604800，即死信队列的保留时长（Redis 模式下死信队列已接线、默认启用），与终端任务数据的清理周期无关；

  • Redis 任务键没有设置 EXPIRE——Redis 模式的"键过期自动清理"不存在，任务键与状态索引 SET 都会无限累积；

  • SQLite 模式也没有任何自动 VACUUM——DELETE 后文件页只复用不缩水，磁盘不会自动回收。

清理函数写得完整却无人接线，多半是"预留能力、调度留给使用方"的取舍，但对生产是不可忽视的缺口：默认配置下，任务数据只增不减。SQLite 表无限膨胀拖慢 list_by_status 与 VACUUM 成本，Redis 内存被历史任务吃光，最终是整个调度器劣化。

5.3 清理盲区：每状态 1000 条、无排序、无翻页

即便用户手动调 cleanup_expired，还有一层隐蔽缺陷：list_by_status(status, limit=1000) 不带 ORDER BY、不带 offset。当某状态的历史任务超过 1000 条时：

  • 每次调用只取"任意 1000 条"（SQLite 无 ORDER BY 时行序不稳定，Redis 的 SET 遍历序更是无序）；

  • 检查的是这批任务的 completed_at 是否超龄，超龄者被删，但没被选中的更老任务可能永远轮不到；

  • 结果：调用方看到"每次都能清掉 1000 条"，但总量不见下降——清理只能追平增量，清不掉存量尾部。

要彻底清存量，需要按时间分批扫（📝 见故障场景二补丁）。

5.4 生产补丁建议（📝 示例）

# 1. 在 TaskPool 生命周期挂钩/外部定时任务中周期触发
async def maintenance_loop(pool, interval: float = 3600.0):
    while True:
        cleaned = await pool._lifecycle.cleanup_expired()   # 说明:内部组件,正式接入建议走官方扩展点
        logger.info("cleanup expired: %s", cleaned)
        await asyncio.sleep(interval)

# 2. SQLite 定期收缩文件（源码无自动 VACUUM）
#    sqlite3 neotask.db "VACUUM;"   # 或应用内 await conn.execute("VACUUM")

# 3. 清存量尾部：按 created_at 分批删（绕过 1000 条无排序盲区）
#    自定义 SQL: DELETE FROM tasks WHERE status IN ('success','failed','cancelled')
#              AND completed_at < ? LIMIT 5000;  循环执行直到影响行数为 0

模块内部 API 的直连调用（如 _lifecycle）在版本间可能变动，生产接入请关注官方维护入口或升级版本。

六、故障场景实战

场景一：SQLite 多进程共享，同一任务被执行两次

现象：两个 Python 进程各自 TaskPoolConfig.sqlite("shared.db") 消费同一批任务，监控发现同一个 task_id 多次进入 RUNNING，业务侧幂等校验报警（重复扣款/重复发信）。

根因：两层叠加——(1) SQLiteQueueRepository.pop 的 SELECT 与 DELETE 之间没有事务，多进程各自持有连接时，A 查出 task_id 尚未删除，B 也查到同一批（3.2 的 await 窗口在多进程下变成真实并发）；(2) 两进程各自 lock_type="memory"，执行锁互不可见，第二道防线失效。即便出队没撞车，A 执行完成后锁已释放，迟到的 B 拿到同一 task_id 仍会再执行一次。

排查：任务表里同一 task_id 出现多条 RUNNING 记录但 node_id 不同；队列日志中同批 task_id 被 pop 两次；检查两进程 sqlite_path 与 lock_type 配置。

解决：优先把 lock_type 切到 redis（执行互斥跨进程）；要根治出队重复，为 SQLite 出队补事务（📝）：

async def pop(self, count: int = 1) -> List[str]:
    ...
    # 以写事务串行化"查+删"，阻塞其他写者
    await self._conn.execute("BEGIN IMMEDIATE")
    cursor = await self._conn.execute("SELECT task_id FROM queue ORDER BY priority ASC, created_at ASC LIMIT ?", (count,))
    rows = await cursor.fetchall()
    task_ids = [row[0] for row in rows]
    if task_ids:
        placeholders = ",".join("?" * len(task_ids))
        await self._conn.execute(f"DELETE FROM queue WHERE task_id IN ({placeholders})", task_ids)
    await self._conn.commit()
    return task_ids

本质教训：SQLite 档位的正确部署形态是"单进程 + 默认锁"；任何引入多进程的念头都应直接升级 Redis 档位，而不是在 SQLite 上打补丁。

场景二：跑了清理任务，库里任务总数却不见少

现象：接入方写了个定时器每天调 cleanup_expired()，日志显示每次清理数千条，但 SELECT COUNT(*) FROM tasks 长期徘徊在数万不下，且磁盘持续增长。

根因：命中 5.3 的清理盲区——每状态 limit=1000、无 ORDER BY、无翻页。三个终端状态各取"任意 1000 条"，老任务不在抽样窗口里就永远不超龄判定；只要日新增超过日清理，总量就只增不减。另一个帮凶：终态保留时长 = ttl（默认 3600s），若业务统一提交了很大的 ttl（比如 7 天），终态数据本就该留 7 天——先确认清理预期与 ttl 语义匹配。

排查：比对 completed_at 最早的一条是否被清理过；检查任务 ttl 分布；观察单次清理量是否恒等于 1000×3 的上限。

解决：按时间分批自清存量（📝）：

# 每批删除最旧的 5000 条超过保留期的终态任务，直到删不动
while True:
    n = await conn.execute(
        "DELETE FROM tasks WHERE status IN ('success','failed','cancelled') "
        "AND completed_at < ? LIMIT 5000",
        (cutoff_iso,))
    await conn.commit()
    if n.rowcount == 0:
        break

本质教训：“清理逻辑存在"不等于"数据会被清理”——生产接入前必须验证调度者与盲区，并明确 ttl 到底是执行超时还是保留时长。

场景三：外部系统直接读 Redis 任务键，解析出来是字符串不是对象

现象：数据团队从 task:{id} 键取任务做离线分析，json.loads 后发现 data 字段的值仍是字符串（带 \" 转义），取业务字段全部落空。

根因：命中 1.3 的双层 JSON——Redis 键里存的是 json.dumps(to_dict()) 的产物，而 to_dict() 已把 data/result 再序列化了一层。外部读取必须解两层（📝）：

outer = json.loads(redis.get(f"task:{task_id}"))   # 外层:任务整体
payload = json.loads(outer["data"])                # 内层:业务载荷

排查：redis-cli GET task:xxx 直接看原始值，data 字段若带反斜杠转义即为双层结构；与 Task.from_dict 的 parse_json 逻辑对照。

解决：短期在消费端解两层；长期让外部系统走 NeoTask API/序列化入口读取任务，而不是直连 Redis 键——键格式是内部实现细节，双层 JSON 与否随版本可能变化。

本质教训：存储格式是"内部契约"，跨系统消费共享键空间前，必须确认序列化层级。

场景四：进程在"实体落库"与"入队"之间崩溃，任务永久 PENDING

现象：Redis 模式运行中节点突然 OOM 退出，重启后部分提交过的任务永远停留在 PENDING，既不被执行、也不会报错；按 task_id 查实体存在，但队列里没有它。

根因：写路径是"实体先落库、索引后入队"两步（dispatcher → create_task → push），中间没有任何事务或补偿机制。入队失败本身会被 dispatcher 捕获——任务标记 FAILED 并抛 QueueFullError（优先级任务 详述），但进程在两步之间直接崩溃时，没有任何返回值或异常可供捕获：实体已写入、队列尚无成员，就成了无索引孤儿；而 reclaimer 只回收 RUNNING 超时任务，PENDING 孤儿没有回收路径（故障恢复 已述）。数据库本身没有丢数据——丢的是"这个任务还要执行"的意图。

排查：对账脚本对比"PENDING 实体集合"与"queue:priority + queue:delayed 成员集合"，差集即孤儿。

解决（📝 兜底对账）：定期把 PENDING 且 created_at 超过阈值、但不在任何队列中的实体重新入队：

async def reconcile_orphans(pool, max_age: float = 60.0):
    orphans = []
    for task in await pool._task_repo.list_by_status(TaskStatus.PENDING, limit=10000):
        if task.created_at.timestamp() < time.time() - max_age:
            if task.task_id not in await pool._queue_repo.peek(10000):
                orphans.append(task.task_id)
    for tid in orphans:                              # 幂等:已在队列会被 ZSET 覆盖
        await pool._queue_repo.push(tid, TaskPriority.NORMAL.value)

本质教训：实体与索引分离的代价是双写窗口需要对账兜底——“数据在库"不等于"调度语义完整”，生产系统要有孤儿检测或至少可观测性。

七、配置示例

选型口诀：开发用内存、单机用 SQLite、多机用 Redis；锁与存储同档位（🔧 真实类方法签名，见 models/config.py）：

from neotask import TaskPool

# 开发测试 - 内存存储（默认即此配置，可省略）
pool = TaskPool(config=TaskPoolConfig.memory())

# 单机生产 - SQLite（务必保持单进程；路径默认 neotask.db）
pool = TaskPool(config=TaskPoolConfig.sqlite(path="neotask.db"))

# 分布式生产 - Redis（唯一启用分布式组件的档位）
pool = TaskPool(config=TaskPoolConfig.redis(url="redis://localhost:6379"))

补充两点注意事项：

  1. 显式声明锁档位：SQLite + 多进程必须 lock_type="redis"（见 4.2 组合表），否则执行去重失效。

  2. 主动接清理：默认无任何自动清理调度，生产接入请按 5.4 方案补维护循环，并留意 ttl 双语义对保留时长的拉扯。

总结

NeoTask 的持久化层，本质是"实体全量快照 + 瘦索引"模型的三种落地：

  • 统一序列化：Task 14 字段模型驱动、双层 JSON 整体覆盖，换来字段演化自由与一致性简单，代价是存储层的不可读与全量读写。

  • 内存靠拷贝、SQLite 靠文件、Redis 靠原子：三者的可靠性差异集中在出队原子性与锁可见性上——memory 与 sqlite 都只在单进程内安全，Redis 的 ZSET+Lua 是唯一跨进程正确的组合，这也解释了为何分布式组件只装配在 Redis 模式。

  • 清理能力悬空：cleanup_expired 实现完备但无调度者、有 1000 条无排序盲区；Redis 无键过期、SQLite 无自动 VACUUM——"持久化"管好了写入，回收需要使用方自己补上。

用一句话收束：在 NeoTask 里选择存储，不是选择"数据放哪"，而是选择"原子性边界画在哪、谁来兜底一致性窗口"。下一站可继续阅读 节点监控 了解如何观测这套存储，或回 配置说明 核对全部参数默认值。
