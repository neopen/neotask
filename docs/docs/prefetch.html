概述

在分布式任务调度系统中，共享队列（Redis）是所有节点的竞争焦点。没有预取时，每个任务的消费都需要一次"从队列取出"的网络往返，任务吞吐量越高，网络 I/O 越接近瓶颈。

NeoTask 的预取机制把「从 Redis 取任务」和「交给 worker 执行」解耦成两段：一个独立的后台协程（TaskPrefetcher）批量把任务从共享队列搬到本节点的内存队列，worker 协程只从内存队列消费，不再直接打 Redis。

┌──────────────────────── 节点 ────────────────────────┐
│                                                      │
│   Redis 共享队列          ┌─────────────┐             │
│   queue:priority  ──────▶ │TaskPrefetcher│ 批量拉取   │
│   (ZSET 全局有序)   pop(n) │(单一生产者)  │            │
│                          └──────┬──────┘             │
│                                 │ put_nowait          │
│                          ┌──────▼──────┐             │
│                          │ 本地队列      │ 内存缓冲     │
│                          │ (asyncio.Queue│            │
│                          │  maxsize=100) │            │
│                          └──────┬──────┘             │
│                                 │ get(timeout)        │
│                    ┌────────────▼───────────┐        │
│                    │ worker 协程 × concurrency│        │
│                    └────────────┬───────────┘        │
│                                 │ acquire 执行锁       │
│                    Redis lock:task:{id} ◀────────────┘
└──────────────────────────────────────────────────────┘

一句话总结它的设计：把「每次执行一次 RTT」变成「每 N 次执行一次 RTT + 内存队列吸收抖动」，用本节点内存换共享存储带宽。

预取机制解决的问题

网络 RTT 的重复付费

先做量纲分析。一次 pop 的耗时近似：

[
T_{pop} \approx RTT + T_{redis}
]

  • 同机 Redis：RTT 可忽略，单次操作约 10~50μs；

  • 局域网 Redis：RTT 约 0.1~0.5ms；

  • 跨机房/公网 Redis：RTT 可达 1~10ms。

假设跨机房 RTT=1ms、任务执行 5ms：每任务取一次，队列开销占执行时间的 20%；批量取 20 个，队列开销摊到每个任务只有 0.05ms（1%）。注意量级要分场景——局域网下单次操作约 0.1~0.5ms，一万任务也就几秒的额外等待；跨公网时这笔开销会放大到分钟级。预取的收益不是恒定的，它 ≈ ((n-1) \times RTT)，RTT 越大收益越大。

队列竞争与出队窗口

多个节点同时从共享 ZSET 出队，每次 ZRANGE + ZREM 之间虽然被 Lua 保证原子，但竞争本身会增加重试与等待。预取把每个节点访问队列的频率从"每任务一次"降到"每批一次"，竞争时间窗口缩小到原来的 1/20。

延迟敏感任务的响应

预取本身不区分优先级——批量拉取时队列头的任务照单全收，因此低延迟高优任务要面对的是"在途量×时长"的反转窗口，收敛手段是水位控制（max_threshold）与调小 prefetch_size，详见下文「优先级与预取」章节。

# src/neotask/worker/prefetcher.py
class PrefetchStrategy(Enum):
    SIZE_BASED = "size_based"      # 基于队列大小
    TIME_BASED = "time_based"      # 基于时间间隔
    HYBRID = "hybrid"              # 混合策略（默认）

@dataclass
class PrefetchConfig:
    prefetch_size: int = 20        # 每次预取数量
    local_queue_size: int = 100    # 本地队列最大大小
    min_threshold: int = 5         # 低于此阈值触发预取
    max_threshold: int = 80        # 高于此阈值停止预取
    prefetch_interval: float = 0.1 # 预取检查间隔（秒）
    idle_timeout: float = 5.0      # 空闲超时（秒）
    strategy: PrefetchStrategy = PrefetchStrategy.HYBRID
    enable_batch_pop: bool = True  # 启用批量弹出
    enable_stats: bool = True
    stats_window: int = 100        # 统计窗口大小

预取策略：三种模式的语义

预取循环（🔧）每一轮做两件事：_should_prefetch 判断要不要拉，_calculate_wait_time 决定下一轮等多久：

# src/neotask/worker/prefetcher.py
async def _prefetch_loop(self) -> None:
    while self._running:
        try:
            current_size = self._local_queue.qsize()
            # 检查是否需要预取
            if self._should_prefetch(current_size):
                await self._do_prefetch()
            # 根据策略决定等待时间
            wait_time = self._calculate_wait_time(current_size)
            await asyncio.sleep(wait_time)
        except asyncio.CancelledError:
            break
        except Exception:
            await asyncio.sleep(0.5)

策略判定（🔧 _should_prefetch）

def _should_prefetch(self, current_size: int) -> bool:
    # 1. 防止并发预取（预取进行中直接跳过本轮）
    if self._prefetch_in_progress:
        return False

    # 2. 空闲超时检查
    idle_time = time.time() - self._last_activity
    if idle_time > self._config.idle_timeout:
        return False

    # 3. 按策略判定
    if self._config.strategy == PrefetchStrategy.SIZE_BASED:
        return current_size < self._config.min_threshold

    elif self._config.strategy == PrefetchStrategy.TIME_BASED:
        last_prefetch = self._stats.last_prefetch_time or 0
        time_since_last = time.time() - last_prefetch
        return time_since_last > self._config.prefetch_interval * 10

    else:  # HYBRID
        return (
            current_size < self._config.min_threshold or
            (current_size < self._config.max_threshold and
             self._is_consuming_fast())
        )

三个策略的真实行为（与常见直觉有出入的地方标注 ⚠）：

策略 触发条件 真实语义 备注
SIZE_BASED 本地队列 < min_threshold 纯低水位触发：低于 5 就拉，拉到不满为止 高水位 max 只影响等待时间，不影响"是否拉"
TIME_BASED 距上次预取 > interval×10（1s） 每 ≥1s 固定检查一次，不看队列水位 ⚠ 文档常说"固定间隔预取"，但 _do_prefetch 里有容量保护：队列接近满时 to_fetch≤0 直接返回，不会硬塞
HYBRID（默认） 见下 低水位必拉；中水位"消费快"才拉；高水位不拉 默认策略

HYBRID 的分段逻辑：

flowchart TB
    Start([本地队列大小 size]) --> L1{size < 5?}
    L1 -->|是| P1[必拉<br/>水位告急]
    L1 -->|否| L2{size < 60/80?}
    L2 -->|否| W[不拉<br/>队列充足 慢慢等]
    L2 -->|是| L3{消费快?<br/>最近5批平均 > 10}
    L3 -->|是| P2[拉<br/>防止追不上]
    L3 -->|否| W2[不拉<br/>供应≥需求]

注意上图中的高水位：直接实例化 TaskPrefetcher 时 max=80（配置默认），但经 WorkerPool 接线后 max=60——两套默认值，见下节。

等待时间三档（🔧 _calculate_wait_time）

def _calculate_wait_time(self, current_size: int) -> float:
    if current_size >= self._config.max_threshold:   # ≥80(或60)
        return self._config.prefetch_interval * 5    # 0.5s
    elif current_size >= self._config.min_threshold: # ≥5
        return self._config.prefetch_interval * 2    # 0.2s
    else:                                             # <5
        return self._config.prefetch_interval        # 0.1s

为什么用三档离散值而不是连续函数？ 三点考虑：

  1. 事件循环粒度：asyncio.sleep 本身有调度开销，连续调整没有意义，档位足够表达"急/缓/闲"三态；

  2. 反作用回路稳定：如果等待时间与队列大小成连续反比，队列抖动会传导成预取频率抖动，容易在多个节点间形成共振；离散档位天然带滞回特性；

  3. 档位与策略语义对齐：低水位（<5）是"快断粮"，必须 0.1s 高频巡检；中水位 0.2s；高水位说明缓冲充足，0.5s 慢慢来，减少空转。

为什么 HYBRID 成为默认策略，而不是更简单的 SIZE_BASED？ 看两组数字：prefetch_size=20，一批任务如果执行很快（如 1ms），20 个任务 20ms 就耗尽。SIZE_BASED 的触发条件是 size<5，意味着本地队列从 20 消耗到 4 才补货——水位回落需要时间，而"消耗速率×回落时间"就是断粮窗口。HYBRID 增加了一条"消费快就提前补"的规则：只要最近 5 批平均批次消费量 >10（prefetch_size 的一半），说明 worker 消化速度超过半批/轮，即使水位还有 30、40 也提前拉货，把断粮窗口压到接近零。SIZE_BASED 是"事后补救"，HYBRID 是"事前预防"。

WorkerPool 接线：两套默认值

直接 TaskPrefetcher(queue_scheduler) 使用配置默认值（max=80）；但生产主链路 WorkerPool 会重新算一套（🔧 src/neotask/worker/pool.py）：

# WorkerPool.__init__（节选）
if enable_prefetch:
    prefetch_config = PrefetchConfig(
        prefetch_size=prefetch_size,            # TaskPoolConfig.prefetch_size，默认 20
        local_queue_size=prefetch_size * 5,     # = 100
        min_threshold=max(1, prefetch_size // 4),  # = 5
        max_threshold=prefetch_size * 3,        # = 60  ← 注意不是默认的 80
        enable_batch_pop=True,
        strategy=PrefetchStrategy.HYBRID
    )
    self._prefetcher = TaskPrefetcher(queue_scheduler, prefetch_config)
参数 TaskPrefetcher 类默认 WorkerPool 接线值（prefetch_size=20） 比例关系
local_queue_size 100 100 5 × prefetch_size
min_threshold 5 5 prefetch_size / 4
max_threshold 80 60 3 × prefetch_size

为什么 max_threshold 要压到 3 倍而不是 5 倍（队列容量）？ 本地队列的容量上限（100）是"装得下的极限"，但预取的高水位是"还想不想继续装"的决策点。如果把高水位设在容量上限附近，缓冲区长期接近满载——新任务、高优任务都挤不进来，节点对全局队列的"抢货积极性"过低。3 倍 prefetch_size 意味着：缓冲区最多留 60 个在途任务，至少留 40 个空位给"未来可能出现的更高优任务"。这是吞吐（多囤）与响应（留空）的平衡点。这也解释了一个反直觉现象：高水位不是"内存保护"而是"竞争策略参数"。

批量拉取的原子性：出队与加锁是分离的

批量拉取不含"加锁"步骤：预取阶段只做出队，锁在执行前由 worker 单独获取。

执行链

sequenceDiagram
    participant PF as TaskPrefetcher
    participant Q as Redis queue:priority (ZSET)
    participant LQ as 本地队列
    participant W as Worker 协程
    participant LK as Redis lock:task:{id}

    loop 预取循环 (每0.1~0.5s)
        PF->>Q: pop(n) [Lua: ZRANGE + ZREM]
        Note over Q: 原子出队，但无锁
        Q-->>PF: [task_a, task_b, ...]
        PF->>LQ: put_nowait × n
    end

    loop worker 循环
        W->>LQ: get(timeout=0.1)
        LQ-->>W: task_id
        W->>LK: acquire(task:{id}, ttl=30)
        alt 抢锁成功
            LK-->>W: OK
            W->>W: 执行 + 看门狗续期
        else 抢锁失败（他人执行中）
            LK-->>W: 失败
            W->>W: 直接 return（不重试、不入队）
        end
    end

真实的 Redis 出队脚本（🔧 src/neotask/queue/redis_queue.py 的 pop Lua）只有两步：ZRANGE queue 0 count-1 取最小 score（最高优先级）的一批，然后 ZREM 移除。没有 SETNX，没有锁。锁发生在更晚的时刻——worker 真正要执行时，由 WorkerPool._execute_task 调用 lock_manager.acquire(f"task:{task_id}", ttl=30)。

这与分布式锁一文中的链路完全一致：出队原子 ≠ 执行原子。

为什么预取阶段故意不加锁？

如果"批量抢占"真的在 Lua 里完成"出队+加锁"，会引入三个问题，而 NeoTask 的设计恰好绕开了它们：

  1. 锁的持有时间会与排队时间耦合。任务被预取进本地队列后，可能要等前面的任务执行完才轮到它。如果出队即加锁，锁 TTL 必须覆盖"排队等待 + 执行时长"，30s 的 TTL 根本不够；要设多长？无法预知。锁的生命周期只绑定执行期（acquire → 执行 → finally release），这是租约锁的基本纪律；

  2. 加锁失败的任务无处安放。若在 Lua 里做"取到但锁失败就留在队列"的处理，Redis ZSET 里 score 相同、成员唯一，反复扫描头部会让一批 worker 同时尝试同一批任务，产生 thundering herd；而"取走再说"的策略里，锁失败只是本节点白跑一趟，任务已在别的节点手里正常执行；

  3. 锁的语义是"执行权"而非"所有权"。预取只是搬运，搬运不需要锁；只有执行需要互斥。把两种语义混在一个原子操作里，会让"预取多少"（受水位控制）与"能否执行"（受并发控制）互相干扰——水位低想多囤货时，却可能因为锁失败而囤不到货。

代价是什么？ 分离设计有一个明确的牺牲：任务被 ZREM 出队后就失去了队列保护，若本节点在"已出队、未执行"窗口内崩溃，任务不会自动回到队列——只能等回收器超时兜底（默认 1 小时，详见故障恢复）。这是 NeoTask 用"预取深度"换"恢复延迟"的取舍：批量越大，吞吐越高，崩溃丢任务窗口也越大。

HYBRID 的消费速率判定：为什么用"批均"而不是"速率"？

# src/neotask/worker/prefetcher.py
def _is_consuming_fast(self) -> bool:
    if len(self._stats.recent_batch_sizes) < 5:
        return False          # 冷启动：样本不足，保守不预判
    recent = self._stats.recent_batch_sizes[-5:]
    avg_size = sum(recent) / len(recent)
    return avg_size > self._config.prefetch_size * 0.5   # >10

注意判定依据是 recent_batch_sizes——每次预取实际拉到的数量（不是消费速度、不是时间窗口内的吞吐）。为什么这么设计？

  1. 预取拉到的数量本身就携带消费信息：如果 worker 消化快，本地队列水位会快速下降，两次预取之间队列一直低于水位，下一次 pop 就能拉满 20；如果消化慢，队列长期在高位，_should_prefetch 返回 False，拉不到货，批次大小为 0。批次大小是消费压力的低通滤波结果——不需要额外计时器去测速率；

  2. 不依赖时钟，避免测量窗口误差：速率 = 数量/时间，需要精确定义"时间窗"，事件循环抖动会污染测量；批次样本只统计"拉到了多少"，天然抗抖动；

  3. 为什么是 5 个样本、为什么阈值是 10（prefetch_size 的一半）：5 个样本 ≈ 0.5~2.5s 的窗口（取决于预取频率），太短会被单批抖动误导，太长反应迟钝；阈值取半批意味着"每轮至少消化一半库存"，此时若不补货，两轮内必然断粮——提前量正好是半轮预取周期。

冷启动为什么返回 False？ 刚启动时没有任何批次历史，如果贸然判定"消费快"会立刻触发一次预取，而本地队列此时接近空、本来就该预取（HYBRID 的低水位分支已覆盖）；样本不足时保守处理，避免双重拉货。

空闲判定：idle_timeout 挡不住"活跃的空转"

PrefetchConfig.idle_timeout=5.0 的设计意图是：空闲时不预取。判定依据是 _last_activity，而它在哪里刷新？

# src/neotask/worker/prefetcher.py
async def get(self, timeout: float = 1.0) -> Optional[str]:
    self._last_activity = time.time()      # ← 每次 get 都刷新，与队列空否无关
    try:
        task_id = await asyncio.wait_for(self._local_queue.get(), timeout=timeout)
        return task_id
    except asyncio.TimeoutError:
        return None

再看 WorkerPool 的 worker 循环（🔧）：

# src/neotask/worker/pool.py
if self._prefetcher:
    # 预取模式：每次从本地队列取 1 个
    task_id = await self._prefetcher.get(timeout=0.1)
    if task_id:
        consecutive_empty = 0
        exec_task = asyncio.create_task(self._execute_task(worker_id, task_id))
        ...
    else:
        # 没有任务时，指数退避
        consecutive_empty += 1
        sleep_time = min(0.01 * (1 << min(consecutive_empty, 6)), 0.5)
        await asyncio.sleep(sleep_time)
        continue

worker 侧是"单任务 + 指数退避"，不是批量取。 预取的批量只发生在"Redis → 本地队列"这一段；"本地队列 → worker"以单任务为粒度消费。worker 空转时退避从 10ms 指数增长，封顶 500ms。

idle_timeout=5s 在主链路里几乎不会触发。 worker 只要活着，每 0.1~0.6s 就会调一次 get()，_last_activity 被持续刷新——即使队列永远是空的。idle 判定在"有活跃消费者"场景下形同虚设。它只对两类场景生效：

  • 直接用 TaskPrefetcher API、消费者暂停消费的场景；

  • 预取器启动但 worker 还没拉起来的窗口。

空批退避（已内建）。 队列为空时 HYBRID 的低水位分支（size=0 < 5）恒为 True，预取循环会不断醒来对 Redis 执行空 pop。为避免空转，循环记录 empty_streak：真正尝试过预取却一个任务都没拿到时按指数拉长下一轮间隔，拿到任务则立即回到正常节奏（🔧 _prefetch_loop）：

EMPTY_BACKOFF_BASE = 0.1        # 首次退避（秒）
EMPTY_BACKOFF_MAX = 0.5         # 退避上限（秒），与 worker 侧一致
EMPTY_BACKOFF_MAX_EXPONENT = 6  # 指数封顶

if attempted and fetched == 0:
    self._empty_streak += 1
    wait_time = min(
        EMPTY_BACKOFF_BASE * (2 ** min(self._empty_streak, EMPTY_BACKOFF_MAX_EXPONENT)),
        EMPTY_BACKOFF_MAX
    )
else:
    self._empty_streak = 0
    wait_time = self._calculate_wait_time(current_size)

两点说明：只有"尝试过且返回 0"才计入 streak——_should_prefetch 判为无需预取（高水位正常等待）时不会误判为空转；退避上限取 0.5s（与 worker 侧一致），而非更大的 5s，因为预取是任务进入执行前的最后一跳，退避上限直接等于"断粮后补货的最坏延迟"。连续空 pop 的稳态频率因此约 2 次/秒/节点，比无退避时低一个量级。

get 与 get_batch：预留的批量消费 API

# src/neotask/worker/prefetcher.py
async def get(self, timeout: float = 1.0) -> Optional[str]:
    """取 1 个任务，超时返回 None"""
    ...

async def get_batch(self, max_count: int, timeout: float = 0.1) -> List[str]:
    """批量取：第一个任务等待最多 timeout，其余 get_nowait 不等待"""
    self._last_activity = time.time()
    tasks = []
    try:
        first = await asyncio.wait_for(self._local_queue.get(), timeout=timeout)
        tasks.append(first)
        for _ in range(max_count - 1):      # 剩余的非阻塞扫
            try:
                tasks.append(self._local_queue.get_nowait())
            except asyncio.QueueEmpty:
                break
    except asyncio.TimeoutError:
        pass
    return tasks

get_batch 的语义是"等一个、捞一把"：第一个任务最多等 0.1s（给生产者一点时间），一旦等到立刻把队列里现有的全部拿空——适合"一批任务要同时启动"（扇出/并行子任务）的消费方。但 v1.0.2 的 WorkerPool 主链路只用 get，没有调用 get_batch（全局检索无引用），它是为下游消费者预留的 API。

优先级与预取：反转窗口与水位控制

ZSET 全局有序下的反转窗口

先厘清概念：Redis queue:priority 是全局 ZSET，score 越小优先级越高。新提交的高优任务 score 极小，任何节点下一次 pop 都会先取到它——高优任务不会被埋在共享队列里。

真正的优先级反转发生在节点内部：某节点本地队列已预取了 60 个低优任务（score 大），worker 按 FIFO 逐个执行。此刻新提交一个 P0 任务——它会被别的节点（或本节点下一轮预取）从共享队列取走，但它依然排在本节点已出队的 60 个旧任务之后。高优任务的等待时间上界 ≈ 该节点在途任务数 × 平均执行时长。

flowchart LR
    subgraph Global["全局 ZSET（有序，P0 永远在头部）"]
        P0[P0 新任务<br/>score=0]
        P1[P2 任务<br/>score=50]
        P2[P3 任务<br/>score=100]
    end
    subgraph NodeA["节点 A 本地队列（FIFO）"]
        A1[P3 任务 1]
        A2[P3 任务 2]
        A3[... 最多 60 个]
    end
    Global -->|pop 优先取 P0| Other["其他节点 / 下一轮预取"]
    Note over NodeA: P0 到达时，A 已出队任务仍要<br/>先执行完 → 反转窗口 = 在途量×时长

为什么接受这个窗口？ 批量预取的本质就是"提前把任务锁定到本节点"，锁定量越大，全局调度越滞后。这是吞吐的代价，工程上通过两个手段收敛：

  1. max_threshold（默认 80，约 4×prefetch_size）把在途量压在有限区间内，高水位时停止预取；

  2. 用户可以缩小 prefetch_size 甚至禁用预取来换取延迟。

预取不做优先级过滤：_do_prefetch 只管"要多少"，不管"要哪个"——批量拉取时队列头的任务照单全收。因此结构上的缓和来自水位控制，剩下的靠调参与物理隔离。

为什么 HYBRID 的水位控制能部分缓解饿死

设想一个极端场景：低优任务洪峰把节点本地队列长期顶在 60 以上，此时 P0 任务到达共享队列——HYBRID 下该节点 size≥60 不再预取，把全局头部让给其他节点；若所有节点都满载，P0 会滞留在共享队列中等待第一个空出缓冲区的节点。低水位分支（size<5 必拉）保证节点永远不会"占着缓冲区却不消费"。所以 HYBRID 的贡献是：它不保证 P0 的绝对延迟，但保证不会有一个节点因为"囤货癖"而饿死全局队列。

_do_prefetch 的关键实现（🔧）：

async def _do_prefetch(self) -> None:
    self._prefetch_in_progress = True
    start_time = time.time()
    try:
        needed = self._config.prefetch_size                 # 20
        available = self._config.local_queue_size - self._local_queue.qsize()
        to_fetch = min(needed, available)                   # 永不超容量
        if to_fetch <= 0:
            return

        if self._config.enable_batch_pop:
            task_ids = await self._queue.pop(to_fetch)      # 一次批量
        else:
            task_ids = []
            for _ in range(to_fetch):                        # 逐个拉
                task_id = await self._queue.pop(1)
                if task_id:
                    task_ids.extend(task_id)
                else:
                    break

        for task_id in task_ids:                             # 入本地队列
            try:
                self._local_queue.put_nowait(task_id)
            except asyncio.QueueFull:
                break
        await self._update_stats(len(task_ids), start_time)
    except Exception as e:
        self._stats.total_errors += 1
    finally:
        self._prefetch_in_progress = False

enable_batch_pop=False 的逐个拉取分支有什么用？ 两种模式对 Redis 的压力相同（总量一样），但批量模式是一次原子 ZRANGE+ZREM 拿 20 个，逐个模式是 20 次独立 pop——中间任何时刻其他节点都能插队。批量模式实际等于"声明式抢占一段队列区间"，窗口内新到的高优任务要等下一次预取；逐个模式对高优任务响应更快（每 pop 一次都在取全局最小 score），但代价是 20 次 RTT。默认 True 是吞吐优先的选择，这个开关就是吞吐/延迟的旋钮。

运维派生指标（非源码输出，供自行计算）：

  • 预取效率 = total_fetched / total_prefetch：接近 prefetch_size 说明每次拉得满、Redis 基本没白跑；明显偏低说明队列经常空或预取过于频繁；

  • 批均填充率 = avg_batch_size / prefetch_size：长期 <50% 说明供应不足或水位参数不匹配。

与 API 的通路：WorkerPool 的 get_prefetcher_stats()（🔧）会被 TaskPool.get_stats() / get_stats_async() 调用——启用预取时输出里直接带 prefetcher 子对象：

stats = pool.get_stats()

    p = stats["prefetcher"]
    print(p["local_queue_size"], p["avg_batch_size"], p["empty_streak"])

需要两点注意：WorkerPool.get_stats() 返回的是每个 worker 的 WorkerStats（worker_id/active_tasks/completed_tasks/failed_tasks/is_busy），不含预取统计——预取统计只挂在 TaskPool.get_stats()["prefetcher"] 这一处；另外 MetricsCollector 与 TaskPrefetcher 之间没有数据通路，预取统计不会进指标，要监控预取健康度得读这个子对象：

# 自建监控示例：定时读取预取统计
async def monitor_prefetch(pool):
    while True:
        stats = (await pool.get_stats_async()).get("prefetcher")
        if stats and stats["total_prefetch"] > 0:

            if fill < 0.3 and stats["total_errors"] > 0:
                log.warning(f"预取填充率异常: {fill:.0%}, errors={stats['total_errors']}")
        await asyncio.sleep(60)

故障场景实战

场景 1：队列见底时的"空转风暴"

现象：业务低谷期（队列几乎为空），Redis 监控显示大量空 pop 调用；CPU 不高但连接数/QPS 异常，节点越多越明显。

根因链：本地队列 size=0 < min_threshold=5 → HYBRID 低水位分支恒 True → 反复对 Redis 执行空 pop(20)；空结果同样写入统计 → Redis 返回空 list，循环不休。没有退避时每节点就是 10Hz 空查询。

排查命令：观察预取统计 total_prefetch 增速与 avg_batch_size，以及 get_stats()["prefetcher"]["empty_streak"]：若 total_prefetch 每秒 +10 而 avg_batch_size≈0、empty_streak 不增长，说明退避没生效（预取被禁用或计数器被重置）。

解决：内建的空批退避已经兜住（见上文「空批退避」）：连续空 pop 时按 empty_streak 指数拉长间隔，0.5s 封顶，稳态约 2 次/秒/节点。若仍觉得巡检偏频，可把 prefetch_interval 调大（退避基数随之变化），代价是断粮后补货变慢。

场景 2：批量出队后节点崩溃 → 任务滞留 1 小时

现象：节点 A 崩溃后，其"已领取但未执行"的任务集体消失，1 小时后才陆续恢复重跑。

根因：预取的瞬间任务已被 ZREM 出队，队列里没有它的位置了；它只存在于节点 A 的内存本地队列。崩溃 = 内存蒸发，Redis 侧一无所知。任务状态仍是 PENDING、无 node_id 标记——直到回收器按 ttl（默认 3600s）兜底重排（详见故障恢复）。

损失上界：本地队列容量 100 + 正在执行的并发任务（10）≈ 110 个任务/节点。批量越大、队列越长，损失窗口越大——这就是"预取深度"与"恢复延迟"的杠杆，生产上要按任务价值定 prefetch_size，而不是只按吞吐定。

解决：对 SLA 高的任务，用 redispatch/重试语义补偿；或缩小 prefetch_size（建议 5~10）让"已出队未执行"的库存变小；真正需要零丢失时禁用预取（见下节），让任务始终受队列保护。

场景 3：低优洪峰挤占预取，高优任务响应劣化

现象：促销批量任务（P3）涌入后，P0 的即时任务延迟从几十 ms 劣化到数秒。

根因：节点本地队列被 P3 预取占满（60 在途），P0 到达后：若所有节点都在途饱和 → P0 滞留共享队列等空位；若某节点有 5~60 的空位，该节点只有在"消费快"判定下才拉——而 P0 会在下一轮 pop 被取到（score 最小），延迟 ≈ 一轮预取周期（0.1~0.5s）+ 该节点在途任务排空时间。

排查：先看 queue_size 是否持续 >0 而 worker 活跃（说明任务在排队）；再看是否所有节点的本地队列长期满（日志里 prefetcher 拉取批次是否满 20）。

解决：

  • 结构性手段：调小 prefetch_size，在途量随之缩小，反转窗口同步变窄；

  • 调小 max_threshold，让节点更早停止囤货，把全局头部让给其他节点；

  • 需要硬性优先级保证时，用独立 TaskPool 实例跑高优任务，物理隔离。

场景 4：优雅停机超时，本地队列残留如何处理

现象：节点滚动发布，停机日志显示"All workers stopped"，本地队列里还有一批已出队但未执行的任务。

为什么值得关注：WorkerPool.stop(graceful=True, timeout=30) 先调 prefetcher.stop(graceful, 30)——_wait_until_empty 每 0.1s 轮询本地队列，30s 内没排空就放弃，随后取消预取协程。这些 task_id 已经出队、不在 Redis 队列里了，如果不做处理就只能等回收器按 ttl（默认 3600s）兜底重排，延迟一小时。

内建方案：drain_back。 WorkerPool.stop 在预取器停下后立即把本地队列残留放回共享队列（🔧 worker/pool.py → prefetcher.drain_back）：

# 🔧 worker/pool.py —— 停止预取器后回队，避免残留变孤儿
if self._prefetcher:
    await self._prefetcher.stop(graceful, timeout)
    drained = await self._prefetcher.drain_back(self._resolve_task_priority)
    if drained:
        debug(f"Drained {drained} prefetched task(s) back to shared queue")

drain_back(priority_resolver) 逐个 get_nowait 取出残留任务，并用 priority_resolver 从存储还原其原始优先级再 push 回共享队列——不是一律按 NORMAL 重排：

# 🔧 prefetcher.py
priority = TaskPriority.NORMAL.value
if priority_resolver is not None:
    priority = await priority_resolver(task_id)   # 从存储读回真实优先级
if await self._queue.push(task_id, priority):
    drained += 1
else:
    # 共享队列也满了：放回本地队列，宁可保留也不要凭空丢弃
    self._local_queue.put_nowait(task_id)
    break

因此默认路径下"停机丢任务"已经不会发生；只有共享队列同时满载/被禁用时才会保留在本地并告警（Cannot drain task ... queue full/disabled）。

运维建议：停机窗口尽量选在队列低水位期，让 drain_back 一次成功；若看到上面的告警，说明共享队列已满，残留任务仍要靠回收器兜底——此时先恢复队列可用性再重启。

性能分析

官方基准（性能基准详解、v0.3.0 Windows 实测）只给出一个与预取直接相关的数字：批量弹出相对单任务弹出约 2.00x 提升。注意这是"内存存储基准下的批量 pop"——同一批任务用 1 次批量调用 vs N 次单次调用。

真实的收益模型如下：

[
\text{预取收益} = \frac{N \times T_{single}}{T_{batch}} \approx N \text{ 当 } T_{batch} \ll N \times RTT
]

场景 Redis RTT 批量 20 个的收益 结论
同机 loopback ~0.05ms 拉取耗时从 1ms→0.1ms 级 收益小，瓶颈在 executor，不在队列
局域网 ~0.3ms 每批省 ~5.7ms 中等收益，worker 数量大时可观
跨机房 ~5ms 每批省 ~95ms 收益巨大，预取是刚需

另一个必须认识的分层事实（引用官方实测）：TaskPool 端到端约 1700 ops/s，而队列入队/出队原始操作达 20万~31万 ops/s——队列从来不是瓶颈，执行器（含 Python 解释器开销）才是。这意味着：

  • 预取解决的是"队列访问频率"问题，不是"执行吞吐"问题——先确认瓶颈在 Redis 往返上再调预取；

  • 本机 Redis 场景，预取带来的收益常常被它引入的复杂度抵消（内存、孤儿窗口、停机残留），禁用预取是合理的选项。

与其他模块的协作

graph TB
    subgraph Pipeline["真实协作关系"]
        QS[QueueScheduler<br/>pop → Lua ZRANGE+ZREM]
        PF[TaskPrefetcher<br/>批量搬运]
        LQ[本地队列]
        WP[WorkerPool<br/>worker 协程]
        LK[LockManager<br/>执行前 acquire ttl=30]
        RC[TaskReclaimer<br/>超时/孤儿兜底]
    end
    QS -->|pop n| PF
    PF -->|put_nowait| LQ
    LQ -->|get 0.1s| WP
    WP -->|仅执行前| LK
    RC -. 兜底已出队未执行 .-> PF

  • QueueScheduler：任务来源，pop(n) 内部走优先级队列 Lua（批量原子出队）；

  • WorkerPool：消费者。两种模式——预取模式（本节点单一预取器 + 本地队列分发）与直接模式（每个 worker 协程各自 pop(prefetch_size)）；

  • LockManager：不在预取路径上，只在执行前抢 lock:task:{id}（ttl=30 + 看门狗续期）；

  • MetricsCollector：与预取器无数据通路，预取统计走 TaskPool.get_stats()["prefetcher"]（见上文统计章节）；

  • TaskReclaimer：预取造成的"出队即失保护"窗口的最终兜底方（ttl=3600s）。

禁用预取：什么时候该关？

真实 API 两个入口（🔧）：

# 方式一：构造时关闭（推荐）
config = TaskPoolConfig.redis("redis://127.0.0.1:6379", enable_prefetch=False)

# 方式二：代码里直接建 WorkerPool（🔧 真实签名）
worker_pool = WorkerPool(
    executor=executor,
    task_repo=task_repo,
    queue_scheduler=queue_scheduler,
    event_bus=event_bus,
    lifecycle_manager=lifecycle_manager,
    concurrency=10,
    prefetch_size=20,
    task_timeout=None,
    lock_manager=lock_manager,
    enable_prefetch=False      # 禁用预取
)

一个容易误解的点：禁用预取后 worker 并不是"每个任务独立操作、单任务获取"——直接模式的 worker 循环同样走批量：task_ids = await self._queue.pop(self._prefetch_size)（🔧 pool.py），每轮批量 pop 20 个、逐个 create_task 执行。两种模式的真正区别在于由谁访问队列、以及有没有缓冲层：

维度 预取模式 直接模式
谁访问 Redis 单一预取器协程 每个 worker 协程（并发 N 个）
缓冲层 本地队列（≤100） 无（pop 完直接执行）
出队节奏 由水位统一控制 各 worker 自由竞争
优先级保持 好（单一消费者按序取） 差（N 个 worker 同时抢，执行顺序乱序）
空转行为 预取循环空批退避（0.5s 封顶）+ worker 退避 每 worker 独立退避（0.5s 封顶）
崩溃窗口 本地队列残留（最多 ~110/节点） pop 后未执行的在途任务（每 worker ≤20，但执行是异步 create_task，实际窗口 = pop 批 × 未完成数）

建议禁用的场景：同机/低延迟 Redis（预取收益小）、内存敏感（本地队列是纯额外内存）、任务需要严格接近实时的全局优先级（直接模式每轮 pop 都取全局最小 score）、以及调试期想观察原始队列行为。

总结

设计点 真实实现 深度理解
批量拉取 pop Lua = ZRANGE + ZREM，无锁 锁绑定执行期而非搬运期；出队原子 ≠ 执行原子
默认 HYBRID 低水位必拉 / 中水位看消费快慢 / 高水位停 SIZE_BASED 事后补救，HYBRID 事前预防
消费快判定 最近 5 批平均 > prefetch_size/2 用批均近似速率，抗时钟抖动
高水位 WorkerPool 接线 = 3×prefetch_size（60） 是竞争策略参数，不是内存保护
空闲判定 idle_timeout=5s 但 get() 持续刷新 主链路几乎不触发；空转由空批退避兜底
优先级过滤 预取不区分优先级，批量照单全收 反转窗口靠水位控制与调参收敛
统计 TaskPool.get_stats()["prefetcher"] 已注入 WorkerPool.get_stats 是 per-worker，不含预取统计

预取机制是 NeoTask 吞吐设计的核心，但它的每一分收益都对应一份代价：崩溃窗口、优先级滞后、空转查询。理解它的真实边界，比记住它的默认参数更重要——停机回队（drain_back）与空批退避已经把这部分代价收窄，剩下的要靠 prefetch_size / max_threshold 按业务取舍。
