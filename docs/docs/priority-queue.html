概述：先划清"承诺的边界"

NeoTask 的优先级保障只覆盖"提交 → 入队排序"这一段，不包含"执行时抢占"：

  • ✅ 入队排序成立：任务提交时按优先级进入有序队列，高优任务必然排在共享队列头部；

  • ❌ 没有"执行时抢占"：worker 从本地队列 FIFO 取任务，正在执行的任务不会被新到的高优任务打断（无抢占式调度）；

  • ⚠️ "同优先级 FIFO"有条件成立：内存实现靠序列号严格保证；Redis 实现只做到近似 FIFO（详见下文）；

  • ⚠️ 没有"饥饿避免/动态提权"：队列模块中不存在任何按等待时间提升优先级的逻辑。

本文对照源码逐层拆解：优先级从哪定义、队列如何排序、两种存储实现的行为差异在哪、边界处有什么坑。

四级优先级的真实定义

# 🔧 src/neotask/models/task.py
class TaskPriority(Enum):
    """Task priority enumeration."""
    CRITICAL = 0
    HIGH = 1
    NORMAL = 2
    LOW = 3

    @classmethod
    def from_value(cls, value: int) -> "TaskPriority":
        """Create from integer value."""
        for priority in cls:
            if priority.value == value:
                return priority
        return cls.NORMAL      # ← 非法值回退普通，不抛错

关键语义如下：

枚举名 数值 文档场景 排序位置
CRITICAL 0 健康检查、监控告警、故障恢复类系统任务 ZSET 最前
HIGH 1 用户触发任务：API 请求、订单、支付 次前
NORMAL 2 常规业务：数据处理、报表、消息推送 中部
LOW 3 后台维护：日志清理、数据归档 末尾

数值即分数：优先级直接作为 Redis ZSET 的 score（score = priority.value），“数字越小越靠前”。Task 实体的默认优先级是 NORMAL；任务入队时的分值由 TaskDispatcher.dispatch 统一归一化（🔧）：

# src/neotask/core/dispatcher.py
if isinstance(priority, int):
    priority_enum = TaskPriority(priority)   # ← 注意：非法 int 直接抛 ValueError
else:
    priority_enum = priority
...
priority_value = task.priority.value
if delay > 0:
    await self._queue.schedule_delayed(task.task_id, priority_value, delay)
else:
    await self._queue.push(task.task_id, priority_value)

为什么用四档离散枚举，而不是连续权重（如 1~100）？ 三点工程考量：

  1. 语义可读性：score 直接就是业务语义（0=紧急），Redis 里 ZRANGE queue:priority 0 10 排查问题时一眼可读；权重分（如 73/58）无法从分数反推业务含义；

  2. 档位即配额思想：分布式调度里，优先级本质是"相对次序"而非"绝对数值"。0~3 四档把任务分到四个"车道"，任何一档内部 FIFO。如果分数连续，业务方会倾向用"差一分"表达微妙差别，最终退化成"人人都是 99 分"，排序失去意义；

  3. 与 ZSET 升序语义天然对齐：ZRANGE 0 count-1 取最小 score 即最高优先级，无需反向索引。若采用"数字大=优先"的体系，则必须引入 ZREVRANGE/ZREVRANK，脚本与索引都要绕一层——选择与 Redis 惯例一致，少一个出错面。

两个入口的行为不一致值得注意：dispatcher.dispatch 用 TaskPriority(priority) 直接构造——传入 5 会抛 ValueError（快速失败）；而 from_value() 类方法对非法值静默回退 NORMAL（容错）。v1.0.2 中这两个入口同时存在但语义不同：submit 链路走前者（严格），from_value 尚未被主链路使用（预留的宽松解析器）。在提交层快速失败是对的：优先级写错是程序 bug，静默降级会把 bug 藏进队列里。

PriorityQueue 是门面下的核心组件（🔧 src/neotask/queue/priority_queue.py），构造时决定存储策略：

def __init__(self, repository: Optional[QueueRepository] = None, max_size: int = 10000):
    self._repository = repository
    self._heap: List[Tuple[int, float, str]] = []  # (priority, sequence, task_id)
    self._use_repository = repository is not None
    self._max_size = max_size
    self._sequence = 0          # 用于稳定排序（相同优先级时 FIFO）
    self._task_index: Dict[str, Tuple[int, float, str]] = {}  # task_id -> item

  • 无 repository（内存模式）：本地 heapq 二叉堆，单机/测试用；

  • 有 repository（Redis/SQLite 模式）：操作委托给存储层，_heap 不参与。

注意 delay > 0 的任务根本不会进 PriorityQueue（入队直接返回 False），它们由 QueueScheduler 分流到 DelayedQueue——这也是为什么 push 接口里还带一个 delay 参数（历史兼容），但真实的延迟分流发生在更上层。

内存实现：二叉堆 + 序列号 = 严格 FIFO

入队/出队（🔧）

async def push(self, task_id: str, priority: int, delay: float = 0) -> bool:
    if delay > 0:
        return False                    # 延迟任务不直接入优先级队列
    if await self.size() >= self._max_size:
        return False                    # ← 满队列返回 False（dispatcher 快速失败，见故障场景 4）
    ...
    async with self._lock:
        self._sequence += 1
        item = (priority, self._sequence, task_id)
        heapq.heappush(self._heap, item)   # O(log n)
        self._task_index[task_id] = item

async def pop(self, count: int = 1) -> List[str]:
    ...
    async with self._lock:
        result = []
        for _ in range(min(count, len(self._heap))):
            priority, seq, task_id = heapq.heappop(self._heap)  # O(log n)
            result.append(task_id)
        return result

堆元素是三元组 (priority, sequence, task_id)：

  • heapq 按元组字典序比较：先比 priority，再比 sequence；

  • _sequence 全局递增 → 同优先级任务按入队顺序出队，严格 FIFO；

  • 这就是"二叉堆 + 序列号避免同优先级乱序"的真实出处——它只在内存实现中成立。

为什么是堆而不是别的结构？

结构 入队 出队 同优先级 FIFO 其他
二叉堆 (heapq) O(log n) O(log n) 加 seq 即可 无
有序数组 O(n) O(1) ✓ 插入搬移成本高
桶队列（按优先级分 list） O(1) O(1) ✓ 只有 4 档时最简

四档优先级下"桶队列"其实更快，为什么还用堆？ 两个原因：① 内存队列可能收到任意 int 优先级（pop_with_priority、delay 通道、repository 直连），堆对任意分值健壮，桶则依赖"档位有限"这个前提；② 与 Redis ZSET 的语义对齐——堆序 = ZSET 升序，代码迁移成本低。通用性优先于微优化，这是框架代码的典型取舍。

remove：被遗忘的 O(n)

async def remove(self, task_id: str) -> bool:
    ...
    # 重建堆（延迟删除策略）
    self._heap = [item for item in self._heap if item[2] != task_id]
    heapq.heapify(self._heap)          # ← O(n)，不是 O(log n)
    del self._task_index[task_id]

注释写着"延迟删除策略"，实际是全量重建：先列表过滤再 heapify（O(n)）。对于"按 task_id 取消任务"这种低频操作（API 层 cancel 用），O(n) 可接受——框架明确用空间（_task_index）换快速存在性判断，把复杂删除留给了低频路径。

Redis 实现：ZSET 全局有序

真实数据结构

# 🔧 src/neotask/storage/redis.py
self._queue_key = "queue:priority"      # 即时任务：ZSET，score = 优先级数值
self._delayed_key = "queue:delayed"     # 延迟任务：ZSET，score = 到期时间戳
操作 命令 说明
入队 ZADD queue:priority {task_id: priority} score 直接是 0~3
出队（单） 走 Lua（见下） 不是 ZPOPMIN
窥视队首 ZRANGE queue:priority 0 count-1 peek
移除 ZREM remove

v1.0.2 的出队不使用 ZPOPMIN 命令（那是 Redis 6.2+ 的独立命令，且每次只弹一个）。真实实现是注册的 Lua 脚本，批量时一次往返完成"取+删"（🔧）：

-- redis.py _get_pop_script
local queue_key = KEYS[1]
local count = tonumber(ARGV[1])
local task_ids = redis.call('ZRANGE', queue_key, 0, count-1)
if #task_ids > 0 then
    redis.call('ZREM', queue_key, unpack(task_ids))
end
return task_ids

ZRANGE 0 count-1 按 score 升序取队首 count 个 → ZREM 移除 → 返回。整个脚本原子执行，多节点不会重复取到同一任务（无锁，但原子出队；执行期互斥靠执行前抢锁，详见去中心化与分布式锁）。

为什么 ZRANGE+ZREM 而不是 ZPOPMIN？ 兼容性与批量：ZPOPMIN 一次只弹 1 个（Redis 7 才支持 count），每弹一个都要一次 RTT；Lua 里 ZRANGE count 个 + 一次 ZREM 把"批量取+删"压成一次往返——这正是预取机制批量拉货的底层支撑。单条命令的简洁性让位于批量场景的往返次数。

同优先级 FIFO 的边界 ⚠

Redis ZSET 的排序规则：先按 score，score 相同按成员（member）字典序。score 相同的任务（同为 CRITICAL）谁先出队，取决于 task_id 的字典序——与入队顺序无关！

而 NeoTask 的 task_id 生成规则（🔧 core/lifecycle.py）：

def _generate_task_id(self) -> str:
    return f"TSK{datetime.now().strftime('%y%m%d%H%M%S%f')}{random.randint(100000, 999999)}"

TSK + 提交时间（微秒级）+ 6 位随机数——于是同分任务的字典序近似等于提交序：

提交间隔 字典序行为 FIFO 保证
> 1 微秒 时间戳前缀主导，先提交的 task_id 更小 ✅ 基本 FIFO
同一微秒内 6 位随机数定序，随机 ❌ 乱序（概率极低）
不同节点（时钟偏差） 时间戳来自各自节点时钟 ⚠️ 时钟快的节点任务"插队"

结论：Redis 模式是"近似 FIFO"，不是内存模式的"严格 FIFO"。 对顺序敏感的业务（同优先级下的流水线任务），要么业务侧自带序号校验，要么接受微秒级窗口的乱序。内存版用序列号实现严格 FIFO，Redis 版却直接拿 task_id 当序——为什么两套实现不一致？ 因为 Redis 的 ZSET 不支持"每成员独立二级序"：若要把 seq 编进 score，就得用浮点编码（如 score = priority*10^12 + seq），代价是：① score 失去可读性（不再是 0~3）；② 浮点精度有限，seq 超过 2^12 就开始丢精度；③ 每次出队后还要维护 seq 水位。框架选择了"近似 FIFO + 明确边界说明"而不是"复合 score + 复杂度"——这是典型的 80/20 取舍，但对顺序敏感的业务是必须知道的边界。

延迟任务与优先级：两条通道，一个魔法数

延迟任务涉及两条通道，优先级保留情况完全不同（这是延时与优先级联动的核心坑）：

flowchart TB
    subgraph ChannelA["通道 A：主链路 QueueScheduler（Redis 模式）"]
        A1[dispatcher.dispatch delay>0] --> A2[QueueScheduler.push<br/>delay>0]
        A2 --> A3[DelayedQueue.schedule<br/>内存定时管理]
        A3 -->|到期回调| A4[push task_id, priority<br/>score = 原优先级 ✓]
    end
    subgraph ChannelB["通道 B：repository 直连（绕过 QueueScheduler）"]
        B1[RedisQueueRepository.push<br/>delay>0] --> B2[ZADD queue:delayed<br/>score=到期时间戳]
        B2 --> B3[pop 时惰性迁移<br/>ZRANGEBYSCORE 到期]
        B3 --> B4[ZADD queue:priority<br/>score = 5 ⚠ 魔法数]
    end

  • 通道 A（主链路）：QueueScheduler.push(task_id, priority, delay) 把任务交给内存 DelayedQueue，到期回调 _on_delayed_task_ready 用原始 priority 重新入队——优先级完整保留（🔧 queue/queue_scheduler.py）。

  • 通道 B（repository 层）：RedisQueueRepository.push(delay>0) 直接写入 queue:delayed（score=到期时间戳）；下游 pop() 时惰性迁移到期任务——但迁移分数是硬编码 5（🔧 storage/redis.py）：

# 加入优先级队列（默认中等优先级）
for task_id in delayed_tasks:
    await client.zadd(self._queue_key, {task_id: 5})

score=5 意味着什么？优先级枚举只有 0~3，5 是一个不存在的"第五档"，比 LOW(3) 还低——从通道 B 迁出的延迟任务会永远排在所有即时任务之后；且代码注释写"默认中等优先级"，中等（NORMAL）应该是 2，实现却写 5，注释与代码不一致。同款魔法数还出现在 PriorityQueue.pop_with_priority 的 repository 分支（硬编码返回 (tid, 5)，🔧 queue/priority_queue.py）——"5"在 v1.0.2 中已经符号化：凡是需要"取不到真实优先级"的地方，都用 5 兜底。

这是缺陷还是设计？ 从"默认中等优先级"注释看是缺陷（数值错 + 注释不符）；但更深一层，它也暴露了真实约束：迁移时刻确实读不到原任务的优先级（queue:delayed 里只存了 task_id 与到期时间，没有 priority 字段；要恢复原优先级必须回查 task:{id} 的 JSON）。修复的正确姿势不是改 5 为 2，而是迁移时回查任务实体的 priority（📝 改进建议：pop 迁移前 GET task:{id} 拿 priority.value，或入 delayed 时把 priority 编码进 score 高位）。主链路（通道 A）不受此缺陷影响——只有绕过 QueueScheduler 直用 repository 的集成场景会踩中，集成方需自查。

预取与优先级：批量拉取如何影响公平性

预取机制把"全局 ZSET 有序"打散成"各节点本地 FIFO 队列"，对优先级的影响链条（详见预取机制一文，此处只给结论）：

  1. 共享队列内部永远有序：新提交的 CRITICAL 任务 score=0，任何节点下一轮 pop 都会先取到它——不会被埋在共享队列；

  2. 反转窗口在节点本地：某节点已预取 60 个 LOW 任务后，新到的 CRITICAL 只能等别的节点来取，或等本节点在途任务排空。等待上界 ≈ 在途量 × 平均执行时长；

  3. 预取不做按优先级裁剪：PrefetchConfig 里没有优先级过滤字段，预取器按共享队列的全局顺序批量拉货、不区分优先级——唯一的调节杠杆是 prefetch_size（批量大小）与 max_threshold（本地队列水位），把在途量压小即可缩短反转窗口；

  4. HYBRID 高水位让位：本地队列 ≥ 3×prefetch_size 时节点停止预取，把全局头部让给有空的节点——这是唯一结构性的"防囤积"机制；

  5. 停机回灌不丢优先级：优雅停机时 WorkerPool.stop() 会调用 prefetcher.drain_back(priority_resolver)，把本地队列里尚未消费的任务按存储中的真实优先级放回共享队列，避免残留任务变成孤儿或被降级。

结论：NeoTask 的优先级是"全局队列级"的（谁先被取走），不是"节点执行级"的（谁先被执行完）。高优任务的最坏延迟由"其他节点在途低优任务量"决定，需要硬优先级保证的场景，请用独立 TaskPool 隔离，而不是依赖队列排序。

优先级反转与饥饿：真实的边界与不存在的机制

优先级反转：哪些成立、哪些不成立

经典"优先级反转"（低优持锁阻塞高优）需要资源锁竞争 + 优先级抢占两个前提。NeoTask 的任务模型里：

  • 任务之间没有资源依赖声明（编排层 v1.5 才规划），不存在"任务 A 等任务 B 释放锁"的调度层模型；

  • worker 是非抢占式的：正在执行的任务不会被高优任务打断，锁（lock:task:{id}）只互斥"同一任务被两个节点执行"，与优先级无关。

因此"数据库锁导致订单任务等库存任务"这种 OS 教科书例子不适用于 NeoTask 的调度语义——那属于业务层资源竞争，应由业务数据库的行锁/队列去解决，调度器管不到也不该管。

NeoTask 的真实优先级风险只有两类：

  1. 队列饥饿：低优任务洪峰期间，高优任务虽有绝对优先权（score 最小），但 CRITICAL 提交流量本身过大时，HIGH/NORMAL 会持续让位——这是正确行为（高优就该先走），真正需要观察的是低优任务的最长等待；

  2. 本地队列滞留：预取批量把低优任务锁进节点缓冲后，全局对高优任务的响应依赖"有空的节点"，多节点全部满载时高优也会等。

饥饿避免：NeoTask 不做动态提权

NeoTask 没有 aging/动态提权逻辑：队列模块只有 push/pop/remove/peek/pause/disable，不存在任何按等待时间调整 score 的代码路径。低优任务不会因为等得久而自动升档。

为什么 NeoTask 不做优先级老化？ 分布式环境下做 aging 的代价被放大了：

  • 写放大：Redis 版要周期性扫描 ZSET 里每个低优任务、按等待时长上调 score——每次调整是一次 ZADD（O(log n)），扫描+调整会与高吞吐出队抢 Redis 带宽；

  • 全局等待时间不可得：任务在"共享队列 + 本地队列 + 执行中"三态间流转，等待时间跨节点累计，单点无法准确度量；回收器的孤儿判定依赖节点注册表——未配置节点管理器时直接跳过回收并打一次警告，配置了也只按"活跃节点集合 + 本地节点豁免"判定，并不维护每个任务的等待时长；

  • 老化会破坏语义：按等待时间提权本质是"时间换公平"，但调度器无法区分"低优任务等了 10 分钟"和"这个任务本来就该最后跑"（比如凌晨的数据归档），误提权反而挤占真正的 CRITICAL。

工程结论：NeoTask 的选择是"不做老化，用档位+容量控制饥饿"——低优任务需要严格 SLA 时，用独立 TaskPool + 定时器提交，而不是依赖优先级系统兜底。这是框架边界，不是 bug。

配置与使用建议

提交任务（真实 API 🔧）

from neotask.api import TaskPool
from neotask.models.task import TaskPriority

pool = TaskPool.redis("redis://127.0.0.1:6379")

# 推荐：枚举传参，类型可查
task_id = pool.submit(
    data={"order_id": 12345},
    priority=TaskPriority.HIGH,
)

# 兼容：int 传参（0~3，越界抛 ValueError）
task_id = pool.submit(data={"x": 1}, priority=1)

# 完整签名（🔧 api/task_pool.py）
# submit(data, task_id=None, priority=TaskPriority.NORMAL, delay=0, ttl=3600) -> str

分档建议

档位 放什么 不放什么
CRITICAL 故障恢复、配额内告警（严控流量） 高频业务——CRITICAL 洪峰会饿死其他档
HIGH 用户可感知链路：下单、支付、实时查询 批处理（会造成用户任务排队）
NORMAL 常规异步：消息推送、报表、同步 无
LOW 归档、清理、统计、预热 有时效性要求的任务

为什么 CRITICAL 要控流？ 0~3 档的排序语义下，CRITICAL 无限插队，其他三档在 CRITICAL 洪峰时集体饥饿；且同一档内部是 FIFO，CRITICAL 一多，它自己也会排队。档位不是 QOS 令牌，是相对次序——高优任务总量必须远小于系统容量。

故障场景实战

场景 1：延迟任务到期后变成"第五档"，永远垫底

现象：通过某直连 repository 的集成组件提交的延迟任务，到期后迟迟不执行；Redis 里 ZRANGE queue:priority 0 -1 WITHSCORES 能看到 score=5 的任务（正常任务 score 只有 0~3）。

根因：走了通道 B（repository 层惰性迁移），迁移代码硬编码 zadd score=5（比 LOW=3 还低）；任务实体里的 priority 字段虽然是原值，但 ZSET 排序只看 score。

排查：ZCARD queue:delayed 与 ZRANGEBYSCORE queue:delayed -inf now 找到期未迁出的任务；检查调用链是否绕过 QueueScheduler 直用 RedisQueueRepository.push(delay=...)。

解决：主链路（submit(delay=N)）无此问题，无需处理；直连 repository 的集成方应改为走 QueueScheduler.push(task_id, priority, delay)；或自行在迁移后修正 score（📝：ZADD queue:priority N task_id，N 取任务实体的 priority.value）。

场景 2：同优先级任务"乱序"被业务方投诉

现象：同一优先级大批量提交的流水线任务（如逐条状态流转），处理顺序偶尔与提交顺序不符；单机压测复现不了，多节点一上就出现。

根因：Redis 模式同分任务按 task_id 字典序出队，task_id 前缀是各节点本地时钟生成的提交时间戳——节点时钟偏差大的，后提交的任务反而 task_id 更小、先出队；同微秒内提交的任务由随机数定序。

排查：ZRANGE queue:priority 0 20 观察同分任务顺序 vs 提交日志顺序；对比节点间时钟偏差（ntpdate/w32tm）。

解决：需要严格顺序的业务——① 业务数据里带业务序号，消费端排序/校验；② 需要"同档严格 FIFO"时给提交方传单调递增的自定义 task_id（submit(task_id="TSK0000000001")，注意 task_id 需全局唯一，且要短于 64 字节、避免特殊字符）；③ 接受近似 FIFO 语义（多数场景足够）。

场景 3：提交 priority=7，任务"消失"且无任何错误日志

现象：调用方按旧版 0~10 的理解传了优先级 7，submit 调用抛 ValueError: 7 is not a valid TaskPriority——这是快速失败，任务根本没创建。但如果调用方捕获了异常继续跑，会误以为任务已提交。

根因：TaskPriority(priority) 严格枚举构造。注意与 from_value() 的区别：后者对非法值回退 NORMAL（容错），主链路用前者（严格）——行为分叉是有意的：提交时暴露错误，解析时容忍脏数据。

解决：提交层做参数校验与告警，不要吞异常；跨版本升级时先查调用的优先级数值体系是否仍是 0~3。

场景 4：队列打满 10000，提交抛 QueueFullError

现象：洪峰期大批量提交后，submit 直接抛 neotask.QueueFullError；ZCARD queue:priority 长期顶在 10000。

根因链：QueueScheduler.push/PriorityQueue.push 在 size() >= max_size 时返回 False（🔧），dispatcher.dispatch 检测到入队失败后立即把任务标记为 FAILED 并抛出 QueueFullError：

# dispatcher.py —— create_task 已先成功保存任务
task = await self._lifecycle.create_task(...)
...
queued = await self._queue.push(task.task_id, priority_value)

if not queued:
    reason = "queue is disabled" if self._queue.is_disabled else "queue is full"
    await self._lifecycle.fail_task(
        task.task_id,
        f"Failed to enqueue task: {reason}",
        allow_pending=True,
    )
    raise QueueFullError(self._queue.max_size)

也就是说，任务不会停在 PENDING：实体被回写为 FAILED（带 Failed to enqueue task 错误原因），调用方立刻收到异常。延迟任务的 schedule_delayed 走同一条失败分支，push 层返回 False 的失败也会被记录为错误日志。

排查：捕获 QueueFullError（from neotask import QueueFullError）；结合 pool.get_stats()["queue_size"] 与 ZCARD queue:priority 确认水位。

解决：提交侧捕获 QueueFullError 做退避重试或限流；持续打满说明吞吐不足，应扩容 worker 或提高 queue_max_size（📝 同时保留队列水位告警）。任务不会静默丢失，但被拒绝的任务需要调用方自行决定重提策略。

总结

主题 真实实现 边界/坑
优先级定义 TaskPriority 0~3 四档枚举 分数即 ZSET score；非法 int 提交抛错
内存队列 heapq + 全局序列号 严格同档 FIFO；remove 是 O(n) 重建
Redis 队列 ZSET + Lua ZRANGE/ZREM 出队不用 ZPOPMIN；同档仅"近似 FIFO"
同档 FIFO 内存严格 / Redis 靠 task_id 时间戳前缀 同微秒随机序、跨节点时钟漂移乱序
延迟迁移 主链路保留优先级；repository 层 score=5 "5"是魔法数，注释写"中等"实为最低档
执行抢占 不存在（worker FIFO + 非抢占） 高优最坏延迟 = 其他节点在途量×时长
饥饿避免 无 aging/动态提权代码 低优任务需严格 SLA 时用独立池隔离
队列容量 max_size=10000 满则 push False dispatcher 标记 FAILED 并抛 QueueFullError

优先级系统在 NeoTask 里的定位要准确：它保证"全局队列谁先被取"，不保证"谁先执行完"。理解这个边界后，四级枚举 + ZSET 的实现是清晰且恰当的——真正的风险从来不在排序本身，而在排序之外的接力点：延迟迁移的魔法数、队列满时的拒绝、预取缓冲的滞留。
