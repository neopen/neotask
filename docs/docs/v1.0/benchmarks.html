性能基准

基准测试环境、结果口径与解读边界。

v1.0 · NeoTask 1.0.x 更新于 2026-10-30 约 5 分钟 读完 GitHub

以下数据来自 NeoTask 1.0.5 的官方基准脚本，运行在单台开发笔记本上。它们用于判断相对趋势与配置影响，不构成性能承诺。

测试环境

项目配置
CPUIntel Core i7-1165G7，4 核 8 线程
内存15.8 GiB
系统Windows 10 19045，64 位
Python3.13.15
存储memory（主套件）；SQLite（边界探针）
旁路组件metrics、health check、reporter、reclaimer、heartbeat、dead letter、retry 全部关闭

口径

指标定义
提交吞吐第一个 submit_async 到第 N 个返回
完成吞吐第一个 submit_async 到第 N 个 task.completed 事件
任务延迟单任务提交前到该任务完成事件
等待吞吐N 个并发 wait_for_result_async 全部返回的速率

每个场景独立创建 TaskPool，预热 10 个任务；主套件重复 2–3 轮取中位数。提交吞吐与完成吞吐分母不同，不能直接比较。

任务体为 asyncio.sleep(0.020)，N=400。

IO 任务随 Worker 数接近线性扩展。1 worker 的绝对值受 Windows 定时器粒度影响（20 ms 的 sleep 实际约 31 ms），扩展效率比绝对值更有参考意义。

SQLite 边界

noop 任务，每次重建数据库。

模式Workers结果
串行提交 100 条130.1 tasks/s，P50 31.31 ms，P95 66.34 ms，全部成功
突发提交 100 条125.5 tasks/s，全部成功
突发提交 100 条2第 37 次起 database is locked
突发提交 100 条4第 36 次起 database is locked

SQLite 适合低频、单写入者场景。高并发或分布式请使用 Redis。

预取的配置影响

极短任务（数十微秒）下，默认预取按约 0.1 秒一批补充，可能把完成吞吐限制在约 200 tasks/s；关闭预取后官方实测恢复到约 2,382 tasks/s。任务较长时预取通常有利。

不要直接引用绝对值做容量规划。操作系统、Python 版本、CPU、存储后端和旁路组件都会显著影响结果。请在自己的目标环境用相同口径复测。

复现

git clone https://github.com/neopen/neotask.git
cd neotask
pip install -e ".[dev]"
python tests/benchmark/run_benchmark.py

基准脚本位于仓库 tests/benchmark/，不属于 PyPI 包内容。主套件约需 2 分钟，SQLite 探针另需约 2 分钟。

解读边界

  • 所有数据来自单机笔记本，不能外推到服务器或容器环境。
  • 主套件使用 memory 后端，SQLite 数据单独测量，两者不可混用。
  • 旁路组件全部关闭，开启 metrics、health check、reclaimer 后吞吐会下降。
  • 延迟分位数来自单次场景，不代表长期稳定性；持续负载与突发负载应分开评估。
  • 版本间口径可能变化，1.0.5 之前的历史数字不应直接比较。
