可靠性

断点续跑

保存任务中间状态，并在自动重试、手动重试或显式提交时从最近 checkpoint 恢复。

v1.0 · NeoTask 1.x 更新于 2026-11-22 约 7 分钟 读完 GitHub

1.1 起 NeoTask 支持断点续跑：任务在执行过程中把中间状态写入 checkpoint 仓储，任务被重试或重新提交时，最近一次状态会注入 data["__checkpoint__"]，业务代码不必从头开始。它适合分页导入、批量处理、长链路调用等可以按进度切分的任务。

启用与配置

from neotask import TaskPool, TaskPoolConfig

config = TaskPoolConfig(
    enable_checkpoint=True,        # 默认开启
    checkpoint_keep_versions=5,    # 每个任务保留最近 5 个版本
)
pool = TaskPool(executor=handle, config=config)
字段默认值说明
enable_checkpointTrue关闭后不创建 checkpoint 仓储；save_checkpoint() 返回 0 / False，不抛异常
checkpoint_keep_versions5单个任务保留的版本数；每次保存后裁剪更旧的版本，0 表示不保留

SchedulerConfig 提供同名字段，并传递给内部 TaskPool。三种存储后端都实现了 checkpoint 仓储：memory 保存在进程内，SQLite 写入 task_checkpoints 表，Redis 写入 neotask:ckpt:{task_id} 哈希。

保存与读取

执行器内部使用模块级函数，按执行器类型选择异步或同步版本：

from neotask import load_checkpoint, save_checkpoint
from neotask import load_checkpoint_sync, save_checkpoint_sync

async def async_job(data):
    state = await load_checkpoint() or {"cursor": 0}
    for index in range(state["cursor"], data["total"]):
        await handle_row(index)
        if index % 100 == 0:
            await save_checkpoint({"cursor": index + 1})
    return {"rows": data["total"]}

def thread_job(data):
    state = load_checkpoint_sync() or {"cursor": 0}
    for index in range(state["cursor"], data["total"]):
        handle_row(index)
        if index % 100 == 0:
            save_checkpoint_sync({"cursor": index + 1})
    return {"rows": data["total"]}

拿不到执行上下文时（进程执行器的父进程、外部调度组件），使用任务级 API：

version = pool.save_checkpoint(task_id, {"cursor": 42})
state = pool.load_checkpoint(task_id)
调用位置方法返回值
异步执行器await save_checkpoint(state) / await load_checkpoint()bool / dict | None
线程执行器save_checkpoint_sync(state, timeout=5.0) / load_checkpoint_sync(timeout=5.0)bool / dict | None
进程执行器父进程 / 外部调用pool.save_checkpoint(task_id, state) / pool.load_checkpoint(task_id)新版本号，失败为 0 / dict | None
返回 False 的含义：执行器内的函数在任务上下文外被调用、任务已结束或 checkpoint 未启用时返回 False / None，不抛异常。业务代码应把保存失败视为“这次没有进度可续”，而不是任务失败。

三种恢复路径

路径触发方式行为
自动重试执行抛异常且 retry_count < max_retries写回最近 checkpoint 到 task.data，按 retry_delay × n 重新入队
手动重试pool.retry(task_id)终态任务重置为 pending，注入最近 checkpoint 后重新入队；retry_count 保留
显式提交submit(data, task_id="job-1", resume_from_checkpoint=True)先创建任务记录并注入 checkpoint，再入队，避免 Worker 抢先执行

显式提交必须同时提供 task_id，否则 resume_from_checkpoint 不生效，任务按普通提交执行。没有找到 checkpoint 时也不会报错，任务使用原始 data 运行。

同一个 task_id 不能重复提交：只要任务记录仍存在（包括已经成功或失败），submit() 都会抛 TaskAlreadyExistsError。要复用已有记录从断点继续，应调用 retry(task_id)；只有记录被删除、或在另一个进程中首次创建时，才使用 resume_from_checkpoint=True 的提交方式。

版本、事件与查询

每次保存都会生成递增版本号，并把任务记录的 checkpoint_version 更新为新版本。超过 checkpoint_keep_versions 的旧版本会被裁剪；恢复时总是读取最新版本。

task = pool.get_task(task_id)
print(task["checkpoint_version"])

async def on_checkpointed(event):
    print(event.task_id, event.data)   # {"version": 3}

pool.event_bus.subscribe("task.checkpointed", on_checkpointed)

1.1 新增 task.checkpointed 事件，event.data 形如 {"version": 3}。它没有 on_checkpointed() 便捷方法，通过 event_bus.subscribe() 订阅。

生命周期与清理

  • 删除任务（delete()）会同时删除该任务的 checkpoint。
  • 终态清理删除过期任务记录时，一并删除对应 checkpoint；需要跨清理周期恢复时，先调大 terminal_retention_seconds。
  • memory 后端的 checkpoint 随进程退出丢失；SQLite 与 Redis 的 checkpoint 跨重启保留。
  • Redis 模式下 checkpoint 由所有节点共享，任务被其他节点接管后仍能读取最近版本。

边界

  • state 必须可 JSON 序列化，保存的是完整快照而不是增量日志。状态应保持精简，避免把大结果反复写入存储。
  • checkpoint 不是事务。保存成功代表业务进度已落库，保存之后、下一次保存之前的工作在恢复时仍会重复执行，因此每个步骤仍需幂等。
  • 保留键 __checkpoint__ 会覆盖 data 中的同名业务字段，业务数据不要使用该键。
  • 业务失败（report_failure）不会触发自动重试，因此不会自动续跑；需要续跑时显式调用 retry()。
