开发者指南

项目结构、开发环境、测试、构建、发布与贡献规范。

v1.0 · NeoTask 1.x 更新于 2026-11-22 约 8 分钟 读完 GitHub

这一章面向想阅读源码、提交补丁或发布版本的开发者。NeoTask 使用 src 布局、无运行时框架依赖，测试与发布流程都在仓库内完成。

项目结构

neotask/
├── src/neotask/
│   ├── api/            # TaskPool、TaskScheduler（公共入口）
│   ├── core/           # 生命周期、分发、进度、成本、断点、上下文
│   ├── queue/          # 优先级队列、延时队列、队列调度、死信
│   ├── worker/         # Worker 池、预取器、回收器
│   ├── storage/        # Memory / SQLite / Redis 仓储实现
│   ├── executor/       # 异步 / 线程 / 进程执行器
│   ├── lock/           # 内存锁、Redis 锁、看门狗
│   ├── distributed/    # 节点、协调器、分片
│   ├── event/          # 事件总线与中间件
│   ├── monitor/        # 指标、健康检查、报告器
│   ├── models/         # Task、配置、周期任务模型
│   ├── cli/            # neotask 命令行入口
│   └── common/         # 异常、常量、日志
├── tests/              # unit / integration / distributed / chaos / benchmark
├── benchmarks/         # 压测脚本与结果
├── examples/           # 可运行示例
├── scripts/            # 迁移与维护脚本
├── pyproject.toml
└── CONTRIBUTING.md

数据流：TaskPool → TaskDispatcher → QueueScheduler → WorkerPool → TaskExecutor，生命周期事件经 EventBus 广播，状态与结果写入仓储。

开发环境

git clone https://github.com/neopen/neotask.git
cd neotask
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
工具用途
pytest + pytest-asyncio单元与集成测试
ruffLint 与格式化
mypy类型检查
pre-commit提交前自动检查
build / twine构建与发布

最低 Python 为 3.8，CI 覆盖 3.8 / 3.10 / 3.12。本地开发建议使用 3.10 以上，便于获得更完整的类型提示。

本地开发

  • 以可编辑模式安装（-e），修改源码后无需重新安装。
  • 新增示例放在 examples/，命名与现有文件保持序号前缀。
  • 运行单个示例验证行为：python examples/01_simple.py。
  • 涉及 Redis 的改动需要本地 Redis，或使用容器启动一个临时实例。
  • 日志级别可通过 NEOTASK_LOG_LEVEL 之类的应用侧变量控制（NeoTask 不强制读取环境变量）。

提交前建议先跑一个最小回归：

pytest tests/unit -q
ruff check src tests

测试

# 全量
pytest tests/

# 按层次
pytest tests/unit/ -v
pytest tests/integration/ -v
pytest tests/distributed/ -v

# 单个文件
pytest tests/unit/test_task.py -v

# 覆盖率
pytest --cov=src/neotask tests/

# 超时保护（慢用例）
pytest tests/ -q --timeout=60

测试目录说明：

目录内容
tests/unit模型、队列、解析器、配置等纯逻辑
tests/integration池、调度器、存储与事件的端到端组合
tests/distributedRedis 队列、锁、节点与回收
tests/chaos故障注入与恢复
tests/benchmark性能回归与基准脚本

当前仓库约有 500+ 个单元测试；1.2.1 的完整回归结果见 性能基准 · 测量环境。新增行为应同时补充单元测试与至少一个集成用例。

构建

python -m build
# 产物：dist/neotask-X.Y.Z-py3-none-any.whl 与 .tar.gz

# 本地安装验证
pip install dist/neotask-*.whl
python -c "import neotask; print(neotask.__version__)"

构建使用 setuptools，包数据与入口点定义在 pyproject.toml。构建后建议在干净虚拟环境中验证：导入、neotask --version、neotask --benchmark --tasks 50。

发布

维护者使用 release-please + GitHub Actions 发布：

  1. 向 main 合并符合 Conventional Commits 的提交（fix: → PATCH，feat: → MINOR，feat! / BREAKING CHANGE → MAJOR）。
  2. 机器人创建 Release PR，自动更新 pyproject.toml、__init__.py、CHANGELOG.md 与 manifest。
  3. 合并后打 vX.Y.Z 标签并创建 GitHub Release。
  4. publish-pypi 工作流构建并上传 PyPI。

紧急情况下可手动构建并 twine upload dist/*。无论哪种方式，发布后都要验证 PyPI 页面、安装命令与版本号一致。

贡献代码

  1. 先搜索 Issue，避免重复；较大的特性先开 Issue 对齐设计与边界。
  2. 从 main 拉分支，命名如 feat/checkpoint-resume。
  3. 保持改动聚焦：一个 PR 只解决一件事，避免顺手重构。
  4. 补充测试与文档；公共 API 变化需更新 CHANGELOG.md 与文档。
  5. 提交信息使用 Conventional Commits，说明「为什么」而不只是「改了什么」。
  6. 发起 PR，填写复现步骤、验证方式与兼容性影响。

不要在 PR 中提交本地数据文件、日志、虚拟环境或密钥。涉及 Redis / SQLite 行为变化时，请说明测试使用的后端与版本。

代码规范

  • 遵循 PEP 8；模块 snake_case，类 PascalCase，函数与变量 snake_case，常量 UPPER_SNAKE。
  • 公共 API 必须有类型注解与简短 docstring；Args / Returns / Raises 按现有风格书写。
  • 私有成员使用前导下划线；内部实现不要从包入口导出。
  • 异步代码不要在执行器内做阻塞调用；阻塞库交给线程或进程执行器。
  • 日志使用项目统一的 logger，不要直接 print。
  • 异常使用 common/exceptions.py 中的类型，避免抛裸 Exception。
ruff check src tests
ruff format src tests
mypy src/neotask/
pre-commit run --all-files

格式化与 lint 通过是合并前提；类型检查允许存量模块逐步收敛，但新增公共接口不应引入新的 mypy 错误。

相关：贡献流程的完整版本见仓库 CONTRIBUTING.md；安全问题请遵循下方安全策略，不要公开提交漏洞细节。

安全策略

安全更新仅覆盖最新 1.x 稳定版本。发现漏洞时请不要公开提交 Issue，按以下方式私下披露：

  1. 通过 GitHub Security Advisory 提交，或发送邮件至 helpenx@gmail.com。
  2. 提供受影响版本、复现步骤、影响范围与可能的 PoC。
  3. 维护者在 48 小时内确认，7 天内完成评估；修复时间按严重程度为 7–30 天。
  4. 修复发布后更新更新日志，并在获得同意后致谢报告者。
等级示例目标修复窗口
严重远程代码执行、未授权访问、数据泄露7 天内
高权限提升、敏感信息泄露、拒绝服务14 天内
中信息泄露、安全功能绕过21 天内
低需要特定条件才能利用的问题30 天内

部署侧的安全建议见 部署指南 · 安全部署。
