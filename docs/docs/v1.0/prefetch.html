预取机制

批量预取的触发条件、阈值配置与对延迟和优先级的影响。

v1.0 · NeoTask 1.0.x 更新于 2026-10-30 约 5 分钟 读完 GitHub

预取器把共享队列中的任务批量搬到每个 Worker 的本地队列，减少对 Redis 或存储层的出队请求。默认开启。

配置

from neotask import TaskPool, TaskPoolConfig

config = TaskPoolConfig(
    prefetch_size=20,        # 每次预取数量
    enable_prefetch=True,
)
pool = TaskPool(executor=handle, config=config)

其余参数由 prefetch_size 推导，不能通过 TaskPoolConfig 单独设置：

参数推导规则（默认 prefetch_size=20）
本地队列容量prefetch_size × 5 = 100
触发下限max(1, prefetch_size // 4) = 5
停止上限prefetch_size × 3 = 60
预取检查间隔0.1 秒
空闲超时5 秒无消费后暂停预取
空预取退避0.1 秒起指数增长，上限 0.5 秒

触发逻辑

默认使用 HYBRID 策略：

  • 本地队列低于下限（5）时立即预取；
  • 低于上限（60）且最近 5 个批次的平均消费量超过 prefetch_size × 0.5 时也会预取；
  • 本地队列达到上限后延长检查间隔，避免空转；
  • 连续空预取时按指数退避，最高 0.5 秒，与 Worker 空转退避对齐。

一次预取

  1. 计算本地队列剩余容量。
  2. 从共享队列批量弹出最多 prefetch_size 个任务。
  3. 放入本地队列；容量不足时停止放入。
  4. Worker 从本地队列取任务执行。

对优先级的影响

预取按批出队，跨优先级的严格顺序只在每批出队时成立。本地队列中已存在的低优先级任务，可能先于共享队列中新到达的高优先级任务执行。

需求配置
严格优先级顺序enable_prefetch=False
降低顺序影响减小 prefetch_size，例如 1–5
高吞吐、任务较长增大 prefetch_size，例如 50–100

吞吐影响

预取优化的是队列争用，不是极短任务的吞吐。预取补充节奏约为每 0.1 秒一批；当任务本身只有几十微秒时，默认 20 个/批会成为瓶颈。官方基准中，极短任务关闭预取后的完成吞吐明显高于默认预取配置。

是否启用应基于任务耗时判断：毫秒级以上任务通常受益；微秒级任务建议先关闭预取做对照测试。数据口径见 性能基准。

统计

stats = pool.get_stats()
print(stats.get("prefetcher"))
# total_prefetch / total_fetched / total_errors
# avg_batch_size / avg_latency_ms / p95_latency_ms

仅在预取启用时返回 prefetcher 字段。预取器统计不包含 Worker 实际执行时间。

关闭与停机

  • enable_prefetch=False 后 Worker 直接从共享队列出队。
  • 优雅停机时，预取器先等待本地队列被消费；超时后把剩余任务放回共享队列，避免任务变成孤儿。
  • 强制终止会丢失本地队列中已出队但未执行的任务，只能等待回收器按 ttl 兜底。
