v1.0 的能力边界，以及 v1.5、v2.0 的规划项。

v1.0 · NeoTask 1.0.x 更新于 2026-10-30 约 5 分钟 读完 GitHub

本页区分“1.0 已交付”与“后续规划”。规划项来自仓库公开路线图，尚未实现，接口与行为以最终发布为准。

1.0 能力边界

能力状态说明
即时任务、批量提交已支持TaskPool
四级优先级已支持数值越小越优先
延时、固定间隔、Cron已支持TaskScheduler
Memory / SQLite / Redis已支持Redis 支持多节点共享队列
自动重试、超时、进度已支持重试为线性延迟
节点心跳、任务回收、死信已支持（Redis）死信无公开查询 API
DAG 工作流未支持规划于 v1.5
多租户隔离未支持规划于 v2.0
独立 Web UI / CLI未提供仓库有 Web 代码，但未接入公开入口

1.0 上的替代方案

规划中的能力在 1.0 上通常可以用业务代码组合现有原语实现，但状态与失败处理需要自行承担。

需求1.0 做法需要自行处理
串联多个任务在任务完成事件或 wait_for_result() 返回后提交下一步失败传播、超时、重复提交与断点恢复
条件分支任务返回结构化结果，由业务层决定提交哪个后续任务分支状态记录与失败补偿
并行子任务submit_batch() + wait_all()部分失败时的清理与重试策略
定时编排用 TaskScheduler 分别定义周期任务多实例重复触发；同一周期定义只应有一个调度者
多租户每个租户使用独立 TaskPool 与存储（独立 SQLite 文件或 Redis 库）资源配额、统一鉴权与跨租户统计
可视化管理基于 get_stats()、get_task() 与事件自行构建Web UI 与 CLI 尚未接入公开入口

v1.5：任务编排

  • DAG 工作流定义与提交；
  • 节点依赖、条件分支与并行执行；
  • 工作流级状态查询与失败重跑。

规划中的工作流引擎只负责拓扑推进与节流，节点执行仍复用 TaskPool。当前版本没有 workflow 模块，不应在 1.0 上使用相关接口。

v2.0：企业级特性

  • 独立 Web UI；
  • 多租户隔离；
  • 更完整的 Prometheus 集成。

1.0 已提供 MetricsCollector 与 Pushgateway 上报器，但没有内置 HTTP 指标端点；v2.0 的集成范围以发布说明为准。

升级准备

  • 保持任务幂等：后续的工作流重跑、故障恢复和人工重试都会再次执行任务。
  • 只依赖公开 API：不要直接读写 Redis 键或调用内部模块，存储结构可能随版本变化。
  • 记录当前配置：升级前保存 TaskPoolConfig 与 SchedulerConfig，发布后逐项对照新版配置参考。
  • 不要把规划项写进生产依赖，也不要在 1.0 上导入尚不存在的 workflow 模块。

版本与文档路径

库版本文档路径说明
1.0.x/docs/v1.0/当前版本；补丁版本共享此路径
后续 1.x/docs/v1.x/发布时新增，旧路径继续保留

文档按次版本线固定路径，补丁版本不会改变链接；升级后请切换到目标版本文档阅读配置与 API 变化。

版本策略：文档按版本发布，1.0 文档只描述 1.0.x 的行为。后续版本文档会以新路径提供，旧版本链接保持可访问。
