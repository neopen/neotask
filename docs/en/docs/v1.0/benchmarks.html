Benchmarks

v1.2.1 measurements for submission, completion, prefetch, batching, and SQLite boundaries.

v1.0 · NeoTask 1.x Updated 2026-11-22 9 min read GitHub

The figures below were measured with the official NeoTask 1.2.1 benchmark scripts and stress suite. They are meant to show relative trends and the effect of configuration, not to serve as a performance promise. Numbers vary with CPU, Python version, storage backend and sidecar components, so re-measure with the same method on your own target environment.

Version scope: the data on this page was collected on 1.2.1 (2026-11-22), running on Python 3.13. 1.2.1 fixed prefetch empty-queue backoff, in-memory queue batch write/remove, blocking metric sampling and Redis batch reads, so the throughput and latency figures are not directly comparable with 1.0.x. After upgrading, re-measure in your target environment with neotask --benchmark or the repository benchmark scripts.

The micro-benchmarks, the prefetch suite and the cross-storage comparison are three independent measurements taken with different methods; they cannot be merged or compared directly. All numbers come from a single developer machine, with sidecar components disabled per suite.

Measurement method

MetricDefinition
Completion throughput2,000 noop tasks at concurrency 10, from submission until all complete; one run with prefetch on and one with prefetch off
Sparse task latencySubmit a single task after 1 idle second, 8 times in a row, recording end-to-end latency
Queue micro-benchmarkBatch write, batch remove, peek and invariant validation on the in-memory priority queue
Cross-storage end to endOne submission-to-completion run each on Memory / SQLite / Redis; scale and concurrency are given in the table

The prefetch core benchmark (throughput) and sparse latency (single-task response) measure opposite goals: prefetch trades batch dequeue for throughput, at the cost of the fixed latency introduced by the coalescing window. Confirm the method and configuration before comparing.

Two sides of prefetch: under the same parameters, completion throughput with prefetch on is 4,241 tasks/s and 3,156 tasks/s with prefetch off; but the latency of a single task after idle rises from 1.1–2.2 ms to 12.2–26.2 ms. 1.2.1 fixed exponential backoff on empty queues, so sparse tasks no longer see worst-case 500 ms latency, but the 10 ms prefetch coalescing window still applies.

Batch write and removal on the in-memory queue have moved from full heap rebuilds to incremental maintenance with lazy tombstones: writing 1,000 tasks at once into a 10,000-task queue takes about 0.471 ms (about 2.12M tasks/s), and batch removal of 1,000 tasks takes about 0.668 ms. The invariant test that pops everything and validates it confirms there are no duplicates and no tombstone leaks; peek(5) on a 10,000-task queue takes 0.008 ms. The complete 1.2.1 regression is 538 passed / 12 skipped unit tests and 87 passed / 1 skipped integration tests.

Prefetch and completion throughput

2,000 noop tasks with 10 workers, comparing prefetch off against prefetch_size=20. Prefetch moves tasks from the shared queue to local queues in batches, raising throughput by about 34%, but single-task P50 rises from 1.20 ms to 11.24 ms.

ConfigCompletionP50P95
Prefetch off3,156/s1.20 ms3.07 ms
Prefetch 204,241/s11.24 ms15.14 ms

The throughput bottleneck lies in lifecycle transitions, state persistence and event dispatch, not in the executor itself; simply adding workers cannot break through this ceiling. When task bodies have IO waits or run for longer, the batch gain from prefetch is more obvious; for pure micro-tasks that demand low latency, turning prefetch off is the better fit.

Sparse task latency

Submit a single task after 1 idle second to simulate a low-frequency event trigger. With prefetch off, end-to-end latency is 1.1–2.2 ms; with prefetch on it is 12.2–26.2 ms, mostly from the prefetcher's coalescing window.

Latency-sensitive scenarios (such as a background action triggered by an interactive request) should disable prefetch or reduce prefetch_size; batch, collection and transcoding tasks can keep the default prefetch. See Prefetch mechanism for the trade-off between the two.

Sustained and burst load

Covers four boundary categories: sparse submission, prefetch empty-queue wakeup, batch cancellation and a full queue. The empty-queue backoff fix and lazy tombstones are the main changes in this 1.2.1 round.

Regression: 538 unit tests passed / 12 skipped; 87 integration tests passed / 1 skipped. One timing-sensitive test is flaky under full concurrency and passes alone. Empty-queue wakeup no longer stacks a 0.5 s backoff, which is the direct cause of sparse task latency dropping from hundreds of milliseconds to the millisecond range; when the queue is full, all three backends return False or QueueFullError, with consistent semantics.

Memory uses an in-process queue at 4,761 tasks/s; SQLite is constrained by serial single-file writes at 519 tasks/s; Redis is affected by network round trips and serialization at 232 tasks/s. SQLite suits single-machine persistence and low-frequency writes; switch to Redis when you need multi-node sharing or higher concurrency. Always validate in a staging environment before migrating between backends, and note the acceptable loss window for tasks and events.

Event bus and wakeup

The event bus delivers lifecycle events to subscribers asynchronously. Since 1.2, events with no subscribers are no longer enqueued, reducing idle work; when a bounded queue is full, new events are dropped and counted, and callbacks slower than the threshold log a warning.

CapabilityConfigBehavior
Unsubscribed eventssince v1.2not enqueued, less idle work
Bounded queueevent_queue_max_sizedrops new events and counts when full
Slow handler warningevent_slow_handler_threshold=1.0swarns without blocking tasks
Periodic snapshoton_metrics(interval=1.0)counts and queue depth without loading tasks
Terminal cleanupenabled by defaultremoves SUCCESS/FAILED/CANCELLED by ttl

When complete auditing is required, keep the event queue unbounded and move time-consuming callbacks out of the event loop; in production, set event_queue_max_size and monitor dropped_events. For periodic monitoring, prefer pushing snapshots with on_metrics() instead of subscribing to events for each metric separately.

Reproducing the numbers

# Quick self-test with the built-in 5 ms executor
neotask --benchmark

# Use your own executor
neotask --benchmark --executor my_tasks:handle --tasks 2000 --json

# Full benchmark suite in the repository
git clone https://github.com/neopen/neotask.git
cd neotask
pip install -e ".[dev]"
python tests/benchmark/run_benchmark.py

neotask --benchmark ships with the PyPI package and defaults to 200 tasks at concurrency 10, which suits quick comparison; the full benchmark scripts live in the repository under tests/benchmark/, and the 1.2.1 regression and suite results come from the same environment. When re-measuring, record the CPU, Python version, storage backend and worker count, otherwise the results are not comparable.

Interpretation boundaries

  • The data comes from a single developer laptop (4 cores / 8 threads, 16 GB, Windows 10, Python 3.13) and does not extrapolate to servers or container environments.
  • Throughput, sparse latency and the cross-storage comparison use different methods; the three sets of numbers must not be mixed.
  • Sidecar components (metrics, health check, reporter, reclaimer, heartbeat, dead letter) are disabled per suite; enabling them lowers throughput.
  • 1.2.1 fixed empty-queue exponential backoff and in-memory queue batch write/remove, so sparse task latency and batch-operation numbers are not directly comparable with 1.0.x; historical figures serve only as a trend reference.
  • Latency percentiles come from a single-run scenario and do not represent long-term stability; evaluate sustained and burst load separately.
Do not quote absolute values directly for capacity planning. Re-measure on your own target environment with the same scripts and the same method, and factor the real duration distribution of your business tasks into the evaluation.
