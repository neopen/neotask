Best practices

Executor choice, concurrency, retries, timeouts, storage selection, and production guidance.

v1.0 · NeoTask 1.x Updated 2026-11-22 8 min read GitHub

The guidance below comes from the actual behavioral constraints of the 1.x series, not from a generic best-practice checklist. Each item maps to a concrete limitation.

Production configuration template

This is a starting point for a multi-node Redis deployment, not a universal answer for every scenario. Each instance must use a unique node_id. The TaskPoolConfig.redis() factory sets lock_type to redis automatically; this example constructs the config directly, so it must be set explicitly.

from neotask import TaskPool, TaskPoolConfig

config = TaskPoolConfig(
    storage_type="redis",
    redis_url="redis://10.0.0.10:6379/0",
    node_id="worker-1",          # must be unique per instance
    worker_concurrency=16,
    task_timeout=60,             # upper bound for a single execution
    max_retries=3,
    retry_delay=2.0,
    lock_type="redis",           # direct construction defaults to memory; the redis() factory sets it for you
    enable_prefetch=True,
    prefetch_size=20,
    enable_metrics=True,
)
pool = TaskPool(executor=handle, config=config)

Long-running tasks also need a larger task-level ttl, otherwise the reclaimer treats them as timed out after the default 3600 seconds. For periodic tasks, also make sure only one scheduler instance is active; see Delayed and periodic tasks.

Executors

  • Stay idempotent. A task may run again after a retry, a timeout reclamation or a node crash, so your business logic must tolerate repeated processing.
  • Inputs and outputs must be serializable. Task data and return values are both written to storage; the return value must be JSON-serializable, so do not return connections, file handles or custom objects.
  • Keep payloads small. Task data is stored with every record and travels with events; large objects amplify storage and network overhead.
  • Use a thread executor for blocking synchronous code. A plain sync function still runs on the event loop thread and blocks other tasks.
  • Use a process executor for CPU-bound work. The function must be picklable; progress reporting is not available in a process executor.
  • Save checkpoints for long tasks. Both automatic and manual retries inject the latest state; work between checkpoints is still repeated, so business steps must be idempotent. With a process executor, the parent process calls pool.save_checkpoint().
  • Reject work with report_failure(). Deterministic outcomes such as failed data validation or a rejected review end the task immediately; do not use exceptions to trigger pointless retries.

Concurrency and timeouts

  • worker_concurrency is the number of tasks executing at once, not the number of threads. Raise it for IO-bound tasks; do not exceed the available core count by much for CPU-bound tasks.
  • task_timeout bounds a single execution; when it expires the task is treated as failed and enters the retry flow. If the executor cannot be cancelled (for example, a blocking thread), the timeout only stops waiting and does not guarantee that the underlying call has ended.
  • ttl is a task-level parameter, 3600 seconds by default. In Redis mode the reclaimer uses ttl to decide whether a RUNNING task has timed out, so long tasks need an explicitly larger ttl.

Retries

  • Automatic retries are suitable for transient failures only. Deterministic outcomes such as invalid parameters or failed validation should be ended with report_failure() rather than left to retries.
  • Use report_failure() when a business rule rejects a task: the task goes straight to failed, records a failure_reason, consumes no retry budget and writes nothing to the dead-letter queue.
  • Retries read the latest checkpoint; if a task must start from scratch, do not save checkpoints, or delete the task record and recreate it.
  • The delay of the n-th retry is retry_delay × n, not exponential backoff.
  • Manual retry() accepts terminal tasks only; retry_count is preserved and the automatic retry budget is not reset.

Prefetch

  • Prefetch trades batch dequeue for throughput: in the 1.2.1 benchmark prefetch_size=20 completes 4,241 tasks/s versus 3,156 tasks/s with prefetch disabled; the cost is that sparse-task latency rises from 1.1–2.2 ms to 12.2–26.2 ms.
  • Disable prefetch, or lower prefetch_size below 5, for low-latency, interactive or sparse submission scenarios.
  • Prefetch dequeues several tasks at once, so strict ordering across priorities no longer holds; disable prefetch when order matters.
  • To tune prefetch, change prefetch_size first: both the local queue capacity and the trigger threshold are derived from it; since 1.2.1 an empty queue no longer accrues exponential backoff, so sparse tasks are not pushed into the hundreds of milliseconds by prefetch.

Event bus

  • Subscribers must return quickly. The EventBus dispatches asynchronously in a dedicated task, so a slow subscriber delays later events but does not block worker execution.
  • The default event queue is unbounded (event_queue_max_size=None). Processes with heavy event volume should set a limit; when the queue is full, new events are dropped and counted according to event_overflow_policy="drop".
  • Use pool.event_bus.get_stats() to watch queue_size, dropped_events and slow_handler_calls. Events are notifications only; storage is the source of truth for task state.

Terminal cleanup

  • By default 1.0.8 cleans up successful, failed and cancelled tasks past their retention period every 60 seconds. The retention period comes from terminal_retention_seconds; when it is 0, the task ttl applies (3600 seconds by default).
  • If you need to query task results afterwards or keep an audit trail, raise terminal_retention_seconds rather than disabling cleanup and retaining everything indefinitely.
  • Cleanup applies to terminal records only; it does not touch pending / running tasks and is not failure reclamation.

Shutdown and reclamation

  • Use shutdown(graceful=True) when a service exits so queued tasks finish; set a reasonable timeout to avoid waiting indefinitely.
  • Periodic tasks survive a restart only with SQLite / Redis and enable_persistence=True; memory mode emits one warning.
  • In Redis mode node IDs must be unique, otherwise heartbeats and orphan reclamation interfere with each other.

Observability

  • Use get_metrics() or on_metrics(callback, interval) from 1.2 for high-frequency probes and periodic reporting: they read counters and aggregates only, do not load task entities and cost far less than get_stats().
  • get_stats() suits on-demand manual investigation; polling it at high frequency adds load to storage queries.
  • get_health_status() caches results for 5 seconds, so it does not run checks on every call; use it for readiness and liveness probes, not get_stats().
  • Progress reporting is best effort: a report is dropped when the task has already ended or storage is temporarily unwritable, without affecting the task result.
  • get_result() provides queue_wait_ms, duration_ms and the cost fields; use get_cost_summary() for cross-task totals rather than substituting event counts for storage queries.
  • Metrics depend on event delivery; counters lag when events are dropped or subscribers are slow. Check pool.event_bus.get_stats() at the same time when investigating.
