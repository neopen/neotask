Reliability

Checkpoints

Save intermediate state and resume from the latest checkpoint on retry or explicit submission.

v1.0 · NeoTask 1.x Updated 2026-11-22 7 min read GitHub

Since 1.1, NeoTask supports resuming from a checkpoint: while a task runs it writes intermediate state to the checkpoint repository, and when the task is retried or resubmitted the latest state is injected into data["__checkpoint__"], so business code does not have to start over. It suits paged imports, batch processing, long call chains and any task that can be split by progress.

Enable and configure

from neotask import TaskPool, TaskPoolConfig

config = TaskPoolConfig(
    enable_checkpoint=True,        # enabled by default
    checkpoint_keep_versions=5,    # keep the latest 5 versions per task
)
pool = TaskPool(executor=handle, config=config)
FieldDefaultNotes
enable_checkpointTrueWhen off, no checkpoint repository is created; save_checkpoint() returns 0 / False instead of raising
checkpoint_keep_versions5Versions kept per task; older versions are trimmed after each save, and 0 keeps none

SchedulerConfig exposes the same fields and passes them to the internal TaskPool. All three storage backends implement the checkpoint repository: memory keeps it in-process, SQLite writes to the task_checkpoints table, and Redis writes to the neotask:ckpt:{task_id} hash.

Save and load

Inside an executor, use the module-level functions, picking the async or sync variant for the executor type:

from neotask import load_checkpoint, save_checkpoint
from neotask import load_checkpoint_sync, save_checkpoint_sync

async def async_job(data):
    state = await load_checkpoint() or {"cursor": 0}
    for index in range(state["cursor"], data["total"]):
        await handle_row(index)
        if index % 100 == 0:
            await save_checkpoint({"cursor": index + 1})
    return {"rows": data["total"]}

def thread_job(data):
    state = load_checkpoint_sync() or {"cursor": 0}
    for index in range(state["cursor"], data["total"]):
        handle_row(index)
        if index % 100 == 0:
            save_checkpoint_sync({"cursor": index + 1})
    return {"rows": data["total"]}

When no execution context is available (the parent process of the process executor, external scheduling components), use the task-level API:

version = pool.save_checkpoint(task_id, {"cursor": 42})
state = pool.load_checkpoint(task_id)
Call siteMethodReturn value
Async executorawait save_checkpoint(state) / await load_checkpoint()bool / dict | None
Thread executorsave_checkpoint_sync(state, timeout=5.0) / load_checkpoint_sync(timeout=5.0)bool / dict | None
Process executor parent process / external callpool.save_checkpoint(task_id, state) / pool.load_checkpoint(task_id)New version number, or 0 on failure / dict | None
What False means: The executor-level functions return False / None instead of raising when called outside a task context, when the task has already finished, or when checkpoints are disabled. Treat a failed save as "there is no progress to resume from this time", not as a task failure.

Three recovery paths

PathTriggerBehavior
Automatic retryThe executor raises and retry_count < max_retriesWrites the latest checkpoint back into task.data and re-enqueues with retry_delay × n
Manual retrypool.retry(task_id)Resets a terminal task to pending, injects the latest checkpoint and re-enqueues; retry_count is preserved
Explicit submitsubmit(data, task_id="job-1", resume_from_checkpoint=True)Creates the task record and injects the checkpoint before enqueueing, so a worker cannot pick it up early

Explicit submission must also provide task_id; otherwise resume_from_checkpoint has no effect and the task runs as a normal submission. A missing checkpoint is not an error either — the task runs with the original data.

The same task_id cannot be submitted twice: as long as the task record exists (including tasks that already succeeded or failed), submit() raises TaskAlreadyExistsError. To continue from a checkpoint on an existing record, call retry(task_id); use a submission with resume_from_checkpoint=True only when the record has been deleted or you are creating it for the first time in another process.

Versions, events and queries

Every save produces an increasing version number and updates the task record's checkpoint_version to the new version. Versions beyond checkpoint_keep_versions are trimmed; recovery always reads the latest version.

task = pool.get_task(task_id)
print(task["checkpoint_version"])

async def on_checkpointed(event):
    print(event.task_id, event.data)   # {"version": 3}

pool.event_bus.subscribe("task.checkpointed", on_checkpointed)

1.1 adds the task.checkpointed event, with event.data shaped like {"version": 3}. It has no on_checkpointed() convenience method; subscribe through event_bus.subscribe().

Lifecycle and cleanup

  • Deleting a task (delete()) also deletes that task's checkpoints.
  • Terminal cleanup deletes the matching checkpoints when it removes expired task records; to survive longer than a cleanup cycle, raise terminal_retention_seconds first.
  • Checkpoints on the memory backend are lost when the process exits; checkpoints in SQLite and Redis survive restarts.
  • In Redis mode checkpoints are shared by all nodes, so the latest version is still readable after another node takes over the task.

Boundaries

  • state must be JSON-serializable, and each save stores a full snapshot rather than an incremental log. Keep state small and avoid writing large results repeatedly.
  • A checkpoint is not a transaction. A successful save means business progress is persisted, but work done after a save and before the next one still runs again on recovery, so every step must remain idempotent.
  • The reserved key __checkpoint__ overwrites a business field of the same name in data; do not use that key for business data.
  • A business failure (report_failure) does not trigger an automatic retry and therefore does not resume automatically; call retry() explicitly when you want to continue.
