Developer guide

Project layout, development setup, tests, build, release, and contribution rules.

v1.0 · NeoTask 1.x Updated 2026-11-22 8 min read GitHub

This chapter is for developers who want to read the source, submit a patch or cut a release. NeoTask uses a src layout with no runtime framework dependencies; testing and release all happen inside the repository.

Project structure

neotask/
├── src/neotask/
│   ├── api/            # TaskPool, TaskScheduler (public entry points)
│   ├── core/           # lifecycle, dispatch, progress, cost, checkpoints, context
│   ├── queue/          # priority queue, delayed queue, queue scheduling, dead letter
│   ├── worker/         # worker pool, prefetcher, reclaimer
│   ├── storage/        # Memory / SQLite / Redis repository implementations
│   ├── executor/       # async / thread / process executors
│   ├── lock/           # in-memory lock, Redis lock, watchdog
│   ├── distributed/    # nodes, coordinator, sharding
│   ├── event/          # event bus and middleware
│   ├── monitor/        # metrics, health checks, reporter
│   ├── models/         # Task, config, periodic job models
│   ├── cli/            # neotask command-line entry
│   └── common/         # exceptions, constants, logging
├── tests/              # unit / integration / distributed / chaos / benchmark
├── benchmarks/         # stress scripts and results
├── examples/           # runnable examples
├── scripts/            # migration and maintenance scripts
├── pyproject.toml
└── CONTRIBUTING.md

Data flow: TaskPool → TaskDispatcher → QueueScheduler → WorkerPool → TaskExecutor, with lifecycle events broadcast on EventBus and state and results written to the repository.

Development environment

git clone https://github.com/neopen/neotask.git
cd neotask
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
ToolPurpose
pytest + pytest-asyncioUnit and integration tests
ruffLint and formatting
mypyType checking
pre-commitPre-commit hooks
build / twineBuilding and publishing

Minimum Python is 3.8, and CI covers 3.8 / 3.10 / 3.12. For local development prefer 3.10+ for more complete type hints.

Local development

  • Install in editable mode (-e) so source edits need no reinstall.
  • Put new examples in examples/ and keep the numeric prefix convention.
  • Run a single example to verify behavior: python examples/01_simple.py.
  • Changes touching Redis need a local Redis, or a temporary container instance.
  • Log level can follow an application-side variable such as NEOTASK_LOG_LEVEL (NeoTask does not read environment variables itself).

Before committing, run a minimal regression:

pytest tests/unit -q
ruff check src tests

Testing

# Full suite
pytest tests/

# By layer
pytest tests/unit/ -v
pytest tests/integration/ -v
pytest tests/distributed/ -v

# One file
pytest tests/unit/test_task.py -v

# Coverage
pytest --cov=src/neotask tests/

# Timeout guard for slow cases
pytest tests/ -q --timeout=60

Test directories:

DirectoryContents
tests/unitModels, queues, parsers, config and other pure logic
tests/integrationEnd-to-end combinations of pool, scheduler, storage and events
tests/distributedRedis queue, locks, nodes and reclamation
tests/chaosFault injection and recovery
tests/benchmarkPerformance regressions and benchmark scripts

The repository currently has roughly 500+ unit tests; the full 1.2.1 regression result is in Benchmarks · Measurement method. New behavior needs unit tests plus at least one integration case.

Build

python -m build
# Output: dist/neotask-X.Y.Z-py3-none-any.whl and .tar.gz

# Verify a local install
pip install dist/neotask-*.whl
python -c "import neotask; print(neotask.__version__)"

Builds use setuptools; package data and entry points live in pyproject.toml. After building, verify in a clean virtual environment: import, neotask --version and neotask --benchmark --tasks 50.

Release

Maintainers release with release-please and GitHub Actions:

  1. Merge Conventional Commits into main (fix: → PATCH, feat: → MINOR, feat! / BREAKING CHANGE → MAJOR).
  2. The bot opens a release PR that updates pyproject.toml, __init__.py, CHANGELOG.md and the manifest.
  3. After merge, tag vX.Y.Z and create a GitHub Release.
  4. The publish-pypi workflow builds and uploads to PyPI.

In an emergency you can build manually and run twine upload dist/*. Either way, verify afterwards that the PyPI page, install command and version number agree.

Contributing

  1. Search issues first to avoid duplicates; open an issue to align design and scope before a large feature.
  2. Branch from main, for example feat/checkpoint-resume.
  3. Keep changes focused: one PR solves one problem; no drive-by refactors.
  4. Add tests and documentation; public API changes update CHANGELOG.md and docs.
  5. Use Conventional Commits and explain why, not just what.
  6. Open the PR with reproduction steps, verification method and compatibility impact.

Never commit local data files, logs, virtual environments or secrets in a PR. When Redis / SQLite behavior changes, state the backend and version used for testing.

Code style

  • Follow PEP 8; snake_case for modules, PascalCase for classes, snake_case for functions and variables, UPPER_SNAKE for constants.
  • Public APIs need type annotations and a short docstring; write Args / Returns / Raises in the existing style.
  • Prefix private members with an underscore; do not export internals from the package entry.
  • No blocking calls inside async executors; hand blocking libraries to thread or process executors.
  • Log through the project logger; never use bare print.
  • Raise types from common/exceptions.py; avoid bare Exception.
ruff check src tests
ruff format src tests
mypy src/neotask/
pre-commit run --all-files

Passing format and lint is a merge prerequisite; type checking allows existing modules to converge gradually, but new public interfaces must not add mypy errors.

Related: the full contribution process lives in the repository's CONTRIBUTING.md; for security issues follow the Security policy below and never publish vulnerability details publicly.

Security policy

Security updates cover the latest stable 1.x release only. Report vulnerabilities privately rather than opening a public issue:

  1. Use GitHub Security Advisory or email helpenx@gmail.com.
  2. Include the affected version, reproduction steps, impact and a PoC if possible.
  3. Maintainers acknowledge within 48 hours and complete triage within 7 days; fixes ship in 7–30 days depending on severity.
  4. After a fix is released, the changelog is updated and reporters are credited with consent.
SeverityExamplesTarget fix window
CriticalRemote code execution, unauthenticated access, data exposure7 days
HighPrivilege escalation, sensitive data leak, denial of service14 days
MediumInformation disclosure, security feature bypass21 days
LowIssues that require specific conditions to exploit30 days

Deployment-side hardening is covered in Deployment · Security.
