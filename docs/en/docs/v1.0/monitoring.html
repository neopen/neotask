Monitoring and health checks

Metric snapshots and periodic push, health checks, event backpressure, UI, and Prometheus.

v1.0 · NeoTask 1.x Updated 2026-11-22 7 min read GitHub

NeoTask offers three capabilities: task metrics, health checks and metric reporting. Core metrics are in-process data and no HTTP endpoint starts by default; when you need a UI or a JSON entry point, you can start the lightweight WebUIServer manually.

Stats snapshot

stats = pool.get_stats()
print(stats["queue_size"], stats["completed"], stats["failed"])
print(stats["metrics"]["p95_execution_time"])
FieldDescription
queue_sizeTotal tasks in the priority queue and the delayed queue
total / pending / runningTask counts by storage state
completed / failed / cancelledNumber of tasks in terminal states
success_rateSuccess / (success + failure)
node_idIdentifier of the current node
metricsMetrics summary; present only when enable_metrics=True
reclaimerReclamation statistics; Redis mode only
prefetcherPrefetch statistics; present only when prefetch is enabled

TaskScheduler.get_stats() adds periodic and time_wheel on top of the same fields.

Lightweight monitoring snapshot (1.2)

get_stats() runs relatively heavy aggregate queries. If you only need numbers for probes, dashboards or log collectors, use get_metrics(), added in 1.2. It reads counters and aggregation results only and never loads task entities, so a single call is cheap and safe at high frequency.

snapshot = pool.get_metrics()
# {
#   "pending": 12, "running": 4, "completed": 1820, "failed": 3,
#   "worker_concurrency": 10, "active_workers": 4,
#   "queue_depth_by_priority": {0: 0, 1: 2, 2: 6, 3: 4},
#   "retry_queue_size": 1,
#   "oldest_pending_age_seconds": 0.8,
#   "storage_backend": "sqlite", "storage_healthy": True,
#   "checkpoint_count": 7, "context_key_count": 0
# }

unsubscribe = pool.on_metrics(push_snapshot, interval=30)
# ... call unsubscribe() before exit to stop the pushes
FieldDescription
pending / runningNumber of tasks currently pending and currently executing
completed / failedTerminal counts within the current retention period; these are not historical totals
worker_concurrency / active_workersConfigured concurrency and the number of workers actually busy
queue_depth_by_priorityQueue depth per priority, with keys 0–3
retry_queue_sizeTasks waiting to retry; a sustained rise indicates an unstable upstream
oldest_pending_age_secondsWait time of the oldest pending task, the most direct signal of queue degradation
storage_backend / storage_healthyBackend type and the result of a lightweight health probe
checkpoint_count / context_key_countNumber of checkpoints and Blackboard keys; 0 when the feature is disabled
  • If any underlying query fails, the corresponding field degrades to None instead of raising; handle None explicitly when the snapshot feeds a probe.
  • on_metrics(handler, interval=60) pushes snapshots to the callback at a fixed interval and returns an unsubscribe function; it connects directly to StatsD, logs or your own dashboard without a custom timer.
  • The snapshot does not include duration percentiles or cost details; read those from get_stats()["metrics"], get_result() or get_cost_summary().
Choosing among the three observation interfaces: get_stats() is for manual investigation and a complete summary; get_metrics() is for high-frequency probes and periodic reporting; get_health_status() is for readiness and liveness probes. Do not poll get_stats() at high frequency from a probe.

Event bus status

bus = pool.event_bus.get_stats()
# {
#   "queue_size": 0,
#   "max_queue_size": None,
#   "processed_events": 12034,
#   "dropped_events": 0,
#   "slow_handler_calls": 0,
#   "slow_handler_threshold": 1.0,
#   "is_running": True
# }
FieldDescription
queue_sizeEvents currently waiting; a sustained rise means consumers cannot keep up with producers
max_queue_sizeConfigured limit; None means unbounded
processed_eventsTotal events dispatched
dropped_eventsEvents dropped when a bounded queue was full
slow_handler_callsNumber of callbacks that exceeded the threshold
slow_handler_thresholdSlow-callback warning threshold in seconds
is_runningWhether the event consumer task is running
Metrics depend on event ordering: metrics.throughput and the completion counters are derived from lifecycle events. Because the event bus dispatches asynchronously, a slow subscriber delays the moment task.completed is observed, which makes short-window throughput and latency look lower than they are. When investigating, check queue_size and slow_handler_calls at the same time; do not mistake an event backlog for slow task execution.
Terminal cleanup affects counters: expired terminal tasks are cleaned up every 60 seconds by default, so completed / failed / cancelled are the record counts in current storage, not historical totals. For cumulative figures use counters such as metrics.total_completed.

Task metrics

MetricDescription
total_submittedTotal submissions
total_completed / total_failed / total_cancelledTerminal counts
total_retriedNumber of retries
pending / runningInstantaneous counts
avg_execution_time, p50/p90/p95/p99_execution_timeExecution duration, from the most recent 1,000 samples
avg_queue_time, p95_queue_timeQueueing duration
throughputThroughput computed from completion events
priority_countsSubmissions per priority
systemCPU, memory, thread count and similar; requires psutil
Sampling window: duration percentiles are computed over a sliding window (1,000 samples by default), not over all history. Once the window is full, older samples are discarded; long-tail metrics need an external monitoring system.

Per-task duration and cost (1.1)

Besides aggregate metrics, every task record stores queueing and execution duration plus any cost reported by the caller:

result = pool.get_result(task_id)
print(result["queue_wait_ms"], result["duration_ms"])
print(result["estimated_cost"], result["cost_tracking"])
# cost_tracking: {"tokens_in": 120, "tokens_out": 48,
#                 "api_calls": 1, "estimated_cost": 0.0012, "currency": "USD"}

pool.get_cost_summary(task_ids)   # aggregate across tasks
  • queue_wait_ms and duration_ms are computed automatically by NeoTask and are overwritten by each new attempt after a retry.
  • Costs are accumulated by the executor through report_cost() or pool.report_cost(); tasks that never report cost produce no cost data.
  • The task.cost_reported and task.checkpointed events can drive real-time dashboards, but events may be dropped by a bounded queue, so storage queries are the source of truth for totals.

Health checks

health = pool.get_health_status()
# {
#   "status": "healthy" | "degraded" | "unhealthy",
#   "node_id": "...",
#   "checks": {...},
#   "active_nodes": 2,
#   "heartbeat": {...},
#   "reclaimer": {...}
# }
CheckWhat it verifies
storageStorage is readable and writable
queueWhether the queue is available and approaching its capacity limit
systemCPU, memory and disk usage; above 90% is reported as degraded; skipped when psutil is not installed
  • Results are cached for 5 seconds, so repeated calls in a short window do not re-run the checks.
  • Each check times out after 5 seconds by default, so an unreachable dependency does not block the caller.
  • If any check is unhealthy the overall status is unhealthy; if any check is degraded the overall status is degraded.

Console reporting

config = TaskPoolConfig(enable_reporter=True)
pool = TaskPool(executor=handle, config=config)

When enabled, a get_stats() summary is printed to the console every 60 seconds. It suits local observation, not production monitoring.

Lightweight monitoring entry point (optional)

1.0.8 does not start a web service automatically. If you need an HTTP metrics entry point, install neotask[ui] and start WebUIServer manually. It serves a root page and /api/stats, the latter returning the result of get_stats().

from neotask.web.server import WebUIServer

server = WebUIServer(scheduler, host="127.0.0.1", port=8080)
server.start()   # starts uvicorn in a background thread

# GET http://127.0.0.1:8080/api/stats
# call server.stop() on exit
  • This is a lightweight monitoring entry point; it provides no task orchestration, editing, authentication or history storage.
  • TaskPool / TaskScheduler do not mount it automatically; instantiate it yourself.
  • It listens on localhost only by default. Put it behind an authenticated proxy before exposing it to other hosts.

Prometheus

The library includes PrometheusReporter, which pushes metrics through a Pushgateway and does not expose a /metrics endpoint.

from neotask import ReporterManager, PrometheusReporter

reporter = PrometheusReporter("http://pushgateway:9091", job_name="neotask")
manager = ReporterManager(interval=60)
manager.add_reporter(reporter)
manager.set_metrics_callback(pool.get_stats)
await manager.start()
Extra dependency: PrometheusReporter uses aiohttp, which is not part of the NeoTask dependencies or extras and must be installed separately. Reported fields cover only submitted/completed/failed/success rate, pending/running, and average and P95 execution time.

Event-driven collection

Metrics are derived from lifecycle events: task.created, task.started, task.completed, task.failed, task.cancelled and task.retry. Metrics therefore cover only the events produced or consumed by the current process; cross-node aggregation requires shipping each node's data to the same monitoring system. When a bounded event queue drops events, event-based statistics lose the corresponding records as well.

The task.checkpointed and task.cost_reported events added in 1.1 are not part of the built-in throughput and duration statistics; use them for application-side collection of checkpoint versions and cost details.
