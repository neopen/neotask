Prefetch

Demand-driven prefetch triggers, batch sizing, and effects on latency and priority.

v1.0 · NeoTask 1.x Updated 2026-11-22 5 min read GitHub

The prefetcher moves tasks from the shared queue to each worker's local queue in batches, reducing dequeue requests to Redis or the storage layer. It is on by default. Refill is driven by consumption progress on the local queue and woken by enqueue events when idle; since 1.2.1 an empty queue no longer adds exponential backoff, so sparse tasks are not slowed to hundreds of milliseconds by prefetching.

Configuration

from neotask import TaskPool, TaskPoolConfig

config = TaskPoolConfig(
    prefetch_size=20,        # tasks fetched per batch
    enable_prefetch=True,
)
pool = TaskPool(executor=handle, config=config)

The remaining parameters are derived from prefetch_size and cannot be set individually through TaskPoolConfig:

ParameterDerivation rule (default prefetch_size=20)
Local queue capacityprefetch_size × 5 = 100
Low-water triggermax(1, prefetch_size // 4) = 5
High-water stopprefetch_size × 3 = 60
Wait fallback interval0.1 seconds; used only as a timeout while waiting for consumption, no longer a cap on refill cadence
Idle timeoutPrefetching pauses after 5 seconds without consumption
Empty-queue waitWaits for an enqueue notification; no exponential backoff since 1.2.1

Trigger logic

The default is the HYBRID strategy:

  • When the local queue drops below the low-water mark (5), prefetch immediately; every time a worker takes a task it checks and sets the demand signal.
  • While the local queue still has stock, refill waits for the worker to consume down to the low-water mark; the wait timeout is the fallback.
  • When the shared queue is empty, wait for an enqueue notification instead of sleeping a fixed 0.1 seconds; since 1.2.1 consecutive empty prefetches also add no backoff.

One prefetch cycle

  1. Compute the remaining capacity of the local queue.
  2. Pop up to prefetch_size tasks from the shared queue in one batch.
  3. Put them into the local queue; stop when capacity runs out.
  4. Workers take tasks from the local queue and run them.

Impact on priority

Prefetching dequeues in batches, so strict ordering across priorities holds only within each batch. A low-priority task already sitting in the local queue can run before a high-priority task that arrives later in the shared queue.

RequirementConfiguration
Strict priority orderingenable_prefetch=False
Reduce the ordering effectDecrease prefetch_size, for example 1–5
High throughput, longer tasksIncrease prefetch_size, for example 50–100

Throughput versus latency

The main gain from prefetching is on the batch dequeue side. In the 1.2.1 baseline with 2,000 noop tasks and 10 workers, prefetch_size=20 reaches 4,241 tasks/s of completion throughput against 3,156 tasks/s with prefetching off, about 34% higher. The cost is per-task P50 rising from 1.20 ms to 11.24 ms.

Sparse submission shows a wider gap: submit a single task after 1 second idle and end-to-end latency is 1.1–2.2 ms with prefetching off versus 12.2–26.2 ms with it on, mostly from the prefetcher's coalescing window. 1.2.1 fixed the exponential backoff on an empty queue, so the worst-case 500 ms-class delay is gone, but the coalescing window remains.

When task bodies wait on IO or run for a while, saving the dequeue round trip is worth more; for very short tasks that need low latency, turning prefetching off or reducing the batch size fits better.

Decide based on task duration and queue backend: tasks in the millisecond range or longer usually benefit; for very short tasks, run an A/B comparison with the same set of parameters rather than turning prefetching off by default. See Performance benchmarks for the measurement basis.

Statistics

stats = pool.get_stats()
print(stats.get("prefetcher"))
# total_prefetch / total_fetched / total_errors
# avg_batch_size / avg_latency_ms / p95_latency_ms

The prefetcher field is returned only when prefetching is enabled. Prefetcher statistics do not include actual worker execution time.

Disabling and shutdown

  • With enable_prefetch=False, workers dequeue directly from the shared queue.
  • On graceful shutdown the prefetcher first waits for the local queue to be consumed; after the timeout it returns the remaining tasks to the shared queue so they do not become orphans.
  • A forced termination loses tasks that were dequeued into the local queue but not yet run; only the reclaimer's ttl fallback can recover them.
