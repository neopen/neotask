Roadmap

Delivered 1.x capabilities, remaining boundaries, and NeoFlow orchestration plans.

v1.0 · NeoTask 1.x Updated 2026-11-22 5 min read GitHub

NeoTask is positioned as a lightweight, embeddable execution layer that can be orchestrated. Complex task orchestration is no longer this library's responsibility: DAGs, conditional branches, dynamic routing and plugin systems belong to the upper orchestration service NeoFlow, while NeoTask only executes individual tasks reliably and exposes lightweight monitoring metrics.

Division of labor with NeoFlow: NeoFlow is the DAG orchestration service above NeoTask, responsible for workflow decomposition, task dispatch, event listening and state progression; NeoTask handles queueing, execution, retries, persistence and reclamation. The two layers cooperate through public APIs and lifecycle events and can be deployed and evolved independently.

Alternatives on 1.x

Capabilities outside the library can usually be composed from the existing primitives in business code, or handed to the NeoFlow orchestration service; state and failure handling then become your responsibility. 1.x includes checkpoints, business failure reporting, cost collection and lightweight monitoring snapshots, but none of them provides cross-task orchestration semantics.

RequirementApproach on 1.xLeft to you
Chaining multiple tasksLink tasks with parent_task_id and submit the next step on the completion event or after wait_for_result() returnsOrdering dependencies, failure propagation, timeouts and cross-task checkpoint recovery

Parallel subtasksUse submit_batch(), or submit individually with parent_task_id, then aggregate with wait_all()Cleanup on partial failure, retries and parent/child status rollup

Visual managementInspect tasks and metrics with neotask[ui], or consume get_metrics() and build your own viewOrchestration views and operations consoles belong to the upper service

v1.1: local task capabilities (released)

1.1.0 was released on 2026-11-13; 1.1.1 on 2026-11-15 resolved concurrency and startup readiness issues in the automatic legacy database upgrade, and 1.1.2 fixed timing precision and configuration handling. All of the following are available:

  • Checkpoint resume: save_checkpoint() / load_checkpoint(), with three recovery paths — automatic retry, manual retry and explicit submission;
  • Cost and duration collection: report_cost(), queue_wait_ms / duration_ms and get_cost_summary();
  • Parent/child task links: parent_task_id, get_children() / get_parent(); links only, no aggregation;
  • Local context reads and writes (Blackboard) and business failure reporting with report_failure();
  • The task.checkpointed / task.cost_reported events, plus support for an externally supplied task_id;
  • Legacy SQLite databases gain missing columns and tables automatically at startup; no manual migration is needed.

For details see Checkpoint resume, Cost and duration, Task relations and shared context and Failure recovery.

v1.2: lightweight monitoring and performance fixes (released)

  • 1.2.0: standardized get_metrics() snapshots and periodic on_metrics() pushes; benchmarks for monitoring, concurrency, checkpoints and progress reporting.
  • 1.2.1: in prefetch mode an empty queue no longer accrues exponential backoff, cutting sparse-task latency from a worst case in the 500 ms range to 12–26 ms; in-memory queue batch writes dropped from O(total queue size) to O(k log n) and batch removal became a lazy tombstone; psutil sampling moved to a thread pool, eliminating periodic stalls on the event loop; Redis batch reads are coalesced.

For monitoring fields and push mechanisms see Monitoring and health checks; for how the numbers are defined see Performance benchmarks.

v1.3: metrics export and reliability

  • Optional Prometheus exporter: adapts get_metrics() to a mountable HTTP service or render(), without listening on a port by default;
  • Crash recovery boundaries: state explicitly that pending records that were never enqueued are not executed automatically, and count them in metrics;
  • Shutdown configuration: clarify whether undelivered delayed tasks are drained, with the behavior documented;
  • A semantics matrix for automatic retry, manual retry and checkpoint resume.

v2.0: orchestration integration (not committed)

Work will start only after the local capabilities are stable and there is real multi-service demand; it is not part of the current release commitment. Integration will be delivered as a client for the NeoFlow orchestration service:

  • OrchestratorClient: task consumption, event reporting, heartbeats and local retry storage;
  • Redis Stream consumer groups and a cross-language protocol;
  • Instance registration, reclamation of tasks from lost instances and control message handling.

The following are handled by the NeoFlow orchestration layer and will not be implemented in NeoTask: DAG workflows, conditional branches, parallel orchestration, dynamic routing, plugin systems, a standalone web UI and multi-tenant isolation.

Upgrade preparation

  • Keep tasks idempotent: orchestration reruns, failure recovery and manual retries all execute tasks again.
  • Depend on public APIs only: do not read or write Redis keys directly or call internal modules; storage structures may change between versions.
  • Record your current configuration: save TaskPoolConfig and SchedulerConfig before upgrading, then compare them against the new configuration reference after release.
  • 1.0.x → 1.1.x → 1.2.x require no manual migration: missing columns and the task_checkpoints table are created at startup; backing up the SQLite file before upgrading is still recommended.
  • 1.2.1 changed the internal implementation of prefetch on empty queues and of queue batching, with compatible behavior; custom monitoring that depends on internal counters or log formats needs retesting in staging.
  • Do not put planned items into production dependencies, and do not import a workflow module on 1.x — it does not exist yet.

Versions and documentation paths

1.x delivers backward-compatible feature enhancements and performance work only, with no breaking changes; major-version capabilities are reserved for 2.0. The current documentation line v1.0 covers the entire 1.x series (baseline 1.2.1); 2.0 will open a separate documentation path when it ships.

Library versionDocumentation pathNotes
1.x (including 1.1, 1.2…)/docs/v1.0/Current documentation line; ongoing enhancements and bug fixes are published at this path
2.0/docs/v2.0/Added when 2.0 ships; major-version features and breaking changes are documented there

Minor releases within 1.x do not change documentation links; when upgrading to 2.0, switch to the new documentation line to compare configuration and API changes.

Versioning policy: the v1.0 documentation covers the entire 1.x line, its baseline follows the latest patch release, and it is maintained at the original path; 2.0 opens a new documentation path for major-version capabilities, while old links remain accessible.
