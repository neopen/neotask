Core concepts

Task lifecycle

State transitions from submission to terminal states, event callbacks, and result access.

v1.0 · NeoTask 1.x Updated 2026-11-22 6 min read GitHub

A task passes through only a small set of states between submission and completion. States live in the storage layer and events are published through the event bus; the sync and async APIs read the same record.

States

StateMeaningTerminal
pendingCreated and waiting for a worker to dequeue itNo
runningClaimed by a node and executingNo
successExecution finished and the return value is savedYes
failedExecution failed and retries are exhausted, the reclaimer judged it failed, or the executor reported a business failureYes
cancelledExplicitly cancelledYes
scheduledReserved in the enum; delayed tasks in 1.x stay pending while they waitNo

Normal transitions

submit()
  │
  ▼
pending ──► running ──► success
  │            │
  │            ├──► failed ──► pending (automatic retry)
  │            │                 │
  │            │                 └──► failed (retries exhausted)
  │            │
  │            └──► failed (timeout / reclaimed)
  │
  └──► cancelled (cancelled before start or while running)

Querying and waiting

MethodReturns
get_status(task_id)The state string; None if the task does not exist
get_task(task_id)The full record, including data, priority, progress, node, retry count and timestamps
get_result(task_id)task_id, status, result, error, failure_reason, parent_task_id, estimated_cost, cost_tracking, queue_wait_ms, duration_ms, plus creation and completion times
wait_for_result(task_id, timeout=300)Returns the result on success; raises on failure, cancellation or timeout
wait_all(task_ids, timeout=300)Waits item by item and returns {task_id: result}; failed items are {"error": "..."}
Cross-node waiting: besides listening to local events, wait_for_result() re-checks storage every 0.2 seconds, so it still returns promptly when the task runs on another node.

Events

Callbacks must be async functions with the signature async def handler(event: TaskEvent). Events enter a background queue first; the EventBus consumer task then dispatches them to subscribers in order. Exceptions raised by a callback are logged and swallowed, and never affect task execution.

Registration methodEventevent.data
on_createdtask.createdThe full task dict
on_startedtask.started{"node_id": "..."}
on_completedtask.completedThe executor's raw return value
on_failedtask.failed{"error": "..."}
on_cancelledtask.cancelledNone
on_progresstask.progress{"progress": 0.5, "message": "...", "timestamp": ...}
on_reclaimedtask.reclaimedReclaim reason and related details
event_bus.subscribe("task.checkpointed", handler)task.checkpointed{"version": 3}
event_bus.subscribe("task.cost_reported", handler)task.cost_reportedCost details of this report
The 1.1 events have no convenience methods: task.checkpointed and task.cost_reported can only be subscribed through pool.event_bus.subscribe("event_name", handler); TaskPool does not provide on_checkpointed() / on_cost_reported().
import asyncio
from neotask import TaskPool, TaskPoolConfig

async def on_completed(event):
    print("done", event.task_id, event.data)

pool = TaskPool(executor=handle)
pool.on_completed(on_completed)

Event bus backpressure

By default the event queue is unbounded, so production speed is limited only by memory. With event_queue_max_size set, new events are dropped and counted once the queue is full; when a single callback exceeds event_slow_handler_threshold seconds, the slow-callback counter is incremented. Dropped events do not change task state, but any monitoring or downstream step that depends on them misses a notification.

config = TaskPoolConfig(
    event_queue_max_size=1000,        # None means unbounded
    event_overflow_policy="drop",    # only drop is supported
    event_slow_handler_threshold=0.5,
)
pool = TaskPool(executor=handle, config=config)

print(pool.event_bus.get_stats())
# queue_size / max_queue_size / processed_events / dropped_events
# slow_handler_calls / slow_handler_threshold / is_running
Slow subscribers delay event timestamps: events are handled by a separate consumer task, so task.completed may be observed later than the task actually finished. When you need exact durations, instrument inside the task body or use the timestamps from get_task(); do not treat event lag as execution latency.

Terminal state cleanup

Since 1.0.8, success / failed / cancelled tasks past their retention period are cleaned up every 60 seconds by default, so memory and storage do not grow without bound as task volume increases. The retention window comes from terminal_retention_seconds; when it is 0, each task's own ttl is used.

config = TaskPoolConfig(
    enable_terminal_cleanup=True,
    terminal_cleanup_interval=60.0,
    terminal_retention_seconds=0,     # 0 = clean up by each task's ttl
)

# Clean up expired terminal tasks now and return the number removed
removed = pool.cleanup_terminal_tasks()
Cleanup removes only terminal records past their retention period. It does not touch pending / running tasks and is not the same as failure reclamation. The checkpoints of removed tasks are deleted as well. If you need long-term audit records, disable automatic cleanup or set terminal_retention_seconds high enough, and archive the records yourself.

Progress reporting

Async tasks call report_progress(); sync tasks running under the thread executor call report_progress_sync(). Progress values are clamped to 0–1, and a successful task is set to 1.0 automatically.

from neotask import report_progress, report_progress_sync

async def async_task(data):
    await report_progress(0.3, "parsing input")
    await asyncio.sleep(1)
    await report_progress(0.8, "writing results")
    return {"ok": True}

def thread_task(data):
    report_progress_sync(0.5, "processing")
    return {"ok": True}
The process executor runs in a separate process and cannot share the progress context, so report_progress() returns False.

Cancel, retry and delete

OperationBehaviorRestriction
cancel(task_id)Removes the task from the queue and sets it to cancelledOnly pending / running tasks can be cancelled; running business code is not forcibly terminated
retry(task_id, delay=0)Resets a terminal task to pending, re-enqueues it and injects the latest checkpointOnly failed / cancelled tasks can be retried; retry_count is preserved
delete(task_id)Deletes the task record and clears waitersDoes not stop code that has already started
Automatic retry: after an execution failure, if retry_count < max_retries, the task returns to pending and is re-enqueued with a retry_delay × n delay. Both automatic and manual retries inject the latest checkpoint into data["__checkpoint__"]; once retries are exhausted the task is written as failed, and in Redis mode an entry is also published to the dead-letter queue.
Business failures: after the executor calls report_failure(reason, detail), the task is set to failed as soon as the current execution ends and failure_reason is recorded; no retry budget is consumed and nothing is written to the dead-letter queue. For how failures are judged and ended externally, see Failure recovery.
