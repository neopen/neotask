Troubleshooting

Common issues, log analysis, diagnosis, deployment problems, and performance questions.

v1.0 · NeoTask 1.x Updated 2026-11-22 8 min read GitHub

NeoTask troubleshooting follows a fixed order: confirm the task's state, identify which layer owns that state, then check that layer's inputs (submit parameters, config, storage and upstream dependencies). This page is organized by symptom for direct lookup.

Common issues

SymptomLikely causeAction
Task stays pendingPool not started, concurrency is 0, queue occupied by other tasks, delayed task not yet dueCall pool.start() explicitly; check worker_concurrency; observe get_queue_size() and get_metrics()
Task stays runningExecutor blocked, waiting on external IO, no timeout setSet task_timeout; look for blocking calls in the executor
QueueFullError on submitQueue reached queue_max_sizeRaise consumption, lower submit rate or increase capacity
database is lockedMultiple processes writing the same SQLite fileKeep a single writer, or switch to Redis
Redis connection failureneotask[redis] not installed, wrong address, password / TLS mismatchInstall the extra; verify the URL; check security groups and certificates
Empty result / serialization failureReturn value is not JSON-serializable, or the task is still runningReturn JSON-native types only; check get_status() first
Same task runs twiceBusiness logic not idempotent; lock expired or cross-node Redis lock not usedDeduplicate in business logic; use TaskPoolConfig.redis() in Redis mode
Periodic job never firesMemory backend does not persist, invalid Cron, scheduler instance stoppedUse SQLite / Redis; validate expressions at startup; confirm the scheduler process is alive
Historical tasks missingTerminal cleanup removed them, or ttl is too shortIncrease retention; export in completion events when audit is needed

Log analysis

NeoTask uses the standard logging module with the logger name NeoTask. Your application can take over its handlers and level:

import logging

logging.getLogger("NeoTask").setLevel(logging.DEBUG)
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s %(message)s",
)

Focus on these keywords while diagnosing:

KeywordMeaningNext step
Task execution timeoutA single run exceeded task_timeoutCheck executor duration and external dependencies
Queue is fullQueue capacity exhaustedScale out or throttle
Failed to initialize distributed componentsRedis component initialization failedCheck Redis connectivity and installed extras
slow handler / event drop countersEvent callback exceeded the threshold or a bounded queue overflowedMake callbacks asynchronous and set a sane bound
reclaimThe reclaimer took over an unreachable or timed-out taskCheck node liveness and ttl
database is lockedSQLite write lock contentionMove to a single writer or migrate to Redis

When logs include task IDs, correlate submit, execute, retry and completion by task_id. For structured logs, add a JSON formatter on the application side instead of changing the library's log format.

Diagnosis

State first, then fields

result = pool.get_result(task_id)
print(pool.get_status(task_id))
print(result)
print(pool.get_task(task_id))
FieldDiagnostic value
statusWhich phase the task is in
errorSystem exception summary; empty does not mean success, read it with status
failure_reasonBusiness failure reason, distinct from system exceptions
retry_countWhether it keeps failing; hitting the cap means fixing business logic or upstream
queue_wait_msQueue time; far above execution time means insufficient capacity
duration_msExecution time; near the timeout threshold means tuning or optimization
node_idWhich node executed or lost the task

Then the global snapshot

import json

print(json.dumps(pool.get_metrics(), ensure_ascii=False, indent=2))
print(json.dumps(pool.get_health_status(), ensure_ascii=False, indent=2))

A rising queue_depth_by_priority means under-consumption; a rising oldest_pending_age_seconds means worsening queues; a rising retry_queue_size points at an unstable upstream; storage_healthy=False points straight at the storage layer.

Exception reference

ExceptionMeaningAction
TaskNotFoundErrorID does not exist or was cleaned upVerify the ID; increase retention
TaskAlreadyExistsErrorExplicit task_id duplicatedUse automatic IDs or query first
BatchSubmitErrorSome batch entries failed and the batch was rolled backRead index / cause and fix that entry
TimeoutErrorWaiting for a result timed out; the task did not failQuery status; the task may still be running
UnsupportedFeatureErrorThe backend does not support the feature (for example, Blackboard outside Memory)Switch backends or use another approach

Deployment issues

ScenarioCauseFix
All tasks lost after a container restartMemory backend, or SQLite without a persistent volumeSwitch to SQLite and mount /data, or use Redis
Duplicate execution after a rolling updateOld container exited without graceful shutdown; tasks were reclaimedExtend stop_grace_period; make business logic idempotent
Periodic jobs fire on every replicaEvery replica registered the same periodic jobKeep one scheduler instance, or use Redis persistence and mutual exclusion
SQLite writes slow down or lockMultiple processes writing one file, or the file sits on a network shareSingle writer, local disk; migrate to Redis when needed
Redis memory keeps growingTerminal records or dead letters are not cleaned upCheck ttl, cleanup flags and dead-letter capacity
High CPU from K8s probesHigh-frequency probing with get_stats()Use get_health_status() and lower the frequency
Process exit hangsIn-flight tasks did not finish within the shutdown timeoutShorten tasks or raise shutdown(timeout), and extend the orchestrator grace period

Performance issues

Throughput will not rise

  1. Check worker_concurrency and node count; total concurrency is the sum across nodes.
  2. Check whether the executor blocks the event loop; move CPU-heavy work to a process executor.
  3. Check event callback duration; slow callbacks stall event consumption and may trigger drops.
  4. Check storage: SQLite serial writes cap throughput, and Redis is bound by network round trips.
  5. For batches, use submit_batch() instead of per-item round trips across the event loop.

Latency increased

  • High queue_wait_ms: a queueing problem; scale out or raise priority.
  • High duration_ms: an execution problem; inspect external calls and lock waits.
  • Latency-sensitive sparse tasks: disable prefetch or reduce prefetch_size; prefetch raises throughput but increases single-task latency.
  • Scheduling latency: check scan_interval and system load; enable the time wheel for many delayed tasks.

Memory keeps growing

  • The event bus is unbounded by default: set event_queue_max_size and confirm callbacks do not back up.
  • Terminal records are not cleaned up: confirm enable_terminal_cleanup=True and the retention period.
  • Progress or results are too large: shrink result and store large objects externally.
  • Prefetch is too large: lower prefetch_size.

FAQ

Why is there no neotask start command?

NeoTask is an embedded library, not a standalone daemon. Create a TaskPool or TaskScheduler at application startup and tasks run with the process. The CLI only offers version output and a light benchmark.

wait_for_result timed out — is the task still running?

It may be. The wait timeout affects only the caller and does not cancel the task. Confirm with get_status() and call cancel() if needed.

Do synchronous functions block the event loop?

A plain synchronous function passed directly is wrapped into an async call by the default executor, so it does not block. But calling synchronous blocking code inside a coroutine still blocks the whole loop; move that logic into ThreadExecutor or ProcessExecutor.

Why does automatic reclamation only exist in Redis mode?

Heartbeat and reclamation depend on a cross-node view and shared storage. Memory / SQLite are single-process semantics with no reliable node registry or task ownership, so the reclaimer is not enabled. Use Redis when production needs automatic takeover.

Should I set both ttl and task_timeout?

Yes. The former controls record retention and reclamation criteria; the latter forcibly interrupts overly long execution. Setting only one leaves a blind spot.

How do I confirm a task did not run twice?

Locks reduce probability but do not replace business idempotency. Deduplicate with a stable business key or upsert, carry an idempotency key in task data, and ensure Redis locks are used in a multi-node deployment.

Can I delete task records directly?

You can call delete(task_id), but it does not undo side effects already applied. Cancel queued tasks with cancel() first; deleting a running task does not interrupt execution.

Do I need to migrate data after upgrading?

SQLite adds missing columns automatically at startup; for cross-backend or major-version migrations, back up first and validate the scripts in staging.

Still stuck: open an issue on GitHub Issues with neotask.__version__, backend type, task state, the get_metrics() snapshot and relevant logs. Never paste logs containing secrets or business data publicly.
