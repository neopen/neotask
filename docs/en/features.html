01 · Immediate tasks

Submit and run, with priority deciding order

TaskPool hands incoming work to the worker pool at once. Four priority levels give critical work a first chance under bursty traffic, with FIFO within a level.

  • Sync, async and batch submission
  • Result waiting, status queries and cancellation
  • Context manager starts and stops the pool

02 · Scheduling

Delays, intervals and Cron in one scheduler

TaskScheduler adds a time dimension on top of the task pool: delayed runs, run-at timestamps, fixed intervals and Cron expressions, plus pause and resume for periodic jobs.

  • Second-level delays and run-at times
  • Fixed-interval periodic jobs
  • Cron expressions and missed-run policy

03 · Reliability

Retries on failure, reclamation on node loss

Exceptions retry automatically per configuration. In Redis multi-node mode, heartbeat expiry and the reclaimer return tasks from a silent node to the queue; tasks that ultimately fail land in the dead letter queue for manual inspection. Memory and SQLite do not reclaim across nodes.

  • Automatic retries with linear delay
  • Orphan task reclamation and zombie-lock scanning
  • Dead letter queue preserves the failure state

04 · Persistence

Three stores, one abstraction

Pick a backend by deployment scale: in-memory for development, SQLite for single-machine persistence, Redis for multi-node sharing. Switching storage does not change business code.

  • Memory: zero config, in-process
  • SQLite: single-file durability
  • Redis: shared queue and state indexes

05 · Distributed

Peer nodes, no master

After switching to Redis, nodes consume the shared queue as peers. Heartbeats track node liveness, locks with a watchdog prevent duplicate execution, and prefetch cuts round-trip overhead.

  • Competitive consumption, no scheduler center
  • Redis distributed locks with watchdog renewal
  • Demand-driven prefetch and batch operations

06 · Observability

Task state in your existing monitoring

Subscribe to six lifecycle events and read statistics and health status; the event bus offers bounded queues and slow-callback statistics. When you need an HTTP metrics endpoint, the optional neotask[ui] extra starts WebUIServer manually.

  • created / started / completed / failed
  • cancelled / reclaimed events
  • Event backpressure, drop counts and metrics collection
  • Lightweight monitoring entry point (optional neotask[ui])
  • neotask --benchmark self-check

HONEST LIMITS

Knowing what it does not do matters more than knowing what it does

NeoTask is a focused task queue, not a universal workflow platform. The following are out of scope or available only as options:

  • —
    DAG workflow orchestration

    Out of scope. The NeoFlow orchestration service owns task topology, conditional branches and parallel execution; NeoTask executes individual tasks.

  • —
    Multi-tenancy and quotas

    Out of scope; tenant isolation and resource quotas belong to the platform or orchestration layer above.

  • ○
    Lightweight monitoring endpoint

    WebUIServer from neotask[ui] serves a root page and /api/stats, and you start it yourself; there is no separate orchestration console.

  • ○
    Progress callbacks

    Tasks can call report_progress() and applications subscribe via on_progress; process executors cannot share context, so progress is unavailable there.
