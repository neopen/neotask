每个场景独立创建 TaskPool，预热 10 个任务；主套件重复 2–3 轮取中位数。提交吞吐与完成吞吐的分母不同，不能直接比较：前者衡量入队链路，后者包含调度、执行与状态落库。

调度与执行开销

{{BENCH_SCHEDULING_TABLE}}

空任务单条提交的主链路开销约 68 μs。完成吞吐的瓶颈在生命周期流转、状态落库与事件分发，不在执行器本身；单纯增加 Worker 无法突破这一上限。

IO 扩展性

任务体为 asyncio.sleep(0.020)，N=400，Memory 后端。完成吞吐随 Worker 数增加接近线性增长。

{{BENCH_IO_CHART}} {{BENCH_IO_TABLE}}

1 Worker 的绝对值受 Windows 定时器粒度影响：20 ms 的 sleep 实际约 31 ms，因此 32.1 tasks/s 略低于理论上限。评估扩展性时看相对倍率，不要只看单点绝对值。

SQLite 边界

noop 任务，每次重建数据库，对比单写入者与并发写入的行为。

{{BENCH_SQLITE_BOUNDARIES}}

SQLite 适合低频、单写入者场景。需要多 Worker 并发写入或跨节点共享队列时改用 Redis，配置方式见 持久化存储 与 分布式部署。

预取的配置影响

极短任务由事件循环直接调度更快；默认预取按约 0.1 秒一批补充任务，批间隔会限制微任务的完成吞吐。

{{BENCH_PREFETCH_CHART}}

任务体本身有 IO 等待或执行时间较长时，预取节省的取任务往返通常更有价值，保持默认即可。触发条件与批量参数见 预取机制。

怎么选配置

场景建议配置依据
数十微秒的纯计算微任务关闭预取，Worker 数与 CPU 核数对齐预取批间隔成为瓶颈，关闭后完成吞吐从约 200 提升到 2,382 tasks/s
毫秒级 IO 任务保持默认预取，Worker 16–32 起步20 ms 睡眠任务在 8 Worker 下仍有 7.76× 扩展
CPU 密集任务ProcessExecutor，Worker 不超过物理核数异步 Worker 共享 GIL，超配只增加切换开销
单机低频、需重启恢复SQLite，单写入者100 条突发在 1 Worker 下全部成功；2 Worker 起出现 database is locked
多节点或高并发写入Redis，唯一 node_id，lock_type="redis"SQLite 没有跨进程写协调，见分布式部署
优先级严格生效关闭预取或调小批量预取会提前取走任务，后提交的高优先级任务可能排在已取走的低优先级任务之后

复现

git clone https://github.com/neopen/neotask.git
cd neotask
pip install -e ".[dev]"
python tests/benchmark/run_benchmark.py

基准脚本位于仓库 tests/benchmark/，不随 PyPI 包分发。主套件约需 2 分钟，SQLite 探针另需约 2 分钟。复测时记录 CPU、Python 版本、存储后端与 Worker 数，否则结果不可比。

解读边界

  • 数据来自单台开发笔记本（4 核 8 线程），不能外推到服务器或容器环境。
  • 主套件使用 Memory 后端，SQLite 数据单独测量，两者不可混用。
  • 旁路组件（metrics、health check、reporter、reclaimer、heartbeat、dead letter、retry）全部关闭，开启后吞吐会下降。
  • 延迟分位数来自单次场景，不代表长期稳定性；持续负载与突发负载应分开评估。
  • 版本间口径可能变化，1.0.5 之前的历史数字不应直接比较。
不要直接引用绝对值做容量规划。请在自己的目标环境用相同脚本、相同口径复测，并把业务任务的真实耗时分布纳入评估。
