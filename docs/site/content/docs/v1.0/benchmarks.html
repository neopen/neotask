预取核心基准（吞吐）与稀疏延迟（单任务响应）衡量的是相反目标：预取用批量出队换吞吐，代价是合并窗口带来的固定延迟。比较前先确认口径与配置。

预取的两面：同一套参数下，开启预取的完成吞吐为 4,241 tasks/s，关闭为 3,156 tasks/s；但空闲后单条任务的延迟从 1.1–2.2 ms 升到 12.2–26.2 ms。1.2.1 修复了空队列上的指数退避，稀疏任务不再出现最坏 500 ms 级延迟，但预取的 10 ms 合并窗口仍然存在。

调度与执行开销

{{BENCH_SCHEDULING_TABLE}}

内存队列的批量写入与移除已从整堆重建改为增量维护与惰性墓碑：向 10,000 条队列一次写入 1,000 条约 0.471 ms（约 212 万条/s），批量移除 1,000 条约 0.668 ms。全部弹出并校验的不变量测试确认没有重复项或墓碑泄漏；peek(5) 在 10,000 条队列上为 0.008 ms。1.2.1 的完整回归为单元测试 538 通过 / 12 跳过，集成测试 87 通过 / 1 跳过。

预取与完成吞吐

2,000 个 noop 任务、10 Worker，对比关闭预取与 prefetch_size=20。预取把共享队列批量搬到本地队列，吞吐提升约 34%，但单任务 P50 从 1.20 ms 升至 11.24 ms。

{{BENCH_IO_CHART}} {{BENCH_IO_TABLE}}

吞吐瓶颈在生命周期流转、状态落库与事件分发，不在执行器本身；单纯增加 Worker 无法突破这一上限。任务体有 IO 等待或执行时间较长时，预取的批量收益更明显；纯微任务且要求低延迟时，关闭预取更合适。

稀疏任务延迟

空闲 1 秒后提交单条任务，模拟低频率事件触发。关闭预取时端到端延迟为 1.1–2.2 ms；开启预取后为 12.2–26.2 ms，主要来自预取器的合并窗口。

{{BENCH_PREFETCH_CHART}}

延迟敏感的场景（如交互式请求触发的后台动作）应关闭预取或调小 prefetch_size；批处理、采集与转码类任务保持默认预取即可。二者的取舍见 预取机制。

持续与突发负载

覆盖稀疏提交、预取空队列唤醒、批量取消与队列满载四类边界。1.2.1 的空队列退避修复与惰性墓碑是这一轮的主要变化。

{{BENCH_STRESS_TABLE}}
{{BENCH_STRESS_NOTE}} 空队列唤醒不再叠加 0.5 秒退避，是稀疏任务延迟从数百毫秒降至毫秒级的直接原因；队列满载时三种后端均返回 False 或 QueueFullError，语义一致。

跨存储对照

同一业务路径在三种后端上的端到端对照：Memory 2,000 任务、SQLite 与 Redis 各 1,000 任务。规模不同，只看量级与 P50 的相对差距。

{{BENCH_SQLITE_BOUNDARIES}}

Memory 走进程内队列，4,761 tasks/s；SQLite 受单文件串行写入约束，519 tasks/s；Redis 受网络往返与序列化影响，232 tasks/s。SQLite 适合单机持久化与低频写入；需要多节点共享或更高并发时改用 Redis。跨存储迁移前务必在预发环境验证，并注意任务与事件的可接受丢失窗口。

事件总线与唤醒

事件总线把生命周期事件异步投递给订阅者。1.2 起无订阅者的事件不再入队，降低空转；有界队列满时丢弃新事件并计数，慢回调超过阈值会记录告警。

{{BENCH_EVENT_TABLE}}

需要完整审计时保持事件队列无界，并把耗时回调移出事件循环；生产环境建议设置 event_queue_max_size 并监控 dropped_events。周期监控优先用 on_metrics() 推送快照，避免为每个指标单独订阅事件。

怎么选配置

场景建议配置依据
数十微秒的纯计算微任务Worker 数与 CPU 核数对齐；预取可关可开预取 4,241 与关闭 3,156 tasks/s 处于同一量级，预取主要降低出队开销
毫秒级 IO 任务保持默认预取，Worker 16–32 起步预取批量出队，IO 等待期间吞吐收益明显
低延迟、稀疏提交关闭预取或 prefetch_size 降到 5 以下关闭预取 1.1–2.2 ms，开启 12.2–26.2 ms
CPU 密集任务ProcessExecutor，Worker 不超过物理核数异步 Worker 共享 GIL，超配只增加切换开销
单机低频、需重启恢复SQLite，单写入者519 tasks/s，P50 1.0 s；写入串行化
多节点或高并发写入Redis，唯一 node_id共享队列、锁、心跳与回收只在 Redis 模式可用
优先级严格生效关闭预取或调小批量预取会提前取走任务，后提交的高优先级任务可能排在已取走的低优先级任务之后
事件完整性优先保持无界事件队列，回调快速返回有界队列会丢弃事件；慢回调会延后 task.completed 的观测时间

复现

# 用内置 5 ms 执行器做一轮轻量自测
neotask --benchmark

# 用自己的执行器
neotask --benchmark --executor my_tasks:handle --tasks 2000 --json

# 仓库内完整基准
git clone https://github.com/neopen/neotask.git
cd neotask
pip install -e ".[dev]"
python tests/benchmark/run_benchmark.py

neotask --benchmark 随 PyPI 包分发，默认 200 个任务、10 并发，适合快速对照；完整基准脚本位于仓库 tests/benchmark/，1.2.1 的回归与套件结果来自同一环境。复测时记录 CPU、Python 版本、存储后端与 Worker 数，否则结果不可比。

解读边界

  • 数据来自单台开发笔记本（4 核 8 线程、16 GB、Windows 10、Python 3.13），不能外推到服务器或容器环境。
  • 吞吐、稀疏延迟与跨存储对照口径不同，三组数字不可混用。
  • 旁路组件（metrics、health check、reporter、reclaimer、heartbeat、dead letter）按套件关闭，开启后吞吐会下降。
  • 1.2.1 修复了空队列指数退避与内存队列批量写删，稀疏任务延迟与批量操作数字与 1.0.x 不可直接比较；历史数字仅作趋势参考。
  • 延迟分位数来自单轮场景，不代表长期稳定性；持续负载与突发负载应分开评估。
不要直接引用绝对值做容量规划。请在自己的目标环境用相同脚本、相同口径复测，并把业务任务的真实耗时分布纳入评估。
