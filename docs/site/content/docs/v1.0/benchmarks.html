口径

指标定义
提交吞吐第一个 submit_async 到第 N 个返回
完成吞吐（官方套件）第一个 submit_async 到第 N 个 task.completed 事件
完成吞吐（压力套件）任务执行完成时计数，不等待事件订阅回调
任务延迟单任务提交前到该任务完成事件
等待吞吐N 个并发 wait_for_result_async 全部返回的速率

每个场景独立创建 TaskPool，预热 10 个任务；主套件重复 2–3 轮取中位数。提交吞吐与完成吞吐的分母不同，不能直接比较：前者衡量入队链路，后者包含调度、执行与状态落库。

1.0.8 的完成吞吐有两个口径：事件总线改为异步队列后，官方套件按 task.completed 事件计时，订阅者处理慢时测到的是事件投递速率，而不是任务执行速率。同一版本的压力套件在任务完成时计数，20,000 任务实测 3,035 tasks/s；官方套件 3,000 任务为 1,804 tasks/s。两者都不是容量上限，比较时先确认口径。

调度与执行开销

{{BENCH_SCHEDULING_TABLE}}

2,000 个 noop 任务顺序提交为 9,681 tasks/s，折算单条约 0.10 ms；串行往返 P50 0.86 ms 包含出队、执行、状态写回与事件唤醒。完成吞吐的瓶颈在生命周期流转、状态落库与事件分发，不在执行器本身；单纯增加 Worker 无法突破这一上限。

IO 扩展性

任务体为 asyncio.sleep(0.020)，N=400，Memory 后端。完成吞吐随 Worker 数增加接近线性增长。

持续与突发负载

20,000 个 noop 任务一次性提交，观察持续完成能力；其余场景覆盖 Worker 数、缓存淘汰、空闲 CPU、延时精度与三后端突发。压力套件在空闲机器上以最终 wheel 运行。

事件总线与唤醒

1.0.8 起 Worker 与预取器由事件唤醒，不再按固定间隔轮询。EventBus 默认无界；设置 event_queue_max_size 后队列满会丢弃新事件并计数，慢回调超过 event_slow_handler_threshold 时会告警。

{{BENCH_EVENT_TABLE}}

空闲后提交的唤醒延迟中位 1.3 ms，是串行往返降到 0.86 ms 的主要原因。有界队列会牺牲事件完整性换取内存上限：需要完整审计时保持无界，并把耗时回调移出事件循环。

SQLite 边界

noop 任务，每次重建数据库，对比串行提交与 1–4 个 Worker 的突发提交。

{{BENCH_SQLITE_BOUNDARIES}}

1.0.8 为单连接写入加了串行锁，多 Worker 并发提交不再出现 database is locked，但吞吐随 Worker 数增加而下降：2 Worker 61.8 tasks/s、4 Worker 41.3 tasks/s。SQLite 仍适合低频、单写入者场景；需要高并发写入或跨节点共享队列时改用 Redis。

预取的配置影响

1.0.8 的预取由本地队列消费进度驱动，prefetch_interval 只作为等待兜底，不再按固定 0.1 秒一批补货。极短任务下关闭预取与开启预取的完成吞吐处于同一量级。

{{BENCH_PREFETCH_CHART}}

预取的价值主要在批量出队侧：20,000 任务压力套件中，预取开启的提交吞吐比关闭高 22.4%（25,760 对 21,052 tasks/s），完成吞吐高 12.7%。任务体有 IO 等待或执行时间较长时收益更明显。触发条件与批量参数见 预取机制。

怎么选配置

场景建议配置依据
数十微秒的纯计算微任务Worker 数与 CPU 核数对齐；预取可关可开预取不再是数量级瓶颈，关闭 1,453 与预取 100 的 1,538 tasks/s 处于同一量级
毫秒级 IO 任务保持默认预取，Worker 16–32 起步20 ms 睡眠任务在 8 Worker 下仍有 8.03× 扩展
CPU 密集任务ProcessExecutor，Worker 不超过物理核数异步 Worker 共享 GIL，超配只增加切换开销
单机低频、需重启恢复SQLite，单写入者写入已串行化；1 Worker 突发 87.4 tasks/s，4 Worker 降至 41.3 tasks/s
多节点或高并发写入Redis，唯一 node_idTaskPoolConfig.redis() 自动启用 Redis 锁；手工构造配置时需显式设置 lock_type="redis"
优先级严格生效关闭预取或调小批量预取会提前取走任务，后提交的高优先级任务可能排在已取走的低优先级任务之后
事件完整性优先保持无界事件队列，回调快速返回有界队列会丢弃事件；慢回调会延后 task.completed 的观测时间

复现

# 用内置 5 ms 执行器做一轮轻量自测
neotask --benchmark

# 用自己的执行器
neotask --benchmark --executor my_tasks:handle --tasks 2000 --json

# 仓库内完整基准
git clone https://github.com/neopen/neotask.git
cd neotask
pip install -e ".[dev]"
python tests/benchmark/run_benchmark.py

neotask --benchmark 随 PyPI 包分发，默认 200 个任务、10 并发，适合快速对照；完整基准脚本位于仓库 tests/benchmark/，主套件约需 2 分钟，SQLite 探针另需约 2 分钟。复测时记录 CPU、Python 版本、存储后端与 Worker 数，否则结果不可比。

解读边界

  • 数据来自单台开发笔记本（4 核 8 线程），不能外推到服务器或容器环境。
  • 主套件与压力套件使用 Memory 后端，SQLite 数据单独测量，三者不可混用。
  • 旁路组件（metrics、health check、reporter、reclaimer、heartbeat、dead letter、retry）全部关闭，开启后吞吐会下降。
  • 延迟分位数来自单次场景，不代表长期稳定性；持续负载与突发负载应分开评估。
  • 1.0.8 事件总线改为异步队列，完成吞吐的事件口径与 1.0.7 及更早版本不可直接比较；历史数字仅作趋势参考。
不要直接引用绝对值做容量规划。请在自己的目标环境用相同脚本、相同口径复测，并把业务任务的真实耗时分布纳入评估。
