以下建议来自 1.0 系列的实际行为约束，不是通用最佳实践清单。每条都对应一个具体限制。

生产配置模板

下面是一份 Redis 多节点部署的起点配置，不是所有场景的通用答案。每个实例必须使用唯一 node_id，并显式设置 lock_type="redis"。

from neotask import TaskPool, TaskPoolConfig

config = TaskPoolConfig(
    storage_type="redis",
    redis_url="redis://10.0.0.10:6379/0",
    node_id="worker-1",          # 每个实例必须唯一
    worker_concurrency=16,
    task_timeout=60,             # 单次执行上限
    max_retries=3,
    retry_delay=2.0,
    lock_type="redis",           # 默认是 memory，多节点必须显式设置
    enable_prefetch=True,
    prefetch_size=20,
    enable_metrics=True,
)
pool = TaskPool(executor=handle, config=config)

长任务需要同时调大任务级 ttl，否则回收器会按默认 3600 秒判定运行超时。周期任务还要确认只有一个调度实例，详见 延时与周期任务。

执行器

  • 保持幂等。任务可能因重试、超时回收或节点宕机被再次执行，业务侧必须能安全重复处理。
  • 输入输出可序列化。任务数据与返回值都写入存储；返回值需可 JSON 序列化，不要返回连接、文件句柄或自定义对象。
  • 数据尽量小。任务数据随每条记录存储并参与事件传递，大对象会放大存储与网络开销。
  • 同步阻塞代码使用线程执行器。直接传同步函数时它仍运行在事件循环线程，会阻塞其他任务。
  • CPU 密集任务使用进程执行器。注意函数需可 pickle；进度上报在进程执行器中不可用。

并发与超时

  • worker_concurrency 是同时执行的任务数，不是线程数。IO 密集任务可适当调大，CPU 密集任务不应超过可用核心数太多。
  • task_timeout 控制单次执行时长；超时后任务按失败处理并进入重试流程。执行器若无法被取消（如阻塞线程），超时只停止等待，不保证底层调用已终止。
  • ttl 是任务级参数，默认 3600 秒。Redis 模式下回收器用 ttl 判断 RUNNING 任务是否超时，因此长任务需要显式传更大的 ttl。

重试

  • 自动重试只适合瞬时故障。参数错误、数据校验失败等确定性错误应直接抛出，避免无意义重试。
  • 第 n 次重试延迟为 retry_delay × n，不是指数退避。
  • 手动 retry() 只接受终态任务；retry_count 会保留，不会重置自动重试预算。

存储选型

需求选择原因
开发、单元测试memory无外部依赖，进程退出即清空
单机低频持久化SQLite单写入者约 30 tasks/s；多 writer 易锁冲突
高并发或跨节点Redis共享队列、节点心跳、故障回收与死信

预取

  • 预取优化的是队列争用，不是极短任务的吞吐。任务体只有几十微秒时，默认预取可能成为瓶颈。
  • 预取会一次取出多个任务，跨优先级的严格顺序不再成立；对顺序敏感的场景应关闭预取。
  • 需要调整时优先修改 prefetch_size，本地队列容量和触发阈值都由它推导。

关闭与回收

  • 服务退出使用 shutdown(graceful=True)，让队列中的任务执行完成；设置合理的 timeout，避免无限等待。
  • 周期任务只有在 SQLite / Redis 且 enable_persistence=True 时才能跨重启恢复；memory 模式会输出一次告警。
  • Redis 模式下节点 ID 必须唯一，否则心跳与孤儿回收会互相干扰。

可观测性

  • get_stats() 适合按需拉取；高频轮询会增加存储查询压力。
  • get_health_status() 结果缓存 5 秒，不会每次调用都触发检查。
  • 进度上报是尽力而为：任务已结束或存储暂不可写时会被丢弃，不影响任务结果。
