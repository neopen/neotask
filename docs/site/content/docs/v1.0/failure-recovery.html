故障恢复依赖 Redis 模式下的节点心跳、任务回收器与死信队列。memory 与 SQLite 模式没有自动回收能力：进程退出后，运行中的任务会停留在 running。

恢复来源

场景检测方式处理
执行超时回收器扫描 running 任务，比较 started_at 与任务 ttl未耗尽重试则重新入队，否则标记失败
节点宕机心跳超过 heartbeat_timeout 未刷新存活节点回收该节点的任务
孤儿任务任务所属节点不在活跃节点集合中回收并重新入队
僵尸锁锁 TTL 低于阈值或已过期由锁扫描器清理
重试耗尽retry_count ≥ max_retries标记失败并写入死信队列

时间参数

参数默认值作用
task_timeoutNone单次执行超时；由 Worker 计时，触发后进入重试
任务 ttl3600回收器判断运行中超时的阈值；长任务需显式调大
reclaimer_interval30回收器扫描间隔（秒）
heartbeat_interval5节点心跳间隔（秒）
heartbeat_timeout20节点失联判定（秒）
两个超时不是一回事：task_timeout 限制单次执行；任务 ttl 是回收器判断“这个 running 任务是否已经失联”的依据。仅设置 task_timeout 不会改变回收阈值，反之亦然。

回收流程

  1. 回收器发现超时或孤儿任务。
  2. 若 retry_count < max_retries，计数加一，状态重置为 pending，以 retry_delay × retry_count 的延迟重新入队。
  3. 否则状态置为 failed，写入死信队列，并释放任务锁。
  4. 每次处理都会发布 task.reclaimed 事件，负载包含原因与动作（requeued / failed）。
async def on_reclaimed(event):
    print(event.task_id, event.data)

pool.on_reclaimed(on_reclaimed)

死信队列

Redis 模式下，下列情况会写入死信队列：

  • 自动重试次数耗尽；
  • 回收后重新入队被拒绝（队列已满或已禁用）；
  • 回收时重试已耗尽。

死信保存在 neotask:dead_letter 列表与 neotask:dead_letter:index 哈希中，默认保留 7 天、最多 10000 条。当前版本没有公开的查询或重放 API，需要人工通过 Redis 客户端读取 DeadLetterQueue 数据结构，或自行封装。

边界与前提

  • 自动回收只在 storage_type="redis" 且配置 redis_url 时创建。
  • 孤儿回收需要节点管理器；没有活跃节点信息时会跳过，避免误判。
  • 回收不终止原进程中的业务代码。若旧节点恢复后仍在执行，任务可能被重复执行。
  • 锁能降低重复执行概率，但不能替代业务幂等。
  • 回收器每周期最多处理 100 个任务；大量堆积时需要多个节点共同回收。
推荐做法：为所有长任务显式设置 ttl，保持 heartbeat_timeout 小于节点重启时间，并确保任务幂等。相关配置见 配置参考。
