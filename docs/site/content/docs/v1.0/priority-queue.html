NeoTask 使用四级优先级。数值越小越优先，CRITICAL 最先被取出。优先级在提交时确定，任务执行期间不会改变。

优先级取值

枚举数值用途
TaskPriority.CRITICAL0必须尽快处理的任务
TaskPriority.HIGH1高于常规优先级
TaskPriority.NORMAL2默认值
TaskPriority.LOW3可延后处理的后台任务
 
from neotask import TaskPool, TaskPriority

pool = TaskPool(executor=handle)

pool.submit({"job": "cleanup"}, priority=TaskPriority.LOW)
pool.submit({"job": "billing"}, priority=TaskPriority.HIGH)
pool.submit({"job": "alert"}, priority=0)  # 也可直接传整数

# 批量提交共用一个优先级
pool.submit_batch([{"job": "report"}], priority=TaskPriority.NORMAL)

排序规则

存储实现同优先级顺序
memory最小堆，元素为 (priority, sequence, task_id)严格 FIFO，由自增序号保证
SQLiteORDER BY priority ASC, created_at ASC按入队时间 FIFO
RedisZSET，score 为优先级按成员字典序；默认任务 ID 带时间戳前缀，效果接近 FIFO
自定义任务 ID 会影响 Redis 顺序：Redis 中相同 score 的成员按字典序排列。如果传入无序的自定义 task_id，同优先级任务将不再按提交顺序出队。需要严格 FIFO 时请使用默认 ID 或选择 SQLite。

优先级与并发

优先级决定出队顺序，不抢占正在执行的任务。若 10 个 Worker 都在执行低优先级长任务，新到的 CRITICAL 任务仍需等待空闲 Worker。需要更低延迟时：

  • 提高 worker_concurrency，保留空闲执行能力；
  • 把长任务拆分为多个短任务，减少单次占用；
  • 为关键任务使用独立的 TaskPool 实例与存储命名空间。
没有优先级老化：队列只按数值排序，不会因为等待时间长而提升低优先级任务。持续不断的高优先级流量会让 LOW 任务长期得不到执行；需要公平性时，应在业务层限流高优先级提交，或把低优先级任务放到独立队列。

预取对顺序的影响

启用预取后，Worker 会一次从队列取出 prefetch_size 个任务放入本地队列。跨优先级的严格顺序只在每次批量出队时成立；本地队列中的低优先级任务可能先于共享队列中新到达的高优先级任务执行。

对顺序敏感的场景应设置 enable_prefetch=False，或使用 worker_concurrency=1 并将 prefetch_size 设为 1。更多说明见 预取机制。

延时任务

submit(..., delay=n) 的任务先进入延时队列，到期后再按原优先级进入优先队列。delay=0 直接进入优先队列。延时队列是进程内最小堆，不随存储持久化。
