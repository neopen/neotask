NeoTask 的定位是轻量、可嵌入、可被编排的执行层。复杂任务编排不再由本库承担：DAG、条件分支、动态路由与插件系统交给上层编排服务，NeoTask 只负责可靠地执行单个任务，并提供轻量监控指标。

1.0 上的替代方案

不在库内的能力通常可以由业务代码组合现有原语实现，或交给上层编排服务；状态与失败处理需要自行承担。

需求1.0 做法需要自行处理
串联多个任务在任务完成事件或 wait_for_result() 返回后提交下一步失败传播、超时、重复提交与断点恢复
条件分支任务返回结构化结果，由业务层决定提交哪个后续任务分支状态记录与失败补偿
并行子任务submit_batch() + wait_all()部分失败时的清理与重试策略
定时编排用 TaskScheduler 分别定义周期任务多实例重复触发；同一周期定义只应有一个调度者
多租户不在库内；由上层平台为每个租户部署独立 TaskPool 与存储资源配额、统一鉴权与跨租户统计
可视化管理使用 neotask[ui] 查看任务与指标，或基于 get_stats() 自行构建编排视图与运维后台交给上层服务

v1.1：本地任务能力补全

  • Checkpoint 断点续跑：save_checkpoint() / load_checkpoint()，重试时从检查点恢复；
  • 成本与耗时采集：report_cost()、queue_wait_ms / duration_ms 与 get_cost_summary()；
  • 父子任务关联：parent_task_id、get_children() / get_parent()，不做自动汇总；
  • 本地上下文读写（Blackboard）与自定义失败状态 report_failure()；
  • 补充 task.checkpointed / task.cost_reported 事件，支持外部指定 task_id。

v1.2：性能优化与轻量监控

  • 批量提交单事务写入、状态查询索引、调度开销优化与进度上报节流；
  • SQLite WAL 与连接复用，减少每任务新建连接的开销；
  • 标准化 get_metrics() 快照与 on_metrics() 定时推送；
  • 轻量 UI 监控指标：展示状态计数、队列深度、最老 pending 等待、存储健康等，不建设独立编排后台；
  • benchmarks/ 基准套件，发布前跑基准防止性能回退。

v1.3：监控导出与可靠性

  • 可选 Prometheus 导出器：挂载到已有 HTTP 服务或调用 render()，不默认监听端口；
  • 崩溃恢复边界：明确未入队 pending 记录不会自动执行，并在指标中计数；
  • 停机配置：明确是否 drain 未到期延时任务；
  • 自动重试、手动重试与 Checkpoint 续跑的语义矩阵。

v2.0：编排集成（后移）

待本地能力稳定且有真实多服务需求后再启动，不属于当前版本承诺。集成以上层编排服务客户端的形态提供：

  • OrchestratorClient：任务消费、事件上报、心跳与本地重试存储；
  • Redis Stream 消费者组与跨语言协议；
  • 实例注册、失联任务回收与控制消息处理。

以下能力由上层编排服务负责，不在 NeoTask 内实现：DAG 工作流、条件分支、并行编排、动态路由、插件系统、独立 Web UI、多租户隔离。

升级准备

  • 保持任务幂等：上层编排重跑、故障恢复和人工重试都会再次执行任务。
  • 只依赖公开 API：不要直接读写 Redis 键或调用内部模块，存储结构可能随版本变化。
  • 记录当前配置：升级前保存 TaskPoolConfig 与 SchedulerConfig，发布后逐项对照新版配置参考。
  • 不要把规划项写进生产依赖，也不要在 1.0 上导入尚不存在的 workflow 模块。
