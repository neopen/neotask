排查 NeoTask 问题有一条固定顺序：先确认任务处于哪个状态，再看这个状态由哪一层负责，最后检查那一层的输入（提交参数、配置、存储与上游依赖）。本文按现象组织，便于直接对照。

常见问题

任务一直 running执行器阻塞、等待外部 IO、未设置超时设置 task_timeout；检查执行器内是否有阻塞调用

日志分析

NeoTask 使用标准库 logging，默认 logger 名为 NeoTask。应用可以接管其 handler 与级别：

import logging

logging.getLogger("NeoTask").setLevel(logging.DEBUG)
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s %(message)s",
)

排查时重点关注以下关键字：

关键字含义下一步
Task execution timeout单次执行超过 task_timeout查执行器耗时与外部依赖
Queue is full队列容量耗尽扩容或限流
Failed to initialize distributed componentsRedis 组件初始化失败检查 Redis 连通性与依赖安装
slow handler / 事件丢弃计数事件回调超过阈值或有界队列溢出异步化回调，设置合理上限

日志中同时记录任务 ID 时，优先用 task_id 串联提交、执行、重试与完成记录。需要结构化日志时，在应用侧添加 JSON formatter，而不是修改库内日志格式。

错误诊断

先看状态，再看字段

result = pool.get_result(task_id)
print(pool.get_status(task_id))
print(result)
print(pool.get_task(task_id))
字段诊断价值
status确定任务处于哪一阶段
error系统异常摘要；为空不代表成功，需结合状态
failure_reason业务失败原因，与系统异常区分
retry_count是否反复失败；达到上限说明需要修业务或上游
queue_wait_ms排队时间；远大于执行时间说明容量不足
duration_ms执行耗时；接近超时阈值说明需要调参或优化
node_id定位是哪个节点执行 / 失联

再看全局快照

import json

print(json.dumps(pool.get_metrics(), ensure_ascii=False, indent=2))
print(json.dumps(pool.get_health_status(), ensure_ascii=False, indent=2))

queue_depth_by_priority 持续增长说明消费不足；oldest_pending_age_seconds 上升说明排队恶化；retry_queue_size 上升说明上游不稳定；storage_healthy=False 直接指向存储层。

性能问题

吞吐上不去

  1. 确认 worker_concurrency 与节点数；总并发是各节点并发之和。
  2. 检查执行器是否阻塞事件循环；CPU 密集任务改用进程执行器。
  3. 检查事件回调耗时；慢回调会拖慢事件消费并可能触发丢弃。
  4. 检查存储：SQLite 串行写入吞吐有限，Redis 受网络往返影响。
  5. 批量场景改用 submit_batch()，避免逐条跨事件循环往返。

延迟变高

  • queue_wait_ms 高：排队问题，扩容或提高优先级。
  • duration_ms 高：执行问题，查外部调用与锁等待。
  • 稀疏任务延迟敏感：考虑关闭预取或减小 prefetch_size；预取提高吞吐但会拉高单任务延迟。
  • 调度延迟：检查 scan_interval 与系统负载；大量延时任务可启用时间轮。

内存持续增长

  • 事件总线默认无界：设置 event_queue_max_size，并确认回调不堆积。
  • 终态记录未清理：确认 enable_terminal_cleanup=True 与保留期。
  • 进度或结果过大：缩小 result，大对象外置存储。
  • 预取过大：降低 prefetch_size。

FAQ

为什么没有 neotask start 命令？

NeoTask 是嵌入式库，不提供独立守护进程。应用启动时创建 TaskPool 或 TaskScheduler，任务随进程运行。CLI 只提供版本查询与轻量基准。

wait_for_result 超时了，任务还在跑吗？

可能仍在执行。等待超时只影响调用方，不会取消任务。用 get_status() 确认，必要时调用 cancel()。

同步函数会阻塞事件循环吗？

直接传入普通同步函数时，默认执行器会包装为异步调用，避免阻塞。但协程内部如果调用同步阻塞代码，仍会阻塞整个循环；这类逻辑应放入 ThreadExecutor 或 ProcessExecutor。

为什么 Redis 模式才有自动回收？

心跳与回收依赖跨节点视图和共享存储。Memory / SQLite 是单进程语义，没有可靠的节点注册与任务归属信息，因此不启用回收器。生产环境需要自动接管时使用 Redis 后端。

ttl 和 task_timeout 都要设吗？

建议都设。前者控制记录保留与回收判定，后者强制中断超长执行。只设其中一个都会留下盲区。

如何确认任务没有被执行两次？

锁只能降低概率，不能替代业务幂等。使用稳定的业务键做去重或 upsert，并在任务数据里携带幂等键；跨节点部署时确保使用 Redis 锁。

可以直接删除任务记录吗？

可以调用 delete(task_id)，但它不撤销已经发生的副作用。排队中的任务应先 cancel()；执行中的删除不会中断执行。

升级后需要迁移数据吗？

SQLite 会在启动时自动补齐缺失列；跨后端或跨大版本迁移请先备份并在预发验证脚本。

仍未解决：带上 neotask.__version__、后端类型、任务状态、get_metrics() 快照与相关日志，在 GitHub Issues 提问。请勿公开粘贴包含密钥或业务数据的日志。
