NeoTask uses a facade structure: only TaskPool and TaskScheduler are public, while internally it is split by responsibility into dispatch, queue, execution, lifecycle, event and storage components. All nodes are peers and no central scheduler is involved.

Task execution path

  1. Call submit() or submit_async(); TaskDispatcher creates a PENDING task and writes it to storage.
  2. QueueScheduler places the task in the priority queue; with delay > 0 it enters the delayed queue first and wakes waiting consumers.
  3. WorkerPool dequeues the task and sets it to RUNNING, acquires the task lock, binds the checkpoint, cost and failure-reporting contexts, then invokes the executor.
  4. On completion it writes SUCCESS / FAILED, publishes the event to the EventBus and wakes wait_for_result(); business failures are finalized by failure_reason, and execution duration and cost are written to the task record.
  5. If the task failed and max_retries is not exceeded, it is reset to PENDING, the latest checkpoint is injected, and it is re-enqueued with a linear delay.
Execution context: checkpoint, cost and business-failure reporting are all bound to a single execution through contextvars. Async and thread executors can call the module-level functions directly; the process executor runs in a separate process and cannot see these contexts, so the parent process must call pool.save_checkpoint(), pool.report_cost() or pool.report_failure().

Event-driven dispatch and backpressure

Workers no longer poll the queue at a fixed interval: when the local queue runs dry the prefetcher refills it immediately, and when the shared queue is empty the worker waits for an enqueue notification. Since 1.2.1, prefetching an empty queue no longer adds exponential backoff, and sparse-task latency is 1.1–2.2 ms (prefetch disabled). The EventBus likewise uses a background queue: task threads only publish events and never wait for subscribers to finish.

FieldBehavior
event_queue_max_sizeNone is unbounded; with a positive integer, a full queue drops new events and increments dropped_events
event_overflow_policyOnly "drop" is supported; any other value raises ValueError at construction
event_slow_handler_thresholdWhen a single callback exceeds the threshold, slow_handler_calls is incremented and a warning is logged

A bounded queue protects memory at the cost of event completeness; keep it unbounded when you need a full audit trail, and make sure subscribers do not perform blocking work inside callbacks. Runtime state is available through pool.event_bus.get_stats().

Decentralization boundaries

In Redis mode every node consumes the same queue; there is no primary node, leader election or task assignment. Nodes register liveness through heartbeats, and any idle node can claim and run a task. As a result:

  • TaskPool.is_leader() always returns False;
  • a task is not guaranteed to run on the node that submitted it;
  • when a node goes down, its RUNNING tasks are taken over by the reclaimer on other nodes;
  • ordering is guaranteed only for dequeue order from the queue, not for completion order across nodes.
