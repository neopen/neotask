NeoTask is an embedded library, not a standalone service: deploying NeoTask means deploying your application process and choosing a storage backend. This page covers local, container and production shapes, plus storage, network, security and upgrade notes.

Local deployment

A single-machine script or desktop tool uses Memory or SQLite directly with no extra process:

pip install neotask

# Verify
python -c "import neotask; print(neotask.__version__)"
from neotask import TaskPool, TaskPoolConfig

pool = TaskPool(
    executor=handle,
    config=TaskPoolConfig.sqlite("/var/lib/myapp/neotask.db"),
)
  • During development use TaskPoolConfig.memory(); it clears on restart, which keeps runs reproducible.
  • Use SQLite when tasks must survive a restart, and make sure the directory exists and the runtime user can write to it.
  • Scheduled work uses SchedulerConfig.sqlite(); periodic jobs registered against Memory do not recover after a restart.

Docker deployment

NeoTask starts with your application process, so the image is "your app plus the neotask dependency". A generic Dockerfile:

FROM python:3.12-slim

ENV PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# Default SQLite path /data/neotask.db; mount a persistent volume
RUN mkdir -p /data && chown -R 10001:10001 /data
USER 10001

CMD ["python", "-m", "myapp.worker"]

Declare neotask[redis] or neotask[monitor] in requirements.txt as needed. Application code must handle SIGTERM: call pool.shutdown(graceful=True, timeout=30) so in-flight tasks finish and queue state is written back.

docker build -t myapp-worker .
docker run --rm -v neotask-data:/data --env-file .env myapp-worker

Docker Compose

For a shared queue across nodes, start Redis and two peer workers with Compose:

services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes", "--requirepass", "${REDIS_PASSWORD}"]
    volumes:
      - redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "-a", "${REDIS_PASSWORD}", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5

  worker-a:
    build: .
    command: ["python", "-m", "myapp.worker"]
    environment:
      NEOTASK_REDIS_URL: "redis://:${REDIS_PASSWORD}@redis:6379/0"
      NEOTASK_CONCURRENCY: "8"
    depends_on:
      redis:
        condition: service_healthy
    stop_grace_period: 40s

  worker-b:
    build: .
    command: ["python", "-m", "myapp.worker"]
    environment:
      NEOTASK_REDIS_URL: "redis://:${REDIS_PASSWORD}@redis:6379/0"
      NEOTASK_CONCURRENCY: "8"
    depends_on:
      redis:
        condition: service_healthy
    stop_grace_period: 40s

volumes:
  redis-data: {}

worker-a and worker-b run the same code against the same queue; there is no primary/replica setup. Each process gets a node_id that includes its pid, which is already unique inside a container.

Production deployment

ShapeStorageScaleWatch out for
Single process, embeddedSQLiteLow concurrency, one machineKeep a single writer; back up regularly
Multi-process, one machineSQLite read queries + one writing processModerate concurrencyNever let processes write the same file concurrently
Shared queue across nodesRedisHorizontal scalingRedis high availability; lock and heartbeat settings
Separated scheduler and workersRedis / SQLiteMany periodic jobsRegister periodic jobs from a single scheduler instance

Production checklist:

  • Deploy separately from the web service: the web process only submits, workers execute, so long tasks never occupy request threads.
  • Set task_timeout and a generous ttl; raise both together for long tasks.
  • In Kubernetes set terminationGracePeriodSeconds above shutdown(timeout) so graceful exit can finish.
  • Enable metrics and health checks; probe with get_health_status(), not high-frequency calls to get_stats().
  • Bound event_queue_max_size in production so a slow handler cannot grow memory without limit.
  • Register periodic jobs on exactly one instance, or rely on Redis periodic persistence and mutual exclusion.
  • If you need automatic reclamation of tasks from crashed nodes, use Redis. Memory / SQLite have no heartbeat or reclaimer, so running records left by an abnormal exit need manual handling.

See Configuration · Environment variables for the mapping code. Inject passwords and connection strings as secrets; never bake them into images or log them.

Storage and databases

BackendStrengthsLimitsBackup
MemoryZero config, lowest latencyLost on exit; not shared across processesNone needed
SQLiteSingle file, transactional, easy to back upSingle writer; unsuitable for network filesystemssqlite3 .backup or a file snapshot
RedisShared across nodes, low latencyOperational overhead; memory capacity limitsRDB / AOF plus managed snapshots
  • Keep the SQLite file on local persistent disk, never on NFS / SMB mounts.
  • Enable AOF or periodic RDB on Redis, and accept a bounded loss window for tasks and events.
  • Terminal records are cleaned up per ttl or terminal_retention_seconds; export them in event callbacks when you need long-term audit.
  • 1.2.1 automatically adds missing columns to SQLite databases created by 1.0.x; cross-backend migration still uses the migration scripts in the repository.

Network configuration

  • Redis: enable authentication and TLS (rediss://) in production, and restrict security groups to worker subnets.
  • Connections: the Redis pool cap is set by redis_max_connections (default 50); size it from per-node concurrency and replica count.
  • Latency: a cross-AZ Redis adds submit and heartbeat latency; co-locate it with workers when latency matters.
  • SQLite: local file access only, no network port; mount it as a volume inside containers.
  • Health checks: expose an HTTP probe from your application that calls get_health_status(); do not expose the Redis port to the probe system.

Security deployment

  • Run containers as a non-root user with a read-only root filesystem and only the data volume writable.
  • Always set a Redis password; never expose port 6379 to the public internet.
  • Task data, result and checkpoints are persisted; avoid plaintext credentials and encrypt on the application side when required.
  • Executors are registered through code; never dynamically import modules or execute arbitrary code from external input.
  • Restrict read permissions on SQLite files and backups; backups contain the same business data.
  • Read release notes before upgrading and watch for default changes and security fixes.

Upgrade guide

  1. Read the release notes: confirm default changes, deprecations and behavior changes in the target version.
  2. Back up storage: copy the SQLite database file; trigger one Redis snapshot.
  3. Validate in staging: run the same submit, retry, cancel and recovery cases with identical config.
  4. Upgrade the dependency: pip install -U "neotask[redis,monitor]" and verify neotask.__version__.
  5. Rolling restart: restart nodes one at a time in a multi-node setup; let old nodes shut down gracefully before new ones take over the queue.
  6. Watch metrics: queue depth, age of the oldest pending task, failure rate and reclamation count.

SQLite upgrades only auto-add columns with defaults. Back up before any major-version or cross-backend migration, validate the scripts in staging, and never trial-run a migration against production.
