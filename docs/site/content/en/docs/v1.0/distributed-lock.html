Task locks keep the same task from running on several nodes at once. The default is an in-memory lock that works only within a process; cross-node mutual exclusion requires the Redis lock.

Enable

from neotask import TaskPool, TaskPoolConfig

config = TaskPoolConfig(
    storage_type="redis",
    redis_url="redis://10.0.0.10:6379/0",
    node_id="worker-1",
    lock_type="redis",       # key: explicitly enable cross-node locks
    lock_timeout=30,
)
pool = TaskPool(executor=handle, config=config)
Default-value trap: TaskPoolConfig.redis() turns on both Redis storage and the Redis lock, but when you build TaskPoolConfig(storage_type="redis", ...) by hand, lock_type still defaults to "memory". A multi-node deployment that does not use the factory method must set lock_type="redis" explicitly.

Automatic locking

The worker acquires the lock automatically before running each task, using the key lock:task:{task_id} (RedisLock prefix lock:), and releases it when the task ends.

PropertyBehavior
TTLAutomatic locks use a fixed 30 seconds
RenewalA watchdog renews every TTL × 0.3 (minimum 0.5 seconds)
ReleaseA Lua script checks the owner before deleting, so another holder's lock is never removed
Acquisition failureThis run is skipped and the task stays pending

The lock is acquired when the task starts and released when it ends; it does not cover the queueing phase. So the same task never starts on two workers at once, but duplicate execution after an execution timeout or a lost node is still possible, and business code must be idempotent.

Manual locking

if pool.acquire_lock("report-2026-10", ttl=60):
    try:
        generate_report()
    finally:
        pool.release_lock("report-2026-10")
MethodNotes
acquire_lock(task_id, ttl=30)Acquires the task:{task_id} lock and returns whether it succeeded
release_lock(task_id)Releases the lock held by this instance

Manual locks and automatic task locks share one namespace. Do not use the ID of a running task as a manual lock key, or you will contend with the worker.

Implementation details

StepImplementation
AcquireSET key owner NX EX ttl
ReleaseLua: DEL only if the value equals owner
RenewalLua: EXPIRE only if the value equals owner
ownerA random UUID generated per lock instance and kept in-process
Not reentrant: Acquiring the same lock again from the same instance fails. If you need reentrancy, merge the critical sections in business code rather than calling acquire_lock() repeatedly.

Correctness boundaries

  • A lock guarantees "one holder at a time", not "executed exactly once". Execution timeouts, process pauses (GC, container freeze) and network partitions can all cause duplicate execution.
  • The watchdog can renew only while its process is alive; after the process is killed the lock expires within the TTL.
  • A Redis primary/replica failover can drop lock writes that were not yet replicated. Strong consistency needs additional mechanisms such as Redis Cluster/Redlock, which this version does not include.
  • If the lock TTL does not match task duration, a long task can lose its lock while still running. Automatic locks use a fixed 30 seconds with continuous renewal; manual locks need a ttl you set high enough.
