Multi-node deployments use Redis as shared storage. All nodes consume the same queue, with no primary node, leader election or task assignment; any node can submit and execute tasks.

Prerequisites

  • All nodes connect to the same Redis database and set a unique node_id;
  • install neotask[redis];
  • the code and task data format are identical on every node;
  • business tasks can be safely executed more than once.
pip install "neotask[redis]"

Node configuration

from neotask import TaskPool, TaskPoolConfig

config = TaskPoolConfig(
    storage_type="redis",
    redis_url="redis://10.0.0.10:6379/0",
    node_id="worker-1",          # must be unique per node
    lock_type="redis",           # cross-node mutual exclusion must be enabled explicitly
    worker_concurrency=20,
    heartbeat_interval=5,
    heartbeat_timeout=20,
    reclaimer_interval=30,
)
pool = TaskPool(executor=handle, config=config)
pool.start()
Hand-built configs still default to the in-memory lock: TaskPoolConfig.redis() sets lock_type to "redis" automatically in 1.0.8, but when you construct TaskPoolConfig(storage_type="redis", ...) directly, lock_type still defaults to "memory" and the task lock is valid only inside the process, so it cannot prevent duplicate execution across nodes.

How it runs

Start the same process on every machine. A task submitted to any node enters the shared queue and is executed by whichever node picks it up first.

             ┌──────────── Redis ────────────┐
             │ queue:priority   task:*       │
             │ neotask:nodes    lock:*       │
             └───────▲───────────▲───────────┘
                     │           │
          ┌──────────┴──┐   ┌────┴──────────┐
          │  worker-1   │   │  worker-2     │
          │ TaskPool    │   │ TaskPool      │
          └─────────────┘   └───────────────┘

Node discovery

CapabilityDescription
RegistrationWrites neotask:node:{node_id} at startup and joins neotask:nodes
HeartbeatRefreshed every 5 seconds by default; the key expires at twice the heartbeat timeout
LivenessNo refresh for longer than heartbeat_timeout (20 seconds by default) marks the node as unreachable
Querypool.get_active_nodes() returns node ID, hostname and process ID
 
pool.get_active_nodes()
# [{"node_id": "worker-1", "hostname": "host-a", "pid": 1234}, ...]

Leaderless architecture

  • pool.is_leader() always returns False; there is no leader;
  • tasks are not bound to the submitting node and may execute on any node;
  • when a node goes down, its running tasks are reclaimed by surviving nodes and re-enqueued;
  • the queue guarantees dequeue order only, not completion order across nodes.

Multi-node limits for scheduled tasks

TaskScheduler has no leader election or distributed deduplication. When several scheduler instances register the same periodic task, each instance fires it on its own clock, producing duplicate executions.

  • Register periodic tasks on a single scheduler instance;
  • or make the periodic task itself idempotent and add distributed mutual exclusion on the application side;
  • nodes that only need immediate tasks can use TaskPool alone and should not start TaskScheduler.

Scaling

OperationSteps
Scale outStart a new node with a new node_id; it begins consuming the shared queue automatically
Scale inCall shutdown(graceful=True) and exit after the queue drains
Forced removalTerminate the process directly; other nodes reclaim its tasks once the heartbeat times out
