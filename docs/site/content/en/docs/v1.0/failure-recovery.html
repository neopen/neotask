Failure recovery relies on node heartbeats, the task reclaimer and the dead letter queue in Redis mode. Memory and SQLite modes have no automatic reclamation: after a process exits, running tasks remain in running. Terminal cleanup only deletes finished records and is not part of failure recovery.

Timing parameters

The two timeouts are not the same: task_timeout bounds a single execution; the task ttl is what the reclaimer uses to decide whether a running task has lost contact. Setting only task_timeout does not change the reclaim threshold, and vice versa.

Reclaim flow

  1. The reclaimer detects a timed-out or orphaned task.
  2. If retry_count < max_retries, the count is incremented, the status reset to pending, and the task re-enqueued with a delay of retry_delay × retry_count.
  3. Otherwise the status is set to failed, the task is written to the dead letter queue, and the task lock is released.
  4. Every handling publishes a task.reclaimed event whose payload contains the reason and the action (requeued / failed).
async def on_reclaimed(event):
    print(event.task_id, event.data)

pool.on_reclaimed(on_reclaimed)

Dead letter queue

In Redis mode, the dead letter queue receives tasks in the following cases:

  • automatic retries are exhausted;
  • the re-enqueue after reclamation is rejected (queue full or disabled);
  • retries were already exhausted at reclaim time.

Dead letters are stored in the neotask:dead_letter list and the neotask:dead_letter:index hash, kept for 7 days and up to 10,000 entries by default. The current version exposes no query or replay API, so you must read the DeadLetterQueue data structures manually through a Redis client or wrap them yourself.

Business failures versus system errors

Since 1.1 an executor can explicitly register a "business check failed" outcome. It is handled differently from an exception: a business failure is finalized as failed immediately, does not enter automatic retry, and is not written to the dead letter queue.

from neotask import report_failure

async def review(data):
    score = await grade(data["answer"])
    if score < 60:
        report_failure("qa_failed", f"score={score}")
    return {"score": score}

Inside an executor, report_failure() is synchronous: it only registers the outcome and does not interrupt the business code. When the task function returns normally, the worker marks the task failed with the registered reason. The first registration wins, and later calls do not override the reason. Thread executors work the same way; process executors have no access to this context and return False.

The parent process of a process executor, or an external orchestrator, uses the task-level API:

# applies to running tasks only
pool.report_failure(task_id, "qa_failed", "score=42")
  • The task-level report_failure() finalizes the task immediately; for tasks still in pending, call cancel() first.
  • The task's error field reads reason: detail; when no detail is provided, only the reason is written.
  • Read the verdict through failure_reason in get_result() / get_task(), which distinguishes it from exhausted retries.
  • A business failure is not resumed automatically; call retry(task_id) explicitly to continue from a checkpoint.

Boundaries and preconditions

  • Automatic reclamation is created only when storage_type="redis" and redis_url are configured. Since 1.0.8, enable_reclaimer and enable_heartbeat genuinely control component creation; disabling heartbeats removes the node liveness view and orphan reclamation is skipped.
  • Orphan reclamation requires the node manager; without active node information it is skipped to avoid false positives.
  • Reclamation does not terminate the business code in the original process. If the old node recovers and is still executing, the task may run twice.
  • Locks reduce the probability of duplicate execution but do not replace business-level idempotency.
  • The reclaimer handles at most 100 tasks per cycle; with a large backlog, several nodes must reclaim together.
Recommended practice: set an explicit ttl for every long task, keep heartbeat_timeout below the node restart time, and make tasks idempotent. See Configuration for the related settings.
