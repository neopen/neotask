The storage backend determines whether task records, queues and periodic definitions survive a process exit. NeoTask 1.x provides three implementations — memory, SQLite and Redis — selected with storage_type.

memory

from neotask import TaskPool, TaskPoolConfig

pool = TaskPool(executor=handle, config=TaskPoolConfig.memory())

Tasks, the queue and periodic definitions exist only in the current process. Everything is lost when the process exits, and no heartbeat, reclaimer or dead letter queue is created. The Blackboard shared context is available only on this backend and is likewise not persisted.

SQLite

config = TaskPoolConfig.sqlite("/var/lib/neotask/neotask.db")
pool = TaskPool(executor=handle, config=config)

The database contains four groups of tables:

TableContents
tasksTask data, status, priority, node, retry count, result, progress, failure reason, parent-child links, cost and duration
queueID, priority and enqueue time of tasks waiting to execute
task_checkpointsCheckpoint state for resuming, stored by (task_id, version)
periodic_tasks / periodic_executionsPeriodic task definitions and execution records (when persistence is enabled)
Concurrent write limits: SQLite writes on a single connection are already serialized, so concurrent submissions from multiple workers in the same process do not raise database is locked. Writes still execute one after another, and additional workers do not produce linear scaling. In the 1.2.1 end-to-end comparison, 1,000 tasks with 4 workers reached 519 tasks/s at P50 1.0 s; the Memory backend measured 4,761 tasks/s on the same path. A single writer is still recommended in production; switch to Redis when you need high-concurrency writes.

The path must be writable and its directory must already exist. In containers, mount a persistent volume rather than placing the file on the container's ephemeral layer.

Redis

config = TaskPoolConfig.redis(
    "redis://127.0.0.1:6379/0",
    node_id="worker-1",
)
pool = TaskPool(executor=handle, config=config)

All nodes must connect to the same Redis database and use a unique node_id. Redis mode enables node heartbeats, task reclamation, the dead letter queue and distributed locks. TaskPoolConfig.redis() sets lock_type to "redis" automatically; if you construct TaskPoolConfig(storage_type="redis", ...) by hand, lock_type still defaults to "memory", so multi-node deployments must set it to "redis" explicitly.

Automatic upgrade of existing databases (1.1)

1.1.0 adds seven columns to task records — failure_reason, checkpoint_version, parent_task_id, estimated_cost, cost_tracking, queue_wait_ms and duration_ms — and adds the task_checkpoints table. Upgrading from 1.0.x requires no manual migration:

  • When an existing SQLite file is opened, the startup path issues ALTER TABLE ADD COLUMN for each missing column, and a missing task_checkpoints table is created automatically;
  • 1.1.1 adds TaskRepository.ensure_ready(); TaskPool.start() returns only after the schema is ready, so queries at startup cannot hit missing columns;
  • When several repositories or processes open the same old database at the same time, repeated column additions are treated as idempotent and no longer crash with duplicate column name; other errors are still raised.

The automatic upgrade only adds columns and default values; it does not move data and does not replace migration scripts between backends. Back up the SQLite file before upgrading. New columns read as their default values on old records, so no backfill is needed.

Cleanup

1.0.8 enables terminal cleanup by default: every terminal_cleanup_interval (60 seconds by default) a scan deletes success / failed / cancelled records older than the retention period. The retention period comes from terminal_retention_seconds; 0 means reusing each task's own ttl (3600 seconds by default).

config = TaskPoolConfig(
    enable_terminal_cleanup=True,
    terminal_cleanup_interval=60.0,
    terminal_retention_seconds=7 * 24 * 3600,  # keep terminal records for 7 days
)

# trigger one cleanup manually; returns the number of deleted records
pool.cleanup_terminal_tasks()

A task-level ttl is also what the reclaimer uses to detect a running timeout, so it affects both failure reclamation and the default terminal retention period. To keep audit records long term, disable automatic cleanup or set a larger terminal_retention_seconds and archive records yourself. Checkpoints of cleaned-up tasks are deleted as well; the dead letter queue still expires per dead_letter_ttl (7 days by default) and is unaffected by terminal cleanup.
