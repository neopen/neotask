NeoTask uses four priority levels. Lower numbers run first, so CRITICAL is dequeued first. Priority is fixed at submission time and never changes while the task executes.

Priority values

EnumValueUse
TaskPriority.CRITICAL0Work that must be handled as soon as possible
TaskPriority.HIGH1Above normal priority
TaskPriority.NORMAL2Default
TaskPriority.LOW3Background work that can be deferred
 
from neotask import TaskPool, TaskPriority

pool = TaskPool(executor=handle)

pool.submit({"job": "cleanup"}, priority=TaskPriority.LOW)
pool.submit({"job": "billing"}, priority=TaskPriority.HIGH)
pool.submit({"job": "alert"}, priority=0)  # integers work too

# One priority for the whole batch
pool.submit_batch([{"job": "report"}], priority=TaskPriority.NORMAL)

Ordering rules

StorageImplementationOrder within the same priority
memoryMin-heap of (priority, sequence, task_id)Strict FIFO, guaranteed by an auto-incrementing sequence
SQLiteORDER BY priority ASC, created_at ASCFIFO by enqueue time
RedisZSET with the priority as scoreLexicographic by member; default task IDs carry a timestamp prefix, so the result is close to FIFO
Custom task IDs affect Redis ordering: members with the same score are ordered lexicographically in Redis. If you pass unordered custom task_id values, same-priority tasks no longer dequeue in submission order. For strict FIFO, use default IDs or choose SQLite.

Priority and concurrency

Priority decides dequeue order; it does not preempt running tasks. If all 10 workers are executing long low-priority jobs, a newly arrived CRITICAL task still waits for an idle worker. To reduce latency:

  • raise worker_concurrency to keep idle execution capacity;
  • split long jobs into several shorter tasks so each one holds a worker briefly;
  • give critical work a dedicated TaskPool instance and storage namespace.
No priority aging: the queue sorts by value only and never promotes a low-priority task because it has waited long. Sustained high-priority traffic can starve LOW tasks indefinitely; when you need fairness, rate-limit high-priority submissions in the business layer or move low-priority work to a separate queue.

How prefetch affects ordering

With prefetch enabled, a worker pulls prefetch_size tasks from the queue into its local queue at once. Strict cross-priority ordering holds only within each batch dequeue; a low-priority task already in the local queue can run before a high-priority task that arrives later on the shared queue.

For order-sensitive workloads, set enable_prefetch=False, or use worker_concurrency=1 with prefetch_size set to 1. See Prefetching for details.

Delayed tasks

Tasks submitted with submit(..., delay=n) enter the delayed queue first and move to the priority queue at their original priority once they are due. delay=0 goes straight to the priority queue. The delayed queue is an in-process min-heap and is not persisted with storage.
