1.1 filled in three cross-task capabilities: parent-child task links, a caller-supplied task_id, and an in-process shared context (Blackboard) in memory mode. NeoTask only records, queries and stores; it does not orchestrate dependencies, aggregate state or share data across nodes.

Parent-child task links

Pass parent_task_id at submit time to attach a child task to a parent. The link is written to the task record only: NeoTask does not check that the parent exists, and it changes neither execution order nor parent waiting.

parent_id = pool.submit({"batch": "2026-11"}, task_id="batch-2026-11")
child_ids = [
    pool.submit({"doc": doc}, parent_task_id=parent_id)
    for doc in documents
]
MethodReturnsNotes
get_children(task_id)List[str]Queries by parent_task_id, oldest first; returns an empty list if the parent does not exist
get_parent(task_id)str | NoneNone if the task does not exist or has no parent
get_result(task_id)dictIncludes parent_task_id
No automatic aggregation: a parent finishes with its own executor return value, and child success or failure does not change the parent's state. get_children() returns IDs only; to aggregate, call wait_all() or get_result() from your business code or from an upper-layer orchestration service (NeoFlow).

submit_batch() and create_pending_task() currently have no parent_task_id parameter; when you need parent-child links, submit items one by one with submit(). Redis and SQLite maintain a lookup index for each parent, but with many children under a single parent you should still consume the results in pages.

Caller-supplied task_id

submit(), submit_async() and create_pending_task() all accept a caller-supplied task_id, which makes it easy to map a business key to a task ID.

pool.submit({"order_id": 42}, task_id="order-42")

# Submit again while the same ID still exists, including terminal states
pool.submit({"order_id": 42}, task_id="order-42")
# TaskAlreadyExistsError
  • Uniqueness is guaranteed by an atomic create in the storage layer: when several nodes submit the same ID at once, only one succeeds and the rest raise TaskAlreadyExistsError.
  • It prevents duplicate creation only; it does not mean the task executes once. Retries, reclamation and manual retry() still re-execute it, so business logic must remain idempotent.
  • To re-run a task that already has an ID, call retry(task_id); after deleting the record you can create it again, but that task's checkpoints are deleted as well.

Blackboard: in-process shared context

The Blackboard is a key-value space that ships with every TaskPool instance, letting tasks in the same process read shared state such as feature flags, temporary credentials or batch metadata. It is available only with the memory storage backend.

pool.context_set("feature_flags", {"qa": True}, ttl=600)
flags = pool.context_get("feature_flags") or {}
pool.context_delete("feature_flags")
MethodNotes
context_set(key, value, ttl=None)Writes or overwrites; ttl is in seconds and None means no expiry
context_get(key)Reads; returns None if the key is missing or expired
context_delete(key)Deletes; returns whether the key was found
  • Both writes and reads deep-copy values, so mutating a returned value does not affect stored content.
  • TTL is lazy: expiry is evaluated on read and expired keys are swept on write; no background thread is started.
  • The context exists only in the current process: it does not cross processes or nodes and is not persisted with tasks, so it is lost when the process exits.
  • When storage_type is not memory, these methods raise UnsupportedFeatureError; use external storage for state shared across nodes.
  • TaskScheduler's context_* methods delegate to its internal TaskPool, so their scope is limited to that scheduler instance as well.
Concurrent writes: the Blackboard guarantees thread safety for single-key reads and writes only and provides no multi-key transactions. When several tasks read-modify-write the same key at once, they overwrite each other; use a database or Redis when you need atomic counters or state machines.
