WHY NEOTASK

Lightweight, not limited.

An embedded task runtime built for time-consuming work: from in-process background jobs to a queue shared across nodes, with one API and one mental model.

One less middleware, one less failure class

Memory or SQLite by default, usable as soon as your app starts. No broker, worker fleet and monitoring stack to maintain for a few dozen background jobs.

Your app → TaskPool → SQLite

From one process to many nodes, same API

One config factory moves you to a Redis shared queue: peer nodes consume competitively, and heartbeat plus the reclaimer take over tasks left behind by a failed node.

node-1 node-2 node-3 Redis Queue

Observable by default, recoverable on failure

Lifecycle events, metrics and health checks work out of the box; failures retry automatically, and timed-out or orphaned tasks return to the queue through the reclaimer.

Submit and wait for the result

Define an async executor, create a TaskPool, submit tasks. Use the synchronous, asynchronous or context-manager form as needed.

  • Starts the background event loop automatically
  • Result waiting and status queries
  • Graceful shutdown on exit

Delays, intervals and Cron

TaskScheduler adds scheduling on top of TaskPool; all three modes share the same executor.

  • Delayed execution and run-at timestamps
  • Fixed-interval periodic jobs
  • Cron expressions with pause and resume

Switch to a shared queue

Use a config factory to move to Redis: multiple nodes consume one queue, and heartbeat, reclamation and task locks come along automatically.

  • Peer nodes, no master
  • Redis locks with watchdog renewal
  • Optional prefetch for throughput

from neotask import TaskPool

async def process_order(data):
    # Time-consuming business logic
    await asyncio.sleep(2)
    return {"status": "ok", "id": data["id"]}

pool = TaskPool(executor=process_order)

task_id = pool.submit({"id": "order_001"})
result = pool.wait_for_result(task_id, timeout=30)

print(result)
pool.shutdown()
from neotask import TaskScheduler

scheduler = TaskScheduler(executor=process_order)

# Run once after 60 seconds
scheduler.submit_delayed({"id": "123"}, delay_seconds=60)

# Run every 5 minutes
scheduler.submit_interval(
    {"job": "heartbeat"},
    interval_seconds=300,
)

# Run daily at 09:00
scheduler.submit_cron(
    {"job": "daily_report"},
    cron_expr="0 9 * * *",
)

scheduler.shutdown()
from neotask import TaskPool, TaskPoolConfig

cfg = TaskPoolConfig.redis(
    url="redis://localhost:6379/0",
    node_id="worker-1",
    lock_type="redis",
    enable_prefetch=True,
    prefetch_size=30,
)

pool = TaskPool(executor=process_order, config=cfg)

# Same code, a queue shared across nodes
task_id = pool.submit({"id": "order_002"})
result = pool.wait_for_result(task_id)

When should you choose NeoTask?

FAQ

Frequently asked questions

Still have questions? Start a thread in GitHub Discussions.

Does NeoTask require Redis or a message queue?

No. Memory or SQLite is used by default, so it works inside your application process right after install. Switch to Redis only when multiple nodes must share the queue.

How is it different from Celery?

NeoTask is lighter: no broker, with scheduling, priorities and a storage abstraction built in, which suits embedded scenarios. Celery has a more mature ecosystem, complex workflow orchestration and operational tooling, which suits existing large task platforms.

Are failed tasks retried automatically?

Yes. max_retries and retry_delay configure the attempt count and linear delay; tasks left behind by a crashed node are re-queued by the reclaimer, and tasks that keep failing enter the dead letter queue.

Does it support Python 3.8?

Yes. The base package requires Python ≥ {{PYTHON}} and depends on aiosqlite, croniter and colorama; Redis, psutil and the Web UI are optional extras installed via neotask[redis], neotask[ui] or neotask[full].

Can it be used in production?

Yes. Since v1.0 it has shipped persistence, failure recovery, distributed locks, a dead letter queue and metrics collection. Use SQLite or Redis persistence, configure retries and monitoring for critical tasks, and read the production practices before going live.
