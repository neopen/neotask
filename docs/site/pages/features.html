01 · 即时任务

提交即执行，优先级决定顺序

TaskPool 接收任务后立即交给 Worker 池处理。四级优先级让关键任务在突发流量下优先获得执行机会，同优先级保持 FIFO。

  • 同步、异步与批量提交
  • 结果等待、状态查询与取消
  • 上下文管理器自动启停

03 · 可靠性

失败可重试，节点故障可回收

执行异常按配置自动重试；心跳过期与回收器把失联节点上的任务重新放回队列。最终失败的任务进入死信队列，等待人工处理。

  • 自动重试与退避
  • 孤儿任务回收与僵尸锁扫描
  • 死信队列保留失败现场

04 · 持久化

三种存储，同一套抽象

根据部署规模选择后端：开发时用内存，单机持久化用 SQLite，多节点共享用 Redis。存储切换不需要改动业务代码。

  • Memory：零配置，进程内
  • SQLite：单文件落盘
  • Redis：共享队列与状态索引

05 · 分布式

对等节点，无主架构

切换 Redis 后，多个节点对等消费共享队列。心跳维护节点存活状态，锁与看门狗避免重复执行，预取减少往返开销。

  • 抢占式消费，无需调度中心
  • Redis 分布式锁与看门狗续期
  • 可选预取与批量操作

HONEST LIMITS

知道它不做什么，比知道它做什么更重要

NeoTask 是一个聚焦的任务队列，而不是万能工作流平台。以下能力目前不具备，或仅以可选项提供：

  • —
    DAG 工作流编排

    规划于 v1.5，当前版本未实现。多任务串联请在业务层组合提交与等待。

  • —
    多租户与配额

    暂无租户隔离与资源配额，规划在企业级版本中提供。

  • ○
    Web UI

    以 neotask[ui] 扩展提供，需要自行装配，TaskPool 不会自动挂载。

  • ○
    进度回调

    v1.0.5 起任务内可调用 report_progress() 上报进度，通过 on_progress 订阅；进程执行器无法共享上下文，进度不可用。
