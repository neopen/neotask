# NeoTask 性能优化建议

> 适用版本：NeoTask 1.0.5（PyPI）  
> 数据来源：`性能基准测试.md`、`E:\neotask-demo\bench\results.json`、`E:\neotask-demo\bench\sqlite_results.json`  
> 测试平台：Windows 10 / Python 3.13.15 / i7-1165G7（4 核 8 线程）

本文只回答一个问题：**在 NeoTask 1.0.5 上，改哪个参数、按什么顺序改、预期能拿到多少收益。** 所有数字都来自同一台机器的实测；绝对值不可直接外推，相对趋势可以直接参考。

## 0. 优化优先级

先做 P0，再考虑 P1。P0 的两项如果配错，后面的调参基本无效。

| 优先级 | 动作 | 适用条件 | 实测依据 | 预期收益 |
|--------|------|----------|----------|----------|
| P0 | 同步阻塞/CPU 任务改用 `ThreadExecutor` / `ProcessExecutor` | 任务是同步阻塞或 CPU 密集型函数 | CPU 任务在 async 执行器内 1,110 → 1,269/s，仅 1.14x | 把任务移出事件循环，上限取决于核数 |
| P0 | 极短任务关闭预取 | 单任务执行 < 1 ms | 关闭 2,382/s，默认预取 181/s | 关闭后吞吐为默认的 **13x** |
| P1 | 按任务类型设置 worker 数 | IO 密集或执行时间占比高 | IO 任务 1→8 workers，7.76x | 最高接近线性 |
| P1 | 大批量结果回收改用事件 | 一次提交数千任务 | 事件 2,433/s，3,000 waiter 759.6/s | **3.2x** |
| P1 | 高并发场景替换 SQLite | QPS 高或多 worker 写入 | SQLite 串行 30.1/s，多 worker 出现 `database is locked` | 串行口径约 2.1x |
| P2 | 压测时关闭旁路组件 | 做容量测试/基准 | 主套件关闭 metrics、health、reclaimer、heartbeat、dead letter、retry | 消除旁路噪声 |
| P2 | 周期任务启用时间轮 | `interval < 1s` | 默认 `scan_interval=1.0s` | 提升定时精度（本轮未测吞吐） |

## 1. 先判断瓶颈在哪一层

四条基线数字：

| 指标 | 实测值 | 含义 |
|------|--------|------|
| 提交吞吐 | **14,657 tasks/s** | 创建任务 + 落库 + 入队的成本，单任务约 **68 μs** |
| 完成吞吐（noop） | **2,433 tasks/s** | 排队 + 生命周期 + 状态写回 + 事件通知的合计上限 |
| 单任务往返 P50 | **15.50 ms** | 无积压时一次 submit→complete 的延迟 |
| 持续负载 | **2,565 tasks/s** | 在途 200、5 秒窗口、0 失败 |

由此得到三个判断：

1. **提交不是瓶颈。** 单任务约 68 μs，提交侧通常不是首先要优化的环节。
2. **noop 的完成吞吐只有 2,433/s，而队列本身能到 240,000 ops/s。** 说明剩余成本在生命周期、状态写回和事件分发，不在队列。
3. **优化顺序取决于任务执行时间 `t`。**

| 任务执行时间 | 主要矛盾 | 先做什么 |
|--------------|----------|----------|
| `t < 1 ms` | 预取节奏、生命周期开销 | 关闭预取；不要盲目加 worker |
| `1 ms ≤ t < 50 ms` | 执行并发度 | 匹配执行器、调 worker、按公式设置预取 |
| `t ≥ 50 ms` | 执行器/外部依赖 | 执行器与下游容量，调度层几乎可忽略 |

## 2. P0：执行器必须与任务类型匹配

### 2.1 实测：错误用法下加 worker 几乎无效

任务体是 5000 次同步累加，放在 async 执行器里：

| Workers | 完成吞吐 | 相对 1 worker |
|---------|----------|---------------|
| 1 | 1,110/s | 1.00x |
| 4 | 1,215/s | 1.09x |
| 10 | 1,269/s | 1.14x |

同步循环阻塞了事件循环，worker 从 1 加到 10 只提升 14%。这不是 NeoTask 的上限，而是**执行器选错**的结果。

### 2.2 一个容易踩的坑：`executor_type` 对同步函数不生效

`TaskPool._init_executor` 的逻辑是：

```python
# 简化自 neotask/api/task_pool.py
if not inspect.iscoroutinefunction(executor):
    async def wrapped_executor(data):
        return executor(data)
    return ExecutorFactory.create(wrapped_executor)   # 直接按异步创建

return ExecutorFactory.create(
    executor,
    executor_type=self._config.executor_type,
    max_workers=self._config.max_workers,
)
```

也就是说，**传入同步函数时，它会被包装成 `async def`，`config.executor_type=THREAD` 不会把它送进线程池。** 必须显式传入执行器实例。

### 2.3 正确写法

阻塞 IO（同步 HTTP、文件、数据库驱动）：

```python
from neotask import TaskPool, TaskPoolConfig, ThreadExecutor

def blocking_io(payload):
    # 例如 requests.get(...) 或 time.sleep(0.02)
    return payload

pool = TaskPool(
    executor=ThreadExecutor(blocking_io, max_workers=8),
    config=TaskPoolConfig(
        worker_concurrency=8,
        enable_prefetch=True,
        prefetch_size=60,      # 见第 3 节公式
        storage_type="memory",
    ),
)
```

CPU 密集：

```python
from neotask import TaskPool, TaskPoolConfig, ProcessExecutor

def cpu_bound(payload):
    return sum(range(5000))

if __name__ == "__main__":          # Windows 进程池必需
    pool = TaskPool(
        executor=ProcessExecutor(cpu_bound, max_workers=4),
        config=TaskPoolConfig(
            worker_concurrency=4,
            enable_prefetch=False,
            prefetch_size=1,
            storage_type="memory",
        ),
    )
```

### 2.4 选型规则

| 任务类型 | 执行器 | 说明 |
|----------|--------|------|
| `async def` + `await` IO | `AsyncExecutor`（默认） | 首选。不要套线程 |
| 同步阻塞 IO | `ThreadExecutor` | 线程能掩盖等待；纯 Python CPU 仍受 GIL 限制 |
| 纯 Python CPU 密集 | `ProcessExecutor` | 避开 GIL；任务函数必须可 pickle |
| 极短任务（< 1 ms） | `AsyncExecutor` | 线程/进程的调度成本会超过任务本身 |

注意事项：

- `ThreadExecutor` / `ProcessExecutor` 的 `max_workers` 与 `worker_concurrency` 应对齐，否则总有一侧先饱和。
- `ProcessExecutor` 在 Windows 使用 `spawn`：函数必须是模块顶层、参数必须可 pickle、入口必须有 `if __name__ == "__main__":`。
- 本轮未测进程执行器的吞吐，**不要把 1.14x 当作 CPU 任务的优化上限**；它只是 async 执行器内联同步代码的结果。

## 3. P0：极短任务必须显式关闭预取

### 3.1 实测：默认预取把完成吞吐降到关闭时的 1/13

3,000 个 noop 任务，10 workers，只改预取配置：

| 预取配置 | 完成吞吐 | 相对关闭 | P50 |
|----------|----------|----------|-----|
| 关闭，`prefetch_size=1` | **2,382/s** | 1.00x | 816.05 ms |
| 开启，`prefetch_size=20`（默认） | 181/s | 0.08x | 8,209.44 ms |
| 开启，`prefetch_size=100` | 864/s | 0.36x | 1,706.64 ms |

### 3.2 机制：预取器是全局单例，按固定节奏补货

- `WorkerPool` 只创建一个 `TaskPrefetcher`，所有 worker 从同一个本地队列取任务，**不是每个 worker 一个预取器**。
- `prefetch_interval` 默认 `0.1s`，一次补 `prefetch_size` 个（该间隔是 `PrefetchConfig` 内部默认值，`TaskPoolConfig` 未暴露）。
- 本地队列容量 `local_queue_size = prefetch_size * 5`；`max_threshold = prefetch_size * 3`，队列接近上限时补货间隔会拉长到 `0.5s`。

所以对“消费速度远快于补货速度”的短任务，存在一个全局节奏上限：

```text
完成吞吐上限 ≈ prefetch_size × 10 tasks/s
```

实测值约为该上限的 86%～91%（`20 → 200` 上限，实测 181；`100 → 1,000` 上限，实测 864）。反推配置：

```text
prefetch_size ≈ 目标完成吞吐 × 0.1 × (1.1 ~ 1.2)
```

例：目标 2,000 tasks/s → `prefetch_size ≈ 220～240`。

> 只要开启预取，就先确认 `prefetch_size × 10` 不低于目标完成吞吐；否则预取本身就是瓶颈，与任务快慢无关。

> 该公式只适用于任务执行时间远小于补货周期的场景。慢任务会先被 `max_threshold` 降频，此时瓶颈是执行时间，不是预取。

### 3.3 配置规则

| 单任务执行时间 | 建议 |
|----------------|------|
| `< 1 ms` | `enable_prefetch=False`，`prefetch_size=1` |
| `1～10 ms` | 可开启，`prefetch_size` 用上面的公式起步 |
| `> 10 ms` | 开启，按公式设置；重点转向 worker 数与下游容量 |

补充两点：

- 直接模式下，`prefetch_size` 同时是 worker 每次 `queue.pop()` 的批量大小。`pop(10)` 的队列微基准比 `pop(1)` 快 2.75x，但**批大小对端到端吞吐的影响本轮未取得可靠数据**，不要照搬，需在目标机器上复测。
- 预取关闭后，空队列退避从 10 ms 指数增长到最多 0.5s。任务长期稀疏时，单个任务的唤醒延迟会增加；这类场景应开启预取，而不是关闭。

## 4. P1：worker 数量按任务类型设置

IO 任务（`await asyncio.sleep(0.020)`），N=400：

| Workers | 完成吞吐 | 相对 1 worker | P50 |
|---------|----------|---------------|-----|
| 1 | 32.1/s | 1.00x | 6,230.53 ms |
| 2 | 64.0/s | 1.99x | 3,132.25 ms |
| 4 | 127.0/s | 3.96x | 1,582.69 ms |
| 8 | 249.3/s | **7.76x** | 808.96 ms |

建议：

- 异步 IO 任务从 `2～4 × CPU 核心数` 起步，用第 10 节的脚本复测后再定值。
- `worker_concurrency` 同时决定 worker 循环数和并发信号量上限；它限制的是**同时在执行的任务数**，不只是“线程数”。
- 达到目标吞吐后继续加 worker，只会增加排队与上下文切换；以 P95/P99 是否继续下降为准。
- CPU 任务应通过 `ProcessExecutor` 并行，worker 数接近物理核心数，而不是继续堆 async worker。
- Windows 定时器粒度会把 `asyncio.sleep(0.020)` 实测成约 31 ms，所以 IO 绝对值偏低；**看扩展倍数，不看绝对 TPS**。

## 5. P1：批量结果回收改用事件或分片等待

### 5.1 实测：3,000 个并发 waiter 只剩 31% 吞吐

N=3,000，noop，10 workers：

| 回收方式 | 速率 | P50 | P99 |
|----------|------|-----|-----|
| 订阅 `task.completed` 事件 | **2,433/s** | 790.21 ms | 881.74 ms |
| 3,000 个并发 `wait_for_result_async` | 759.6/s | 3,249.06 ms | 3,700.06 ms |

### 5.2 机制

`TaskFuture.wait` 是事件驱动的，不是轮询：每个 waiter 注册一个 Future，任务完成时由 `FutureManager` 通过 `call_soon_threadsafe` 唤醒。3,000 个 waiter 的成本来自：

- 3,000 个等待协程与 `gather` 的调度；
- 3,000 份 Future 注册、查找与唤醒；
- 跨事件循环的线程安全投递。

这不是任务执行变慢，而是**结果回收方式的开销**。

### 5.3 推荐写法

观测、统计、批量编排用事件：

```python
from collections import Counter

completed, failed = Counter(), Counter()

def on_completed(event):
    completed[event.task_id] += 1
    # 只做计数/入队，重活交给外部队列或批处理

def on_failed(event):
    failed[event.task_id] += 1

pool.on_completed(on_completed)
pool.on_failed(on_failed)
```

必须逐个拿结果时，用有界分片：

```python
import asyncio

async def wait_in_chunks(pool, task_ids, chunk_size=200, timeout=60):
    results = {}
    for i in range(0, len(task_ids), chunk_size):
        chunk = task_ids[i:i + chunk_size]
        values = await asyncio.gather(
            *(pool.wait_for_result_async(task_id, timeout) for task_id in chunk),
            return_exceptions=True,
        )
        results.update(zip(chunk, values))
    return results
```

不要做三件事：

- 不要一次挂起数千个 waiter；分片大小从 100～300 起测。
- 不要在事件回调里做重 IO 或 `await` 长任务；回调运行在 TaskPool 的事件循环上，会直接拖慢完成管线。
- 不要指望 `submit_batch_async` / `wait_all_async` 并行：它们内部都是顺序 `for` 循环。`wait_all_async` 在超时时还会逐个等待，长尾会被放大；大批量请用上面的分片 `gather`。

## 6. P1：存储后端按并发级别选择

### 6.1 实测

| 场景 | 结果 |
|------|------|
| memory 串行往返（同口径参照） | 64.3 tasks/s，P50 15.50 ms |
| SQLite 串行提交 100 条，1 worker | **30.1 tasks/s**，P50 31.31 ms，P95 66.34 ms |
| SQLite 突发 100 条，1 worker | 25.5 tasks/s，100/100 成功 |
| SQLite 突发 100 条，2 workers | 第 37 次提交起 `database is locked`，33/37 完成，耗时 66.9 s |
| SQLite 突发 100 条，4 workers | 第 36 次提交起 `database is locked`，34/36 完成，耗时 61.5 s |

串行口径下 SQLite 比 memory 慢约 **2.1x**；但完成吞吐从 2,433/s 跌到 30.1/s，差距被放大到 **81x**。原因不是 SQL 慢，而是每次状态变更都要写库并提交。

### 6.2 为什么多 worker 会锁死

- `SQLiteTaskRepository` 和 `SQLiteQueueRepository` 各自持有一个连接。
- `save` / `push` / `pop` / `remove` 每次执行后都 `commit()`。
- 当前版本没有启用 WAL、`busy_timeout` 等写并发优化。

多 worker 同时写同一个库文件，写锁竞争会直接打断提交流程。

### 6.3 选型规则

| 场景 | 后端 | 配置 |
|------|------|------|
| 可丢、追求吞吐 | memory | `storage_type="memory"` |
| 本地持久化、低频写入 | SQLite | `worker_concurrency=1`，低提交频率，不突发 |
| 高并发、分布式、多进程 | Redis | `storage_type="redis"` + `neotask[redis]` |

补充：

- SQLite 不要用在“多 worker + 高 QPS”链路上；这不是调 `prefetch_size` 能解决的问题。
- `TaskPoolConfig.sqlite_path` 默认是 `/data/neotask.db`（Unix 风格）。Windows 上请显式传绝对路径，例如 `TaskPoolConfig.sqlite(r"E:\data\neotask.db")`，避免落到盘符根目录或权限不足的位置。
- SQLite 的 30.1/s 是“每次状态变更都落盘”的代价。若业务能接受批量/异步持久化，应换后端，而不是在 SQLite 上叠 worker。

## 7. P2：旁路组件与重试

`TaskPoolConfig` 的默认值与主套件配置对比：

| 配置项 | 默认值 | 主套件 | 建议 |
|--------|--------|--------|------|
| `enable_metrics` | `True` | `False` | 生产保留；压测关闭 |
| `enable_health_check` | `True` | `False` | 生产保留；压测关闭 |
| `enable_reporter` | `False` | `False` | 需要外部上报时再开 |
| `enable_reclaimer` | `True` | `False` | 生产保留；压测关闭 |
| `enable_heartbeat` | `True` | `False` | 多节点/长任务保留；压测关闭 |
| `enable_dead_letter` | `True` | `False` | 需要失败留存时保留 |
| `max_retries` | `3` | `0` | 按幂等性设置，不要无脑保留默认 |
| `retry_delay` | `1.0` | 未启用 | 重试延迟 = `retry_delay × retry_count` |

建议：

- **压测必须关旁路组件**，否则测到的是监控开销，不是调度能力。
- 生产环境不要为了“快”全部关掉；health check、heartbeat、reclaimer 与故障恢复相关。
- 失败率高的业务要显式设置 `max_retries` 和 `retry_delay`。重试会重新入队并占用队列；下游故障时容易形成“失败—重试—再失败”的放大。
- `queue_max_size`（默认 10,000）应作为背压阈值看待。持续负载测试把在途任务限制在 200，系统稳定在 2,565/s；无界提交只会把延迟堆到 P99。

## 8. P2：定时任务的精度

默认 `SchedulerConfig.scan_interval = 1.0s`，周期任务由扫描循环驱动：

- `submit_interval` 的间隔小于 `1.0s` 时可能漏跑。
- 需要亚秒级精度时启用时间轮：

```python
from neotask import TaskScheduler, SchedulerConfig

scheduler = TaskScheduler(
    executor=my_task,
    config=SchedulerConfig.high_performance(),  # 时间轮 360 槽 × 1s，scan_interval=0.5
)
```

需要知道的限制：

- 本轮基准只覆盖即时任务，**时间轮的吞吐收益没有实测数据**，不要引用未经测量的倍数。
- `TaskScheduler` 构造内部 `TaskPool` 时只透传存储、`worker_concurrency`、重试参数，**不暴露 `enable_prefetch` / `prefetch_size`**。周期任务如果单轮批量很大且任务 < 1 ms，会沿用默认预取（`on/20`），可能受约 200 tasks/s 的全局节奏限制。此时应拆小批量，或改用 `TaskPool` 自行调度。
- 不要试图在 `TaskScheduler` 构造后修改底层 pool 的 `_config.enable_prefetch`：`WorkerPool` 在 `TaskPool.__init__` 时已按旧配置创建预取器，改字段不会生效。

## 9. 配置模板

以下只是起点，必须用第 10 节的方法在本机复测。

**A. 高频短任务（< 1 ms，可丢）**

```python
config = TaskPoolConfig(
    storage_type="memory",
    worker_concurrency=10,
    enable_prefetch=False,
    prefetch_size=1,
    max_retries=0,          # 仅当失败可丢弃；否则保留重试
    enable_metrics=False,   # 压测期；生产改回 True
)
```

**B. 异步 IO（`await` 网络/数据库）**

```python
config = TaskPoolConfig(
    storage_type="memory",
    worker_concurrency=16,
    enable_prefetch=True,
    prefetch_size=120,      # 目标约 1,000/s；按 §3 公式调整
)
```

**C. 同步阻塞 IO（线程）**

```python
config = TaskPoolConfig(
    worker_concurrency=8,
    enable_prefetch=True,
    prefetch_size=60,       # 目标约 500/s
    storage_type="memory",
)
pool = TaskPool(executor=ThreadExecutor(blocking_io, max_workers=8), config=config)
```

**D. CPU 密集（进程）**

```python
if __name__ == "__main__":
    config = TaskPoolConfig(
        worker_concurrency=4,       # 接近物理核心数
        enable_prefetch=False,
        prefetch_size=1,
        storage_type="memory",
    )
    pool = TaskPool(executor=ProcessExecutor(cpu_bound, max_workers=4), config=config)
```

## 10. 上线前验收清单

按顺序检查，任何一项不满足都不要直接上量：

1. **分开测四个口径**：提交吞吐、完成吞吐、单任务 P50/P99、持续负载。不要把提交吞吐当成系统吞吐。
2. **固定负载、先预热**：预热 ≥ 1 秒，重复 2～3 轮取中位数。
3. **压测时关闭旁路组件**，并确认失败数为 0。
4. **负载生成器与 TaskPool 分进程**，避免生成器自身占用事件循环和 GIL。
5. **观察背压**：在途任务有界；停止生产后队列能在数秒内排空。
6. **检查日志**：无 `database is locked`、无任务失败、无队列持续增长。
7. **记录版本**：NeoTask 版本、Python 版本、OS、CPU 核数、存储后端、完整配置。

最小验收脚本（在 TaskPool 的事件循环内执行；业务代码请使用公开的 `submit_async` / `wait_for_result_async`）：

```python
import asyncio
import statistics
import time
from neotask import TaskPool

async def measure(pool, n=3000, warmup=200):
    # 预热，不计入结果
    warm_ids = [await pool.submit_async({"i": -i}) for i in range(1, warmup + 1)]
    await asyncio.gather(*(pool.wait_for_result_async(t, 30) for t in warm_ids))

    starts, latencies, failed = {}, [], []
    done = asyncio.Event()

    def on_completed(event):
        start = starts.get(event.task_id)
        if start is not None:
            latencies.append((time.perf_counter() - start) * 1000)
        if len(latencies) + len(failed) >= n:
            done.set()

    def on_failed(event):
        failed.append(event.task_id)
        if len(latencies) + len(failed) >= n:
            done.set()

    pool.on_completed(on_completed)
    pool.on_failed(on_failed)

    started_at = time.perf_counter()
    for i in range(n):
        task_id = await pool.submit_async({"i": i})
        starts[task_id] = time.perf_counter()
    await done.wait()

    elapsed = time.perf_counter() - started_at
    latencies.sort()
    return {
        "complete_rate": round(n / elapsed, 1),
        "failed": len(failed),
        "p50_ms": round(statistics.median(latencies), 2),
        "p95_ms": round(latencies[int(len(latencies) * 0.95)], 2),
        "p99_ms": round(latencies[int(len(latencies) * 0.99)], 2),
    }

# 在 TaskPool 的事件循环中执行
with TaskPool(executor=my_task, config=config) as pool:
    stats = pool._run_coroutine(measure(pool))
```

> 脚本通过 `pool._run_coroutine(...)` 执行（基准套件即如此）；`_run_coroutine` 是内部入口，仅用于测量。生产代码应直接在自己的 async 入口中调用公开 API。

## 11. 数据边界

- 数据来自单台 Windows 10 笔记本，不是专用服务器或容器环境；绝对值会随 CPU、OS、Python 版本变化。
- 主套件使用 memory + noop，测的是调度与生命周期开销；真实业务执行时间会主导结果。
- SQLite 探针为单轮、每个用例独立库文件，只用于确认边界，不代表稳定吞吐。
- Windows 定时器粒度使 20 ms 的 IO 任务实测约 31 ms，IO 绝对 TPS 仅作参考，扩展倍数更可靠。
- 本轮另有一次预取/等待专项探针，因测试机负载（总 CPU 约 59%、存在长期占用进程）与主套件偏差过大，数据未采信；相关结论只使用主套件结果。
