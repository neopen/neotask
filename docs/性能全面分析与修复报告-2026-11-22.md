# NeoTask 全面性能分析与修复报告

> 分析对象：当前 dev 分支源码（`pyproject.toml` version = 1.2.1）
> 真实运行环境：`E:\neotask-demo`（bench / bench_final108 / bench_latest 等实测数据）
> 测试平台：Windows 10 / Python 3.13 / i7 级 4 核 8 线程笔记本

## 0. 结论速览

本轮沿「提交 → 队列 → 预取 → 执行 → 事件 → 存储 → 监控」全链路分析，定位并修复了 **9 处性能问题**，其中 2 处属于会显著放大延迟/吞吐缺陷的 P0/P1 问题：

| 级别 | 问题 | 影响 | 修复 |
|------|------|------|------|
| P0 | 预取模式 worker 空队列时额外指数退避 | 空闲后新任务最坏多等 0.5s；短任务吞吐可跌至关闭预取的约 1/10 | 改为直接回到 `prefetcher.get()` 阻塞等待 |
| P1 | 内存队列 `push_batch` 每次复制整堆 + `heapify` | 批量提交到大队列成本 O(队列总量)，随队列深度放大 | 同一把锁内逐条入堆 |
| P1 | 内存队列 `remove` 每次重建整堆 | 批量取消 k 个任务退化为 O(k·n) | 惰性墓碑 + 在场集合 + 阈值压缩 |
| P1 | psutil 采样在事件循环内阻塞 | 每 60s 卡住任务循环约 100ms；健康检查被探针轮询时周期性卡顿 | 采样下沉到线程池 |
| P2 | `peek` 对整堆排序 | O(n log n) | `heapq.nsmallest` |
| P2 | 高频路径 `debug(f"...")` 提前拼串 | DEBUG 关闭时仍逐次格式化 | `is_debug_enabled()` 短路 |
| P2 | 内存仓储 `list_by_status` 全量克隆后切片 | 列表查询深拷贝全部匹配任务 | 先按 offset/limit 截断再克隆 |
| P2 | `MemoryContextStore.set` 每次全量扫描过期项 | 高频写入 O(n²) | 过期时间最小堆惰性清理 |
| P2 | Redis `list_by_status` 逐条 GET | N 次网络往返 | 一次 `MGET` |

修复后回归：单元测试 538 通过 / 12 跳过（1 个计时敏感用例在全量并发下偶发、单独运行通过），集成测试 87 通过 / 1 跳过。

## 1. 基准与测量方法

### 1.1 队列微基准（内存后端，Python 3.13）

| 场景 | 修复后 |
|------|--------|
| 向 10,000 任务的队列批量写入 1,000 条 | **0.471 ms**（约 212 万条/s） |
| 从 11,000 任务的队列批量移除 1,000 条 | **0.668 ms**（约 150 万次/s） |
| 弹出全部 10,000 条并校验唯一性 | 10,000 条、无重复、无墓碑泄漏 |
| `peek(5)` | **0.008 ms** |

旧实现中「批量写入」单次成本与当前队列总量成正比，「批量移除」每次 O(n) 重建堆；队列越深、取消越多，退化越明显（批量取消 k 条最坏 O(k·n)）。

### 1.2 预取模式吞吐（noop 任务，2000 条，并发 10，预热 50）

| 配置 | 吞吐 | p50 | p95 |
|------|------|-----|-----|
| 关闭预取 | **3156 tasks/s** | 1.20 ms | 3.07 ms |
| 开启预取（prefetch_size=20） | **4241 tasks/s** | 11.24 ms | 15.14 ms |

历史数据（`docs/性能优化建议.md`，v1.0.6，不同机器）中，预取开启时短任务吞吐仅约 180 tasks/s，关闭时为 1670 tasks/s。问题根因正是本轮修复的 worker 空队列额外退避：本地队列被瞬间消费后，worker 进入最长 0.5s 的睡眠，期间预取器补入的新任务无法被唤醒。

### 1.3 稀疏任务端到端延迟（空闲 1s 后提交单条，连续 8 次）

| 配置 | 延迟区间 |
|------|----------|
| 关闭预取 | 1.1 – 2.2 ms |
| 开启预取 | 12.2 – 26.2 ms（修复前最坏可达 500ms+） |

预取模式的剩余 10–25ms 来自预取批处理的合并窗口（`WAKE_COALESCE = 0.01s`）与批量补货，属于吞吐换延迟的设计取舍；要求低延迟的稀疏任务仍建议 `enable_prefetch=False`（见第 4 节）。

### 1.4 日志短路成本

DEBUG 关闭时：

| 写法 | 单次成本 |
|------|----------|
| `debug(f"...")` | 1.098 µs |
| `if is_debug_enabled(): debug(f"...")` | 0.166 µs |

每任务约 6–8 条高频日志，单任务可省约 6 µs；在 3000 tasks/s 量级下对应约 2% 的 CPU。

## 2. 已修复问题详解

### 2.1 P0：预取模式空队列退避放大延迟与拖垮吞吐

**位置**：`src/neotask/worker/pool.py` `WorkerPool._worker_loop`

**现象**：预取开启时，短任务吞吐远低于关闭预取；空闲一段时间后提交的单条任务端到端延迟可达数百毫秒。

**根因**：worker 从本地队列取不到任务时，在 `prefetcher.get(timeout=0.1)` 超时之后又叠加了一层指数退避（`0.01 × 2^n`，上限 0.5s）并直接 `sleep`。预取器此时把新任务放入 `asyncio.Queue` 不会唤醒一个正在 `sleep` 的 worker，于是新任务最坏要等满退避时间。

**修复**：删除额外退避，取不到任务立即回到 `prefetcher.get()`。`get()` 内部本身用 `wait_for` 阻塞至多 0.1s，空队列不会忙旋；任务在等待窗口内到达会被立即唤醒。

**收益**：预取模式吞吐从「被退避钉死」恢复到与直接模式同级甚至更高；稀疏负载延迟从最坏 500ms 级降到 10–25ms 级。

### 2.2 P1：内存队列批量入队 O(n)

**位置**：`src/neotask/storage/memory.py` `MemoryQueueRepository.push_batch`

**根因**：旧实现为保证「全有或全无」，先 `list(self._heap)` 复制整堆、追加新元素再 `heapify` 整体替换。单次批量写入成本 = O(队列总量 + 批量)，批量提交到大队列时被明显放大。

**修复**：在同一把锁内逐条 `heappush`。消费者 `pop` 同样持这把锁，因此不会观察到半批入队的中间状态，原子可见性不变。

**收益**：向 1 万任务队列写入 1000 条仅 0.47ms，成本回到 O(k log n)。

### 2.3 P1：内存队列删除退化为 O(k·n)

**位置**：`src/neotask/storage/memory.py` `MemoryQueueRepository.remove`

**根因**：每次 `remove` 都 `[item for item in heap if id != task_id]` 重建并 `heapify`，单次 O(n)。批量取消/清理 k 个任务时退化为 O(k·n)。

**修复**：改为惰性删除。维护 `_present`（逻辑在场集合）与 `_removed`（墓碑集合）：
- `remove` 只做集合记账，O(1)；
- `pop` 跳过墓碑并顺势清理；
- `size` 返回逻辑在场数量；
- 墓碑超过阈值（>1024 且超过堆一半）才压缩一次；
- 重新入队被移除的 id 时先压缩，避免「墓碑 + 新条目」重复弹出。

**收益**：批量移除 1000 条从秒级降到 0.67ms，`size/pop/peek` 语义与原来一致。

### 2.4 P1：psutil 采样阻塞事件循环

**位置**：`src/neotask/monitor/metrics.py`、`src/neotask/monitor/health.py`

**根因**：`psutil.Process.cpu_percent(interval=0.1)` 与 `psutil.cpu_percent(interval=0.1)` 会同步阻塞约 100ms。前者在指标采集循环中执行（事件循环线程，每 60s 一次），后者在健康检查中执行（探针高频轮询时更频繁）。

**修复**：把阻塞采样抽成同步函数，通过 `loop.run_in_executor(None, ...)` 在工作线程执行，事件循环只等待结果。

**收益**：消除每 60s 一次的 100ms 任务循环停顿，以及健康探针触发的周期性卡顿。

### 2.5 P2：`peek` 整堆排序

**位置**：`src/neotask/storage/memory.py`、`src/neotask/queue/priority_queue.py`

**修复**：`sorted(heap)[:count]` 改为 `heapq.nsmallest(count, heap)`（O(n log count)）；内存仓储版本额外跳过墓碑并去重。

### 2.6 P2：高频 debug 日志提前拼串

**位置**：`common/logger.py` 新增 `is_debug_enabled()`；队列出入队、任务状态流转、worker 执行等热路径改为先判断再拼串。

**收益**：DEBUG 关闭时每条日志成本从约 1.1µs 降到约 0.17µs。

### 2.7 P2：内存仓储列表查询全量克隆

**位置**：`src/neotask/storage/memory.py` `MemoryTaskRepository.list_by_status`

**修复**：迭代时直接按 `offset/limit` 截断，只克隆最终返回的那批任务；不再深拷贝所有匹配任务。

### 2.8 P2：Blackboard 写入全量扫描过期项

**位置**：`src/neotask/storage/memory.py` `MemoryContextStore`

**修复**：用 `(expires_at, key)` 最小堆维护 TTL，写入时只弹出堆顶已到期项；覆盖写产生的陈旧堆条目在到期时按当前值比对后丢弃。`set` 从 O(n) 降为摊还 O(log n)。

### 2.9 P2：Redis 按状态列表逐条 GET

**位置**：`src/neotask/storage/redis.py` `RedisTaskRepository.list_by_status`

**修复**：`SMEMBERS` 取 id 后一次 `MGET` 批量读取，往返次数从 N 降为 1。该路径被心跳/回收器周期性用于扫描 RUNNING 任务，Redis 分布式场景收益明显。

## 4. 使用建议（与修复后的行为对齐）

| 任务形态 | 建议 |
|----------|------|
| 单任务 < 1ms、要求低延迟 | `enable_prefetch=False`。预取批处理会引入约 10–25ms 的合并窗口 |
| 1ms ≤ t < 50ms、追求吞吐 | 可开启预取，吞吐不再被空队列退避拖垮 |
| 同步阻塞 / CPU 密集 | 显式 `executor_type="thread"` / `"process"`，避免阻塞事件循环 |
| 大批量提交 | 用 `submit_many` / `submit_batch` 走批量写入 |
| 大批量取消 | 内存后端已支持惰性删除；SQLite/Redis 仍按各自存储成本计 |

## 5. 未修复但建议关注

以下问题已定位，但涉及跨进程语义或公开数据契约，本轮未改动，建议后续按需立项：

1. **SQLite 单任务提交内的 `SELECT COUNT(*)`**
   `SQLiteTaskRepository.save_if_absent_and_enqueue` 在一个事务里用 `SELECT COUNT(*) FROM queue` 做容量校验，计数随队列深度线性增长。多进程共享 SQLite 时，维护精确计数表需要在同一事务内同步所有入队/出队路径，改动面较大。建议：单进程场景可加进程内计数缓存，或改用近似的 `LIMIT/OFFSET` 存在性探测，并明确容量校验为「尽力而为」。

2. **`Task.to_dict()` 在提交路径重复序列化**
   CREATED 事件携带 `Task.to_dict()`（其中 `data` 已 `json.dumps`），SQLite/Redis 落库时又序列化一次。大 payload 下是可见开销。建议：为内部事件提供不含 JSON 字符串的轻量信封，或让存储层返回已序列化结果复用。需评估 `task.created` 公开契约。

3. **EventBus 单事件加锁与 `task_done()`**
   消费循环对每个事件都取一次处理器锁并调用 `queue.task_done()`，而 `join()` 并未被使用。热点下可缓存处理器快照、去掉无用的 `task_done()`。收益中等，需确认无人依赖 `join()`。

4. **内存版轻量监控快照的 O(n) 聚合**
   `get_metrics_async` 中 `count_by_priority` 遍历堆、`oldest_pending_created_at` 遍历全部任务、checkpoint 计数遍历全部记录。高频推送监控时成本随数据量上升，建议维护增量计数器。

5. **Redis `update_status_batch` 逐条 GET**
   当前循环内 `await client.get(key)` 后再 pipeline 写入，读取仍是 N 次往返。如后续启用该批量接口，可改为先 pipeline 读、再 pipeline 写。

6. **终态缓存队列的陈旧 id**
   `TaskLifecycleManager._terminal_cache_ids` 在任务删除时无法 O(1) 移除对应 deque 元素，只会从集合剔除。缓存长期低于上限时，deque 可能残留已删除 id 的字符串引用。影响很小，建议在删除路径标记计数、达到阈值时整理。

7. **预取稀疏延迟**
   预取模式仍有约 10–25ms 的合并窗口（`WAKE_COALESCE`）与批处理延迟。若需兼顾吞吐与低延迟，可考虑预取器入本地队列时用事件唤醒 worker，或对稀疏负载自适应缩短合并窗口。

## 6. 附：复现命令

```bash
# 微基准（队列批量/移除/peek）
python - <<'PY'
import asyncio, time
from neotask.storage.memory import MemoryQueueRepository
async def main():
    q = MemoryQueueRepository()
    await q.push_batch([(f"pre{i}", i % 4) for i in range(10000)])
    t0 = time.perf_counter(); await q.push_batch([(f"new{i}", i % 4) for i in range(1000)])
    print("push_batch 1000:", round((time.perf_counter()-t0)*1000, 3), "ms")
    t0 = time.perf_counter()
    for i in range(1000): await q.remove(f"pre{i}")
    print("remove 1000:", round((time.perf_counter()-t0)*1000, 3), "ms")
asyncio.run(main())
PY
```
