## 性能优化建议

### 1. Worker 数量配置

- **IO 密集型任务**：设置较高的 worker 数量（如 CPU 核心数的 2-4 倍）
- **CPU 密集型任务**：设置接近 CPU 核心数的 worker 数量
- **轻量任务**：根据实际测试结果调整，避免过多 worker 导致调度开销

### 2. 批量操作

在处理大量任务时，使用批量弹出接口减少锁竞争：

```python
tasks = await queue.pop(batch_size=10)  # 批量获取
```

### 3. 存储后端选择

| 存储类型 | 适用场景 |
|----------|----------|
| Memory | 单机、开发环境、高吞吐量场景 |
| SQLite | 轻量级持久化需求 |
| Redis | 分布式部署、高可用需求 |

## 结论

根据实际测试结果，NeoTask 在以下方面表现优秀：

1. **高吞吐量调度**：基础调度可达 **1697 ops/sec**
2. **高效队列操作**：优先级队列出队可达 **312,000+ ops/sec**
3. **批量操作优化**：批量弹出可提升 **2x** 性能
4. **突发负载处理**：500 任务仅需 **0.08s**
5. **高成功率**：所有测试成功率均为 **100%**

建议根据实际业务场景选择合适的配置参数，以达到最佳性能。

# 三存储极限操作性能（2026-11-10）

本节回答一个具体问题：**在队列容量上限 10,000 条这一"极限规模"下，内存 / SQLite / Redis 三种存储逐层（仓库层 → 队列层 → 任务池层）的吞吐差距有多大，瓶颈分别在哪个操作上。**

## 测试环境与方法

| 项目 | 说明 |
|------|------|
| 操作系统 | Windows 10（10.0.19045） |
| Python | 3.13.15 |
| CPU | Intel i7-1165G7（8 逻辑核） |
| 内存 | 约 16 GB |
| SQLite | 3.50.4（WAL 模式） |
| Redis | Memurai 3.2.100（`redis-py` 5.3.1，DB15 专用库，测前 `FLUSHDB`） |
| NeoTask | dev 分支 `15674af`（模块版本 1.0.5，`pip install -e .` 源码安装） |

方法要点（保证三层口径可比、结果可复现）：

- **规模固定**：批量场景 10,000 条（= `queue_max_size` 硬上限），单条场景 1,000 条，分页每页 500 条。
- **取中位数**：每个后端独立子进程；每个场景每次重复都新建池 / 新建数据库，重复 3 次取中位数，规避预热与缓存漂移。
- **纯存储开销**：任务对象在计时前批量构造完毕；执行器为 noop；关闭 prefetch、metrics、health_check、reporter、reclaimer、heartbeat、dead_letter，`max_retries=0`。
- **并发度**：内存 10 worker（端到端 2,000 条），SQLite / Redis 各 4 worker（端到端 1,000 条），避免 CPU 争抢压平存储差异。
- **单进程隔离**：每个后端单独子进程运行后合并结果（原因见文末「稳定性观察」）。

## 1. 仓库层（TaskRepository / QueueRepository 直接调用）

| 场景 | 规模 | 内存 | SQLite | Redis |
|------|------|------|--------|-------|
| 批量写入 `save_batch` | 10,000 | 46,423 /s（0.22s） | **49,208 /s**（0.20s，DB 1.91 MB） | 30,349 /s（0.33s） |
| 单条写入 `save` | 1,000 | 45,123 /s（0.02s） | 1,191 /s（0.84s） | 712 /s（1.41s） |
| 分页读取 `list_by_status`（500/页） | 10,000 | 2,246 /s（4.45s） | **73,647 /s**（0.14s） | 1,912 /s（5.23s） |
| 点查 `get` | 1,000 | 52,833 /s（0.02s） | 527 /s（1.90s） | 2,036 /s（0.49s） |
| 状态更新 `update_status` | 1,000 | 832,016 /s（0.001s） | 660 /s（1.51s） | 308 /s（3.24s） |
| 批量删除 `delete_batch` | 10,000 | 4,772,586 /s（0.002s） | 314,693 /s（0.03s） | 2,276 /s（4.39s） |

要点：

- **批量写入把持久化后端差距压到 1.6x**：同样 10,000 条，SQLite 单事务 + `executemany` 与内存持平（甚至略快），Redis 用 pipeline 也到 3.0 万/s。批量化后"谁更慢"已不再由存储介质决定。
- **单条接口才是差距来源**：SQLite / Redis 相比各自批量路径慢 **≈41x / ≈43x**；内存因无网络/事务开销几乎无差异（45,123 vs 46,423）。
- **分页读取 SQLite 反超内存 33x**：内存实现会先深拷贝全部匹配记录再切片（每页 O(N)），SQLite 走 `idx_tasks_status` + `LIMIT/OFFSET`，10,000 条全部翻页仅 0.14s。Redis 分页最慢（1,912 /s），因为每页都要 `SMEMBERS(status)` 全量取 ID 再逐条 `GET`。
- **状态更新 Redis 最慢（308 /s）**：一次更新 = `GET` + `SET` + `SREM` + `SADD` 共 4 次串行往返；SQLite 单条 `UPDATE` 660 /s；内存只是改字段，83 万/s 不具备横向可比性。
- **批量删除 Redis 绑定在逐条 `GET` 上**：需先读出台账才能清索引，10,000 条耗时 4.39s；SQLite `DELETE ... WHERE id IN (...)` 仅 0.03s。

## 2. 队列层（PriorityQueue + QueueRepository，容量上限 10,000）

| 场景 | 规模 | 内存 | SQLite | Redis |
|------|------|------|--------|-------|
| 批量入队 `push_batch` | 10,000 | 7,201,498 /s（0.001s） | 189,557 /s（0.05s） | 26,438 /s（0.38s） |
| 批量出队（每次 `pop(100)`） | 10,000 | 721,912 /s（0.014s） | 27,041 /s（0.37s） | 32,000 /s（0.31s） |
| 单条出队 `pop(1)` | 1,000 | 238,738 /s（0.004s） | 328 /s（3.05s） | 575 /s（1.74s） |
| 满队列边界 | — | `push` 返回 `False` | `push` 返回 `False` | `push` 返回 `False` |

- **出队必须批量**：批量出队相对单条出队，SQLite 快 **≈82x**、Redis 快 **≈56x**、内存约 3x。逐条 `pop` 每次都要开事务 / 走一次 Lua 往返，是队列层真正的性能悬崖。
- **批量出队 Redis 反超 SQLite**：Redis 的 `pop` 是一条 Lua 脚本原子完成"取号 + 删条目"，10,000 条 0.31s；SQLite 每批 `DELETE ... RETURNING` 需 `BEGIN IMMEDIATE` 写事务，0.37s。
- **容量边界三后端行为一致且安全**：装满 10,000 条后继续 `push` 均返回 `False`（不抛异常、不越界），实际入队量 `size_at_full = 10000`。

## 3. 任务池层（TaskPool 端到端）

先暂停消费（`pause_async`）再灌满队列，验证提交侧吞吐与溢出语义：

| 场景 | 规模 | 内存 | SQLite | Redis |
|------|------|------|--------|-------|
| 单次 `submit_batch_async`（暂停态） | 10,000 | 30,821 /s（0.32s） | 24,357 /s（0.41s） | 8,872 /s（1.13s） |
| 溢出单条提交 | 1 | `QueueFullError` | `QueueFullError` | `QueueFullError` |
| 溢出批量提交 | 2 | `BatchSubmitError`（cause=`QueueFullError`） | 同左 | 同左 |

端到端批量执行（提交即开始消费，统计从批量提交开始到全部完成的时延）：

| 指标 | 内存（2,000） | SQLite（1,000） | Redis（1,000） |
|------|---------------|-----------------|----------------|
| 吞吐 | 4,761 /s | 519 /s | 232 /s |
| 总耗时 | 0.42s | 1.93s | 4.31s |
| p50 | 297.0 ms | 1,036.5 ms | 2,547.4 ms |
| p95 | 402.5 ms | 1,867.9 ms | 4,136.2 ms |
| p99 | 416.5 ms | 1,916.1 ms | 4,268.2 ms |
| 成功 / 失败 | 2,000 / 0 | 1,000 / 0 | 1,000 / 0 |

- **提交侧被批量接口拉平**：10,000 条单次提交，内存 30,821 /s、SQLite 24,357 /s、Redis 8,872 /s，最慢也只有内存的 29%，量级一致（对比单条提交时代的 100+ 倍差距）。
- **端到端差距来自状态迁移而非入队**：每个任务要经历 created → started → completed 多次 `save` / `update_status` / 事件派发，SQLite / Redis 的单条写与状态更新在此叠加，故内存约为 SQLite 的 9.2x、Redis 的 20.5x。这是"持久化保证"的固有成本，不是调度器开销。
- **溢出语义明确**：单条提交抛 `QueueFullError`；批量提交先做容量预检，容量不足时整批拒绝并抛 `BatchSubmitError(cause=QueueFullError)`，不会只写入一部分。

## 结论

1. **批量 API 是决定性因素**：同一后端内，批量写入比单条写入快 **41x（SQLite）/ 43x（Redis）**，批量出队（`pop(100)`）比逐条出队快 **82x（SQLite）/ 56x（Redis）**。批量化之后，两个持久化后端之间的差距收敛到 2x 内（写入 1.6x、出队 1.2x）；剩下的数量级差距主要是"内存 vs 磁盘/网络"——单条写入 38x~63x、单条点查 26x~100x、状态更新与删除更极端。
2. **按瓶颈选型**：
   - 读多、需要分页或条件查询 → SQLite（10,000 条全量翻页 0.14s，比内存快 33x，且不占常驻内存；代价是单条点查 / 更新走磁盘，约 500~700 /s）。
   - 高频状态流转、低延迟要求 → 内存（唯一能跑到 80 万/s 更新、4.7 百万/s 删除的后端；即使批量入队也有 7.2 百万/s，是 SQLite 的 38x、Redis 的 272x）。
   - 多进程共享队列 → Redis，但必须走批量接口；单条 `update_status`（308 /s）与 `delete_batch`（2,276 /s）会成为明显瓶颈。
3. **10,000 条是硬上限而非性能拐点**：三后端在满队列时都能正常拒绝并返回明确错误类型；本轮未观察到容量相关的异常退化（内存分页的 O(N) 特性除外，见仓库层要点）。
4. **端到端成本 ≈ 调度开销 + 持久化往返**：noop 执行器下，内存 4,761 /s 基本等于调度器上限；SQLite / Redis 的 519 / 232 /s 反映的是每任务多次状态写回的开销。若对吞吐敏感，应减少状态写回频次或使用批量提交。

## 稳定性观察（Windows + Redis 需要关注）

本轮压测暴露出一个**与性能无关但会导致"假死"**的问题，已在测试脚本中绕过，仍建议后续修复：

- 在 Windows Proactor 事件循环下，关闭 Redis socket 时若仍有重叠 I/O 未完成，会触发 `WinError 995` → `ConnectionResetError`；`windows_events._poll` 随后对已完成的 Future 调用 `set_exception`，抛出 `asyncio.exceptions.InvalidStateError: invalid state`，该异常逃出 `run_forever()`，**共享专用 I/O 循环线程直接停止**（但线程仍存活）。
- 由于 `utils/dedicated_loop.py` 的 `get()` 只检查 `thread.is_alive()`，后续调用仍会把协程投递到这个已停的循环；而 `run_on_loop` 的 `wrap_future` 与 `TaskPool._run_coroutine` 的 `future.result()` 均无超时，于是**永久挂起**。
- 本次绕行方案：每个后端在独立子进程运行（`run_all.py`），并对 `TaskPool.shutdown(graceful=True)` 显式限时，避免一个后端的收尾异常污染其他后端。
- 建议的根治方向：`DedicatedLoopRunner.get()` 增加 `loop.is_running()` / ready 事件判断并在异常后重建；`run_on_loop` 增加超时或失败重试；Redis 连接释放前等待在途命令清空。
