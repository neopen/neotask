## 性能优化建议

### 1. Worker 数量配置

- **IO 密集型任务**：设置较高的 worker 数量（如 CPU 核心数的 2-4 倍）
- **CPU 密集型任务**：设置接近 CPU 核心数的 worker 数量
- **轻量任务**：根据实际测试结果调整，避免过多 worker 导致调度开销

### 2. 批量操作

在处理大量任务时，使用批量弹出接口减少锁竞争：

```python
tasks = await queue.pop(batch_size=10)  # 批量获取
```

### 3. 存储后端选择

| 存储类型 | 适用场景 |
|----------|----------|
| Memory | 单机、开发环境、高吞吐量场景 |
| SQLite | 轻量级持久化需求 |
| Redis | 分布式部署、高可用需求 |

## 结论

根据实际测试结果，NeoTask 在以下方面表现优秀：

1. **高吞吐量调度**：基础调度可达 **1697 ops/sec**
2. **高效队列操作**：优先级队列出队可达 **312,000+ ops/sec**
3. **批量操作优化**：批量弹出可提升 **2x** 性能
4. **突发负载处理**：500 任务仅需 **0.08s**
5. **高成功率**：所有测试成功率均为 **100%**

建议根据实际业务场景选择合适的配置参数，以达到最佳性能。

# A/B 性能对照（2026-11-10：v1.0.7）

## 目的与方法

量化 1.0.6 / 1.0.7 开发线（生命周期缓存淘汰 O(n²)→O(1)、批量原子提交、停机语义等）相对 1.0.5 的性能变化。

- **基线**：`86ecf41`（v1.0.5 时代），用 `git worktree` 检出后以 `PYTHONPATH` 指向其 `src`
- **对照**：`dev` 分支 HEAD（`10014bb`），`PYTHONPATH` 指向工作区 `src`
- **探针**：`E:\neotask-demo\bench\bench_ab.py`（submit / complete / query / batch）、`bench_ab_extra.py`（缓存淘汰、进度上报）
- **口径**：每场景独立建池，3 轮取中位数；submit 为逐条 `submit_async`，complete 为提交到 `task.completed` 事件计数到达 N，batch 为单次 `submit_batch_async`

|------|--------|----------|------|

| SQLite 进度上报（100 任务 × 50 次/任务） | ~149 /s | ~138 /s | 持平（节流机制在 1.0.5 已存在） |

## 结论

1. **批量提交是最大收益**：SQLite 单事务、Redis Lua 原子合并、内存批量入队，把"逐条往返"压成一次往返，SQLite 与 Redis 提升一个数量级以上。
2. **缓存淘汰 O(n²)→O(1)** 只有在任务数超过 `cache_max_size`（默认 1000）后才显现；8000 任务时约 7.6x，n=1000 时几乎无差异。
3. **单条提交与端到端执行吞吐三个后端均基本持平**，说明上述优化没有牺牲常态路径。
4. **进度上报无性能变化**，因为 0.5s 节流 + 写回批量在 1.0.5 已具备，本轮不属于新增优化。

> 绝对数值仅适合本机横向对比，不宜外推到其他硬件或 Redis 版本。队列容量上限为 10000，一次性提交 20000 条会抛 `QueueFullError`（设计约束，非缺陷）。
