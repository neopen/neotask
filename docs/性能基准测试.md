# NeoTask 性能基准测试

> 测试日期：2026-10-30  
> 测试版本：NeoTask 1.0.5（PyPI）  
> 测试平台：Windows 10 / Python 3.13.15  
> 原始数据：`E:\neotask-demo\bench\results.json` 与 `E:\neotask-demo\bench\sqlite_results.json`  
> 优化建议：见 [性能优化建议](性能优化建议.md)

## 1. 结论

NeoTask 1.0.5 在内存后端、空操作执行器下的核心指标如下。主套件为多轮实测中位数，SQLite 边界探针为单轮；均为实测值，不是理论估算。

| 指标 | 实测结果 | 测试条件 |
|------|----------|----------|
| 提交吞吐 | **14,657 tasks/s** | memory，noop，10 workers，N=2000 |
| 完成吞吐 | **2,433 tasks/s** | memory，noop，10 workers，N=3000 |
| 空载单任务往返 P50 | **15.50 ms** | 串行提交，无积压，N=200 |
| 20 ms IO 任务扩展 | **32.1 → 249.3 tasks/s** | 1 → 8 workers，7.76x |
| 5 秒持续负载 | **2,565 tasks/s** | 有界在途 200，0 失败 |
| 队列 push / pop | **262,019 / 240,136 ops/s** | 内存堆，N=5000 |
| 批量 pop 提升 | **2.75x** | `pop(10)` vs `pop(1)` |
| SQLite 单 worker | **30.1 tasks/s** | 串行提交，P50 31.31 ms |

需要先明确：**提交吞吐不等于完成吞吐**。提交吞吐只覆盖任务创建、落库和入队；完成吞吐覆盖排队、执行、状态落库和事件通知。两者不能混在一列比较。

测试机为单机笔记本，不是专用服务器。绝对值会随 CPU、操作系统和 Python 版本变化；本文更关注同一环境下的相对差异与扩展趋势。

## 3. 测试口径

四个指标的定义如下：

```text
提交窗口：  第一个 submit_async ──▶ 第 N 个 submit_async 返回
完成窗口：  第一个 submit_async ──▶ 第 N 个 task.completed 事件
任务延迟：  单任务 submit 前 ──▶ 该任务 task.completed 事件
等待吞吐：  N 个并发 wait_for_result_async 全部返回的速率
```

具体做法：

- 每个场景独立创建 `TaskPool`，先跑 10 个预热任务，再开始计时。
- 主套件每个场景重复 2～3 轮，取中位数；原始每轮数据保存在 `results.json` 的 `notes.runs`。SQLite 探针为单轮，只用于确认边界。
- 主套件使用 `storage_type="memory"`，目的是隔离调度器本身的开销，不把磁盘 I/O 混入结论。
- 默认关闭指标、健康检查、上报、回收、心跳、死信和重试，避免旁路任务影响测量。
- 执行器分为三类：`noop`（空操作）、`io20`（`asyncio.sleep(0.020)`）、`cpu5000`（5000 次同步累加）。
- 所有速率均以实际壁钟为分母，不写死名义时长。

> 本文只使用 1.0.5 的实测数据。旧版文档中的 1697 ops/s 等数字来自不同版本与不同口径，不能直接横向比较。

## 4. 实测结果

### 4.1 调度与执行开销

| 场景 | N | Workers | 提交吞吐 | 完成吞吐 | P50 | P95 | P99 | 失败 |
|------|---|---------|----------|----------|-----|-----|-----|------|
| 只提交，不等待完成 | 2000 | 10 | **14,657/s** | — | — | — | — | 0 |
| 提交并等待全部完成 | 3000 | 10 | 10,526/s | **2,433/s** | 790.21 ms | 869.05 ms | 881.74 ms | 0 |
| 串行往返，无积压 | 200 | 10 | 64.3/s | 64.3/s | **15.50 ms** | 16.33 ms | 16.55 ms | 0 |

三点说明：

1. 提交 2000 个空任务仅需约 0.136 s，说明创建、落库、入队主链路的单任务开销约 68 μs。
2. 完成 3000 个空任务时，10 个 worker 的完成吞吐约 2,433 tasks/s。此时瓶颈不在执行器，而在任务生命周期、状态落库和事件分发。
3. 串行往返的 64.3 tasks/s 是“提交一个、等待一个”的节奏，不代表系统吞吐上限；它对应的是无积压时的单任务往返延迟，P50 为 15.50 ms。

### 4.2 IO 任务扩展性

任务体为 `await asyncio.sleep(0.020)`，N=400。

| Workers | 完成吞吐 | 相对 1 worker | P50 | P95 | P99 |
|---------|----------|---------------|-----|-----|-----|
| 1 | 32.1/s | 1.00x | 6,230.53 ms | 11,806.92 ms | 12,303.30 ms |
| 2 | 64.0/s | 1.99x | 3,132.25 ms | 5,914.06 ms | 6,157.46 ms |
| 4 | 127.0/s | 3.96x | 1,582.69 ms | 2,965.99 ms | 3,089.04 ms |
| 8 | 249.3/s | **7.76x** | 808.96 ms | 1,503.44 ms | 1,565.04 ms |

IO 任务随 worker 数量接近线性扩展，1 → 8 workers 获得 7.76x 提升，排队延迟同步下降。

> 绝对值受 Windows 定时器粒度影响。`asyncio.sleep(0.020)` 在本机实测约 31 ms/任务，因此 1 worker 只有 32 tasks/s。这个偏差来自操作系统，不是 NeoTask 的调度开销；扩展效率才是本组数据的有效结论。

### 4.3 CPU 密集任务

任务体为 5000 次同步累加，放在 async 执行器内，N=500。

| Workers | 完成吞吐 | 相对 1 worker | P50 | P95 | P99 |
|---------|----------|---------------|-----|-----|-----|
| 1 | 1,110/s | 1.00x | 244.15 ms | 400.61 ms | 406.93 ms |
| 4 | 1,215/s | 1.09x | 196.97 ms | 354.56 ms | 367.61 ms |
| 10 | 1,269/s | 1.14x | 207.74 ms | 341.30 ms | 350.68 ms |

增加 worker 只带来约 14% 提升。原因是同步循环直接阻塞了 async 执行器所在的事件循环，worker 再多也无法并行。

**正确用法**：CPU 密集任务应交给 thread 或 process 执行器，而不是写在 async 函数里。本组数据说明的是“错误用法下的上限”，不是 NeoTask 对 CPU 任务的扩展能力。

### 4.4 预取器配置

同样的 3000 个空任务、10 workers，只改变预取配置。

| 预取配置 | 完成吞吐 | 相对关闭 | P50 | P95 | P99 |
|----------|----------|----------|-----|-----|-----|
| 关闭，`prefetch_size=1` | **2,382/s** | 1.00x | 816.05 ms | 938.75 ms | 954.97 ms |
| 开启，`prefetch_size=20`（默认） | 181/s | 0.08x | 8,209.44 ms | 15,467.42 ms | 16,107.71 ms |
| 开启，`prefetch_size=100` | 864/s | 0.36x | 1,706.64 ms | 3,097.86 ms | 3,199.12 ms |

预取器会把共享队列批量搬到 worker 本地队列，减少队列争用；但补充节奏约为每 0.1 s 一批。当任务本身只有几十微秒时，`20 个/0.1 s` 就把完成吞吐限制在约 200 tasks/s，形成明显瓶颈。

建议：

- 任务执行时间 **小于 1 ms**：关闭预取，或使用很小的 `prefetch_size`。
- 任务执行时间 **在毫秒到秒级**：开启预取通常更有利，具体批量需按业务实测。
- 不要默认认为“预取一定更快”；它优化的是队列争用，不是极短任务的吞吐。

### 4.5 结果等待方式

N=3000，noop，10 workers。

| 等待口径 | 速率 | P50 | P95 | P99 |
|----------|------|-----|-----|-----|
| 订阅 `task.completed` 事件 | **2,433/s** | 790.21 ms | 869.05 ms | 881.74 ms |
| 3000 个并发 `wait_for_result_async` | 759.6/s | 3,249.06 ms | 3,680.70 ms | 3,700.06 ms |

3000 个并发 waiter 会额外创建 3000 个协程，并引入 Future 注册、`FutureManager` 唤醒和跨事件循环调度的开销，吞吐降到事件口径的约 31%。

建议：

- 观测、统计、批量任务编排优先使用事件回调。
- 需要逐个取结果时，用有界批次等待，不要一次挂起数千个 waiter。
- 这个差异是“等待方式的开销”，不是任务执行能力的下降。

### 4.6 持续负载

5 秒窗口，预热 1 秒，有界在途任务 200，noop，10 workers。

| 轮次 | 窗口内完成 | 提交总数 | 完成总数 | 失败 |
|------|------------|----------|----------|------|
| 第 1 轮 | 2,702/s | 16,518 | 16,518 | 0 |
| 第 2 轮 | 2,428/s | 15,190 | 15,190 | 0 |
| 中位数 | **2,565/s** | 15,854 | 15,854 | 0 |

在持续生产、且有 200 个在途任务的情况下，系统稳定在约 2,565 tasks/s，无失败、无积压失控。停止生产后，在途任务能在数秒内排空。

### 4.7 队列操作

内存堆，N=5000，取多轮中位数。

| 操作 | 实测速率 |
|------|----------|
| `push` | **262,019 ops/s** |
| `pop(1)` | **240,136 ops/s** |
| `pop(1)` 取 1000 条 | 242,907 items/s |
| `pop(10)` 取 1000 条 | **688,895 items/s** |
| `pop(10)` 调用次数 | 68,889 calls/s |
| 批量提升 | **2.75x**（逐轮比值中位数） |

批量出队把每次调用的固定开销摊薄到 10 条任务上，适合 worker 一次取多条的场景。单条出队的速率已经高于调度主链路，队列本身不是常规任务的瓶颈。

## 5. SQLite 持久化边界

SQLite 用独立探针测量（单轮），任务为 noop，数据库文件每次重建。

| 模式 | Workers | 结果 |
|------|---------|------|
| 串行提交 100 条 | 1 | **30.1 tasks/s**，P50 31.31 ms，P95 66.34 ms，100/100 成功 |
| 突发提交 100 条 | 1 | 25.5 tasks/s，100/100 成功，0 错误 |
| 突发提交 100 条 | 2 | 第 37 次提交起 `database is locked`，33/37 完成，耗时 66.9 s |
| 突发提交 100 条 | 4 | 第 36 次提交起 `database is locked`，34/36 完成，耗时 61.5 s |

结论很明确：

- SQLite 适合**低频、单写入者、需要本地持久化**的场景，单 worker 串行约 30 tasks/s。
- 多 worker 并发写入时会出现 `database is locked`。任务仓储与队列仓储各持有连接，且每次写入都提交，写锁竞争会直接打断提交流程。
- 高并发或分布式场景应使用 Redis 后端；不要用多 worker 的 SQLite 写入链路做吞吐测试。

## 6. 配置建议

| 场景 | 建议 |
|------|------|
| 极短任务（<1 ms） | `enable_prefetch=False`，`prefetch_size=1`；不要直接沿用默认预取 |
| IO 密集任务 | 开启预取，`prefetch_size` 按 20～100 起步实测；worker 数可设为 CPU 核心数的 2～4 倍 |
| CPU 密集任务 | 使用 thread 或 process 执行器；worker 数接近物理核心数 |
| 大批量结果回收 | 优先订阅 `task.completed`；需要等待时使用有界批次，避免数千个并发 waiter |
| 本地持久化、低并发 | SQLite，单 worker，控制写入频率 |
| 高并发、分布式 | Redis；不要在多 worker 写入链路上使用 SQLite |
| 生产环境 | 按需开启 metrics、health check、reporter；基准测试中应关闭 |

核心原则：**默认参数是通用起点，不是所有负载的最优解。** 任务粒度、IO/CPU 比例、结果回收方式，都会改变最佳配置。

## 8. 结论与边界

**结论**

1. NeoTask 的调度主链路开销很低：空任务提交可达 14,657 tasks/s，单任务提交开销约 68 μs。
2. IO 任务扩展性良好：1 → 8 workers 获得 7.76x 提升，适合异步 IO 型业务。
3. 队列不是瓶颈：push/pop 均在 240,000 ops/s 以上，批量出队可再提升 2.75x。
4. 持续负载稳定：5 秒窗口 2,565 tasks/s、15,854 个任务、0 失败。
5. 配置对结果影响很大：极短任务下默认预取会把完成吞吐压到 181 tasks/s；关闭预取可恢复到 2,382 tasks/s。

**边界**

- 数据来自单台 Windows 10 笔记本，绝对值不能直接外推到服务器或容器环境。
- 主套件使用 memory + noop，测的是调度与生命周期开销；真实业务执行时间会主导结果。
- Windows 定时器粒度使 20 ms IO 任务实测约 31 ms，IO 绝对值仅作参考。
- 3000 个并发 waiter 的 759.6 tasks/s 是等待方式的开销，不代表任务执行上限。
- SQLite 多 worker 并发写入存在 `database is locked`，不适合高并发写负载。
- 本文不与旧版或其他口径的数字做横向比较。

在上述边界内，NeoTask 1.0.5 的调度开销、IO 扩展性和持续负载表现均可复现，可以作为轻量级异步任务队列的选型依据。
