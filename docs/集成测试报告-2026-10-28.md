## 2. 执行方式

项目默认 `addopts` 含 `-v --cov=...`，全量运行时覆盖率与详细输出会严重拖慢并放大超时风险，因此统一覆盖 `addopts` 并按文件分组执行：

```powershell
$env:PYTHONPATH="e:\Projects\neopen\task-schedule-manager\src"
.\.venv\Scripts\python.exe -u -m pytest <file> `
  -o addopts="--tb=line" -p no:cacheprovider --timeout=25 -rfEs
```

- 需要逐用例定位挂起点时使用 `-v`；
- 对稳定挂起的用例使用 `--deselect`（注意 nodeid 以 `pytest.ini` 所在目录 `tests` 为 rootdir，正确写法是 `integration/test_xxx.py::Class::test`，**不能**带 `tests/` 前缀）；
- 全库单进程运行（`pytest tests/`）会因 P0 缺陷在若干用例上永久挂起，最终被 pytest-timeout 杀掉，无汇总输出。

## 6. 关键缺陷分析

### P0：跨事件循环使用 asyncio 原语（既有缺陷，非本次引入）

> ✅ **已于 2026-10-28 晚修复**，修复内容与回归结果见第 9 节。以下为修复前的现象与根因分析。

**现象**

1. `TaskPool.wait_for_result_async()` 在任务“先完成、后等待”时瞬时返回；在“先等待、后完成”时**恰好等待满 timeout 才返回**。
2. `test_end_to_end.test_bulk_operations`（50 个任务顺序等待）直接挂死。
3. `test_end_to_end.test_event_flow` 挂死，且在干净基线 `HEAD~1`（`4414375`）worktree 中同样挂死。
4. 分布式/旧版用例出现 `Future attached to a different loop`、`Event loop is closed`。

**最小复现（本次实测）**

```text
# 先提交，立即等待；执行器毫秒级返回
elapsed=3.013s (timeout=3s) status=success result={'ok': True}
# 先提交，等 0.5s 后再等待（此时任务已完成）
status_before_wait=success elapsed=0.000s result={'ok': True}
```

**根因**

- `TaskFuture` 内部是 `asyncio.Event`，`FutureManager.get/complete` 使用 `asyncio.Lock`（`src/neotask/core/future.py`）。
- 等待发生在调用方事件循环（测试的 loop / `asyncio.run`），而 `Event.set()` 由 `TaskPool` 内部守护线程的事件循环执行。
- `Event.set()` 通过 `Future.set_result()` → `loop.call_soon()` 唤醒等待者，**跨线程写另一个 loop 的 ready 队列并不会唤醒其 selector**；同时 `asyncio.mixins` 会把 Lock/Event 绑定到首次使用的 loop。
- 因此用户可见行为是：`future.wait()` 一直等到 `asyncio.wait_for` 超时抛 `TimeoutError`，随后 `TaskLifecycleManager.wait_for_task`（`lifecycle.py:339-352`）捕获异常后**重新查库发现任务已完成并返回结果** —— 错误被“吞掉”，表现为**每次等待静默消耗一个 timeout**。
- 50 个任务顺序等待 → `50 × timeout`，测试超时被杀，看起来像“挂死”。
- 队列/生命周期中的 `asyncio.Lock` 跨 loop 争用时没有 timeout 兜底，则会**真正永久挂起**（`get_queue_size_async` 等）。

**影响面**：`wait_for_result_async`、`wait_all_async`、依赖 future 的分布式节点/恢复逻辑、`event_loop` fixture teardown。这是基础设施库最不应出现的“静默降级”。

**建议**：所有 `wait_for_result_async` 之类 API 统一经由 pool 的事件循环执行（`run_coroutine_threadsafe`），或用 `loop.call_soon_threadsafe` 投递完成通知；`FutureManager`/队列锁改为线程安全原语（或每 loop 一份实例）。这是后续最优先修复项。

## 7. 结论

1. **本次交付能力已验证可用**：进度回调端到端（ContextVar → 执行器 → lifecycle → repo → `task.progress` 事件 → `pool.on_progress`），异步与线程执行器两条路径均通过；周期任务持久化默认开启，SQLite 跨重启恢复通过，memory/关闭持久化/降级三种场景均输出明确 WARNING。
2. **全库通过率约 543/586（约 93%）**（不含主动跳过/挂起用例），核心回归、Redis、Web UI、12 个示例全部通过。
3. **主要阻塞是全库既有 P0**：跨事件循环的 future/lock 让 `wait_for_result_async` 每次静默耗时一个 timeout，并在批量等待时表现为永久挂起。它不是本次改动引入（基线可复现），但会严重误导使用者与 CI。
4. 其余失败集中在**过期测试资产**（旧 API/旧 fixture/旧返回值约定）与**时序敏感断言**，修复成本低。

**建议的修复顺序**：P0 跨 loop 问题 → 分布式 watch dog/节点管理 → `ExecutorType` 兼容 → 测试资产清理（fixture/旧 API/时序断言）→ 打开 `localhost→127.0.0.1` 与 `pytest-timeout` 的 signal 模式，恢复 `pytest tests/` 一次性可执行。

## 9. P0 修复记录（2026-10-28 晚）

### 9.1 修复内容

核心思路：**不再让 asyncio 原语跨事件循环使用**。内存/队列等共享状态改为线程安全原语；完成通知通过 `loop.call_soon_threadsafe` 投递到等待者所在循环。

| 文件 | 修改 |
|---|---|

## 10. Redis 跨事件循环修复（2026-10-29）

### 10.1 根因

`redis.asyncio.ConnectionPool` 内部持有 `asyncio.Lock` 等与事件循环绑定的原语，连接池在某个 loop 中首次使用后，就无法再从其它 loop 访问，典型报错为
`RuntimeError: <asyncio.locks.Lock ...> is bound to a different event loop` 或 `got Future <Future pending> attached to a different loop`。
NeoTask 同时存在 `TaskPool` 内部守护 loop 与调用方 loop（`asyncio.run` / pytest-asyncio），一旦共用同一个 Redis 客户端，就会触发该错误。

### 10.2 修复方式

在 `src/neotask/utils/redis_compat.py` 中新增“专用事件循环 + 客户端代理”，所有 Redis 命令统一在同一个后台 loop 执行，与调用方 loop 完全解耦：

| 组件 | 职责 |
|---|---|
| `DedicatedLoopRunner`（`src/neotask/utils/dedicated_loop.py`） | 进程内共享的专用事件循环线程（daemon，惰性启动，异常退出后自动重建）；Redis 与 SQLite 共用同一 loop（该模块于 2026-10-29 从 `redis_compat.py` 抽出） |
| `LoopBoundRedisClient` | 客户端代理；命令经 `asyncio.run_coroutine_threadsafe` 投递到专用 loop，`close()` 也在该 loop 释放连接；未显式实现的方法由 `__getattr__` 动态转发 |
| `LoopBoundPipeline` | pipeline 代理：命令先在本地排队（纯 Python），`execute()` 时整体投递到专用 loop 执行 |
| `LoopBoundScript` | Lua 脚本代理：调用时才在专用 loop 注册并执行，适配 `register_script()` 用法 |
| `create_client(...)` | 统一工厂，保留 RESP2 兼容与 `max_connections` / `decode_responses` 等连接池参数 |

改造的调用方（不再直接创建 pool + client）：

| 文件 | 位置 |
|---|---|
| `src/neotask/storage/redis.py` | `RedisTaskRepository`、`RedisQueueRepository` 的 `_get_client` / `close` |
| `src/neotask/storage/periodic.py` | `RedisPeriodicStore` 的 `_get_client` / `close` |
| `src/neotask/queue/dead_letter.py` | `DeadLetterQueue._get_client` |
| `src/neotask/core/heartbeat.py` | `HeartbeatManager._get_client` |
| `src/neotask/distributed/node.py` | `NodeManager._get_client` |
| `src/neotask/lock/redis.py` | `RedisLock._get_client` / `close` |

## 11. SQLite 跨事件循环修复（2026-10-29）

### 11.1 根因

- `aiosqlite` 的每次调用会在**当前事件循环**上创建 Future、由后台线程回填，连接对象与首次使用它的 loop 强耦合。`TaskPool.start()` 在守护线程里新建 loop，而调用方（`asyncio.run` / pytest-asyncio）另有 loop，同一连接被两方并发访问即报 `Future ... attached to a different loop` 或 `Event loop is closed`。
- Redis 的修复方案（§10）已证明“所有 I/O 统一投递到专用 loop”可行，本次把 SQLite 归入同一模型，避免两套机制分叉。

### 11.2 修复方式

抽出共享专用 loop（`src/neotask/utils/dedicated_loop.py`，Redis / SQLite 共用）：

| 组件 | 职责 |
|---|---|
| `DedicatedLoopRunner` | 进程内共享的专用事件循环守护线程；惰性启动，线程异常退出后自动重建 loop |
| `get_shared_loop()` / `run_on_loop(factory, loop=...)` | 目标 loop 与当前 loop 相同时直接执行（避免自我投递死锁），否则 `asyncio.run_coroutine_threadsafe` + `asyncio.wrap_future` 等待结果 |

新增 SQLite 代理（`src/neotask/utils/sqlite_compat.py`）：

| 组件 | 职责 |
|---|---|
| `LoopBoundSQLiteConnection` | 代理 `aiosqlite.Connection`；`execute` / `executemany` / `executescript` / `commit` / `rollback` / `close` 全部投递到专用 loop；连接在首次使用时于该 loop 内惰性建立，并发建连时自动丢弃重复连接 |
| `LoopBoundCursor` | 代理游标；`fetchone` / `fetchmany` / `fetchall` / `close` 同样在专用 loop 执行，`description` / `rowcount` / `lastrowid` 直接透传，支持 `async with` |
| `create_connection(...)` | 统一工厂，保留 `row_factory` 以及 `sqlite3.connect` 参数（如 `timeout`）透传 |

改造的调用方：

| 文件 | 位置 |
|---|---|
| `src/neotask/storage/sqlite.py` | `SQLiteTaskRepository`、`SQLiteQueueRepository` 的 `_ensure_init`（不再直接 `import aiosqlite`） |
| `src/neotask/storage/periodic.py` | `SQLitePeriodicStore._ensure_init` |
| `src/neotask/utils/redis_compat.py` | 删除内部 loop runner，改为复用 `dedicated_loop.py` |
