## 7. 发现的问题

### 7.1 【高危 · 回归 · 已修复】暂停队列后提交死锁 + 事件循环忙等

> **状态：已修复并回归验证通过**（2026-11-11）。修复落在 `src/neotask/queue/queue_scheduler.py`，详见本节末「修复与验证」及第 11 节。以下现象/根因为首测记录，保留以供追溯。

- **引入提交**：`b6aee91`（perf(scheduler): 入队事件唤醒替代空转退避）
- **现象**：`pool.pause()` 后调用 `pool.submit(...)` / `submit_batch(...)`，同步调用**永久阻塞**；事件循环线程 CPU 空转（实测 ~75–100% 单核），整个池的跨线程同步 API（submit/get_stats/shutdown）全部卡死。
- **触发条件**：队列处于暂停态**且非空**。暂停但队列空（如整批被容量拒绝）不触发。
- **影响面**：demo_02 优先级演示、集成验收 test_partial_batch_memory / test_partial_batch_when_queue_full 全部挂起；任何「暂停→批量入队→恢复」的真实用法（优先级排序、削峰填谷）不可用。

**根因**（已定位并双向验证）：

worker 空队列分支由旧版 `await asyncio.sleep(sleep_time)`（必然让出）改为 `await self._wait_for_queue(sleep_time)`（`src/neotask/worker/pool.py:357`），后者调用 `QueueScheduler.wait_for_task`（`src/neotask/queue/queue_scheduler.py:210`）。`wait_for_task` 以 `priority_queue.size() > 0` 作为「有任务」判据并**立即返回 True（不 await 让出）**。但暂停时 `pop()` 恒返回 `[]`（`queue_scheduler.py:236`），队列里又有刚入队的任务（size>0），于是 worker 循环 `pop→[]→wait_for_task→True→pop…` **忙等空转，独占事件循环**，`run_coroutine_threadsafe` 的结果回调永远得不到调度 → submit 死锁。

**复现**：`E:\neotask-demo\bench_latest\repro_pause_submit_hang.py`

```bash
python repro_pause_submit_hang.py          # 复现：submit 挂起 >6s，看门狗强退 exit=3
python repro_pause_submit_hang.py --fixed  # 验证：暂停时让 wait_for_task 真正 sleep 让出 → submit 0.001s 返回，恢复后任务正常完成
```

实测：默认模式挂起 >6s、空闲 CPU 75%；`--fixed`（暂停分支强制 `await asyncio.sleep`）submit 0.001s 返回、任务正常完成。**根因假设双向成立。**

**修复与验证（已落地）**：采用「暂停守卫 + 恢复唤醒」方案，改动仅 `src/neotask/queue/queue_scheduler.py` 两处：

1. `wait_for_task`（约 222 行）：`size()>0` 立即返回前增加 `not self._paused` 守卫。暂停时不再以「队列非空」误判为「有任务可取」，转而走 `event.wait()` 超时分支真正让出事件循环，消除 `pop→[]→wait→True` 忙等。
2. `resume`（约 314 行）：置 `_paused=False` 后调用 `_notify_tasks_available()`，立即唤醒暂停期间等待的消费者，恢复后无需等退避超时即可取走积压任务。

```python
# wait_for_task：暂停时 pop() 恒返回空，不能以 size>0 判定「有任务」并立即返回
if not self._paused and await self._priority_queue.size() > 0:
    return True
# resume：唤醒暂停期间等待的消费者
self._paused = False
self._notify_tasks_available()
```

修复后验证（重建 wheel 覆盖安装）：
- `repro_pause_submit_hang.py` 默认模式 0.001s 返回（首测挂起 >6s）。
- 暂停态持有 50 任务：CPU **0.00%**、completed=0（任务被正确扣留）；`resume()` 后 50/50 全部完成。
- demo_02 3/3（CRITICAL→HIGH→NORMAL→LOW）；test_partial_batch_memory、test_partial_batch_when_queue_full 均 PASS。

### 7.2 【中危 · 间歇 · 已修复】SQLite 并发提交竞态：cannot commit transaction

> **状态：已修复并回归验证通过**（2026-11-11）。修复落在 `src/neotask/utils/sqlite_compat.py` 与 `src/neotask/storage/sqlite.py`，详见本节末「修复与验证」及第 11 节。以下现象/根因为首测记录，保留以供追溯。

- **现象**：并发负载下 SQLite 后端 submit/submit_batch 偶发 `sqlite3.OperationalError: cannot commit transaction - SQL statements in progress`，导致该次提交失败。
- **复现率**：负载敏感。压力套件运行中命中 1 次；激进复现（8 worker + 批量与单条并发）首轮 1/8；机器空闲时隔离复跑 0/5、0/8、0/20。CPU 争用加剧时窗口放大。
- **影响**：突发并发写入下少量提交失败；非必现但真实存在，属数据完整性隐患。

**根因**：SQLite 仓储共享单连接（`src/neotask/storage/sqlite.py:89` `acquire_shared_connection`），批量原子路径 `BEGIN IMMEDIATE → executemany → commit`（`sqlite.py:228-236`）与 worker 状态写回/其他提交的 `execute→commit` 在**同一连接上交错**。当批量 `commit()` 触发时另有协程持有未结束的游标/语句（如 `sqlite.py:194-201` 的 SELECT 与 fetchall 分属不同 await），sqlite3 抛「SQL statements in progress」。

**复现**：`E:\neotask-demo\bench_latest\probe_sqlite_race.py`（8 worker，批量 800 + 单条 200 并发，多轮统计）。完整堆栈见 `logs/stress_latest.txt` 与 `results_stress.json` 的 `sqlite_burst_500.traceback`。

**修复与验证（已落地）**：采用「共享写连接串行锁 + 批量事务单次投递」方案。

根因补充：共享连接虽已用 `isolation_level=None`（自动提交）消除单条 `execute→commit` 的跨协程事务竞争，但 `save_batch`/`push_batch` 显式 `BEGIN IMMEDIATE … commit` 重新打开了**多语句事务窗口**。多个协程的窗口在专用 loop 上交错，引发两类错误：
- `cannot start a transaction within a transaction`（并发 BEGIN，A 未提交 B 又 BEGIN）；
- `cannot commit transaction - SQL statements in progress`（COMMIT 时另有活跃语句）。

改动：
1. `sqlite_compat.py`：`LoopBoundSQLiteConnection` 增加绑定专用 loop 的写串行锁 `_write_lock`（惰性创建，loop 重建/关闭时随之丢弃）。`execute`（写语句）/`executemany`/`commit`/`rollback` 均在锁内执行；只读 SELECT 不加锁（WAL 下读不阻塞写）。
2. `sqlite_compat.py`：新增 `executemany_transaction(sql, params)`——把 `BEGIN IMMEDIATE → executemany → 关闭游标 → COMMIT`（失败回滚）作为**一次**投递在专用 loop 内执行，全程持锁，其它写无法落入事务窗口。
3. `sqlite.py`：`save_batch`/`push_batch` 改用 `executemany_transaction`，替换原先拆成三次调用的 `BEGIN/executemany/commit`。

```python
# executemany_transaction：整事务一次投递 + 全程持写锁
async with self._write_lock_on_loop():
    begin_cursor = await conn.execute("BEGIN IMMEDIATE")
    await begin_cursor.close()
    try:
        cursor = await conn.executemany(sql, parameters)
        await cursor.close()
        await conn.commit()
    except Exception:
        await conn.rollback()
        raise
```

修复后验证（重建 wheel 覆盖安装）：
- **确定性复现** `probe_sqlite_race_det.py`（每轮 30 并发批量×150 + 150 单条，gather 强制窗口重叠）：首测 **508 错误/6 轮**、submitted=1764/completed=1701（有丢失）→ 修复后 **0 错误/6 轮**、submitted=27900/completed=27900（**零丢失**，批量吞吐完全恢复）。
- 线程版 `probe_sqlite_race.py`：0 错误/8 轮。
- 压力套件 `sqlite_burst_500`：FAIL → **PASS**（500/500，111–154/s，failed=0，两次复跑均绿）。
- 仓库测试：unit+集成 **447 通过 / 6 跳过**，仅 3 个优先级顺序用例失败（对 HEAD 同样失败，存量问题，与本修复无关）；sqlite_compat/storage/submit_many 专项 45 通过。

### 7.3 【低危 · 集成缺口】EventBus 背压未接入 TaskPool / TaskEngine —— **已修复**

- **现象**：当日新增的 EventBus 背压（`max_queue_size` / `overflow_policy` / `slow_handler_threshold`）仅在**直接使用 `neotask.EventBus`** 时可用（示例 14 即此用法）。`TaskPool`（`src/neotask/api/task_pool.py:82`）与 `TaskEngine`（`src/neotask/core/engine.py:135`）均以 `EventBus()` 默认构造——**无界队列**；`TaskPoolConfig` / `SchedulerConfig` / `EngineConfig` 均无背压字段，也无公开访问器触及池内总线。
- **影响**：通过主流 API（TaskPool/TaskScheduler）使用的用户，默认不受背压保护，慢订阅者仍可能令事件队列无限堆积。新特性的保护能力未覆盖主路径。
- **建议**：在三个 Config 增加背压字段并透传到 `EventBus(...)`，或暴露 `pool.event_bus` 只读属性供配置/监控。
- **修复**（已落地，验证见 11.4）：三个 Config 新增 `event_queue_max_size`（默认 `None` 无界，向后兼容）/ `event_overflow_policy`（默认 `"drop"`）/ `event_slow_handler_threshold`（默认 `1.0s`）并透传至 `EventBus(...)`；`TaskScheduler` 经内部 `TaskPoolConfig` 透传；三个入口均新增只读 `event_bus` 属性，供订阅自定义事件与 `get_stats()` 背压监控。非法策略在构造期即抛 `ValueError`。

## 8. 观察与建议（非缺陷）

### 8.1 预取对 noop 微任务无完成吞吐收益
预取开/关在 20k noop 下完成吞吐基本持平（1,563 vs 1,546/s），但提交吞吐提升（11,027 vs 7,457/s）。预取的价值在批量入队侧与有 I/O 的真实任务；纯调度微任务下完成侧收益不明显。建议基准用带真实耗时的执行器评估预取。

### 8.2 负载下延时开销上升
空闲时延时触发开销中位 ~27ms（时间轮与默认相当）；200 个 0.3s 延时任务叠加 500 背景任务时，测得完成开销中位升至 ~260ms。该测量以 `task.completed` 事件时刻为准，**含负载下事件投递延迟**，并非纯触发抖动。建议后续用执行器内打点隔离「触发延迟」与「事件投递延迟」，再评估是否需要优化负载下的事件分发。

### 8.3 空闲能耗优秀
事件唤醒后空闲池 CPU 0.52%、空闲提交延迟中位 1.2ms，相比旧退避睡眠是显著改进，值得在发布说明中强调。
