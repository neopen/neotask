# NeoTask 项目理解与建议

> 本文基于对仓库源码、文档、测试的完整走读，以及本地实测（冒烟测试 + 单元测试运行）整理而成。
> 整理日期：2026-07-20，基于工作区当前代码（`src/neotask`，`__version__ = "1.0.0"`）。

---

## 一、项目概览

NeoTask 是一个**纯 Python、嵌入式的异步任务队列/调度库**（包名 `neotask`，src-layout），目标定位是 Celery / APScheduler 的轻量替代：

- 面向耗时任务（AI 生成、视频处理、爬虫、定时报表等）
- 无需强制外部服务：内存/SQLite 即可运行，Redis 仅用于分布式模式
- 基于 `asyncio`，提供**同步/异步双 API**，上手门槛低

| 维度 | 现状 |
|------|------|
| 代码规模 | `src/neotask` 87 个 .py 文件，约 1.1 万行（另有约 20 个空壳文件） |
| 硬依赖 | aiosqlite、redis、psutil、croniter |
| 可选依赖 | FastAPI/uvicorn（Web UI）、pytest/black/ruff/mypy（dev） |
| Python | >= 3.9（pyproject 声明，但 badges 写 3.8+） |
| 对外入口 | `TaskPool`（即时任务）、`TaskScheduler`（定时任务）、`TaskEngine`（纯异步底层入口） |

## 二、架构剖析

### 2.1 分层结构

```
用户代码
   │
   ▼
API 层        TaskPool / TaskScheduler / TaskEngine      （Facade 模式）
   │
核心层        TaskDispatcher → TaskLifecycleManager → FutureManager
   │                                  │
队列层        QueueScheduler = PriorityQueue(堆) + DelayedQueue(时间堆) + DeadLetterQueue
   │
执行层        WorkerPool(N 协程 + TaskPrefetcher) → TaskExecutor(async/thread/process/class)
   │                                  │
基础设施      EventBus / MetricsCollector / HealthChecker / LockFactory(+WatchDog)
   │
存储层        TaskRepository + QueueRepository：Memory / SQLite / Redis 三实现
   │
分布式(仅 Redis 模式)  NodeManager + HeartbeatManager + TaskReclaimer + Coordinator
调度层(仅 Scheduler)   CronParser + TimeWheel + PeriodicTaskManager
```

### 2.2 即时任务数据流

1. `pool.submit(data)` → `TaskDispatcher.dispatch()`：经 `TaskLifecycleManager` 创建 Task（写入存储 + 发 `task.created` 事件），再按 `delay` 决定进优先级队列还是延迟队列。
2. `WorkerPool` 的 N 个 worker 协程通过 `TaskPrefetcher`（HYBRID 策略，可关）批量取任务。
3. 执行前：`start_task` 做状态机校验（仅 PENDING→RUNNING）；Redis 模式下先抢 `task:{id}` 分布式锁并启动 WatchDog 续期，防止多节点重复执行。
4. 执行后：`complete_task/fail_task` 校验状态机（仅 RUNNING→终态）→ 写存储 → 通知 `FutureManager` → 发事件。
5. 失败重试：重置为 PENDING、延迟 `retry_delay * retry_count` 重新入队；超过 `max_retries` 标记 FAILED。

### 2.3 线程与事件循环模型（本项目最关键的设计）

- `TaskPool.start()` 在**守护线程**中创建独立 event loop，所有内部组件共享该 loop。
- 同步 API（`submit`、`wait_for_result` 等）通过 `asyncio.run_coroutine_threadsafe(...).result()` 桥接到该 loop —— **每次同步调用都是一次跨线程阻塞提交**。
- `TaskScheduler` 复用 TaskPool 的 loop 提交任务，另起一个**调度线程**（自带独立 loop）扫描周期任务。
- 这一模型让同步用户使用零成本，但也是性能报告中"高并发提交测试失败（asyncio 事件循环绑定问题）"和同步提交吞吐受限的根因。

### 2.4 分布式设计（去中心化）

- 仅在 `storage_type="redis"` 时启用：NodeManager（Redis 注册+心跳）、HeartbeatManager、TaskReclaimer（超时/孤儿/僵尸锁回收）、Coordinator、DeadLetterQueue。
- 所有节点对等、抢占式消费共享 Redis 队列，无主从选举（`is_leader()` 恒为 False）。
- Coordinator 的负载均衡策略（round_robin 等）在共享队列模式下实际不生效，`rebalance()`、`handle_node_failure()` 仍是 TODO。

### 2.5 定时调度

- `submit_delayed/submit_at` → 委托 TaskPool 的延迟队列（时间堆，到期自动提升进优先级队列）。
- `submit_interval/submit_cron` → `PeriodicTaskManager`（支持 max_runs、起止时间、MissedExecutionPolicy 四种错过策略、执行历史）；`CronParser` 为自研，支持 `L`/`#` 与 `@daily` 等预定义表达式；另有可选 `TimeWheel` 高精度定时器。

## 三、实测验证

### 3.1 冒烟测试（通过）

`python examples/00_quick_start.py`：提交 → 执行 → 取结果 → 优雅关闭，全链路正常。

### 3.2 单元测试运行（暴露问题）

以 `PYTHONPATH=src` 运行 `pytest tests/unit`（绕过 venv 中的旧副本）：

| 文件 | 结果 |
|------|------|
| test_cron_parser (30) / test_delayed_queue (11) / test_event_bus (8) / test_executors (8) / test_future (8) | 全部通过 |
| test_lifecycle.py | **跑完 22 个用例后整体挂死**，`tests/fixtures/event_loop.py` 的 teardown 中 `asyncio.gather(*pending)` 无超时保护，等待一个永不结束的任务（timeout=60s/300s 均复现） |

### 3.3 环境问题

- `.venv` 中安装的是 **neotask 0.4.0 的非可编辑副本**（site-packages 实体目录），与 `src` 当前代码不一致：直接 `pytest` 会因旧副本缺少 `ClassExecutor` 而 collection 失败。venv 无 pip（uv 创建）。
- 性能报告（`docs/性能基准测试.md`）：内存模式基础调度约 1697 ops/s，队列出队 31 万 ops/s；另有两项未完成测试（高并发提交、预取器）。

## 四、发现的问题

### P0 — 阻塞级 Bug

1. **CLI 入口完全失效**。`pyproject.toml` 声明 `neotask = "neotask.cli:main"`，但 `neotask/cli/__init__.py` 与 `cli/main.py` 均为空壳（仅 docstring），不存在 `main` 函数。安装后执行 `neotask` 命令必报 ImportError。
2. **周期任务存在双调度循环，可能重复执行**。`PeriodicTaskManager.start()` 自己启动 `_scheduler_loop` 并执行到期任务（[periodic.py](../src/neotask/scheduler/periodic.py)）；而 `TaskScheduler._scheduler_loop` 又扫描 `list_tasks()` 并直接调用其私有方法 `_execute_periodic_task`（[task_scheduler.py](../src/neotask/api/task_scheduler.py)）。两个循环跑在**不同事件循环**、无共享锁，`next_run` 更新存在竞态 —— 同一周期任务可能被投递两次。
3. **`TaskEngine.submit()` 默认参数即崩溃**。其默认 `priority=5`，而 `TaskDispatcher.dispatch` 会执行 `TaskPriority(5)`，合法值仅 0–3，必抛 `ValueError`（[engine.py](../src/neotask/core/engine.py)、[dispatcher.py](../src/neotask/core/dispatcher.py)）。
4. **单元测试套件挂死**（见 3.2），导致 CI 无法跑完 unit 目录。

### P1 — 文档与代码不符

5. **README 宣称的 DAG Workflow 不存在**：全库 grep `workflow|DAG` 零匹配，README 的 `engine.submit_workflow(definition)`、`docs/ARCHITECTURE.md` 中的 `workflow/`、`engine/` 目录均无对应实现。
6. **版本号混乱**：pyproject=1.0.0；CHANGELOG 最新条目=0.3.0；`.claude/CLAUDE.md` 与 v0.4 测试报告称 v0.4.0；venv 内安装副本=0.4.0。对外发布版本无法对齐。
7. **README/CHANGELOG 承诺未兑现**：多租户、Prometheus 集成（`contrib/prometheus.py` 为空壳）、Web UI 的 "WebSocket 实时推送/任务控制"（实际仅有 `/` 和 `/api/stats` 两个路由）。
8. `examples/readme.txt` 引用的 `05_webui.py` 不存在。

### P2 — 代码质量

9. **约 20 个 6 行空壳文件**（仅 docstring）：`cli/*`（5 个）、`web/routes/*`、`web/websocket/*`、`web/app.py`、`config/settings.py`、`common/constants.py`、`monitor/collector.py`、`contrib/prometheus.py`。
10. **跨层访问私有成员**：`WorkerPool._handle_task_failure` 直接操作 `lifecycle._cache/_lock/_cache_enabled`；`TaskScheduler` 调用 `_periodic_manager._execute_periodic_task`。封装已被打破，重构极易引入回归。
11. `PriorityQueue.pop_with_priority` 在 repository 模式下**返回硬编码 priority=5**；`contains()` 在 repository 模式下恒返回 False。
12. `submit_batch` 是伪批量（for 循环逐个同步 submit，每次都跨线程阻塞）；`TaskDispatcher.dispatch_batch` 已存在但未被 API 层使用。
13. 任务 ID 用 `时间戳 + random(100000, 999999)` 生成，同微秒高并发下有碰撞风险（建议 uuid4）。
14. `TaskPool.is_leader()` 恒返回 False，属僵尸接口，容易误导用户。
15. `TaskPool.submit` 中 `result.task_id if hasattr(result, 'task_id') else result`：`dispatch` 已返回 str，该防御分支是死代码，暗示历史上接口不一致。

### P3 — 工程环境

16. venv 旧副本问题（见 3.3），建议改为可编辑安装。
17. `tests/integration` 在 v0.4 报告中自标"待补充"；集成/混沌/基准测试分散在 5 个目录，缺少统一的可运行入口（scripts/*.sh 在 Windows 下不可用）。

## 五、优势亮点（值得保留）

- **分层与 Facade 设计清晰**：TaskPool/TaskScheduler 把 10+ 内部组件收敛成两个易用入口。
- **状态机校验严谨**：`is_terminal()`、仅允许 PENDING→RUNNING→终态，杜绝非法流转。
- **双 API + 独立事件循环线程**：同步用户零 asyncio 负担，这是区别于 Celery 的核心易用性。
- **分布式容错链路完整**：锁 + WatchDog 续期 + Reclaimer 回收 + 死信队列，去中心化抢占模型简单可靠。
- **调度能力超出"轻量"定位**：自研 CronParser（含 `L`/`#`）、时间轮、四种错过执行策略。
- **测试资产丰富**：unit / distributed / integration / chaos / benchmark 多层次，v0.4 报告覆盖率 85%+。

## 六、改进建议（按优先级）

### 立即做（本周）

1. **修复 P0**：实现 `neotask.cli:main`（或从 pyproject 移除 scripts）；删除 `TaskScheduler._scheduler_loop` 中对 PeriodicTaskManager 的重复扫描（二选一保留调度职责）；`TaskEngine.submit` 默认 priority 改为 2；给 `tests/fixtures/event_loop.py` 的 teardown gather 加 `asyncio.wait_for(timeout)`。
2. **统一版本号**：以 pyproject 1.0.0 为准，CHANGELOG 补 0.4→1.0 条目，同步 CLAUDE.md。
3. **重建 dev 环境**：`uv pip install -e ".[dev]"`，确保 pytest 跑的是 src 代码；在 CI 中加"安装后即跑 collection"的检查。

### 近期做（下个迭代）

4. **清理空壳文件**：要么实现（cli、webui、prometheus），要么删除，避免"目录看起来很完整"的假象。
5. **文档还债**：README 移除 DAG/多租户等未实现宣称，或打上 "规划" 标记；修正 ARCHITECTURE.md 的目录结构；更新 ARCHITECTURE.md 使其覆盖 Prefetcher/Reclaimer/Heartbeat/DeadLetter。
6. **收敛私有访问**：给 `TaskLifecycleManager` 增加 `reset_for_retry()` 公开方法；`PeriodicTaskManager` 提供 `execute_due_tasks()` 公开接口。
7. `submit_batch` 改为真正的批量分发；`PriorityQueue` 去掉 repository 模式下的硬编码 priority。

### 中长期做

8. **明确分布式路线**：共享队列抢占模式下 Coordinator 的负载均衡/分区模式是"做还是删"，`rebalance`/`handle_node_failure` 两个 TODO 需要结论。
9. **Web UI 决策**：当前实现与 README 宣称差距大，建议先收敛为"只读监控 API"，或单独立项补全 routes/websocket。
10. **同步 API 性能**：高并发提交场景建议引导用户走 `submit_async`/`submit_batch_async`，或在文档中显式说明同步 API 的跨线程开销特性。
